# 解决方案产品化（Packaging）

前线成功若不能复制，公司与客户都不可持续。本篇讲如何把项目收成 **可售/可交付的解决方案包**。

---

## 1. 什么叫「包好了」

| 维度 | 项目制 | 产品化解决方案 |
|------|--------|----------------|
| 范围 | 每次从零谈 | 有标准范围与加价项 |
| 交付物 | 人脑里 | 模板、Terraform/脚本、文档、培训 |
| 评测 | 临时 | 种子黄金集 + 量规 |
| 人员 | 依赖英雄 | 二号位可按手册交付 |
| 反馈 | 散落聊天 | 结构化需求回产品 |

---

## 2. 解决方案包最小目录

```text
solution-name/
  README.md            # 适用/不适用场景
  discovery/           # 访谈与问题陈述模板
  architecture/        # 参考架构与决策记录
  infra/               # 部署脚本或步骤
  eval/                # 种子集与跑分说明
  playbooks/           # 运行与故障
  training/            # 速查与课程
  security/            # 数据流与威胁答疑
  commercial/          # 标准范围与排除项（与销售对齐）
```

---

## 3. 适用 / 不适用（必须写）

例如知识库助手：

- **适用**：制度类、有 ACL、可引用、错误可 HITL  
- **不适用**：开放域医疗诊断、无数据源的「凭空智慧」  

这能保护交付毛利与品牌。

---

## 4. 版本与升级

- 方案版本 ≠ 客户定制分支无限分叉  
- 定制用配置/插件点；上游版本定期合并  
- 每个客户的「分叉债务」进 Review  

---

## 5. 面试与晋升怎么讲

「我将 X 客户试点沉淀为内部解决方案包，第二家客户交付周期从 10 周降到 4 周，并回馈了平台的 ACL 连接器需求。」
