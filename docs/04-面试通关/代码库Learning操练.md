# 代码库 / Learning 操练（Codebase / Learning Drills）

> 原文：The Forward Deployed — Interview Practice（https://www.theforwarddeployed.io/interview-practice）
> 全文翻译整理。本篇是「编码 / Learning」两个轮次的**操练层**，与概念篇 [编码与 Learning](./编码与Learning轮.md) 互补：概念篇讲流程、复习重点与 60 分钟时间分配，本篇讲动手操练——框架、示范题、Bad/Good/Great 对照、追问、题库与 AI 面试官协议。当你临近面试、需要「反复操练（reps）」时使用本篇。

Palantir 有两轮在考同一块肌肉，也正是这份工作每天都在用的那块：**在从没见过的代码里快速变得有用**。（这两轮都来自候选人记录——一篇个人复盘和若干匿名论坛帖——所以请把这些细节当作「相互印证」而非「铁证」。）在 re-engineering 轮，你要「在一个 250 行以上的 codebase 里修 bug」，bug 带有微妙的逻辑缺陷。一个被描述过的例子是「重复计数问题（double-counting issue）」。在 learning 轮，你要对照陌生的文档来构建。一位候选人记录描述：拿到面试官写的模块，用提供的库文档去增强它们；另一位在备战时，计划「去读一门（自己）从没碰过的语言的 API 或文档」，然后实现点基础的东西。这就是任何一次 engagement 第一周的面试版：被扔进一个客户的陌生技术栈，到下午就得能产出。

这里测的信号不是「你是否已经熟悉这段代码」，而是你能否在动手打字之前先**定位（orient）**：读那一条真正要紧的路径，形成一个假设，然后利用工具和文档（包括 AI 助手）快速补齐差距。

---

## 框架：先定位，再行动

1. **找到入口点，顺着一条路径 trace 下去。** 不要通读整个文件。沿着从输入到那个 bug 或那个功能之间的那一条单一流程走。边 trace 边大声口述。
2. **在改动任何东西之前先形成一个假设。** 「我认为 X 在重复计数，因为它在循环里和 helper 里各被加了一次。」先把这个假设说出来，再去证实它。不要散弹枪式地到处乱改。
3. **先复现（reproduce），再修，再验证。** 先让那个失败的用例真的失败一次，这样你才知道你的修复真的生效了，而不是把 bug 挪到了别处。
4. **说出时间更多时你会怎么做。** 点出你会补的测试、你暂时放下的边角情况、你会重构的地方。即便时钟赢了你，这也展示了判断力。

## 操练 1 —— 陌生代码里的微妙 bug

**题目**：给你约 250 行从没见过的代码，比如一个订单合计服务，并告诉你有一个测试在失败：某些订单报出的总额略微偏高。找到并修好它。（这个 bug 的形态对应「重复计数问题」；代码是为练习而虚构的。）

**在读下去之前**：你有二十五分钟。前五分钟你会做什么？它不是「从上到下把 250 行全读完」。

### Bad / Good / Great —— 前五分钟

**Bad**——先全部读完，再开始改。你把 250 行全滚了一遍，滚到第 120 行就丢了线索，然后开始改那些「看起来很可疑」的地方。现在你是在原始 bug 之上再调试自己的改动。面试官看到的是一个「无法定位」的人。

**Good**——先读失败的测试，再读相关函数。你打开测试，看清是哪个输入产出了错误的总额，然后跳到合计函数。扎实。但如果你接着就在第一行可疑代码上开改，那你还是在猜。比散弹枪式地扫全文件好，但仍不是一个假设。

**Great**——先复现，大声说出假设，再确认。「测试说一个两件商品的订单被多算了。让我把一个订单从头 trace 一遍：它在这个循环里被加总，而 addItem 里还设了一个小计字段。我打赌税或折扣在两个地方都被算了一次。在动任何东西之前，我先加个 print 确认……对，折扣在循环里被减了一次，在 finalize 里又被减了一次。这就是那个重复计数。我在 finalize 里修掉它，然后重跑那个失败的测试，外加一个我为『打了折的订单』补的测试。」你从没有在猜测上动过手，而且你给代码留下了一个能证明修复生效的测试。

### 可能遇到的追问

**面试官**：「你找得很快。要是你没法复现它呢？」

**你**：「那我就通过二分这条路径来缩小范围：把折扣逻辑注释掉，看总额对不对，再轮到税，直到那个错误的数字发生移动。我相信复现胜于阅读，因为一个我复现不出来的 bug，就是一个我无法证明自己修好了的 bug。」

## 操练 2 —— 陌生的 API

**题目**：这里有一个你从没用过的库的文档。用二十分钟照着它构建一个能跑起来的小东西，比如调用这个向量存储（vector-store）客户端来索引三份文档并跑一个查询。

**在读下去之前**：你不认识这个 API。到「一个能跑的通话（call）」的最快路径是什么，你首先读什么？

### Bad / Good / Great —— 在时钟下学习

**Bad**——把文档从头读到尾。你从 overview 开始，每一页都读。二十分钟后你理解了整个库，却一行代码都没写。这一轮考的是「在陌生条件下交付」，而你没有交付。

**Good**——找一个例子然后改造它。你在文档里搜 quickstart，复制最接近的那段 snippet，然后改它。好，真正的工程师就是这么动的。但如果它崩了、你闷头静默调试，你就丢掉了「口述」这个信号。

**Great**——先 quickstart，边口述缺口，用上每一个工具。「我先抓 quickstart 让一个 call 跑起来，再把它改成三份文档。这个签名要一个 embedding 函数。文档说它默认有一个，所以我现在先依赖这个默认值，并记下这一点。它在 query 的形状上报错了；我去查一下 reference 里 query 方法的参数……它要的是一个 list 而不是 string。修好了。」你快速拿到了一个能跑的通话，说出了你假设了什么、为什么，并把文档（以及在允许的地方，AI 助手）当作它们在工作中本来的工具来用。

### 可能遇到的追问

**面试官**：「你很依赖 quickstart 和文档。你真会这么干活吗？」

**你**：「会。在一次 engagement 里，我是靠『读我需要的那么一条路径 + 站在例子上』在新的技术栈里变得能产出的，而不是先把整个库吃透。我会在要紧的地方往深里读。这里，我会仔细读 embeddings 和持久化是怎么工作的，因为正确性就藏在那里。我在有风险的地方深读，其余地方浅读。」

## 操练 3 —— AI 辅助，用得好

**示范练习题**

> 为练习而虚构。操练的是现代 FDE 的真实处境：在允许的面试条件下，把 AI 编程助手用好。

**题目**：同样的陌生 codebase 任务，但这次允许你用一个 AI 编程助手。修好那个失败的测试。

**在读下去之前**：助手能帮你把修复写出来。一个强候选人，和一个「把报错贴进去、把返回的东西原样交上去」的人，差别在哪里？

### Bad / Good / Great —— 驾驭这个助手

**Bad**——贴上报错，交付回复。你把 stack trace 交给助手，拿到一个貌似合理的补丁，看都不看就应用了。它甚至可能通过那一个测试。但你解释不了它为什么有效，而当面试官换一个输入时，你就卡住了。你展示的是「助手会写代码」，而不是「你会写代码」。

**Good**——用它来探索，然后验证。你让它解释合计函数，并提示重复计数可能在哪，读它的回答，再对照代码确认。这是把助手当作一个「读得很快的读者」，正当且有效。

**Great**——驾驶它，验证它，为它负责。「我会让它定位折扣是在哪里被应用的，因为那是我的假设。然后在我信任它之前，我自己把那两个调用点（call site）读一遍。我会先写那个失败的测试，这样我就是在拿一个真实的东西给它打分，而不是它自己的说辞。而且我会把改动保持得足够小，小到我能解释每一行，因为在客户面前我得为它辩护。」你用助手加速，同时继续做那个为结果负责的工程师。最后这一点正是 FDE 的全部姿态，而本站作者那门关于「驾驭编程 agent」的相关课程对此有深入讨论。

### 可能遇到的追问

**面试官**：「大部分都是助手写的。你加进去了什么？」

**你**：「假设、那个证明修复生效的失败测试，以及『把改动保持得小而可解释』的判断。助手很快；但它不负责任。在客户的系统上，负责任的是我。所以我验证它给我的东西，而且我只交付我能辩护的东西。」

## 怎么练这个

这一轮的两个半场都可以独自反复操练。下面的 Rep Kit 把它们变成一套协议：一个「帮你埋下一个 bug、却不告诉你它是什么」的助手，外加一批陌生库任务。给自己打分时要看「定位」而不是「先验知识」：你有没有顺一条路径 trace，有没有在改动前先假设，有没有在修复前先复现？在陌生代码里快速变得有用，是 FDE 的日常现实；这一轮只是给它加了个时钟。

---

## Rep Kit（操练工具箱）

上面的操练自带答案，读过一遍之后就不再能考你了。不过这一轮比其他轮有个优势：AI 助手能按需为你现场制造全新的、真正没见过的测试。下面的协议会让它给你藏一个 bug；它后面的题库装着二十道 learning 轮任务。两者全程都要口述，并对照本页顶部的框架打分：顺一条路径 trace，改动任何东西前先假设，修复前先复现，并说出时间更多时你会怎么做。

### 埋 bug 协议（The seeded-bug protocol）

把下面这段**原样**粘贴进任意一个有能力的 AI 聊天，不改动。它会搭好这一轮、跟踪你报告的时钟、要求口述，并对照框架打分。聊天支持语音模式的话就用它；这些轮次全是口头的。

```text
你是 Forward Deployed Engineer re-engineering 操练的埋 bug 员兼计时员。

准备（Setup）：
1. 我会告诉你我熟悉的一门语言，并从两种设置里选一种：
   - "generate"：用那门语言给我写一个自包含的程序——几百行、
     真实的逻辑（合计、解析、调度、缓存），无外部依赖——其中恰好埋有
     一个微妙的逻辑 bug：那种「依然能跑、但产出看似合理却错误的结果」的类型
     （off-by-one、重复计数、边界写错、条件写反）。把完整代码给我，好让我保存并运行。
   - "real repo"：我会挑一个开源文件，最多几百行，把它的完整内容贴进这个聊天，
     并把原件放在一边、不去打开（对比文件会不经过操练就找到 bug）。你把同一份代码
     原样返回、并恰好引入一个那种微妙的逻辑 bug，作为完整文件、从头到尾——
     绝不给 diff 或 patch，也绝不做「其余不变」之类的省略；
     如果文件太长无法整份返回，就直说并停下——其他一律不改。
2. 无论哪种方式，都不要告诉我 bug 是什么、在哪、是哪种类型。
   只描述症状，就像一张 ticket 会写的那样：「这个输入产出了一个略微错误的结果。」
3. 给我一个失败的输入和它的期望输出——对于没有入口点的粘贴代码，
   再给一段能触发它的最小 snippet——好让我在动手排查之前先复现这个失败。
   期望输出要通过对代码的 trace 推导出来，输入保持小到能手工核对，
   并确认那个被埋的 bug 确实会改变这个输入下的输出。

跑这一轮（Running the round）：
4. 我自己跑一个 25 分钟计时器，并在每条消息前加上我已用掉的分钟数；
   当我报告的时间超过 12 分钟和 20 分钟时，告诉我还剩多久；到点喊停。
5. 要求口述。如果我的任何一条消息报告了一个改动或结论，
   却没有给出导向它的「阅读」和「假设」，就问：「你在想什么？」
   并把这一次记作对我不利。
6. 除非我明确说 "hint"，否则不给任何提示——说了就给最小的一个：
   先说是文件的哪个区域，再是哪个函数，再是哪一行，每次请求只给一层，
   并把每次提示都记进评分。

评分（当我说 "done" 或时间到时）：
7. 揭示 bug。对照四个动作打分，并引用具体时刻：
   (a) 我是否从输入到那个错误输出 trace 了一条路径，而不是什么都读；
   (b) 我是否在改动任何东西之前先说出一个假设并确认它（一个 print、一次 trace、
   一次重读）；
   (c) 我是否在修复前先复现失败，并在修复后验证；
   (d) 我是否说出了时间更多时我会怎么做——我会补的测试、我留下的边角。
   评分要狠：典型的第一遍至少挂掉四个动作里的两个——如果一个都没挂，
   先重新审视再表扬，绝不因为我和评分争辩就软化。
8. 结束时只给「下一遍要修的一件事」。然后提出在一个新领域再埋一个新鲜的 bug。
```

### Learning 轮题库（The learning-round bank）

**示范练习题**

> 为练习而虚构。每一道都是对着一个你从没用过的库或工具、限时二十分钟的任务。如果你已经会那个点名的工具，就换一个你不会的；如果某道题需要一个跑起来的服务、一个账号或一个你手头没有的 API key，也等量替换。

1. 用向量存储客户端（Chroma、Qdrant 或 Weaviate）索引三份短文档，并跑一个相似度查询。
2. 用消息队列（NATS、Redis streams 或 RabbitMQ）发布一条消息，再把它读回来。
3. 用一个不在你常用技术栈里的绘图库（Vega-Lite、ggplot2 或 Plotly），从一个硬编码的列表画一张柱状图。
4. 用一个你从没碰过的嵌入式数据库（DuckDB、LevelDB，或用一门你不用的语言操作 SQLite）写入一条记录，再把它读回来。
5. 用一个调度库（APScheduler、node-cron 或 Quartz）安排一个在九十秒后触发的任务。
6. 用一门你不天天写的语言里的日期时间库（java.time、Rust 的 chrono 或 Luxon），从一段凌乱的字符串里解析出一个日期。
7. 用一个 schema 校验库（pydantic 或 zod）校验一个嵌套的配置对象。
8. 用一个抓取库（BeautifulSoup、cheerio 或 goquery）从一个实时网页里提取每一个链接。
9. 用一个图像库（Pillow、sharp 或 ImageMagick 的 bindings）缩放一张图片并写回磁盘。
10. 用一个不在你技术栈里的模板引擎（Jinja、Handlebars 或 Tera）填充并渲染一个模板。
11. 用一个分词库（tiktoken 或 Hugging Face tokenizers）数一段文字里的 token 数。
12. 用一个你从没用过的框架（Fastify、Actix 或 Sinatra）搭一个单路由的 Web 服务器，把查询参数原样 echo 回来。
13. 用一个表格库（openpyxl 或 SheetJS）读取一份表格，并对其中一列求和。
14. 定义一个消息类型，并让它在一个序列化库（protocol buffers 或 MessagePack）里往返一遍。
15. 用一个文本转语音客户端把一句文本变成音频，或者用一个转写库把一段音频变成文本。
16. 用一个地理空间库（Shapely 或 Turf.js）跑一次点是否在多边形内（point-in-polygon）的检查。
17. 用一个你从没直接调用过的密码学库（libsodium bindings 或 Web Crypto）计算一个文件的校验和并验证它。
18. 加载一个小的公开数据集，并用一个不在你常用之列的数据框库（Polars、dplyr 或 DataFrames.jl）过滤它。
19. 用一个你没用过的语言模型提供方的客户端库，逐 token 流式输出模型的响应，边到边打印。
20. 用一个 Markdown 解析器（markdown-it、goldmark 或 comrak）把一个 Markdown 文件解析成它各级标题的列表。

一道题算通过的标准是：一个 call 端到端跑通，且你能大声说出你假设了什么、以及如果正确性要紧你会往哪里深读。对照框架、在二十分钟计时下打分，全程口述：先 quickstart，撞到缺口就说出来，只在有风险的地方深读。文档始终允许；当你在练「操练 3 的允许助手变体」时，再加一个 AI 助手。
