# Palantir FDSE 面试指南

> 原文来源：The Forward Deployed —— https://www.theforwarddeployed.io/interviews/palantir（截至 2026 年 7 月，转述性质，随团队/级别/年份变化，以 recruiter 为准）。本篇是「公司差异与薪酬.md」中 Palantir 章节的延伸子页面，为该公司的专门面试指南，完整全文翻译。与「07-外文精读/03-Palantir-FDSE面试指南.md」（精华精读版）互补：本文件是逐段全文翻译，精读版是摘要导读，二者不重复。

## 证据等级

Palantir 拥有文档化程度最高的 forward-deployed 面试回路，但以下各环节细节均为转述，截至 2026 年 7 月，且随团队、级别、年份而异。请与你的 recruiter 确认具体形式。

## 面试回路一览

| 阶段 | 形式 | 报告的时长 | 考察内容 |
|------|------|----------|----------|
| Recruiter screen | 电话 | 约 30 分钟 | 背景、动机、文化契合度 |
| Technical screen | HackerRank 或 live CodePair，语言灵活 | 约 105–120 分钟 | 偏图的实用编码，偶发 SQL |
| Onsite | 从 Decomposition、Learning、Coding、Re-engineering 中最多四轮 | 每轮约 1 小时 | 问题拆解、代码流利度、适应性 |
| Hiring-manager final | 视频通话 | 约 60 分钟 | 使命契合、ownership、开放问题 |

候选人普遍反馈总共约 3 到 5 场面试，周期约 4 到 6 周；面试官通常会在每轮技术面的最后 15 到 20 分钟留给动机、协作与 ownership。Decomposition 和 Learning 是近乎必考的 onsite 轮次；其余轮次则因候选人与方向而异。候选人来源：Taro、LeetCode Discuss。

## 逐环节拆解

### Recruiter screen（约 30 分钟）

一轮关于你背景的简短电话，而且比大多数公司更看重「为什么是 Palantir 这家公司」。Palantir 官方建议强调，在面试前要理解它的业务与客户。Palantir 面试建议。带上一个具体的、经过思考的回答，而不是泛泛而谈。

代表性提问：为什么是 Palantir，为什么尤其选择 forward-deployed？你对 Palantir 如何与客户合作有哪些理解？带我走一遍你端到端负责过的某个项目。

### Technical screen（约 105–120 分钟）

一场 Palantir 自出的 HackerRank 测评，或与工程师的 live CodePair，通常两到三道题，语言灵活而非仅限 Python。反馈描述的是中等难度、重度偏向图算法（邻接表、topological sort、网格上的 multi-source BFS）以及在小数据集上的应用型 rollup，有时是一道各部分层层递进的多部分题，偶尔夹杂一条 SQL 查询。这是一道门槛：正确、能跑、可读的代码才是标准。请在 coding screen 页面反复练习。

### Decomposition（签名轮）

这是 Palantir 赖以成名的轮次，也被广泛认为是整个回路中最重要的一轮。你会拿到一个模糊的真实世界问题，没有明确范围、没有指定输入、也没有显而易见的标准答案，然后考察你如何把它结构化：用户是谁、什么结果最重要、假设是什么、难点在哪里，最后才是你会构建什么。单靠刷算法是扛不住这一轮的。

代表性题目，呈现为候选人最常反馈的两种形态——对陌生领域的实体进行编目，以及从事件日志为真实世界现象建模：你会如何构建一个系统，为一家从未做过盘点登记的医院编目并追踪每一件设备？给定一家公司的聊天日志，你会如何建模一条谣言在组织内部如何传播？你会如何帮助一家物流公司找出货物卡在哪里？请用下方的框架和 decomposition 操练来练习这些题目。

### Coding 与 re-engineering

在技术筛之后，onsite 的 coding 轮会进一步考察在需求不断变化下的实际实现。re-engineering 轮只在部分回路中出现，并非全部：它会交给你已有的、有时甚至是损坏的代码，且常常是你并不熟悉的语言，让你阅读它、找出 bug 并加以改进——这比一道从零开始的谜题更贴近真实的 forward-deployed 工作。两轮都奖励你边做边叙述推理、以及处理不完美输入的能力。

### Learning

这是足够特别、常让人措手不及的一轮：你会拿到一个陌生的系统、语言特性或 API，文档极少，要求你在一小时内理解它并加以扩展，同时不破坏现有行为。它衡量的是你多快能在别人的代码里变得有用，这正是这份工作的日常现实。有些候选人还会被要求针对一个他们无法执行的 schema 编写 SQL，所以要保持查询编写能力在线。请在 codebase 和 learning 操练中排练。

### System design

Decomposition 实际上就是 Palantir 的设计轮，因此经典的可扩展性 system design 面试在这里并不常见。当设计讨论确实出现时，它聚焦于跨系统的数据集成，以及多方数据所要求的隔离与治理。要从集成与信任模型入手，而不是从机器学习入手。请在 AI system design 案例中准备。

### forward-deployed 特色

FDSE 与标准 SWE 回路的区别在于一条 client-simulation（客户模拟）线索，它可能出现在技术轮次内部，也可能出现在招聘经理对话中：理解一个业务问题、带着理由据理推回、并把一项技术选择转译为运营价值或风险。请在 client-simulation 操练中排练。

### Hiring-manager final（约 60 分钟）

一场关于使命契合、项目 ownership、以及前面轮次遗留开放问题的对话。在这里，一个具体、诚实的「为什么是 Palantir」回答，以及一个你真正负责出结果的故事，分量最重。

代表性提问：讲一次真正的失败，而不是伪装成失败的成功。讲一次你快速上手陌生事物的经历。为什么是 Palantir？请在 values 和 hiring-manager 操练中准备这些。

## 答题框架

### 拆解一个开放式问题

按以下顺序大声说出来：1) 说出用户是谁、以及他们被衡量的结果是什么，要超越交给你的那个 feature 本身。2) 说出你的假设以及你准备排除在范围外的东西，然后加以确认。3) 把问题拆成三到五个各自都必须解决的子问题。4) 指出哪个子问题才是真正的难点，以及为什么。5) 提出一个具体的初步方案，并立刻说明你会如何判断它是错的。常见错误是直接跳到第五步；面试官真正要买的是第一到第四步。

### 快速在陌生代码中变得有用

针对 learning 和 re-engineering 轮：1) 在改动任何东西之前，先复现现有行为。2) 端到端追踪一条路径，而不是把一切都读一遍。3) 对相关逻辑所在的位置形成一个假设，并预测你将会发现什么。4) 做最小改动来验证这个假设，并说明什么样的证据会让你改变想法。5) 全程叙述；这一轮打分的更多是你如何学习，而不是你已经知道什么。

### 回答「为什么是 Palantir」

Recruiter 和招聘经理都会追问这一点，而泛泛的热情会失败。说出 Palantir 所服务的一个你确实有看法的具体客户或问题领域，把它连接到你曾经构建过或真正在乎的事情上，并对各种取舍保持诚实。Palantir 官方建议是理解你要面试的那门业务，并且保持真实。Palantir 面试建议。

## 一个完整范例

以「设计一个系统，把一座城市的紧急呼叫路由到正确的响应者」这道题为例。

Weak（较弱）。「我会建一个 dashboard，让调度员看到来电并进行派单，配一个分类器来推荐正确的处置单元。」你开口第一句就选定了产品和模型，于是此后每一个决策都建立在一个关于「调度员到底需要什么」的猜测之上。

Strong（较强）。「用户是调度员，结果是正确的响应者尽快到达来电者，用 time-to-dispatch（派单耗时）和 mis-route（误派）来衡量。子问题是理解来电、选择处置单元、以及处理首选单元不可用的情况。难点是误派，因为一次失误的代价是延误的救护车，而不是一块难看的屏幕。所以我会围绕『把分类做对』和『在置信度低时安全失败、转交人工』来设计，并把 dashboard 当作最轻松的部分。如果 time-to-dispatch 下降而 mis-route 没有上升，我就知道它奏效了。」你先从用户和结果入手，找到了真正有代价的子问题，并说出了你会如何判断自己是对的。

## 面试官的打分维度

这个回路奖励的是一类特定画像。模糊性下的结构化思考：你在提出方案之前先给一个模糊问题强加秩序。可读的推理：你进行叙述，让面试官能给过程打分。实用的代码：正确、可读、以用户为中心，胜过算法的炫技。学习速度：你能快速在陌生系统中变得有用。客户判断力：你能把一项技术选择转译为运营价值或风险。以及一个具体、诚实地想加入 Palantir 的理由。沉默和炫技都会让你失分；结构和叙述才能赢。

## 练习题目

以下是形态与上述各轮一致的代表性题目。每道题都掐表大声做出来，并给自己结构化的过程打分。

Decomposition：一个医院网络想减少护士在三套永远对不齐的系统之间核对用药清单所花费的时间。你不会拿到任何 schema，也没有规格说明。说出用户是谁、什么结果最重要，把问题拆开，找到难点，并说明你会先交付什么。

时间压力下的 Learning：你被丢进一个庞大、陌生的数据集成 codebase，要求在周末前新增一个 source connector。在其中追踪一条路径，对改动该落在哪里形成一个假设，并说明在动手改任何东西之前你会如何降低风险。

## 两周备考计划

第一周：用 Python 过掉 coding screen 的地板题，然后把大部分训练花在 decomposition 上，掐表大声练习，套用上面的五步框架，直到开场部分能够自动脱口而出。

第二周：轮换练习 learning 操练和客户模拟，跑一个 system design 案例，并准备一个真实的失败故事和一个具体的「为什么是 Palantir」回答（values 操练）。把一切都录下来；心里默念看懂不算面试表现。FDSE 头衔的薪酬见「公司差异与薪酬」，附来源与日期。

## 常见问题

### Palantir Forward Deployed Software Engineer 面试流程是怎样的？

公开记录基本一致：一轮 recruiter screen、一轮 60 到 90 分钟的技术筛（HackerRank，推荐 Python）、一场从 Decomposition、Coding、Re-engineering、Learning 与 System Design 中抽取的最多四轮的 onsite，以及一轮招聘经理终面，总共三到五场面试。轮数与时长因团队、级别、年份而异。请把你 recruiter 的说明当作形式的权威依据。

### Palantir FDSE 面试会考哪些典型题目？

代表各轮次的典型题目有：一道开放式 decomposition 题，如「设计一个系统，把一座城市的紧急呼叫路由到正确的响应者」；一道实用的多部分编码任务；一个需要当场学习并使用的陌生系统；以及行为面题目，如「讲一次真正的失败」和「为什么是 Palantir？」。上文的「答题框架」一节为每一类都给出了结构。

### Palantir 的 decomposition 面试是什么？

这是一轮 case 面，建立在一个模糊、往往非软件的问题之上，没有明确范围。你被考察的是如何把它结构化：识别用户与结果、说出你的假设、把问题拆开、并在提出任何方案之前找到难点。它被广泛认为是回路中最重要的一轮，单靠刷算法扛不住。请用 decomposition 操练来练习。

### Palantir 的 learning 轮是什么？

这是一段限时的环节，你会拿到一个陌生的系统、语言特性或 API，文档极少，要求你当场理解并应用它。它考察的是你多快能在陌生代码里变得有用，这正是 forward-deployed 工作的日常现实。请在 codebase 和 learning 操练中排练。

### Palantir FDSE 面试有多难，要花多长时间？

候选人反馈这是一个要求很高的回路，奖励结构化思考胜过死记算法，从投递到 offer 的时间线约为四到六周。其特有的难度在于模糊性：有好几轮故意不给你范围，就为了看你会如何强加它。请围绕各面试轮次做广度准备，而不是只死磕某一种形式。

### 我需要懂 Palantir Foundry 才能面试吗？

不需要。这个回路考察的是通用工程能力、decomposition、learning 和客户判断力，而不是产品专属知识。帮助大得多的是一个具体、诚实的「为什么是 Palantir」回答，以及你端到端负责出结果的证据。公司背景见「公司差异与薪酬」。
