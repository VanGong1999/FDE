# 18 你在机器学习基础设施（包括分布式GPU集群）方面有哪些经验？


**一句话要点：**

开篇给出有边界的真实能力上限（例如：在Slurm上最多管理过64张GPU，负责过推理服务平台，没有运营过万卡级集群）；按技术栈分层梳理，标注每一层是**自主搭建负责 / 使用过 / 了解原理**；最后讲一个实战案例，结构为：现象 → 排查手段 → 根因 → 修复方案 → 量化结果。
如实说明自己能力上限，会提升可信度；夸大经历，在面试官的追问下很容易露馅。

**回答思路**

把这个问题当成一次由你主导的讲解，而不是一场被动应付的测验。面试官想要从两个维度评估你：你接触过多大规模的集群，以及在技术栈里哪些层是你**主导负责**，哪些只是用过。面试官会从你讲得最熟练的地方继续追问。

所以回答要先划定能力边界、分层梳理技术栈，最后带上有真实数据支撑的运维实战故事。

**优秀回答示例**
先用一句话划定范围，定下后续所有内容的基调：

> 我在Slurm上跑过最多64卡的分布式训练，并且端到端负责推理服务平台；我没有运营过万卡规模的集群。

坦诚说出自己的规模上限是加分项，不是短板。CoreWeave、xAI这类公司的面试官，每周都会遇到很多夸大自己经验、一追问就露馅的候选人。


接着按技术栈分层介绍，清晰说明每一层：**自主负责 / 使用过 / 了解原理**
- **硬件/互联架构**：GPU型号、互联方案（只用NVLink的节点 vs 基于IB/RoCE组网的集群）、存储。哪怕你只说“我们集群是8卡节点，用100G以太网，这也是为什么我们的任务都只跑在单节点内”，也能体现你懂集群互联的逻辑。
- **调度系统**：Slurm（分区、协同调度、抢占机制、公平共享）或者Kubernetes（设备插件、节点池、Volcano/Kueue任务队列）。GPU资源如何分配、资源竞争怎么处理；如果你搭建过配额或者优先级策略，这就属于你自主负责的内容。
- **训练技术栈**：DDP/FSDP/DeepSpeed、断点续存规范、实验追踪、故障检测与重启机制。
- **推理服务栈**：vLLM/TensorRT-LLM/Triton、自动扩缩容触发条件、你的延迟服务等级目标（SLO）。
- **可观测性与成本**：你实际监控的指标；训练侧看MFU（模型算力利用率）、单步耗时；推理侧看首token生成时间（TTFT）、吞吐、队列等待时长、GPU利用率、集群每GPU小时成本。能讲清楚成本，代表你水平更高。

最后讲一个实战故事，固定结构：**现象 → 排查工具 → 根因 → 修复方案 → 量化结果**
> 多节点任务运行速度比预期慢40%；通过NCCL_DEBUG日志发现，集合通信环回退到了管理网的TCP协议，原因是容器内没有暴露IB网卡；修复容器的设备挂载配置后，扩展效率达到线性扩展的8%以内。

这样一个故事，比单纯罗列工具要强得多——这些内容没法只靠读文档编造出来。

如果你实际接触的规模很小，那就突出深度：
> 我只跑过单节点任务，但我可以清楚说明显存占用去向，以及当单节点显存不够时，我们为什么选择FSDP风格的分片策略。

然后再讲你对大规模集群典型故障模式的理解（慢节点、网络拥塞、断点开销）。实验室招人，更看重成长潜力和诚实，而不是夸大的广度。


| 表述 | 可信的佐证要点 |
| ---- | ---- |
| “我用过GPU” | 说服力很弱，几乎所有人都在单卡上跑过东西 |
| “我在多节点上做过训练” | 用了哪种并行方案，为什么选它 |
| “我们遇到了扩展瓶颈” | 瓶颈在哪里：互联带宽、显存、慢节点、数据加载 |
| “我排查过任务卡死问题” | 和NCCL相关，以及你是怎么定位问题的 |
| “我懂成本模型” | 你实际跑出来的利用率，而不是理论峰值 |
| “有一件事我下次不会再这么做” | 这是最亮眼的收尾 |

表格里最后一行，是拉开差距的诚实回答。谁都能背理论峰值浮点算力；真正体现实战经验的数字，是你实际稳定达到的模型算力利用率，以及利用率没法更高的原因。

**面试官接下来大概率追问的问题**
- “集群利用率是什么水平？是什么因素在影响利用率？”
考察你作为集群负责人的思考：队列长度、空闲GPU、多卡任务带来的资源碎片、抢占资源的行为。准备一个你观察到并且优化过的具体低效场景。
- “凌晨两点一个任务挂了，你会怎么处理？”
故障发现链路、由什么机制/谁来重启任务、哪些中间状态丢失。只说“任务从检查点自动重启”，面试官会继续追问：检查点是多久之前的？这次故障带来的损失由谁承担？


- “选Slurm还是K8s，你们团队为什么这么选？”
只要理由合理自洽就可以；如果回答“不清楚，接手的时候就已经是这个方案了”，说明你只是集群使用者（这本身没问题，但就不要宣称自己负责搭建运维平台）。
- “如果预算翻倍，你会怎么改造这套集群？”
考察你是理解原有方案的约束条件，还是只是被动在用这套系统。

**常见误区**

1. **夸大规模**：说自己做过分布式训练，但其实只是单节点；说自己管理集群，但其实只是提交任务。面试官的追问就是专门用来拆穿这类夸大的，这种情况面试基本就到此为止。
2. **只罗列工具，不区分权责、不讲案例**：只是列出Slurm、K8s、vLLM、Ray，只能证明你接触过，不能证明你有能力。
3. **缺少量化数字**：GPU卡数、任务规模、利用率、队列等待时长、服务指标SLO。做基础设施的人会习惯性量化，回答里没有数字，是最明显的破绽。
4. **回避短板、强行吹牛**：“我没有用过IB组网，但是基于XX经验，我知道重点要监控哪些指标”，远好过你不懂装懂，硬扯PFC调优。

**核心要点总结**

1. 先讲清楚你接触过的最大规模上限；这会引导后续所有提问，坦诚说明上限是成熟的表现，不是弱点。
2. 分层说明技术栈，明确标注：自主负责 / 使用过 / 了解原理；只罗列工具，只能证明接触过，不能证明能力。
3. 准备一个带量化数据的实战案例（现象、排查工具、根因、修复方案、结果数字），它的说服力胜过工具清单，因为没法靠读文档编造。

一个显得你资深的小表达技巧：当你说出自己经验上限的时候，除了报数字，顺带提一下更高一档规模下你会重点监控的故障模式。

> “我跑过64卡，没有用过基于IB的多节点集群，但如果要上手这类环境，我最先要加监控的是每个进程的集合通信完成时间离散度。”

这么说，就把一处你坦诚的经验短板，转变成了你理解下一阶复杂度的证明——而这恰恰就是面试官追问时想考察的东西。
