# 摄取40个企业数据源（SharePoint、Confluence、Jira、Drive），支持增量同步与删除处理
这是一道Glean标志性的设计题，**删除操作而非数据摄取才是陷阱**。题目覆盖连接器框架、每个数据源类别的变更检测、墓碑标记（tombstones），以及客户实际签署的新鲜度SLO。



## 18 摄取40个企业数据源（SharePoint、Confluence、Jira、Drive），支持增量同步与删除处理


**TL;DR：** 构建一套连接器框架（标准化文档封装体 + 各数据源适配器），而不是40套定制化流水线。删除是陷阱：很多API不会显式告知数据已被移除。因此需要结合显式删除事件、通过全量枚举做墓碑检测、TTL隔离机制；并且从第一天起，每一份文档都要附带ACL权限元数据。

### 如何着手设计
不要设计40套独立定制流水线。面试官想要的架构是**连接器框架**：一套标准化文档模型与同步契约，搭配各个数据源专属适配器。并且要提前指出两个致命隐患：
1. **删除**：一份被撤销/删除的文档如果仍然对外提供服务，属于安全事故，不只是数据陈旧bug；
2. **权限元数据**：必须从第一天就随每一份文档一起携带。

#### 优秀答案
```mermaid
flowchart LR
    A[40个数据源] --> B[各数据源适配器]
    B --> C[标准化封装体 + ACL]
    C --> D[增量同步：游标 / Webhook / 哈希]
    D --> E[墓碑标记 + ACL变更处理<br/>同步账本]
    E --> F[解析、分块、嵌入、索引]
```

**标准化文档模型**：所有适配器输出统一封装结构：
`{source, doc_id, version/etag, content, mime, acl[], parent_path, updated_at, deleted?}`
下游环节（解析、分块、嵌入、索引）与数据源无关；所有数据源特有的怪异逻辑全部封装在适配器内部。
按照查询价值优先排序连接器：通常5个数据源承载90%的查询量；优先上线这部分，不要试图一次性搞定全部40个数据源。

**变更检测，分为三类数据源**
1. **Webhook / 事件型数据源**（Drive、SharePoint 通过Graph订阅）：可实现近实时推送；但Webhook会丢失、过期，因此必须搭配周期性校验爬取。
2. **游标/增量API数据源**（Jira `updated > t`、Confluence CQL）：可以增量轮询，每个连接器保存水印（watermark）。
3. **简易数据源**（文件共享、部分Wiki）：需要周期性列出全部条目，再对比内容哈希做差异对比。

每个连接器的状态保存在**同步账本**（sync ledger）中：最后游标、最后一次全量爬取时间、错误计数；同步崩溃后可以恢复，不需要从头重新同步。

**删除处理，真正的陷阱**
很多API不会告诉你对象已经消失；增量数据流直接不再返回该条目。需要三种机制：
1. 数据源提供显式删除事件时，直接使用；
2. 通过周期性全量枚举做墓碑检测：把数据源的条目列表和索引做对比，索引中存在、但数据源列表不存在的条目标记为墓碑；
3. 对于全量枚举成本过高的数据源，使用TTL隔离：超过N天没有出现的文档标记待清理，之后再删除。

删除操作必须在约定SLO内完整传播到整条链路：索引、向量库、缓存、衍生分块。
举例：权限撤销的文档需要15分钟内不可访问；普通删除24小时内完成。
同样一套机制也处理ACL变更：对部分用户来说ACL变更等同于文档删除。

> “枚举成本过高”这个说法，在接受之前要做数值验算，墓碑爬取实际成本往往比想象更低（有算术依据）。
> 枚举只是**列出ID，不是重新拉取内容**：一个500万文档的数据源，每页返回1000个ID，总共5000次API调用；即使限流到10请求/秒，大约8分钟即可完成，夜间执行完全可行。
> 真正昂贵的是重新拉取、重新处理文档内容；墓碑检查不会做这件事，只对比ID集合。

以上计算基于前提假设，需要针对每个数据源单独校验：API实际分页大小、实际获得的配额、往返延迟、枚举所需权限、枚举结果是否完整。
如果数据源每页只返回100个ID，每秒只能2次请求，那就是完全另一种方案。

因此合理的设计方案：
- 只要单数据源枚举成本可控，执行夜间全量枚举（24小时内检测删除）；
- 成本不可控的数据源使用TTL隔离；
- 权限撤销需要严格15分钟SLO，依靠ACL刷新循环，而不是枚举爬取。
**把“列出ID的成本”和“拉取内容的成本”明确区分开，才让删除方案从政策变成可工程落地的预算。**

**运维层**
- 每个数据源配置限流预算（SharePoint会限流，必须遵守Retry‑After，否则管理员会封禁你的服务账号）。
- 每个连接器健康大盘：已同步文档数、与源数据的延迟、错误率、最近一次成功全量爬取时间。
- 连接器腐化是常态；静默腐化会导致索引悄悄衰减，用户信任流失。
- 分块/嵌入模型升级时的重建索引路径：蓝绿切换索引；从存储的原始文档层回放数据，而不是重新爬取40个数据源。

**把新鲜度作为产品指标度量**
按每个连接器统计：从源文档编辑完成到可被检索的p95耗时，展示给客户。把“数据是否新鲜”从口头争论变成可视化图表。

#### 面试官会继续追问的问题
> “某个连接器API没有增量端点，并且有500万文档？”
> （对列表做哈希差异对比、分区爬取；和源系统团队协商Webhook或者数据库级CDC）

> “权限如何同步？”
> （ACL随文档一起摄入，并且以更短周期刷新；在查询时解析用户组成员关系，也就是权限感知RAG）

> “同步半失败怎么办？”
> （基于doc_id+version做幂等upsert，允许部分同步失败后安全重试）

#### 常见错误
1. 将摄取当作一次性加载，仅靠定时任务刷新；
2. 面试官不问就完全不考虑删除逻辑，被问到之后临时临场发挥；
3. 忘记ACL元数据：如果没有提前摄入，后续想要补全必须全部重新摄取；
4. 试图一次性设计全部40个连接器，而不是按照业务价值分阶段上线。

#### 核心要点
- 一套标准化封装体 + 各数据源适配器，优于40套独立定制流水线。
- 删除才是真正陷阱：结合删除事件、全量枚举墓碑检测、TTL隔离，全部在约定SLO下执行。
- ACL元数据必须从第一天就跟随每一份文档，无法事后补全。
- 根据查询业务价值排序连接器上线顺序，将每个连接器的新鲜度作为产品指标监控。

---

### 额外风险段落（墓碑‑全量枚举的隐患）
通过全量枚举实现墓碑标记有一个致命风险：如果数据源API不稳定，返回不完整的条目列表，你的差异对比逻辑会把大量仍然存在的活文档标记为“缺失”（墓碑），这属于自己造成的可用性事故。
**必须保证枚举结果完整之后，才执行删除动作**（文档数量在允许误差范围内、无分页错误）；同时对单次校验轮次允许标记为墓碑的文档数量做限流。

### 名词注释（便于理解）
1. **tombstone（墓碑标记）**：标记文档逻辑删除，不直接物理删除，用于后续清理
2. **SLO**：服务等级目标
3. **ACL**：访问控制列表（权限元数据）
4. **watermark（水印）**：增量同步标记，记录上次同步的时间/游标
5. **idempotent upsert（幂等更新插入）**：重复执行不会产生副作用
6. **CDC**：变更数据捕获
7. **delta API**：增量变更API
8. **enumeration**：枚举，列出全部对象ID，不读取内容
