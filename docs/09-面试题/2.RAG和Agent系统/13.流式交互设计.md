# 你的智能体工作流需要30秒。设计流式用户交互，包含中途失败时的处理逻辑。
感知延迟是一个设计层面问题，而不是基础设施细节。内容涵盖渐进式信息披露、服务器推送事件（SSE）与WebSocket对比、可恢复机制，以及大部分面试者从未思考过的中途失败问题。



**12 你的智能体工作流需要30秒。设计流式用户交互，包含中途失败时的处理逻辑。**

要点速览：不要一味追求原始低延迟，要优化首信号响应时间与过程可信度。通过服务器推送事件（SSE）传输一套带类型的事件协议（先输出步骤事件，再输出文本令牌）。工作流在服务端运行，每一步设置检查点，实现重连恢复；即便中途发生故障，也绝不展示一份看似完整实则残缺的回答。

## 解题思路
在动手设计前重新梳理认知：用户感知到的不是总耗时，而是**首信号响应时间**与**过程可信度**。一个耗时30秒、但过程状态可见的工作流，体验要好过15秒全程只显示加载转圈。要理清任务形态：是单次长大模型生成，还是多步骤智能体流程（规划→多次工具调用→结果整合）？二者方案不同：普通生成流式输出令牌，而智能体工作流流式输出**事件**。

### 高分参考答案
**传输方案**：单向从模型到客户端的流式场景选用服务器推送事件(SSE)；它简单、原生基于HTTP，依靠`Last‑Event‑ID`实现自动重连。只有当需要客户端中途输入（比如让用户批准某个操作）时，才选用WebSocket。
如果部署在无服务/边缘架构，要注意代理缓冲与函数超时限制。Vercel环境下一个典型陷阱：基础设施层会悄悄缓冲你的流数据，导致流式失效。

**事件协议设计**：不要直接把每一步内部原始令牌全部推送给客户端。定义一套带类型事件协议：
`step_started("Searching order history")`（步骤开始(“查询订单历史”)），
`tool_result(summary)`（工具返回结果(摘要)），
`answer_delta(tokens)`（回答增量(令牌)），
`done(citations, usage)`（完成(引用信息，用量统计)），
`error(step, recoverable?)`（错误(步骤，是否可恢复?)）。

UI界面把步骤渲染为实时清单，再流式输出最终回答文本。这就是渐进式信息披露：**500毫秒内给出首个反馈（“正在查询相关信息……”），2‑3秒内输出真实业务信息，之后持续推送流程进展**。向用户展示智能体正在做什么（“已核查3个信息源”），不仅缓解等待焦虑，还能提升用户对回答的信任度。

## 流程图：长达30秒，要让用户感知系统一直在运行
1. 请求发起，预计总工作量30秒
2. **500毫秒输出首个信号：“正在查询相关信息……”**
> 优化首信号响应时间与过程可信度，而不是单纯优化原始延迟。用户关心的是系统已经开始干活，而不是最终答案何时落地。
3. 推送`step_started`事件，界面出现实时任务清单
4. 推送`tool_result`工具结果摘要
5. 推送`answer_delta`，开始流式输出回答文本
6. **某一步骤发生故障 → 执行重试，页面不会卡死转圈**
> 第7秒上游服务不稳定时，要如实展示正在重试，而不是界面冻结；这就是重试和直接失败放弃的区别。
7. **从检查点恢复继续执行，用户看到真实状态提示**
8. **done事件：输出引用来源与资源消耗统计**
> 这份保存在服务端的事件日志，既是重连时回放的数据源，也是用户反馈异常问题时我们排查的依据。

### 客户端 ↔ 智能体服务端时序图
客户端发起请求 → 智能体服务端接收
服务端持续推送事件流；
中途发生：第N步执行失败 → 下发`step_retrying`事件（从检查点恢复）；
后续推送完成事件，附带引用信息；
**发生网络断开：客户端携带`Last‑Event‑ID`重连，服务端从该事件开始回放整条事件日志。**
> 工作流始终在服务端继续运行；绝对不要把工作流生命周期绑定在客户端连接的存活时间上。

### 一次真实30秒运行的事件日志示例
```
t=0.3s    step_started     "Reading your order history"       开始步骤：读取你的订单记录
t=2.1s    tool_result      "Found 3 orders, most recent Aug 12" 工具结果：找到3笔订单，最近一笔8月12日
t=2.2s    step_started     "Checking shipping status"        开始步骤：查询物流状态
t=6.8s    step_retrying    "Carrier API slow, retrying (1/2)" 步骤重试：物流接口响应慢，正在重试(第1/2次)
t=11.0s   tool_result      "Package at regional facility since Tuesday" 工具结果：包裹自周二起存放于区域转运中心
t=11.1s   answer_delta     tokens...                         增量输出回答令牌
t=29.7s   done             citations=[2], usage={...}        完成，附带引用来源、资源消耗
```

站在用户视角：半秒就看到系统有反馈，第2秒拿到有效信息；流程中间接口抖动，页面展示“正在重试”，而不是卡死转圈。
站在工程师视角：这份日志同时也是调试排查材料。
**设计一套带类型的事件流，一举三得：实现良好交互体验、支持断点续跑、同时保障可观测性。这是面试要答到的核心要点。**

### 中途故障处理（拉开面试者差距的考点），按故障类型分别处理
1. **瞬时故障（限流、超时）**：在对应步骤N服务端做退避重试，**不要掐断流**，下发`step_retrying`事件告知前端。编排器需要为每一步建立持久化检查点（Redis/Postgres，或Temporal这类工作流引擎），重试从失败的第N步继续，而不是全部从头跑一遍。
2. **网络连接断开**：客户端携带上一条事件ID重连，服务端从日志回放事件。**工作流独立跑在服务端，绝不跟随客户端断连而终止。**
3. **严重故障，已经产生部分输出**：**绝对不能留下一份看起来完整、实际残缺的回答**。两种选择：展示明确的局部状态UI（“已完成步骤1‑2，但无法获取物流信息，这是目前拿到的内容，是否重试？”），或者回滚已经展示的文本。最糟糕的做法是悄无声息截断输出——用户会误以为这份残缺内容就是完整结果。
4. **已产生副作用后发生故障（例如退款已发起，确认邮件发送失败）**：明确告诉用户哪些操作已经生效，并且仅对失败的那一步做幂等重试。

### 指标衡量
- 首事件响应时间 time‑to‑first‑event
- p95完成耗时
- **流中断放弃率（用户中途退出，真实交互核心指标）**
- 局部故障发生率

做A/B对照实验：渐进式步骤展示 vs 单纯加载转圈；可见的步骤展示方案，用户中途放弃率会明显下降。

### 面试官接下来大概率追问的问题
> “用户在第20秒关掉标签页，后台任务还会跑完吗？”
答：会。服务端持续执行，结果存入历史记录，也可以推送通知。

> “用户能不能取消任务？”
答：采用协作式取消，步骤间隙检测取消信号；已经触发的外部副作用要么执行完毕，要么做补偿回滚。

> “如何流式输出JSON这类结构化返回？”
答：可以一路输出展示文本，等全部完成再下发完整结构化数据；或者谨慎做增量JSON解析。

### 常见错误
只简单回答“用SSE”——传输层只是10%的工作量。
没有检查点机制：网络轻微波动就要重新跑完整30秒流程。
故障后保留残缺输出，不做提示。
把内部调试日志直接暴露给UI界面；步骤提示文案要面向普通用户，不是给开发看的debug日志。

## 核心要点总结
- 感知延迟是设计问题：**500ms内给出首个可见反馈，用步骤清单建立用户信任**。
- 工作流在**服务端运行**，每一步持久化检查点；断连重连通过事件ID回放，不因客户端关闭而终止任务。
- 故障分类型处理：瞬时故障展示重试；严重故障绝不静默保留残缺回答；已发生副作用要如实告知。
- 传输优先SSE；仅当需要客户端中途交互时才选WebSocket；注意边缘/无服务环境代理缓冲坑。
- 向前端推送**业务事件协议**，不是底层调试日志，事件日志同时用于可观测性排查。

> 补充容易被低估的一点：即便检查点全部实现，步骤提示文本本身也属于泄露风险点。例如把数据库内部表名、字段名直接作为步骤提示推给前端，会造成信息泄露。面向用户展示的进度提示，要和内部调试日志做隔离，做脱敏改写。
> 进度事件通道要和最终回答输出一样，做内容脱敏过滤，不能直接透传后端内部变量名、表名、敏感标识符。
