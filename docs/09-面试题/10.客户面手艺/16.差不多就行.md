# 你的客户说试点项目“差不多好用就行”。
当场和他们一起定义成功指标。

成功标准模糊不清，试点项目就会陷入“再延期一个月”的无尽拉锯。下面这套引导话术，可以把一句“差不多好用就行”，转化成客户认可的量化指标、基准值，以及决策日期。


你的客户说试点项目“差不多好用就行”，请当场和他们一起定义成功指标。


**一句话摘要：重在引导，而非强行指定。**
把“好用”转化为可观测的业务表现；指标要对齐项目赞助人拍板扩容时需要拿出的依据；搭建【质量指标/运行指标/落地采纳指标】三层指标体系，本周就测出基线数据；让客户共同敲定终止标准和最终决策日期。

---

## 解题思路
“差不多好用就行”，是试点范围沟通里最危险的一句话。成功标准没有量化，试点就谈不上真正成功，只会慢慢拖成“再延长一个月”的僵局；而质疑者随口的主观感受，也会盖过你实实在在的成果。面试官想看到的，是你**引导沟通，而不是单方面下达指标**：从客户自己的表述里提炼指标、绑定基线数据与决策节点，最重要的是，让客户认可这些数字。优秀的候选人还需要熟练掌握AI试点这套标准指标框架。

### 高分回答思路
把它组织成结构化对话，分四步走：
1. 把“好用”转化为可观测的实际表现
> 帮我们把“好用”具象化一点：三个月之后，如果试点跑成功了，你会看到什么变化？在你们的运营复盘会上，会出现哪些现在没有的情况？谁会给出什么样的反馈？
持续追问，直到对方说出可以统计的结果，例如：“客服不用再给简单工单升级上报了”、“我们团队不用每周五花时间整理报表了”。

2. 指标对齐最终扩容决策，而不是只做演示效果
> 这个试点结束之后，会有负责人（大概率是CFO）决定要不要全量上线。这个人需要什么样的证据，才愿意拍板？我们就围绕这个证据来设计试点方案。
这个思路，把指标从单纯的技术验证，变成项目负责人用来争取资源、向上汇报的依据，客户才会愿意深度配合。

3. 搭建三层指标框架，并且坚持先测出基线值
> 针对这类系统，我一般建议每层只定一个核心指标：
> - **质量指标**：基于客户团队整理的100条标准答案数据集计算准确率，由你们来判定结果对错，而不是我们；
> - **业务运行指标**：业务价值数字，比如工单自助解决率、单工单处理时长、每位分析师节省工时；
> - **落地采纳指标**：客户团队的周活跃使用率——一套准确率再高，但没人愿意点开用的系统，本质就是失败的。
> 而且正式上线之前，我们要先确认：现在这些指标的现状是多少？如果本周不先测出现有流程的基线数据，到第8周拿到结果的时候，我们连对比参照都没有。

同时主动增加兜底约束指标（上报率、错误严重等级、客户满意度不低于当前水平），会显得你很专业：你不只盯着收益，也主动把安全风险纳入考核。

4. 坦诚设定达标线、止损线，以及明确的决策日期
> 我们约定两条线：一条是达标线（继续推进），一条是止损线（终止项目）。我更愿意现在就说好，如果指标低于X，我们就停掉，而不是等到第8周再拉扯谈判。我们今天就把最终上线/终止评审会加到日程里，放在第9周，邀请项目负责人参会。
主动提出止损标准，是建立信任的关键一步，也是面试官格外看重的得分点。

收尾复述确认：
> 那我们对齐一下：在你们的100条测试集上准确率≥85%，这三类试点场景工单自助解决率从0提升到20%，团队周使用率≥60%，客户满意度不低于基线水平，3月14日做最终决策。我会把这些整理成一页确认文档，除了你之外，还有谁需要签字确认？

### 表格翻译
| 他们常说的话 | 这句话掩盖的问题 | 用来替代它的量化指标 |
| ---- | ---- | ---- |
| “它只要好用就行” | 没人对“好用”的标准达成共识 | 在一组真实业务案例上的任务成功率 |
| “比现在更快” | 从来没有采集过基准数据 | 开发前就测定的中位处理时长 |
| “精度很高” | 为了这个准确，要承担多大的出错代价 | 高容错成本决策场景下的精确率（Precision） |
| “团队一定会喜欢它” | 想当然认为大家会采纳，而没有做落地设计 | 该工作流覆盖人群中的周活跃用户数 |
| “它要能支撑大规模使用” | 没人统计过实际业务体量 | 在真实业务体量下，每办结一单的成本 |

左栏是别人会跟你说的口头表述。右栏内容，必须在写第一行代码之前就白纸黑字确定下来。如果缺少这些，试点项目就谈不上合格或者失败，最后只会陷入无休止的争论。


基线数据的重要性，举一个反面例子就很好理解：“本周测量基线”听起来只是流程，但等到试点结束你才会体会它的价值。想象第8周复盘，没有基线的场景：你的系统工单中位数处理时长4分钟，大家本来觉得不错，结果质疑者说“我们人工本来3分钟就能做完”。这下试点直接看起来变差了，而且你没法核验这句话真假——事前没有记录原始数据。会议最后只能变成各说各话，负责人选择“再延期一个月”，去补本该在第0周就测好的基线。
反过来，如果提前测了基线：
> 原来处理时长6.2分钟，现在4.0分钟，试点场景下降35%，这是每周的趋势图表。
两种试点，一个顺利全量上线，一个陷入无限延期；差别仅仅是在开发启动前花一天时间采集基线。
这就是为什么“现在这些指标是多少？”不是一个可有可无的话术，它直接决定这个试点最后能不能被认定为成功。

### 面试官后续追问以及应答思路
- 客户提出一个“好看但无效的指标”（例如：用户提问总次数）
温和引导：单纯使用量上涨不等于拿到业务结果，有可能是用户看不懂系统、反复试错，我们需要搭配业务结果指标一起看。
- 客户要求把标准定为99%准确率
结合基线协商：现在人工的准确率是多少？我们用同样的评判口径，目标做到比人工更好就行。
- 第6周的时候，你预判业务指标大概率达不到目标
尽早同步、公开排查根因，启用我们提前约定好的止损框架——这套规则本来就是为这种情况准备的。

## 常见踩坑点
- 单方面指定指标，而不是从客户的诉求里提炼：客户自己认可的数字，扛得住内部政治博弈；厂商单方面定下的指标很容易失效。
- 完全不测基线：这是最普遍的翻车原因，到第8周出结果的时候，没有参照基准。
- 只盯质量指标，没有业务指标和采纳指标：哪怕准确率95%，但没人使用，试点就是失败。
- 回避设置止损终止标准：没有约定“什么时候叫停”的试点，就算做成了，最后的成功结论也没有说服力。

## 补充
止损标准，是绝大多数候选人都会漏掉的一步，主动提出来意义重大：
**只有提前说好“什么时候算失败”的试点，最后得出的“成功”结论才是可信的。**
没有止损线，就算成果很亮眼，大家也会反复质疑，因为事前根本没有对齐“成功的定义”。这不是过度谨慎，而是让你的项目成果经得起推敲。
