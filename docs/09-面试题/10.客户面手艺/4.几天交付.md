# 问题：讲一次你在短短几天内交付了本需要数月才能完成的成果的经历。你做了哪些取舍、是如何做出这些取舍判断的？
原生AI公司会问这道题，用来区分两类工程师：一类是行动迅速且具备判断力的工程师，另一类只是单纯求快的工程师。考察重点**并不是速度本身，而是你选择在哪些地方取舍的逻辑**。下面是答题框架。


## 04 讲一次你在短短几天内交付了本需要数月才能完成的成果的经历。你做了哪些取舍、是如何做出这些取舍判断的？


**一句话要点：** 得分点不在于速度，而在于取舍的判断逻辑。只砍掉那些**可复原、且对本次决策无影响**的内容；绝不动任何关乎信任与安全的模块；把所有简化方案全部如实披露；写下技术债务，明确责任人与完成期限。

---

## 如何作答
这是一道考察抗压文化的面试题（OpenAI考察“高主观能动性”，Scale和xAI用来筛选适应快节奏的候选人），但陷阱在于：不要以为单凭速度就能赢。面试官评估的是**你的取舍决策算法**：你砍掉的是可复原、负面影响范围小的内容，还是直接简化了支付链路的测试、只是靠运气没出事？
挑选这样一个故事：截止时间是真实存在的（一场演示、一次上线、高管评审会），项目周期被压缩到原来的1/5~1/10，并且你能清晰讲清楚，你牺牲了什么、为什么这么选。

### 高分回答范例
快速交代背景风险，然后把大部分篇幅放在你的决策逻辑上：
> “客户这边负责项目的高管把试点评审提前了三周。我们只有四天时间，基于他们真实数据做出一套可用的文档分类演示系统，原本评估这个项目需要六周开发。我组织团队做了一次明确的取舍清单梳理，花一小时和团队把所有需求分成三类：
> **必须真实实现**：模型要在他们真实文档上运行；如果被发现演示用的是预设假数据，会直接毁掉客户信任。
> **可以模拟简化**：鉴权模块，我硬编码写了两个演示专用用户；后台管理界面，我直接手动修改配置文件。
> **绝对不能删减**：任何涉及客户数据安全的部分，数据必须保留在他们的虚拟私有云内，这里不能做任何简化。
>
> 我的取舍原则是：只砍掉**可复原、并且对本次决策无影响**的内容；永远不能动依赖信任或安全的模块。硬编码鉴权功能，后续一周就能修复；但数据处理环节偷工减料，一旦出事会直接终结双方合作。
> 我也坦诚地做简化：演示的时候，我直接说明“后台管理流程是模拟的，生产版本会补齐这些能力”。因为美化一个虚假的演示项目，一旦被戳穿，带来的损失远大于美化本身带来的收益。
>
> 我们四天完成交付。这位高管批准了试点项目。这也是很多人会漏掉的部分：我记录下了技术债务，写了一份清单，列出这7项简化方案，每一项都标注负责人和修复截止日期，在接下来三周内把所有债务清理完毕。快速交付本身没问题；带着未记录的技术债务狂奔，才会让你上线第三个月凌晨两点被紧急呼叫。”

---

> 这道题重点**不在于你有没有偷工减料**，而在于你能不能清晰说出你做了哪些取舍。这就是快速交付和鲁莽蛮干的区别：

| 压力下可以简化的内容 | 永远不能简化的内容 |
| ---- | ---- |
| 覆盖广度：只用一个数据源，而不是12个 | 涉及真实凭证、真实业务数据的链路 |
| 界面打磨：能用就行，界面简陋一点 | 所有一旦改动就无法无确认回滚的内容 |
| 通用性：把后续会变化的内容硬编码写死 | 日志系统，否则后续排查问题完全没有依据 |
| 自动化：先手动操作，维持两周 | 访问控制，任何情况下都不能动 |
| 只针对后续会废弃模块的测试 | 核心保留模块对应的测试 |

高分回答的结尾，要讲清楚：**你为这些取舍后续付出了什么代价，以及你是否还会做出同样的选择**。

有两类候选人，简历上没有客户演示项目，可以参考下面两点。
第一，故事场景可以替换，只要截止时间是外部强加、并且这件事对他人有真实风险：连夜开发故障恢复工具的应急事件、不可推迟的合规截止日期、供应商规定的迁移窗口期、被临时提前的董事会会议。
**不能用的场景**：自己给自己定的截止时间（“我挑战自己，周末写完这个项目”）。因为这件事没有真实利害关系，面试官会认为你没有经受真正的取舍压力，直接判定这个故事无效。

第二，一小时需求分类梳理这个方法，是可复用的核心内容，把它讲清楚，甚至比故事本身更重要：把所有规划需求列出来，分成【必须真实实现 / 可以模拟简化 / 绝对不能删减】三类。每一项都要问同一个问题：**如果这个简化方案在最坏的时刻暴露，会造成多大损失？**
模拟的后台界面出问题，最多被吐槽；伪造的演示结果暴露，会毁掉合作关系。面试官考察的判断力，本质就是这一个问题。这个分类梳理，不管是客户试点项目，还是内部项目，都可以使用。

## 面试官接下来会追问的问题
- “之后出了什么问题？” 准备真实答案，要有东西确实出故障、或者差点出故障，并且这件事完善了你取舍判断的规则。
- “你如何在一小时内让团队统一认可这些取舍？” 讲清楚把权衡关系可视化（白板上列出三类需求），这是团队共同决策，而不是慢慢妥协、不知不觉简化。
- “你还会这么做吗？” 回答：会，但有一处改动，并且说出改动是什么。
- xAI风格深挖：面试官会确认是**你亲自做了工作，还是只负责统筹**。准备第一人称的具体细节，例如：“我写了数据接入链路，玛丽亚负责模拟UI界面”。

## 常见错误
- 取舍的地方是面向用户的功能质量、安全相关模块：这属于鲁莽，不是判断力。
- 没有清晰的取舍逻辑，只说“我们只聚焦核心内容”：面试官会认为这只是运气好，不是能力。
- 向客户或者团队隐瞒简化方案：刻意隐瞒会直接亮起红灯；主动披露的简化，才属于工程权衡。
- 结尾不提清理技术债务：只讲快速交付，不提后续修复，面试官会认为你把烂摊子留给其他人。

### 编者备注
做好准备，“之后出了什么问题？”是紧随其后的追问，需要准备真实答案。一个极速交付的故事，如果全程没有任何故障，听起来要么是虚构，要么只是运气好，体现不出判断力。
如果你的取舍，削减了面向用户或者安全相关的质量，这道题直接失分——这只是借着赶截止日期的名义鲁莽行事。
xAI风格的面试官，还会深挖，确认是你亲手实现，还是仅仅统筹项目。准备第一人称的具体描述，例如：“我写了数据接入链路；玛丽亚负责模拟UI界面”。
