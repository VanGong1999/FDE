# 角色扮演场景：一位CTO对你说：“我们去年试过GPT，它在我们的数据上大量产生幻觉，AI根本没法用。”请做出回应。
这是企业AI场景里最常见的反对意见，而直接争辩是最快把事情搞砸的方式。制胜沟通流程是：共情认可经历 → 诊断问题根源 → 重构认知 → 降低风险。下面是参考话术。

## 13 角色扮演场景：一位CTO对你说：“我们去年试过GPT，它在我们的数据上大量产生幻觉，AI根本没法用。”请做出回应。


一句话要点总结：不要争辩，按这套流程沟通：先认可对方的经历，像排查事故一样定位失败原因（所谓“GPT产生幻觉”几乎总是因为直接使用原始大模型、没有检索增强、没有评估体系），把话题从“模型好不好”转变为“工程化系统”，再设计低成本、可证伪的测试，由客户来打分评判。

---
## 思考思路
客户这个反对理由一半是技术问题，一半是情绪问题。这位CTO在之前的实验上投入了预算，也押上了个人信誉，他同时也在试探你会不会尊重他的这段经历。如果你反驳说“现在模型比当年强很多了”，就会失败：这种说法否定了他真实遇到的问题，只是单纯为技术辩护，而不是解决他的业务难题。
这套高分沟通流程：**认可感受 → 定位问题 → 重构认知 → 降低风险**。其中定位问题这一步，最能体现工程深度。因为“GPT产生幻觉”只是表象，背后有五六种不同根因；一名优秀的前沿部署工程师，会把这件事当成一次线上事故复盘来处理。

### 高分回答话术
首先真诚认可对方感受：“从你看到的结果来看，得出这个结论很合理。说实话，很多团队早期尝试AI的时候，都遇到过一模一样的情况。在讨论结论之前，我想了解下当时的实验细节可以吗？因为‘模型出现幻觉’背后，一般都有明确、可以定位的原因。”

接着像工程师一样诊断问题，抛出3-4个精准问题：“当时模型要回答哪类问题？它是接入了你们自己的数据，还是只依靠模型预训练的通用知识？是直接用原始模型，还是基于你们文档做了检索增强？你还记得有哪些典型的错误回答案例吗？另外当时怎么衡量效果的，有没有专门的测试集，还是大家只是随便提问题试了试？”

十次里面有九次，情况都是：直接用ChatGPT原始模型（或简单封装层），没有对接企业私有数据做检索增强，没有评估体系，仅凭零散主观感受下判断。把这个共性模式讲出来，同时语气不能带有优越感，这一步是建立信任的关键：

“也就是说，模型是依靠预训练的通用知识来回答你们产品相关问题的，它其实根本没有读取过你们内部文档。它只能尽力生成看起来合理的答案。这并不是‘AI没用’，而是这套系统根本没有拿到需要用来作答的资料。”

重构认知，从讨论“模型”转为讨论“系统工程”：“现在思路变了：我们不再把它当成万能先知来提问，而是做工程化搭建：每一条回答都必须从你们文档检索到原文作为依据，回答附带引用来源；检索不到资料时，模型要明确说‘我不知道’。还有几乎所有人第一次尝试都会漏掉的一环：搭建包含几百条真实业务问题、附带标准答案的评估数据集，这样质量就变成可量化的指标，而不是主观感觉。”

提出低风险的下一步方案，方案要简单、可证伪：“我提议的方案，刻意做到低成本，随时可以叫停：选出你们业务里100个最常见的真实问题。我们基于你的文档搭建检索增强系统，一起用这100个问题测评效果，标准答案由你们掌握。如果达不到你们设定的合格标准，整个项目两周就可以结束，你们也拿到了结论。如果达到标准，我们再深入推进。这周能不能安排你的团队整理出这100个问题？”

客户这句质疑背后，通常是四类不同根源，却用同一句话表达，每一类要对应不同话术：

| 所谓的“幻觉”真实根因 | 判断线索 | 你可以这样说 |
| ---- | ---- | ---- |
| 完全没有检索，只用原始大模型 | “我们让它回答内部政策相关问题” | 模型没有读取你们的数据；没有资料支撑的回答，不能用来评判检索增强方案 |
| 检索出现漏召 | 主题对了，但答案不对、内容单薄 | 检索环节出了问题，检索问题可以单独修复，也可以单独量化评估 |
| 拿到了正确上下文，但是模型无视原文 | 回答引用了文档，内容却和文档矛盾 | 生成环节问题：增加引用校验、精简分段、做事实对齐检查 |
| 忠实还原了过时文档 | 自信地引用旧版本政策 | 这根本不是模型故障，是资料版本老旧的问题 |

在辩解任何内容之前，先问清楚属于哪一类。用来定位的问题很简单：**你当时问了模型什么，模型给出了什么回答？**

## 面试官接下来大概率追问的问题
1. CTO反问：“那这套系统就永远不会产生幻觉了吗？”——诚实作答的陷阱。
> “不会完全杜绝，但幻觉会变少，并且可以被发现。整套系统做检索溯源、附带引用、可量化评估；不可逆、高风险的流程保留人工审核。我们的设计思路是，错误回答成本低、容易被检出，而不是做到绝对不可能出错。”

2. “假设他们当初搭建的方案本身就很专业，但项目依然失败了，该怎么应对？”
> 严肃看待这个情况，索要评估数据集，把它当成真实工程难题来排查。保持好奇心，比死记话术更重要。

3. CEO也在场，请用30秒简述整套方案
> 抓重点：可量化的试点项目、由他们掌握标准答案、设置终止条件。

## 常见错误
- 在定位问题之前就争辩，或是抛出“新版模型强很多”这类话术；一味为技术辩护，而不去复盘当初失败的原因。
- 哪怕流露出一丝“是你们操作错了”的意味。复盘时要指出的是**2023年行业普遍采用的这套方案本身不完善**，而不是指责这位CTO。
- 为了拿下项目承诺零幻觉。这种说法违背客观诚实原则，而这位踩过坑的CTO很清楚这并不现实。
- 结束沟通前，没有敲定一个具体、可证伪的后续行动，没有确定负责人和截止时间。

> 如果他们问：“那这套系统就永远不会产生幻觉了吗？”不要为了拿下客户随口答应“绝对不会”。诚实的回答是：幻觉会更少，并且可被监测；回答附带原文引用、可量化评估，高风险的不可逆环节保留人工把关。吃过亏的CTO，会远比相信“零幻觉承诺”更信任这套坦诚的说法。


诊断问题的提问思路没问题，但讲结论时要注意语气。说“模型是基于预训练知识回答，没有看过你们文档”，要表达成**2023年大家普遍采用的这套方案本身不完善**，而不是“是你们搭建错了”。事实不变，但两种表达方式，决定这位CTO是和你站一边，还是继续抵触。


还有一点，**在定位清楚问题前，不要急着说“新模型强很多”**，这句话是在单纯为技术辩护，相当于暗示对方踩坑只是时机不好。用来降低风险的收尾方案，必须做到可证伪，评判权交给对方：由他们选出100个问题、掌握标准答案、合格线由他们设定。核心是：试点成本低，可以随时叫停。
