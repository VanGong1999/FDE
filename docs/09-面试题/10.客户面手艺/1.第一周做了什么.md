# 讲讲你从头到尾全权负责过的、目标最模糊不清的项目。第一周你做了什么？

这是FDE行为面试题里最常问到的一道。而“第一周做了什么”这个追问，是绝大多数候选人翻车的地方。下面这套回答框架，能证明你可以接手一团乱麻的局面，并把它梳理出秩序。

---
### 一句话摘要（TL;DR）
选一个**目标本身就没有明确定义**的项目。把第一周当成一次摸底调研：访谈承受痛点的一线人员、梳理真实数据、撰写一页纸备忘录，这份备忘录就成为原本没有提供给你的需求规格文档。最后用量化成果和真实的反思收尾。

## 答题思路
这道题是FDE的经典必考题目，因为这份工作本身就要面对模糊性：你到客户那边，拿到一个笼统的指令（例如“让AI可以处理理赔业务”），没有任何需求文档。面试官考察两点：
1. 你是否全权负责过一个定义不清晰的任务（不是“领导给我一个写得很模糊的工单”这种）；
2. 你有没有一套可复用的方法，把一团迷雾转化成可执行计划。

要选**目标本身不清晰**的故事，而不只是实现方式有难度。

回答结构分为5部分：
1. 为什么这个项目模糊（没有需求文档、相关方意见冲突、数据情况未知）
2. 你最先做了哪些事
3. 你如何定义“项目完成的标准”
4. 带数字的最终成果
5. 你会做出哪些改进

## 高分回答范例
**第一周的描述是拉开差距的关键。**优秀的候选人会用第一人称，描述一套具体的摸底调研动作：

> “第一周我没有写代码。我做了三件事。
> 第一，我访谈了五位直面业务痛点的一线人员，不是只看项目发起人的PPT。我找真正干活的分析师，问每个人：‘对你来说，顺利的一周是什么样？什么事情会把一切搞砸？’
> 第二，我拿到真实业务数据的访问权限，花两天时间做数据画像分析。因为相比糟糕的架构，不符合预期的数据现状才是毁掉项目方案更常见的原因。
> 第三，我写了一页纸备忘录：写清我理解的业务问题、我们两周内可以交付的最小可用版本（会有人真正使用），以及**明确列出我不打算做的事情**。我把文档发给项目发起人，请他批注修改。这份备忘录最后就成了需求规格文档——我自己写出了原本没有给到我的需求文档。”

然后阐述成果：
> “我们三周内交付了这个精简版本。它把报告准备工作从两天缩短到两小时。这次落地帮我们争取到了内部信任，得以推进更大规模的开发。”

结尾的自我反思要真实：
> “当初我太晚才暴露运营团队和合规团队之间的相关方矛盾。放到现在，我会在第一周就推动这场沟通，而不是等到第四周。”

第一周的描述决定回答成败，面试官几乎一定会追问：**你第一周具体做了什么？**

| 天数 | 你做的事情 | 这件事证明什么 |
| ---- | ---- | ---- |
| 第1-2天 | 和当前负责这项工作的一线人员沟通，而不是只找项目发起人 | 你挖掘真实工作流程，而不是停留在美好的设想 |
| 第2-3天 | 获取真实业务数据，而不是他们提前准备好的样例数据 | 样例数据永远比真实业务数据干净 |
| 第3-4天 | 写下你**不会做**的内容 | 范围界定，靠排除项来实现 |
| 第5天 | 交付一个极简、可以端到端运行的最小版本 | 在正式投入大量资源前，跑完所有边界环节 |

如果候选人描述第一周的工作只是阅读文档、搭建开发环境，那只能说明这是入职熟悉环境，**不是项目全权负责**。

转行的候选人常常觉得自己没有这类模糊项目的故事，因为他们没有对接外部客户。再仔细想想：模糊性的核心是**目标未定义**，而没有明确定义的目标随处可见。
- 一名软件工程师接到需求：“把仪表盘变快”，但没有定义“多快才算达标”，没有明确是哪一个仪表盘，三个团队对这个仪表盘的理解各不相同。当他主动去找出这个需求背后是谁在抱怨问题时，他就是在负责一个模糊项目。
- 数据分析师被问“为什么流失率上升”，但流失率这个指标甚至都没有埋点统计，这就是模糊项目。
- 支持工程师接到需求“想办法降低工单量”，这也是模糊项目。

考察重点不是场景，而是**你是否必须自己定义项目完成标准**，以及你能否拿出你产出的可核查文档。
会直接淘汰故事的反面例子：需求工单写得清清楚楚，只是技术实现很难。**技术难度和目标模糊是两回事**，面试官一眼就能看出你偷换概念。

## 面试官接下来会深挖的问题
- “你怎么确定这个缩小后的范围是正确的？”
  回答思路：讲价值和可行性的权衡，并且和使用者验证。
- “如果项目发起人不同意你的备忘录怎么办？”
  回答思路：备忘录的意义就在这里——在文档上修改成本很低；写成代码之后再修改，代价就很高。
- “还有谁参与了项目？”
  保持第一人称的主人翁视角，同时具体点名感谢其他人；通篇只用模糊的“我们”，会显得夸大自己负责的范围。
- Palantir风格的压力提问：打乱你的故事（“如果根本拿不到这份数据怎么办？”），看你的方法能不能应对变化。
  高分回答：在新假设下重新执行你的整套工作方法，而不是死守旧方案。
  示例：“到第三天的数据探查阶段，我就会发现这个问题。我会更新备忘录，写明目标的阻碍、利用现有资源可以先交付什么内容，再更新时间线，主动同步给项目发起人，而不是等别人告诉他。”
  背好的固定叙事，在这种扰动提问下会崩盘；一套真实可行的工作方法，可以接收新条件。这就是追问的全部目的。

## 常见错误
1. 选的故事只是**难度高**，而不是目标模糊；技术难题是另一道面试题。
2. 第一周就说“我直接开始开发”。还没定义问题就跳到写方案，是最典型的拆解失败，面试官专门考察这点。
3. 没有产出物。高分回答要有可核查的产出：备忘录、评估数据集、排好优先级的待办列表。
4. 结尾没有量化指标，也没有学到的经验。只说“项目进展顺利”是不合格的；要像例子一样：“从两天缩短到两小时，同时讲我的反思”。

最容易直接被淘汰的回答开头就是：**“我直接开始开发”**。在定义清楚问题前就急于写方案，正是面试官要找的思维短板。Palantir的面试官尤其喜欢中途打乱你的故事（假设拿不到数据这类问题），来判断你的方法能否应对变化，还是只是背好的稿子。确保你的故事要有可核验的产出物（备忘录、评估数据集、待办清单）；只说“项目很顺利”，没有量化数据，说明你无法为项目内容辩护。

### 讨论区

> 这套框架有一点讲得不够充分：最强的回答，会主动说出**第一周刻意不去访谈的某一位相关方，以及原因**。判断谁的痛点最重要这件事本身，就是能力证明。任何人都可以列出5次访谈；能选出这5个人、跳过那个嗓门很大但无关紧要的副总，才体现判断力。

> 同意，数据分析环节也是同理。只说“我花两天处理数据”力度弱；更好的说法是“我优先核查了整个模型依赖的核心字段，发现它30%的值是空的”。把你最先核查的内容说具体，才是关键。
