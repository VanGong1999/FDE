# 问题：向客户演示产品的中途，演示突然崩溃了。在现场你会怎么做？
面试官有时会故意制造故障来抛出这个问题。故障恢复有一套60秒处置流程，如果处理得当，一场出问题的演示，甚至比一场完美的演示更容易促成合作。


## 18 向客户演示产品的中途，演示突然崩溃了。在现场你会怎么做？

一句话要点：面试官本质是考察，和你一起处理线上故障是什么体验。执行四步流程，严格遵守时限：冷静说明情况、60秒边操作边排查、切换到当天早上提前录好的备用演示视频，再借着这次故障，向客户展示产品的线上错误处理能力。

---
## 该如何作答
演示翻车是现场工作里非常常见的情况，所以有些面试组会刻意制造故障：比如不稳定的Wi‑Fi、或是专门用来打乱你节奏的提问。他们考察的是你的心态稳定性与故障恢复方案，而不是看你能不能杜绝所有故障。优秀候选人要读懂更深一层的考察点：面试官评估的不是这次演示本身，而是**和你一起处理线上事故会是什么样子**。慌乱、甩锅、或者沉默调试十几分钟，都会让你的回答减分。冷静有序地排查处置，反而效果很好，有时甚至比毫无瑕疵的演示更好。

### 优秀参考答案
我在现场会执行一套四步流程，并且严格遵守时间限制：

1. **前10秒：冷静地把问题说出来**

不要假装一切正常，也不要一言不发直接埋头敲代码。可以这样说：“现场演示的软件偶尔会出现这类情况。给我60秒排查一下，如果没法快速解决，我准备了备用方案。”此时此刻，你的沉稳本身就是演示的一部分。

2. **60秒排查，操作的同时同步说明思路**

严格计时，只排查最常见的三类原因：网络/VPN问题、过期令牌、依赖服务（就是我今早从酒店还能正常使用的那个依赖项）。一边操作一边简单说明，因为在客户面前一声不吭调试，会让所有人都很煎熬。如果一分钟内没法定位明显问题，立刻停止。最糟糕的情况，就是反复说“再给我一分钟”，一拖再拖。

3. **无缝切换备用方案，不打乱演示节奏**

去客户现场做演示前，我一定会给现场演示准备两层兜底方案：一份当天早上录制好的、完全相同流程的演示录屏，还有附录截图。我会说：“咱们不把时间耗在调试上，这里是今早同一套系统上录好的完整流程。等会议结束，如果各位想看，我可以再现场重新跑一遍。”之后继续讲解方案本身，这场会议的核心目标是讲清业务场景，而不是保证我电脑VPN一直在线。

4. **用好这次故障，而不是掩盖它**

收尾之前可以说：“大家刚刚看到系统出故障了，刚好我原本准备后面再展示这部分：当线上环境发生这类故障时，系统会怎么处理。大家可以看错误处理逻辑、降级兜底策略，还有你们团队会在日志里看到的内容。”
我就把这次演示里最糟糕的瞬间，变成了最能打动持怀疑态度工程师的环节。
当天还要跟进闭环：“根因是X；这里是完整录屏；周四我们再现场演示一次可以吗？” 跟进闭环这件事，本身就是在展示：和你一起处理故障是什么样子。

如果面试官问你怎么提前预防故障，简洁回答：提前在客户现场的网络条件下彩排（或者按无网络条件准备本地兜底方案，不依赖不受控的线上依赖服务）、前一晚冻结演示环境、锁定软件版本、提前预热所有服务，并且提前规划好：如果中途损失10分钟，哪些内容可以跳过不讲。

| 时间段 | 你应该做什么 | 绝对不能做什么 |
| ---- | ---- | ---- |
| 0–5秒 | 轻声把故障说出来，保持平稳的音量 | 僵住不动，或者把报错栈信息念出来 |
| 5–30秒 | 执行一个提前彩排过的恢复尝试 | 临时即兴反复试第二种、第三种修复办法 |
| 30–60秒 | 切换备用方案：播放录屏、看截图、口头讲解流程 | 在所有人注视下反复点击尝试 |
| 剩余会议时间 | 继续讲完这次演示原本要传递的业务故事 | 不停道歉，把会议节奏彻底带偏 |
| 会后 | 当天就把可用的演示材料发给客户，同时说明故障原因 | 假装这件事从来没有发生过 |

面试官打分的对象不是软件，而是你。从容镇定、并且有提前准备好的兜底方案，代表你能力可靠；反复重试、不肯收手，只会显得慌乱。

60秒时限不是一个感觉上的要求，而是一套有逻辑的规则。你主动把这套规则讲给面试官，就能证明你真的经历过这种高压场景。

对你来说，每一次在众人面前调试的尝试，感觉只过了一小会儿；但对在场其他人来说，时间被拉长了：到60秒的时候，大家还觉得你只是“查一下问题”；到三分钟的时候，高管们已经悄悄点开别的页面；到五分钟，整场会议的节奏就彻底没了，再也救不回来。

硬性时间截止，远好于“再试最后一下”。因为调试耗时是不确定、不可预估的，到第45秒的时候，你根本不知道剩下的修复还要15秒还是15分钟。继续调试，等于拿客户的注意力去赌，而且你完全不知道胜算。

提前定好时限，就不用在你压力最大、判断力最差的时候临时做决定。这也是为什么你要反复演练切换备用方案，让它变成本能反应，而不是不得已的妥协。

如果你能解释清楚设置倒计时的意义——保护在场所有人的时间，避免调试无限拉长，你就展示出了这道题真正想考察的故障处置判断力。

## 面试官接下来可能追问的问题
- 【客户VP专门就是来看这一段演示的】直接对这位VP回应，立刻播放录屏，并且约好补演示时间：“我周四专门为您现场跑一遍，15分钟就够，我日程可以安排。”
- 【在场一位持怀疑态度的工程师说：这也叫可上线生产？】先认可对方，再把话题转开：“您说得没错。演示环境本身比生产环境更容易出问题，没有冗余保障，还靠酒店Wi‑Fi。我刚好给您展示一下，真正线上环境里，故障是怎么处理的。”
- 【你的备用包里具体都准备了什么？】准备真实清单：当天早上录制的演示视频、截图文档、预装好数据的本地环境、备用笔记本或者随身热点。

### 常见错误
1. 沉默调试十几分钟：最常见、杀伤力最大的错误做法。
2. 甩锅：怪Wi‑Fi、怪客户VPN、怪同事提交的代码。就算原因确实是这些，也会让人觉得你遇到线上事故时就是这个样子。
3. 没有兜底方案：只准备了线上现场演示，这不叫自信，属于准备不足，面试组会这么判定。
4. 反复不停道歉，让故障占据整场会议的重心：简单说明一次就够，尝试恢复，然后回到客户的业务议题上。

> 60秒时限，是这道题的关键。你要主动说清楚背后的逻辑：面试官不是看你能不能修好这个bug，而是看你会不会在真实线上事故里，浪费大家的时间死磕修复。主动给自己设置60秒上限，然后切换到录屏演示，恰恰展现出他们想要看到的判断力。
