# 描述你在客户现场遇到过最严重的生产事故。你告知了他们什么内容，以及何时告知？
事故本身是背景；**披露时间线才是考察重点**。面试官在衡量“你知晓问题”和“客户知晓问题”之间的时间差。下面这个回答能建立信任，而不是毁掉信任。


### 06 描述你在客户现场遇到过最严重的生产事故。你告知了他们什么内容，以及何时告知？


> 一句话总结：**披露的时间线才是考点，而不是bug本身。** 选一个由你造成的真实事故，然后体现：在确认问题后的一小时内联系客户，此时还没完全定位根本原因。表述采用清晰结构：发生了什么、对你方造成什么影响、我们正在采取什么措施、下一次更新时间。

## 思考方式
这个问题藏着两层问题。表层问题是考察你在压力下的业务能力；**真正考察的是披露的职业操守**：当你在客户环境搞出故障，你隐瞒了多久？前沿部署工程师的工作根基是客户信任，面试官衡量的就是“你知道问题”和“客户知道问题”之间的时间差。选一个你（或你的团队）确实造成损害的事故：数据出错、系统宕机、产生资金损失，不能选“险酿事故”的案例。讲故事时，既要讲技术修复，也要重点讲沟通时间线。

### 高分回答范例
“在一次上线部署中，我提交的流水线变更，悄无声息地对客户营收看板里的交易做了重复计数，而这个看板是客户首席财务官日常查看的。我们九天之后才发现这个问题；这段时间里数据一直都是错的。

我告知客户的内容以及时间：在确认这个bug真实存在的第一个小时内，哪怕我们还没有完全摸清影响范围，我致电了客户对接人。我原话是：‘我们发现一处由我方引入的缺陷。自14号起，您的营收看板数据高估了大约3%–6%。我们目前还不清楚确切影响范围。请暂时不要采信这些数据。这是我们目前掌握的信息，我们将在下午4点进行下一次更新。’我没有等到定位根本原因才通知，因为客户每一小时基于错误数据做出决策，都意味着我们在持续造成损害。

我遵循的表述框架：发生了什么、对您产生的影响、我们正在做什么、您何时会收到我的下一次消息。**绝不超出已确认事实做猜测，绝不甩锅，就算暂时没有新进展，也要给出下一次更新的时间**。我们在48小时内推送了修正后的历史数据，之后提交书面事故复盘报告，附带修复方案以及用来防范同类问题的回归测试。

这个结果反直觉，也是我愿意再次用同样方式处理这件事的原因：**双方的合作关系反而变得更牢固**。客户首席财务官告诉我们的客户负责人，这是第一次有供应商在客户自己发现问题之前主动来电。信任不是靠永远不出故障建立的；信任建立在故障发生后的第一个小时里。”

时间线本身就是答案，时间线里的空档，就是面试官打分的地方：

| 时间节点 | 高分回答需要包含的内容 |
| ---- | ---- |
| 你发现问题 | 发现方式，是我方告警触发，还是客户来电告知 |
| 你通知客户 | 尽早通知，信息可以不完整，并且在客户主动询问之前告知。这是整道题的核心 |
| 控制故障 | 缩小受影响功能范围，而不是直接关停全部服务 |
| 评估影响范围 | 哪些对象受到影响，以及你能否确认影响边界 |
| 解决问题 | 以及当你尚未掌握全部信息时，你是如何沟通的 |
| 事后复盘 | 在系统层面做出的改动，而不是只谈主观心态 |

如果是**客户先发现问题，你才告知**，要坦诚说明。在场所有面试官都遇到过这种情况；他们想听的是你从中学会缩短这个信息差。

你值得演练一下：当你几乎一无所知时，第一通电话该怎么说。因为人往往会在这个节点停滞，白白浪费一小时。有效的话术，完全由**已确认事实 + 明确说明哪些信息未知**构成：
“我们发现一处由我方引入的缺陷。它影响您的营收看板。我们认为数据高估问题大约从14号开始；我们目前还不清楚确切影响规模，也不确定下游系统是否使用了这些数据。在收到我们新通知前，请把这些数据视作存疑。无论如何，下午4点会更新情况。”

每一句话要么是已经核实的事实，要么标明信息未知，这样后续无需收回任何表述。
这通电话里，**两句话绝对不能说**：
1. 在评估完影响范围前说“看起来问题不大”——如果后续发现影响扩大，你就相当于二次误导客户；
2. 在找到根本原因前承诺“今晚就能修好”——第二小时如果无法兑现承诺，技术事故就演变成信誉事故。

这套沟通原则是刻意不对称的：**多披露不确定性，少承诺修复结果**，把下午4点的更新，作为发布好消息的窗口（如果有好消息的话）。

## 面试官接下来会追问的问题
- “为什么花了九天才能发现问题？”坦诚承认检测环节存在漏洞，这正是监控方案需要吸取的教训（例如：“我们现在增加告警，当日环比波动超过X%就触发告警”）。
- “如果你的上级领导让你先不要告诉客户，你怎么办？”高分回答：快速升级上报，力争披露问题；沉默会让事态持续恶化。如果通知时间被否决，需要把理由和新的截止时间写成书面记录。
- “事故复盘之后，你们改了什么？”要说出一个可落地的长效机制：校验逻辑、上线门禁、操作手册，而不是“我们以后会更小心”。
- “这件事有没有合同/服务等级协议（SLA）层面的影响？”体现你明白披露这件事存在法律层面的考量（联动客户负责人，不要自行随意承诺责任相关表述），这会体现你的资深程度。

## 常见错误
- 选一个被美化的“险出事故”案例（“我们差点造成服务中断”）。面试官问的是你最严重的事故；拿不出真实事故，会被认为要么经验不足，要么刻意回避。
- 默默修复问题，从来没有告知客户。在重视信任的公司，这个回答直接不合格。
- 甩锅给客户的数据、队友或者第三方服务商。面试官会重点考察你是否主动承担责任。
- 通篇只讲技术细节，缺少沟通细节。题目明确问了你**告知了客户什么，以及何时告知**，一定要回答这部分。

> 最尖锐的追问是：“如果你的上级领导让你先不要告诉客户，你怎么办？”得分的回答是快速升级上报，力争披露问题；如果你的披露时间被否决，要把理由和新截止时间书面记录下来。面试官让你讲最严重的事故，你却选一个美化过的“有惊无险”案例，会被视作经验不足或者刻意回避。同时也要留意SLA维度：体现你会联动客户负责人，而不是自己随意承诺责任，这是体现资深能力的一个隐性信号。

### 讨论区 · 



第一小时内致电客户这个思路是正确的，但要说明在拨打客户电话之前，你在内部先通知了谁。在一小时内联系客户，但完全没提前同步给我方客户负责人，这本身就是另一种失败。客户负责人从客户口中听说这件事，将无法提供支持。规范做法：先用几分钟内部同步，再致电客户。



同样重要的是，把检测环节的教训落实为系统机制，而不是口头承诺。“我们现在增加告警，当日环比波动超过X%就触发告警”是合格回答；“我们上线会更小心”这种表述，会让同类事故再次发生。
