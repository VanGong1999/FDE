### 标题
客户执意要做微调（fine-tuning），但检索增强生成（RAG）明显更适配场景，且客户不肯让步。如果你是可信赖的顾问或者供应商，你会怎么做？

这是典型的可信顾问困境：一味顺从客户、或是固执己见，两种做法都会失败。稳妥的方案流程是：先摸清诉求、书面给出建议、再开展对照测试，让结果来做决定。

> TL;DR（一句话总结）：既不要单纯接单照做，也不要做固执的工程师。先弄清楚客户想要微调背后的原因，用客户听得懂的语言诚恳给出建议，然后提议开展为期两周的对照评测，由客户手握标准答案，凭结果下定论。如果客户仍然坚持，就留下书面记录，按客户要求高质量开发，同时预留低成本切换到检索方案的退路。

---
### 应对思路
这个场景考验一线工程师每天都会遇到的分寸难题：你靠成交拿酬劳，但你的价值在于说出真相。两种极端做法都不可取：

供应商式做法（客户想要微调，那就卖微调方案）：最终上线一套效果糟糕的系统，你的名字绑定在失败项目上；

固执工程师做法（我拒绝做错误的方案）：丢掉客户信任，后续就算证明自己是对的，也失去机会。

得分思路的顺序：弄清客户想要这个方案的底层原因 → 用客户能理解的语言，有理有据诚恳给出建议 → 提议做对照验证实验 → 如果客户依旧否决你的建议，透明地配合执行，同时降低方案出错后的整改成本。

#### 高分回答示例
“首先，我会带着好奇心去了解客户坚持微调背后的想法。客户嘴上说‘我们要微调’，背后一定有深层诉求，而这个诉求会改变我的应对方式。我会这样问：‘帮我理解一下，微调可以帮你们实现什么最核心的目标？是希望模型能精准理解你们行业的专业术语？不想业务数据放到提示词里？还是董事会要求、或是竞品案例让你们考虑这个方案？’

常见的真实原因：高管听说微调代表‘模型懂我们公司’；或者有一种认知，觉得微调能更好保护数据安全（这个想法通常是错的——微调会把数据嵌入模型权重里，之后很难审计、删除）；又或者是去年的顾问推荐了微调。

接下来，我只用客户能听懂的话术，清晰给出一次坦诚建议：‘针对你们的目标——基于内部政策文档给出准确回答，微调并不是合适的工具。如果我顺着你们的想法不说实话，是没有尽到顾问的责任，有三点原因：你们的文档每周都会更新，而微调后的模型会锁定在训练那一刻的内容，之后就要不停重训；但RAG方案当天就能读取文档更新内容。微调学习的是行文风格，不是事实内容，它可以模仿你们公司的语气，但依旧会编造答案，而且没有引用来源，错误很难被发现。另外微调迭代更慢、成本更高，一轮迭代要几周，RAG只需要几天。’

然后，用来打破僵持的办法：不去争辩，而是设计对照实验。我会说：‘我提议这样做：由你们掌握标准答案，准备100条真实业务问题，盲评打分。我们在相同预算周期内，两周内同时搭建一套RAG系统、一套微调版本，两套系统一起打分对比。哪套效果更好，就用哪套，最终决策依据是实测结果，而不是我的观点和你们想法的对抗。’

实际落地里，针对事实查询类任务，RAG在这类对照评测里往往效果更好；客户亲眼看到结果，远比单纯讲道理更容易接受这个结论。

如果客户依旧坚持微调？我会透明配合，不消极对抗：我会礼貌地把我的建议和理由书面留存备案，不是为了追责，只是留存决策记录；之后尽全力搭建高质量的微调系统，同时悄悄做好风险兜底：保留评估框架，持续衡量系统效果；文档接入架构提前设计好，等到第三个月文档内容和模型知识脱节、出现问题时，可以低成本切换到检索方案。就算你的技术判断本身没错，如果项目失败，这个正确就毫无意义；能拿出可验证的证据，同时备好补救方案，才是作为可信顾问‘在争论中让步’的正确方式。

对比维度要站在客户视角，选择他们真正关心、能直观感受到的指标，而不是我们工程师自己在意的指标。”

|  | 微调（Fine-tuning） | 检索增强生成（RAG） |
| ---- | ---- | ---- |
| 首次产出可用回答所需时间 | 数周：数据准备、训练、评估 | 数天 |
| 文档更新时 | 需要重新训练 | 内容直接更新生效 |
| 是否可以标注来源？ | 不可以 | 可以，这也是审计人员的需求 |
| 成本特点 | 前期投入高，单次调用成本低 | 前期投入适中，每次调用都要执行检索 |
| 能解决幻觉问题吗？ | 不能（很多人误以为它可以） | 借助事实锚定和引用，能够约束幻觉 |
| 更擅长处理 | 格式、文风、专属术语 | 会变动、需要核验的事实类内容 |


最后这一行坦诚道出的取舍，才让前面所有对比显得可信：微调本身没有错，但它并不适合用来处理知识库类任务。先把这点说清楚，你就不再是一个一味推销产品的厂商了。





这场对照评测才是真正化解僵局的办法，重点要理解它为什么能说服客户，而不只是知道它能赢：它起作用的关键是心理层面，不是技术层面。

当你和客户争辩时，客户会本能维护自己的立场——让步等于在自己团队面前承认自己错了；你每多拿出一条论据，客户让步的心理成本就越高。

盲评对照评测完全消除了这个面子压力：客户不是输给供应商，而是做了一场实验、读取实验结果。他们可以从容向董事会汇报：“我们严谨测试了两种方案，数据证明了结论”。

让客户手握标准答案，意义就在于这个话术转换。同时，它把微调方案后续大概率会踩的坑提前暴露出来：本来微调方案要等到第三个月文档更新、内容脱节之后，才在正式上线场景当众翻车，让项目蒙羞；现在这个隐患在第二周的受控评测里就暴露，代价很低、影响范围可控。

所以对照评测不只是帮你证明技术观点，更是给客户一个台阶下，让客户可以改变想法而不丢面子。能不能给对方留这个台阶，就是“你是对的”和“别人愿意听你说”的区别；只有后者，才能保住这个客户合作。

#### 面试官后续常追问的问题

- “留存书面记录，难道不是牺牲客户利益来自保吗？”
不是的，这属于**决策规范（decision hygiene）**：它把决策逻辑留存下来，留待后续结果验证；我们可以把这件事表述为：**“记录下我们评估过的所有方案选项”**。

- “如果背后真正的原因，是CEO已经向董事会承诺要自研专属模型该怎么办？”
那就去解决这个问题：用微调控制输出风格、搭配RAG处理事实，这种混合方案完全可行，能够让各方都满意。组织内的权责诉求是一项约束条件，而不是需要去否定的东西。

- “什么时候客户的想法是合理的、选微调才是正确方案？”
要清楚这些真正适配微调的场景：高并发、稳定且范围固定的任务（分类、信息抽取）；有严苛延迟、成本预算限制，适合用经过微调的小模型；需要统一文风、输出格式的场景。主动承认这些适用场景，才能证明你之前说“不适合微调”，是针对他们当前业务场景，而不是固执己见。


### 常见误区
- 轻易妥协、一味顺从。面试官就是要筛掉只会奉命行事的执行者。
- 堆砌专业术语来辩赢对方，而不用对方听得懂的语言沟通（比如对着副总裁喊“灾难性遗忘！”，对方根本听不懂）。
- 在完全可以开展为期两周的对照测试时，却演变成观点之争。评估验证，是**现场方案工程师（FDE）**最稳妥的沟通利器。
- 方案意见被否决后，带着抵触情绪敷衍交付。可以提出异议、留存书面记录，但一旦定案，就要全力保质落地。


对照评测是这里很巧妙的沟通手段，但要让评测公平，有一个前提条件：**由客户手握标准答案，并且采用盲评打分**。
如果你搭建两套系统、由你来打分，那本质只是你赢了一场争论，而不是做实验，客户心里也清楚这点。这套方案的核心价值就是：评测结果，不是由你来操控解读的。
