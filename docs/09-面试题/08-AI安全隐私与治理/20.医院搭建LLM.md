# 一家医院想要基于患者病历搭建大语言模型（LLM）功能。HIPAA（《健康保险流通与责任法案》）对你的设计实际上提出了哪些要求？



> 20. 一家医院想要基于患者病历搭建大语言模型功能。HIPAA对你的设计实际上提出了哪些要求？

>
> 一句话摘要（TL;DR）：按落地优先级分为四道关卡：
> 1. 业务伙伴协议（BAA），协议链条必须覆盖每一个次级处理方，包括模型服务商；
> 2. 最小必要标准，通过字段级过滤、按角色范围检索来落地执行；
> 3. 符合45 CFR 164.312(b)要求的审计管控，记录**谁、何时访问了哪位患者的受保护健康信息（PHI）**；
> 4. 数据泄露处置预案，能够定位异常功能暴露了哪些患者的信息。
>
> 不签署BAA的模型服务商不能接入；**不存在所谓“HIPAA认证”**。

---
### 如何作答
把HIPAA法规转化成工程需求，按落地顺序梳理：**谁有权接收数据（BAA）、可以拿到多少数据（最小必要）、事后如何留证（审计管控）、出事之后怎么处理（泄露通知）**。面试官考察的是：你能不能和医院的合规负责人对接，把合规语言转化成架构方案，而不是死记法规条文。

### 一份优质回答
第一道关卡，在搭建任何架构之前：**业务伙伴协议（BAA）**。

患者病历属于受保护健康信息（PHI）；任何代表医院接触PHI的供应商都属于业务伙伴，必须签署BAA，直接承担HIPAA规定的义务。这个协议要沿着整个链路层层传导：你的公司和医院签BAA，每一个会读取PHI的次级服务商，**包括模型提供商**，都必须纳入协议覆盖范围。

项目第一周就要敲定这个会决定架构走向的现实问题：哪些大模型服务愿意为本业务签署BAA？Azure OpenAI、Bedrock托管模型、各大实验室的企业版产品有可行方案；面向普通消费者的API接口绝对不行。同时配套约定**禁止留存数据、禁止用数据训练模型**的条款，保证数据流的合规逻辑闭环。

第二道关卡：**最小必要标准**，也就是HIPAA的数据最小化规则，对架构设计影响最大。

不要图省事把完整病历全部塞进上下文窗口：如果是出院小结功能，只需要本次就诊记录、用药、检验结果，不需要2014年的精神病史记录。这不只是合规要求，通常也是更优的工程方案——临床医生也会认同这一点：一份完整病历可能有几百页、上万token，只推送当前就诊相关片段，既满足最小必要要求、大幅节约成本，还能直接提升输出质量。因为“中间信息淹没效应”：在4万token的历史冗余信息里掩埋关键检验数据，会明显降低摘要的质量。

具体落地方式：在工具/检索适配器里做**字段级过滤**；在业务流程允许的场景下做去标识化（可以采用安全港方案，移除18类标识符；或者采用专家判定模式——如果就诊日期、年龄对诊疗是必要信息，就不能删掉，这也是为什么纯安全港方案往往会损害病历的临床可用性，这点要讲清楚）；同时**按角色范围检索**：账单助理和临床助理能看到的数据切片不一样。
这也回答了一个常见问题：**RAG（检索增强生成）里按用户分配权限为什么很重要？** 护士调用这个助手查询时，不能检索到不在其诊疗关系内的患者病历——这个大模型助手，继承了它所读取的病历系统的访问控制义务。

第三道关卡：安全规则的落地实现：传输中和静态数据加密（基础标配）、带唯一身份标识的访问控制，还有团队做审计时经常遗忘的：**45 CFR 164.312(b)下的审计管控**：你必须能够证明：**谁、在什么时候、访问了哪位患者的哪些PHI**。
对于大模型功能来说，意味着每一次请求都要记录：用户身份、进入上下文的患者数据、检索来源、模型返回内容的处置方式；日志不可篡改、按政策留存（行业规划一般按6年周期），并且支持按患者维度查询——因为患者有权索要信息披露记录。**第一天设计架构时就要把这套日志做进去；事后再给大模型管线补全溯源日志会非常痛苦。**

第四道关卡：泄露处置预案：

未受保护PHI被违规披露（包括模型把A患者的数据展示给B用户、PHI落入无防护的调试日志），都会触发通知义务（通知涉事个人、上报HHS，时限上限60天）。所以你的事件处置手册里，需要专门新增AI场景章节：如何判定异常功能泄露了哪些患者的数据。**而这件事，只有前面的审计日志存在时才能做到。**

| HIPAA合规要求 | 对应的设计影响 |
| ---- | ---- |
| 和所有接触PHI的合作方签署BAA | 如果模型服务商不愿意签署BAA，就不能让它读取PHI。这一点会直接决定整体架构 |
| 最小必要原则 | 只检索、发送相关片段，而不是推送整份病历 |
| 访问控制 | 检索操作自带权限校验，面向每个临床人员，在索引层执行权限拦截 |
| 审计管控 | 每一次PHI访问都留日志，包括给到模型查看的全部内容 |
| 数据完整性与传输安全 | 传输加密、静态加密，由客户持有密钥 |
| 泄露通知义务 | 你必须可以明确说明哪些患者的PHI遭到泄露，依赖全链路追踪日志 |

第一行这条要求，会在架构设计开始前就筛掉很多方案：没有BAA，就不能把PHI发送到这个端点，倒逼你选择VPC内部部署或者自研权重托管方案。

**在第一次沟通时就要确认这个问题，不要等到安全评审阶段才发现。**

### 面试官接下来常会追问的问题
- “他们能不能用去标识化数据，绕开上面这一整套流程？”
用于数据分析、评估数据集时，通常可以这么做，试点项目可以优先推荐。但必须正式核验去标识化标准（安全港方案或者专家判定方案）；要记住：自由文本的临床笔记里很容易藏标识符，简单清洗无法清除姓名这类信息。
- “HIPAA是否禁止使用PHI训练模型？”
法规条文里没有直接禁止；它要求获得患者授权，或者用于合规允许的业务目的。实操建议：不要用可识别身份的PHI做微调，数据很难彻底抹除标识，授权流程也极其繁琐。优先先做去标识化，或者仅把PHI用于检索、不参与训练。
- “PHI出现在应用日志里怎么办？”
这是现实里最常见的违规场景：包含PHI的提示词，被转发到没有签署BAA的SaaS可观测平台。日志架构本身属于HIPAA管控边界：要么对日志里的PHI做脱敏清洗，要么日志只能保存在合规边界内部。

### 常见误区
1. 一上来只讲架构方案，完全不提BAA。但BAA是合规负责人最先关心的硬性门槛，不是走形式的纸面文件。
2. 把去标识化当成勾选任务，以为“删掉姓名就完事”，不懂安全港方案里的18类标识符，不知道日期也属于标识符。
3. 没有按患者维度的审计能力。“我们记录了请求”不等于“我们可以出具阿尔瓦雷斯女士的信息披露记录”。
4. 承诺“HIPAA认证”：根本不存在这份证书；合规是依靠管控措施、BAA协议、审计记录来证明的。只要说出“已认证”，面试官就知道你没有落地过这类项目。

### 核心要点总结
- BAA是第一道关卡，优先于所有架构设计，协议链条必须把模型服务商作为次级处理方纳入覆盖；
- 最小必要原则落地为字段级过滤、按诊疗关系范围检索，而不是直接推送完整病历；
- 上线之初就要设计支持按患者维度查询的审计日志；后期补全溯源链路非常困难；
- 不存在“HIPAA认证”；依靠管控措施和BAA协议证明合规，不要说“已通过认证”。

### 最后一段补充文字翻译
最小必要标准，和RAG检索机制存在一个值得重点说明的冲突：

语义检索会返回相关性最高的Top-K片段，但是**“相关”不等于“必要”**；宽泛的查询请求，有可能检索到不在当前业务范围、其他就诊记录内的PHI。只在工具适配器做字段级过滤是不够的；检索语句本身，必须加上**诊疗关系范围限制**，否则会超额检索到最小必要规则禁止送入上下文的PHI。
