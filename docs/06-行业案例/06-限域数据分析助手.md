# 案例：限域数据分析助手（Text-to-SQL）

> 状态：可发布  
> 类型：合成教学案例  
> 主模式：主题域语义层 + 只读 SQL 工具 + 强制解释与权限  

## 1. 背景

- **组织**：零售/互联网，业务方希望「用自然语言查数」  
- **痛点**：分析师排队；自助 BI 学习成本高；口径不一致  
- **风险**：错误 SQL → 错误经营决策；权限穿透；全表扫描打爆仓库  

## 2. Discover

- **用户**：运营/品类经理；数据平台负责治理与成本  
- **指标**：自助取数占比、口径争议次数、查询错误率、仓库成本  
- **约束**：行级/列级权限；PII 列；只能打只读副本；部分指标有官方口径  
- **问题陈述**：业务用户在**已治理的主题域**内用自然语言获得可解释的取数结果，并附 SQL/口径说明，降低对分析师的简单查询依赖  
- **非目标**：开放任意库任意表；自动写数；无审批的导出全量客户明细  
- **硬点**：语义到正确 SQL；官方指标口径；权限与成本治理  

## 3. Design

- **主模式**：指标语义层（metrics layer）+ 表/列描述 → LLM 生成 SQL → **静态分析/解释器校验** → 只读执行 → 结果+SQL+口径展示  
- **护栏**：允许表名单；LIMIT 默认；禁止多语句；超时杀查询；成本估算  
- **试点**：「销售日报」主题（5–10 张表）× 一个业务团队 × 6 周  
- **Eval**：金标问答 80 条（含易错口径）；执行正确率；拒绝越权率；P95 延迟  

## 4. Deploy

- **入口**：内部 Web；与现有 BI 并存  
- **HITL**：导出 >N 行或含准标识需审批  
- **观测**：失败 SQL、被拦查询、高费用查询归因到用户/团队  
- **培训**：强调「以官方口径文档为准；有疑义找指标 owner」  

## 5. Review

- **结果**：简单取数自助率上升；仍需分析师处理复杂归因；一次口径错误被语义层修复后复发率下降  
- **学习**：没有语义层的纯 Text-to-SQL 会毁信任；先治理再智能  
- **可复用**：主题域白名单、SQL 校验、口径绑定、成本熔断  
- **下一步**：第二主题域；指标版本管理

- [ ] 只读副本 + 表白名单
