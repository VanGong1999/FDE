# 什么是 FDE

**FDE（Forward Deployed Engineer，前线部署工程师）** 是一类「人在客户现场（或深度嵌入客户团队），用工程手段把产品/模型能力变成可运行业务结果」的角色。

在 AI 时代，FDE 的典型工作不是「把 Chatbot 接到官网」，而是：弄清真实工作流与约束 → 设计可评测的方案 → 在客户数据与权限体系内落地 → 把现场学习反馈给产品。

FDE的价值就在于帮助客户自己提出问题，在很多情况下，客户最初想要的是什么，并不是最终要解决的问题。FDE的特点：贴近、了解透彻、敢于指正客户。客户说“给我做一个聊天机器人”​，普通的乙方就会做出一个聊天机器人；优秀的FDE则会先问一句“你想解决什么样的问题”​，之后可能会发现客户真正想要的是一个可以自动处理报销单的系统——而并非聊天机器人。

---

## 1. 一句话与三句话定义

**一句话**：FDE 是客户侧的全栈问题解决者——既写代码，也定义问题，还对上线结果负责。

**三句话**：

1. **面向结果而非工单**：成功标准是业务指标（时效、准确率、成本、采用率），不是「接口调通了」。
2. **在约束内创新**：数据主权、合规、遗留系统、组织政治，都是问题的一部分。
3. **双向翻译**：把客户语言译成技术方案，把技术限制译成客户能决策的选项。

## 2. 典型一天（合成画像）

以下为合成的「驻场/半驻场」日程，便于建立直觉（不同公司差异见 [公司图谱](./公司图谱与岗位差异.md)）：

| 时段 | 可能在做什么 |
|------|----------------|
| 早上 | 与客户业务负责人对齐本周成功标准；看昨晚评测/错误日志 |
| 午前 | 改检索策略或权限中间层；和客户 IT 对 SSO / 网络白名单 |
| 午饭 | 快速同步内部产品同事：现场需要的平台能力 |
| 午后 | 和工作室用户做可用性观察；发现 prompt 或流程假设错误 |
| 傍晚 | 写决策备忘录（范围变更、风险、下一步）；准备明日演示 |

**你很少整周只写一个内部 ticket**；你经常在「代码、会议、文档、评测」之间切换。

## 3. FDE 做什么 / 不做什么

### 做

- 模糊需求下的问题定义与范围控制
- 数据探查、集成、权限与安全边界设计
- POC → Pilot → Production 的工程与变更管理
- Eval、监控、成本与延迟治理
- 用户培训、运行手册、交接
- 将可复用模式沉淀回产品/解决方案库

### 通常不做（或不应成为主业）

- 纯售前幻灯片与商务谈判（可配合 SE，但不取代）
- 长期只做与客户无关的平台底层研发（那是核心 SWE）
- 无工程落地的「战略咨询报告流水线」
- 对无法验证的指标做口头保证

## 4. 与相近角色对比

| 维度 | FDE | SWE（产品研发） | SE（售前） | SA（架构师） | 顾问 Consultant |
|------|-----|-----------------|------------|--------------|-----------------|
| 主战场 | 客户环境 + 产品反馈 | 产品代码库 | 销售周期 | 架构与集成蓝图 | 建议与变革 |
| 成功标准 | 客户结果 + 可复用性 | 产品指标/稳定性 | 赢单/技术认可 | 架构被采纳 | 报告与工作坊 |
| 代码深度 | 中高，要能独立交付 | 高 | 低–中（Demo） | 中（设计为主） | 低–中 |
| 客户时间 | 很高 | 低 | 高（售前） | 中 | 高 |
| 模糊问题 | 核心能力 | 有 PM 消化 | 有，但偏方案推销 | 有 | 有 |
| 与产品关系 | 强反馈回路 | 本人即产品 | 间接 | 间接 | 弱 |

**转岗提示**：优秀后端转 FDE，缺口通常在「客户发现、范围控制、评测与组织推动」，而不是「会不会写服务」。

## 5. AI-FDE 的特殊之处

相对经典「平台/数据 FDE」，AI-FDE 额外要会：

1. **不确定性管理**：模型会错；系统必须可测、可降级、可审计
2. **Eval 文化**：没有 golden set 就不谈「效果好」
3. **安全与滥用**：提示注入、数据泄漏、越权工具调用
4. **成本与延迟**：token 与检索费用会直接杀掉 ROI
5. **人机流程**：哪些步骤必须 HITL（人机回环）

详见 [03-AI落地](../03-AI落地/企业AI落地全景.md)。

## 6. 价值如何被衡量（入职后你会被问）

- **业务**：周期缩短、正确率、人工分钟数、收入/风险指标
- **采用**：周活用户、任务完成率、CSAT
- **工程**：事故率、P1 次数、权限漏洞、单位成本
- **杠杆**：是否沉淀为可复制解决方案；是否影响产品路线图

面试时准备至少 **一个** 能量化的故事（见 [行为面 STAR](../04-面试通关/行为面STAR题库.md)）。

## 7. 迷你案例：同一需求，不同角色怎么动

**客户说**：「我们要做一个合同审核 AI。」

| 角色 | 第一反应 |
|------|----------|
| 纯 SWE | 「用哪个模型？队列怎么做？」 |
| SE | 「先约 Demo，展示竞品对比幻灯片。」 |
| FDE | 「谁在审合同？漏审的代价是什么？现在 SOP 是什么？数据能否出域？一周内哪个切片能证明价值？」 |

FDE 会把「合同审核」拆成可验证子问题（条款抽取？风险分级？对照模板？），并先做一个**窄而真**的试点。

## 8. 组织何时「需要」FDE（不是跟风）

> 精读补充自 [FDE 101 演讲](https://www.youtube.com/watch?v=KwhgfwOSToQ)（Kevin；Anthropic Applied AI / 前 Palantir、Rippling）。与上文「个人转岗」视角互补——本节问的是**公司要不要建这支队伍**。

客户买的常常是**结果**，不是平台说明书。若产品极技术、买家又非技术，只扔软件让客户自学，培训与自建税负会拖死采用。

| | 技术买家 | 非技术买家 |
|--|----------|------------|
| **技术产品**（要开发/集成） | DevRel / 文档往往够 | **FDE 经典区** |
| **可配置 SaaS** | — | 传统销售+实施通常够 |

**只有**必须向非技术买家推广技术复杂产品时，才认真建 FDE。旁路：技术向 GTM 用 DevRel；标准 SaaS 用 SLG。

**FDE ≠ 开发商店：** 可持续的 FDE 在**共享平台原语**上组装，从不每个客户从零写；否则维护会吃掉毛利。建队前再问一句：我们有（或愿意投资）平台吗？

**变更归属：** 仅该客户独特的 → 客户侧；可反复抽象的 → 回流产品。画像一句：你会聘为 SWE、又信任其站在客户面前的人。

AI 时代许多产品变 agentic、高度可定制，客户更难理解「你到底卖什么」——这提高了嵌入交付的需求面，仍不等于人人都该招 FDE。

## 9. 为什么模型越强，FDE 反而更重要？

> 补充自 [South Park Commons FDE 专题讨论](https://www.youtube.com/watch?v=hWuoH-ODDNc)（RAMP / Nominal / Dataland / OpenAI）与 [Sierra Agent Engineering 演讲](https://www.youtube.com/watch?v=Byv311hdoHE)。

模型变强并不自动等于企业价值变现。公开讨论里反复出现的机制：

| 机制 | 含义 |
|------|------|
| 问题异质 | B2B「待完成工作」比标准 SaaS 形状多几个数量级；劳动力资本远大于软件资本 |
| 解锁点在用例理解 | 模型够用之后，瓶颈变成「像当事人一样理解工作流 + 把前沿模型嵌进去」 |
| 管道成本下降 | 强编码模型缩短胶水代码时间，FDE 可承接更难、更靠近业务价值链的问题 |
| 角色边界模糊 | 代码变便宜后，产品工程、Agent 工程、客户工程都在「对客户结果负责」上汇合 |

**一句话**：模型解决「能不能写」，FDE 解决「该写什么、在约束里写到能用、并能证明」。

Sierra 演讲者 Natalie Mirror 的尖锐说法：**「FDE 并不存在」**——标题被用来描述太多东西，几乎失去统一定义；但**唯一连续性是：对客户结果负责**。她的收束是：「Forward deployed engineering is dead. Long live forward deployed engineering.」——术语可死，责任模型活着。

另可问自己一句有趣的话：**「你是哪一年份的 FDE？」**（像葡萄酒年份）——DevOps、数据集成、本体建模、决策写回、客户赋能……不同年代主业不同，总工作量往往随平台成熟而**增加**而非消失。历史脉络见 [公司图谱 §11](./公司图谱与岗位差异.md)。
