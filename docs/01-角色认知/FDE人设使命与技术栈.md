# FDE 人设、使命与现代技术栈

> 整理并扩展自 Awesome FDE「Persona & Mission / Modern Stack」。补充 [什么是 FDE](./什么是FDE.md)。

---

## 1. 使命一句话

FDE 是总部「完美代码」与客户「脏现实」之间的桥。标准软件撞上损坏 schema、气隙机房、政治阻力时会失败；FDE 不只修 bug，而是做方案、管干系人、写让合同成立的**胶水代码**，并把可复用模式送回产品。

Palantir 语境里的 **Delta（差距）**：产品开箱能力 ↔ 客户使命成功，中间那截必须有人工程化地补上——那就是你。

---

## 2. SWE vs FDE（对照）

| 维度 | SWE | FDE |
|------|-----|-----|
| 用户 | 海量匿名用户 | 高利害干系人（CTO/CEO/指挥链/业务 VP） |
| 环境 | 受控、同质云 | 敌意、遗留、气隙或混合 |
| 目标 | 规模与稳定 | 价值速度与解题 |
| 成功尺度 | 产品指标、SLA | 客户结果 + 可复用性 |
| 代码重心 | 约 90% 功能 | 约 50% 集成胶水 + 50% 策略对齐 |
| 模糊需求 | 常有 PM 消化 | 你就是消化器之一 |
| 政治与采购 | 较少日常接触 | 常见日常 |

传统 SWE 为 **persona** 构建；FDE 为 **mission** 构建。

## 4. 现代 FDE 技术栈（地图）

不必样样精通，但要知道「现场缺哪块该找谁/补什么」。

| 层 | 常见工具 | 你要达到的水位 |
|----|----------|----------------|
| 语言 | Python（数据/AI）、Go/TS（服务）、SQL | 能独立交付胶水与评测脚本 |
| 数据 | dbt、DuckDB、Spark、仓内 SQL | 会画像、会建模直觉、会查慢因 |
| 云/IaC | Terraform、Helm、AWS/GCP/Azure | 能读懂并改 Landing Zone，而非只会控制台点点 |
| AI | RAG、工具调用、Eval、护栏 | 见 [03-AI落地](../03-AI落地/企业AI落地全景.md) |
| 身份安全 | SSO、RBAC/ACL、密钥、审计 | 见 [SSO 专篇](../05-能力补强/企业SSO与权限模型.md) |
| 可观测 | Prometheus/Grafana/Loki；云 Trace/Logging | 能定位「慢在哪一步、错在哪一类」 |
| 边缘/气隙 | K3s、本地推理、离线镜像 | 按需，见 [气隙专篇](../05-能力补强/气隙与战术边缘部署.md) |

### 选栈原则

1. **客户栈优先**，不是你最熟的栈优先  
2. **够用就上**，演示完再谈完美平台  
3. **密钥与权限从第一天按生产规矩**，避免试点债  

深度课：[数据工程基石](../05-能力补强/数据工程基石课程.md)、[GCP 架构](../05-能力补强/GCP云架构与基础设施.md)、[Snowflake/Databricks](../05-能力补强/Snowflake与Databricks现场.md)。

## 5. 「胶水」到底在胶什么

常见 Delta 工作：

- 专有文件格式 → 标准 Parquet/JSON  
- 遗留 SQL / 工单系统 ↔ 新 AI 服务  
- 企业 SSO / 文档 ACL → 检索过滤  
- 无标注 → 共建黄金集与 HITL  
- Demo 环境 → 客户目标网络与驻留  

胶水写得越好，越应该**配置化/产品化**，而不是永远手写 if-else。见 [解决方案产品化](../05-能力补强/解决方案产品化.md)。

## 7. 自我介绍模板（30 秒 / 90 秒）

**30 秒：**  
「我是做客户结果的工程师。最近一次是在【约束】下，把【缺口 Delta】补成【可运行系统】，让【指标】从 A 到 B。」

**90 秒加：** 你怎么发现缺口 → 你推回了什么 → 如何证明有效 → 离开后谁运维。

避免：只报技术名词清单；避免「我啥都能干」。

## 9. 产品战略延伸（不是 GTM 附庸）

> 精读补充自 [Palantir FDE 起源演讲](https://www.youtube.com/watch?v=1OMHGsUZiqA)。公开表述常引用：「这不是一个角色，而是一种**产品战略**」——评判 FDE，看其作为**产品团队延伸**能否识别机会并提炼可泛化能力。

经典隐喻（Palantir 语境流传）：现场吃苦（吃油漆），拉出可复用产品。早期公司尤其不要把 FDE 只当成市场推广人力；**产品杠杆**才是可持续赢客户的东西。与 [解决方案产品化](../05-能力补强/解决方案产品化.md) 对照阅读。

孤立造产品、不嵌入客户的反例（Phoenix 类教训）：实验室里完美、真实脏数据一碰就崩——差距往往在「没和客户坐在一起共建」。

## 10. 「想说是」的团队与结果崇拜

> 补充自 [SPC FDE 专题](https://www.youtube.com/watch?v=hWuoH-ODDNc) 与 [Cognition 部署工程演讲](https://www.youtube.com/watch?v=RVxym6mmIns)。

### 招聘侧反复出现的特质

| 特质 | 现场说法（意译） |
|------|------------------|
| 对价值不懈追求 | 用户不用就撕掉重做；爱功能不爱形式 |
| 想说「是」 | RAMP：FDE 是想赢客户的团队；许多工程师默认想说「不」以保护自己的路线图——两者都可敬，但岗位不同 |
| 前创始人 / 关心收入 | 不只想构建酷东西，还在乎业务是否成立 |
| 超级通才 + 必要时谦逊 | Nominal：scrappy、好奇；并重视 FDE ↔ 核心产品轮换 |
| T 型 | Cognition：广（人际/业务/流程）+ 深尖峰；业务感可学，「房间里的技术专家」难教 |
| 伟大 vs 好 | 好：能映射产品、能解客户问题；伟大： relentlessly 问「为什么解这个问题、能否回流让所有人受益」 |

### 写代码只占约 20%

Cognition 视角：在模型 + 上下文工程足够好时，**写代码块本身基本已解决**；真正杠杆在测试、审查、部署、维护，以及把 agent 指向最高杠杆工作（而不是无方向 token maxing）。这与本篇「约 50% 胶水 + 50% 策略对齐」不矛盾——都在说：**交付价值 ≠ 敲键盘行数**。
