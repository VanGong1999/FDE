## 评测（Evaluations）

如果在生产篇只学一件事，就学这一件。评测（evals）是让你知道一个概率性系统「真的能用」的方式，而「先建评测」这个习惯，是「只会交付 demo 的工程师」与「客户敢在线上信任的工程师」之间最清晰的一条分界线。它是这个角色技术信号的核心。

### 核心（Core）

Eval 是对一个非确定性系统的自动化测试：一组输入，外加一套对照「对这个客户而言什么叫『好』」来给输出打分的方法。你没法用 `assertEqual` 给 LLM 写单元测试，因为同一个 prompt 可能给出两个不同、但都可接受的答案。Eval 用规模化打分替代了精确匹配断言。「评测先行」是 FDE 的习惯：在建东西之前先定义好你如何度量「好」，因为在真实部署里，「我试的时候看起来是对的」不算证据。

#### 为什么这是活儿，而不是杂务

每个 FDE 项目都会撞上同一个模式：模型在 demo 里表现很好；你把它跑在客户的真实数据上——几十年来不一致的记录、没人记录过的边界情形、监管者必须能签字确认的问题——它就崩了。弥合这个落差，就是「部署」这件事本身；而你无法弥合一个你测不出来的落差。

#### 读前思考

客户问：「我怎么知道这个助手是准的？」你可能会说「我们测过了，看起来不错」。为什么这个答案是致命的，资深 FDE 会怎么说？

「看起来不错」之所以致命，是因为它经不起下一问：对「什么」准、用「什么方法」度量的、以及「如果明天变差了你怎么知道」。资深答案会报一个「对照数据集得出的数字」：「我们在一组固定的代表性问题上给它打分，由领域专家和一个自动裁判共同判分；它处于一个已知的准确率水平，而且我们每天重跑这套题，所以回归会在一天之内暴露出来。」这一句话同时包含了数据集、判分者、数字，以及让它保持诚实的那套排期。

#### 按顺序建的三层

Eval 不是单一一样东西。你分层去建，每一层回答上一层回答不了的问题。

**离线 eval——它到底能不能用？** 从一组固定的输入开始，配上「正确答案」的概念，在任何东西上线之前先跑。这就是你的回归套件。对一个检索型助手来说，那就是一组真实问题，配上它们应当浮现的段落或答案。离线 eval 的要义是可重复：同一套题，每次改动都跑一遍，这样你才能判断一个新 prompt 或新模型是帮了忙还是帮了倒忙。没有它，每一次「改进」都是猜。

**在线 eval——它在真实环境里能不能用？** 离线数据永远不是真实用户行为的完整分布。在线 eval 度量的是线上系统：采样真实流量、记录输出、追踪点赞/点踩、升级（escalation）、任务完成情况。你的离线分与在线分之间的差距，本身就是一个信号。差距大，说明你的测试集不像现实，而需要修的是你的测试集。

**LLM-as-judge——如何在规模上给「好」打分？** 大多数 FDE 的输出不是对/错，而是更好/更差——一份摘要、一个答案、一封邮件草稿。你没法每一条都靠人打分。标准做法是用一个强模型当裁判：把输入、输出和一份量规（rubric）交给它，让它打分。它便宜且可扩展，但有两个必须正视的失效模式：裁判有偏（偏向更长的答案、偏向它自己的文风），而且会漂移。所以你要拿裁判在抽样上对照人工打分来做校准，并且在高风险的那一档上始终保留人类把关。裁判是在「扩展」人的判断，而不是取代它。

校准是一套流程，短到可以背下来：从系统里采样真实输出，让人——最好是客户的领域专家——按裁判使用的那同一份量规来打分，然后度量裁判与人类的一致率。当它们不一致时，这些分歧就是诊断线索：量规含糊就重写量规，裁判有偏就换 prompt 或换模型；而如果人类之间彼此都不一致，那说明这份量规对人来说也定义不清。需要知道的那个基准：Zheng 等人系统研究后发现，像 GPT-4 这样的强 LLM 裁判能「达到 80% 以上的一致率，与人类之间的一致率相当」——这让「人与人之间的一致率」成了自然标尺，因为一个接近该水平的裁判，其打分稳定性就和你请的专家差不多。同一篇论文还记录了你要校准掉的那些裁判偏差：位置偏差、冗长偏差、自我偏好偏差。

### 深入（Deeper）

裁判的量规，正是客户的「好」的定义被编码进去的地方。对一个财富管理助手来说，「好」包括合规、扎根于该机构的研究，而不只是通顺。写这份量规既是工程活儿，也是客户手艺活儿：它是把 Discover 阶段的成果转成一个打分函数。

#### 赢得信任的纪律：每天跑

一次性的上线前 eval，在语料库或模型一变动之后就过期了。在受监管的场景里，「上线时它是准的」不构成辩护。真正能赢得采纳的做法，是一套常驻的回归套件，在每次改动、并按排期跑——这样漂移会在一天内暴露，而不是在客户会议上才暴露。Morgan Stanley 的案例就是那个现成例子：团队对一组固定问题集做每日回归测试，顾问采纳率达到了接近全员水平。来源文档把这两个事实并排记录了下来；把前者读作「赢来后者」的原因，是本课程在案例页上的解读。信任不是一个「上线事件」，而是一个客户看得见、始终在运转的流程。

#### 坏 / 好 / 优——「你如何评估这个系统？」

**坏** ——「我试了一堆 prompt，输出看起来是对的。」这是轶事，不是度量。它检不出回归，无法向监管者辩护，还会让面试官知道你从没跑过真东西。

**好** ——「我建了一组代表性用例的测试集，在上线前打了准确率。」一次真实的离线 eval，扎实的中级水准。距「优」的差距：它是一张快照，没有覆盖线上分布，也没说明你怎么能发现系统正在变差。

**优** ——「每次改动都跑离线回归套件，线上流量有在线指标，主观那一档用对照专家打分校准过的 LLM 裁判，而且每天跑一次让漂移快速暴露。客户的合规标准被编码进了裁判的量规。」分层、持续、并紧扣客户对「好」的真实定义——这正是真实受监管部署所用的结构。

#### 这个变化是真的吗？

一套常驻套件会产生一串分数，而一串分数会招来一个前面几层回答不了的问题：套件昨天读数是 82%，你改了 prompt，今天读到 84%。是进步还是噪声？在一个有限用例集上的 eval 分数，是对系统在整个分布上表现的一个估计，而任何估计都带采样噪声。集合越小，噪声带越宽——一个比噪声带还小的增量，就是「披着百分号外衣的抛硬币」。

噪声带的宽度来自比例的标准误，而算式几行就写完了：

```
比例的标准误：  SE = sqrt(p × (1 − p) / n)

在 p = 0.8、n = 200 个用例上：
    0.8 × 0.2 = 0.16
    0.16 / 200 = 0.0008
    sqrt(0.0008) ≈ 0.028          → 一个 SE ≈ 2.8 个点

所以 82% → 84% 的变化是 2 个点的增量，稳稳落在一个 SE 之内。

扩大集合会压缩噪声带：
    0.16 / 1000 = 0.00016
    sqrt(0.00016) ≈ 0.013         → 在 n = 1,000 时，一个 SE ≈ 1.3 个点
```

这段算式推出三条操作规则。第一，把 eval 集的大小定成「你能检测到的最小增量」：小增量需要大集合，而如果你能负担的集合很小，那只有大的变动才可读——在建套件时就决定哪些增量是重要的。第二，优先在同一批用例上做成对（paired）比较：把新旧版本跑在完全相同的套件上，把两者一致的所有用例搁到一边，只从它们分歧的用例里读结果。如果新版本赢下了大多数分歧，那这个改动确实起了作用；如果分歧大致五五开，你看到的就是噪声。相同的用例在比较中相互抵消，这让它能分辨出比两个独立采样分数更小的差异。第三，当某个发布门禁押在这个数字上时，把噪声带和分数并排报出来——「84，加减 3」——让签字的人确切知道这个数字能承受多大的分量。

上面那套裁判校准流程跑的是同一套逻辑：裁判与专家之间的一致率，也是在有限样本上量出来的一个比例，所以它带着同样的噪声带；只在寥寥几个用例上校准过的裁判，只是名义上的校准。

#### 一个极简 eval harness

上手不需要任何框架。下面这个骨架就是全部思想：一个数据集、一个打分器、一个聚合。 （示意代码。）

```python
# eval_harness.py — the smallest thing that is a real eval
import json

def load_cases(path):
    # each case: {"input": ..., "expected": ...(optional), "rubric": ...}
    return [json.loads(line) for line in open(path)]

def score(case, output, judge):
    """Return a 0..1 score. Swap in exact-match, retrieval-hit, or LLM-judge."""
    if "expected" in case:
        return float(case["expected"].lower() in output.lower())  # cheap offline check
    return judge(case["input"], output, case["rubric"])           # subjective -> judge

def run(cases, system, judge):
    results = [(c, system(c["input"])) for c in cases]
    scores = [score(c, out, judge) for c, out in results]
    return {
        "n": len(scores),
        "mean": sum(scores) / len(scores),
        "fails": [c["input"] for (c, _), s in zip(results, scores) if s < 0.5],
    }

# Run it on every change. Check `mean` against last run; investigate `fails`.
```

让它成为一个真 eval、而非 demo 的三个性质：它是可重复的（每次跑同一批用例）、它会聚合（一个你能随时间追踪的数字）、它会浮现失败（一张你去修的问题清单）。其余一切——更好的数据集、校准过的裁判、在线采样——都是在这根脊骨上的精修。

#### 面试要带走的

在 AI 系统设计轮里，当题目带任何准确率、安全或合规的门槛时，不要一上来就谈模型或向量库。一上来就谈「你如何持续地、对照一个看起来像客户现实的数据集来度量正确性」，以及「人在哪里把关」。画架构图证明不了什么；eval 策略才是答案见分晓的地方。

## 护栏与安全（Guardrails & Safety）

评测告诉你系统「平均而言对不对」。护栏是你对「它错的时候」、以及对「那些试图让它错的输入」所做的事。在真实部署里，模型偶尔会产出某种既自信又不可接受的东西，而用户或攻击者偶尔会塞给它敌意输入。护栏让这两者都成不了客户的事故。

### 核心（Core）

护栏是套在一个非确定性模型外面的确定性检查。它约束什么能进、什么能出、以及系统被允许做什么。评测度量质量；护栏在质量失手时兜住爆炸半径。资深者的话术不是「让模型永不出错」（不可能），而是「让出错这件事是可以承受的」——让一个坏输出被抓住、一个敌意输入被拒绝、一个不可逆动作必须有人拍板。

#### 为什么这是活儿，而不是打勾项

FDE 部署的地方，出错是有真实代价的：一个受监管的顾问、一个客户的生产数据库、一个能发邮件或转账的工具。在这种场景里，一个坏答案就不再是用户体验问题，而成了法律责任。Morgan Stanley 的案例恰恰卡在这一点上：顾问不会信任一个可能在客户面前自信地出错的助手，所以保留一个人复核输出这件事是承重的。护栏是你赢来「有资格部署」的方式。

#### 读前思考

你被要求加一个「起草并发送客户邮件」的 AI 功能。说出那个让你夜不能寐的失败——而且它不是一句语法别扭的话。

真正要紧的失败，是「基于错误信念做出的不可逆动作」：模型把邮件发给了错误的客户，或把错误的内容发给了正确的客户。下面所有内容，都是为了让这个特定的失败无法在无人值守时发生。

#### 护栏存在的三个位置

在系统与外部世界交汇的三个点上建。

**输入护栏——模型之前**。校验并清洗进入模型的东西。在个人信息（PII）被发送或落日志之前就剥离或标记它；强制长度与格式；并防御提示注入（prompt injection）——那种试图把自己变成指令的不可信文本。提示注入排在 OWASP Top 10 for LLM Applications 的首位，其防御是「边界思维」：模型读到的东西是数据，从来不是命令；你绝不赋予模型可达的权限，去动任何一条被注入指令所能滥用的东西。

注入不只是用户敲进来的。更隐蔽的路径是间接提示注入（indirect prompt injection）：把指令埋进系统稍后会读的内容里，比如一篇被检索的文档、一个被抓取的网页、或一封助手要总结的邮件。Greshake 等人展示了攻击者可以「远程……利用 LLM 集成的应用，通过策略性地把 prompt 注入到很可能被检索的数据中」；而 OWASP 2025 年的条目划的是同一条线：「当 LLM 接受来自外部来源（如网站或文件）的输入时，就发生间接提示注入。」这意味着 RAG 管道本身就是注入面：你自己的语料库，或任何喂给它的东西，都可能把攻击带到模型面前。防御还是那套边界思维，只是用在检索上：把检索来的文本当数据、永不当指令；在 prompt 里显式地把它分隔（delimit）出来；剥离或标记其中看起来像指令的内容；绝不让检索内容里的任何东西绕过与用户输入相同的门禁就去触发一次工具调用。如果你的助手会读文档且能行动，这就是你要默认存在的攻击。

**输出护栏——模型之后**。在输出到达用户或下游系统之前检查它。过滤不安全内容，验证输出扎根于你检索到的来源（而非编造），对任何漏网的 PII 做脱敏，并在下游系统要解析它时校验结构。对一个扎根型助手来说，最有价值的输出护栏是扎根性检查（groundedness check）：这个答案是否真的从检索到的段落推出来，还是模型用「自信的编造」填了一个空？

**动作护栏——当系统能做事时**。系统一旦开始采取动作，「错」就不再是一句坏句子，而是一个坏事件。约束它在无人值守时能做什么：

- **预算**：在必须停下来汇报之前，对步骤数、工具调用数或开销设一个硬上限。
- **检查点**：任何不可逆或高爆炸半径的动作（发那封邮件、跑那次迁移、转那笔钱）之前，必须有人批准。
- **急停开关（kill switch）**：一个已知的、快速的停机与回滚方式。

设计问题从来不是「它能做什么？」，而是「它能在没有人的情况下做什么？」。对不可逆动作，答案是「暂时什么都不能」，直到 eval 数据为它挣来自主权。

### 深入（Deeper）

护栏和评测是同一门纪律在两个高度上的体现。评测在你上线改动之前抓住一个坏输出；护栏在你上线之后、在运行时抓住一个坏输出。两者你都需要，因为那个你在评测时没想象到的输入，恰恰是敌意用户会找到的那个。

#### 坏 / 好 / 优——「你如何保证它安全？」

**坏** ——「我们加一句免责声明，说 AI 可能出错。」这把整个安全负担推给了用户，对敌意输入和不可逆动作毫无作为。这是从没运营过真实系统的人的答案。

**好** ——「我们过滤不安全输出并校验输入。」真实的输入/输出护栏，确实扎实的中级水准。差距：它对一个会行动的系统只字未提，也完全没提你怎么知道某个护栏正在失效。

**优** ——「分层：输入做清洗与注入检测，输出做扎根性验证与 PII 脱敏，对任何会行动的部分，配一个预算、在不可逆步骤上的人工检查点、以及一个急停开关——而且每个环节都落日志，让我能看见什么正在被拦下。」你在三个点上都兜住了爆炸半径，并让护栏可观测。

#### 一个极简护栏

护栏就是模型调用外面的普通代码。骨架就是全部思想。 （示意代码。）

```python
# guard.py — deterministic checks around a non-deterministic model
def handle(request, model, tools):
    if contains_pii(request.text):
        request = redact_pii(request)              # input guardrail
    if looks_like_injection(request.text):
        return refuse("input flagged")             # refuse hostile input

    output = model(request)

    if not grounded_in(output, request.sources):   # output guardrail
        return refuse("answer not supported by sources")

    action = output.proposed_action
    if action and action.is_irreversible:          # action guardrail
        return await_human_approval(action)        # checkpoint, don't execute
    return output
```

让它成为真护栏的性质：它对输入、输出和动作都起作用；它在较弱系统会去尝试的地方拒绝一个敌意请求；它在任何不可逆之前停下来。其余一切——更好的 PII 检测、更强的注入分类器——都是在这根脊骨上的精修。

#### 在这些具名检查的内部——难点所在

骨架命名了两个函数，却把难点藏在了它们里面，所以把它们拆开。`looks_like_injection()` 起步是一堆廉价模式规则（「忽略你之前的指令」及其同类）加一个小的训练分类器，而两者都抓不住一个全新的攻击。把它当成一个带真实漏报率（false-negative）的绊线即可——这又是下游那个动作门禁必须「即便这道检查通过也依然守得住」的另一个理由。

`grounded_in()` 是你在设计讨论里必须坦诚对待的那个：实践上，扎根性检查本身就是一次模型调用。你把检索到的段落和起草好的答案交给一个裁判模型，问它答案是否被支撑。形状如下：

```
grounded_in(), unpacked — the check is itself a model call (illustrative)

Judge prompt:
  You are verifying a drafted answer against source passages.
  <passages> …the retrieved chunks… </passages>
  <answer> …the drafted answer… </answer>
  For each factual claim in the answer, decide whether the passages
  support it. Return JSON:
  {"grounded": true|false, "unsupported_claims": ["…"]}

Refuse or route to a human when grounded is false.
```

这个设计有三个值得说出口的后果。它增加成本：每个被护栏保护的请求都要多一次模型调用，不过通常用一个比起草答案更小的模型就够了（见「成本与延迟」）。它增加延迟：这次检查串行地跑，在草稿之后、在用户看到任何东西之前。而且它有自己的错误率：裁判有时会放过一个不扎根的答案，有时会拦下一个扎根的答案，所以你评测这道护栏的方式，和你评测其他一切的方式一样——拿人工标注的例子给它打分，追踪它漏了什么（见「评测」）。一个你从未度量过其错误率的护栏，是「一个本应是控制措施的位置上，站着一个猜测」。

#### 面试要带走的

在 AI 系统设计轮里，当一个系统能采取动作时，别去描述快乐路径。一上来就讲「模型错了的时候会发生什么」：画出「自动运行」与「需要人」之间的那条线，报出预算和急停开关，并说出你怎么知道护栏正在抓住东西。为「模型出错的瞬间」做设计，正是这一轮存在要测的本能。

> 相关：这些约束在受监管环境下的版本见「安全、合规与数据」；度量护栏所兜住的质量，见「评测」。

## 可观测性与调试（Observability & Debugging）

关于你描述的任何生产系统，面试官都会问同一个问题，而它把「运营过东西的人」和「只建过东西的人」区分开来：「你怎么知道它坏了？」可观测性就是答案。它是那种仪器化（instrumentation），把一个「你希望它在工作」的系统，变成一个「你看得见它在工作、并在它不工作时能调试」的系统。这一页用这个领域的方式来讲它：把一个调试事故从头跟到尾，因为只有在感受过它为之存在的失败之后，这套仪器化才有意义。

### 核心（Core）

可观测性，是「从你已经收集的数据里，回答『系统现在健康吗？如果不健康，哪里出的错？』」的能力。对 AI 系统而言这意味着三路数据流：trace（一次请求的完整路径，让你能复现一次失败）、质量信号（输出是否真的好用的代理指标）、以及运营指标（每次请求的成本与延迟）。你看不见的东西，你就无法运营、也无法交接。

#### 一起事故：昨天那个错误答案

就拿检索走查里的那个研究图书馆助手来说，它已经在客户那儿上线几个月了。（下面这起事故是示意的：请求、文档、耗时和分数都是虚构的；要研究的是它的「形状」。）某天上午一位顾问写信说：

> 「昨天助手跟我说，我们对欧洲工业股的观点是中性。我们五月就上调到超配了。它还有什么是错的？」

这是最典型的投诉，而表面上看它没法调试。你当时不在场，答案已经没了，而最后那句「它还有什么是错的」，是信任开始流失的声音。确定性系统的那套直觉——先复现、再修复——在这里失效了：你现在可以再问助手同一个问题，但一个概率性系统不欠你同一个输出。如果今天的答案是对的，那证明不了昨天什么；如果它是错的，你依然看不见为什么。所以你去调试「被记录下来的那次实例」，而不是一个你也许永远得不到的复现。昨天那个答案唯一能调试的版本，是系统当时写下来的那一份。那份记录，就是一条 trace。

#### 拉取 trace

你按用户和时间查出昨天那个请求，拉出它的 trace：那一次请求穿过每一个阶段的完整路径，包括每个阶段收到了什么、产出了什么、花了多久。

```
trace_id: 9f3c-0212          2026-06-09 14:12 UTC          total: 2,279 ms

[input]         question received                                  (t=0)
                "What's our current outlook on European industrials?"

[retrieval]     top 3 chunks by vector similarity               (87 ms)
                index build: 2026-01-30
                [1] 0.81  eu-industrials-2026-01.pdf, p.2
                    "We remain neutral on European industrials;
                     order books are soft and pricing power limited…"
                [2] 0.77  global-sectors-2026-01.pdf, p.9
                    "…industrials positioning unchanged this quarter…"
                [3] 0.72  eu-macro-2026-01.pdf, p.4
                    "Euro-area manufacturing surveys remain weak…"

[guardrail]     input pre-check (injection scan, topic scope)   (12 ms)
                result: pass

[model]         model: frontier-large-2026-05, prompt: v14   (1,940 ms)
                tokens: 3,180 in / 210 out
                "The house view on European industrials is neutral,
                 reflecting soft order books and limited pricing
                 power [1], unchanged positioning [2], and weak
                 manufacturing surveys [3]."

[groundedness]  answer supported by retrieved chunks?          (240 ms)
                score: 0.96 — pass

[response]      returned to advisor
                stage sum: 87 + 12 + 1,940 + 240 = 2,279 ms
```

#### 从 trace 里读出的诊断

按顺序读这些阶段，失败自己就定位出来了。护栏预检正确地通过了：这个问题在范围内。模型表现正常：它的答案是对交给它的那三段内容忠实的、带引用的总结。扎根性检查也正确地通过了——这个结论值得停一下：扎根性只对照「检索到的东西」来验证答案，所以它永远抓不到「检索本身是错的」。检索下游的每个阶段，都在坏输入上正确地干了自己的活。

失败就藏在检索阶段的这两行里。排名第一的 chunk 是工业股报告的一月版——正是顾问说的五月已被取代的那版——而它上面那行写着原因：索引最后一次构建是在一月底。五月那版报告在客户的文档库里确实存在；它只是从没被 embedding 和索引过。检索无法浮现一份索引从没见过的文档。

没有这条 trace，这起事故就会以「模型幻觉了」结案——一个既无法修复、也无法证伪的结论，还会让你失去顾问的信任。有了 trace，它就是一个「索引过期」的 bug，一行就能修：重跑 ingestion 任务，让索引反映当前语料。两个后续动作才标志着一个运营者：第一，把重建排期化，因为手工刷新的索引迟早还会过期；第二，把顾问那个问题、配上五月报告里本应回答它的那段内容，加进 eval 套件，这样下一次索引过期会表现为每日运行里的分数下降，而不是出现在顾问的收件箱里。这起事故属于部署页围绕的那个「静默回归」家族：行为在没有代码 diff 的情况下变了，而那边教过的「版本化索引 + 排期化 eval」，本可以提前几周抓住它。trace 是你在事后找到这种失败的方式；部署的纪律是你不再以这种方式撞见它的方式。

#### 这起事故所推广出的东西

这次调试只用到了仪器化的一路数据流，却暴露了对另外两路的需求。AI 系统的生产可观测性是三路数据流，这起事故展示了每一路是干什么用的。

**Trace——调试的基本单位**。一条 trace 记录一次请求的完整路径：输入、检索返回了什么以及带什么分数、哪些护栏触发了、确切的模型与 prompt 版本、输入输出 token 数、每个阶段的耗时、以及最终响应。它是概率性系统的调试基本单位，因为同一个输入可能产生不同输出，所以「被记录的那次实例」就是唯一可调试的对象。这里的管道是标准工程：普通服务的分布式追踪惯例直接适用。OpenTelemetry 是厂商中立的标�准，而那些 LLM 专用的追踪产品在同一个思路上加了这起事故所依赖的检索、prompt 和 token 字段。

**质量信号——在用户之前先觉察**。这起事故最糟的事实，是它到来的渠道：一条用户投诉，在答案过期几周之后。那几周里没有任何运营指标动过：延迟平稳、错误率平稳、在线率干净，因为那些指标没有一个去读答案的内容。要觉察质量衰减，得靠专门为此造的信号：针对固定问题集跑在线 eval 得到的每日分数，以及线上流量的行为代理指标——点踩率、人类纠正或覆盖输出的频率、升级率、任务完成率。假如 eval 集里早有一条由工业股报告回答的问题，过期的索引就会在一天之内表现为分数下降。你的离线 eval 分与这些在线信号之间的差距，本身就是一个要盯着的数字：差距拉大，意味着现实已经从你的测试集漂走。如果发现回归的唯一途径是客户投诉，那你就没有可观测性。

**运营指标——每次请求的成本与延迟**。第三路数据流一直就躺在 trace 里：每个阶段都带一个耗时，而模型阶段还带 token 数。跨请求聚合起来，它们就成了运营数据流：每次请求的美元数、以及延迟分布——读 p50 和 p99 而非平均值，因为用户感受到的是尾巴（「成本与延迟」会讲这两者）。在规模上，其中任何一个的小回归，都是一笔大账单或一条排队的工单，而这些指标也是一条预警通道。一次延迟尖峰或一次成本跳升，常常会在质量信号动之前，就暴露一个缺陷、一次检索死循环或一个过大的 prompt。

### 深入（Deeper）

可观测性，是评测、护栏与成本在同一时刻全部变得可见的地方。护栏拒绝数的一次尖峰，可能意味着一场攻击，也可能意味着一条坏了的输入路径；eval 分数下降而延迟平稳，则指向模型或数据，而非管道——这恰恰是上面那起事故的签名。看板是让你把这些关联起来的地方，也是你交给客户团队、好让他们在没有你的情况下也能运转的工件。

#### 坏 / 好 / 优——「你如何调试上周二的一个错误答案？」

**坏** ——「我会试着在 playground 里复现它。」这是确定性系统的反射，而它在两个方向上都证明不了任何东西：一个概率性系统可能在周二失败之后今天答对了；而即便成功复现，你也只是看到了那个坏输出，却看不到是哪个阶段产出了它。在这里耗一个下午，你对那个真正失败的请求一无所获。

**好** ——「我会去拉那个请求的日志。」方向对了，去找记录数据，但服务日志记录的是「活性」：状态码、延迟、错误计数。对一个错误答案，它们显示的是一个「在正常时间里正常返回」的请求，因为运营上什么都没失败。一条不携带答案内容的日志，说不出系统声称了什么，也说不出这个声称从哪来。

**优** ——「我会拉那个请求的 trace，一段一段地读。」带 chunk 和分数的检索、护栏的判定、带 prompt 版本和 token 的模型调用、扎根性分数：每个阶段都有它的输入和输出，于是失败定位到某个阶段，而不是「模型」。在上面那起事故里，这种读法停在了一个来自旧索引构建的过期 chunk 上；修法是重建索引、把重建排期化、并把那个失败问题加进 eval 套件，好让整类问题下次被每日运行抓住。

#### 面试要带走的

当面试官问「你怎么知道它坏了？」，或其更锋利的形式「一个用户说它上周二给了一个错答案；跟我走一遍你会怎么做」，就用这一页的形状来回答。拉出那个被记录请求的 trace，一段一段读，直到失败定位。然后报出那些本可以在用户之前就暴露问题的质量信号——每日 eval 分数、纠正率与升级率——以及你持续追踪的成本与延迟。对「活性」和「质量」都做仪器化，才让系统能被你之外的人运营，而这正是结束每次项目的那个交接。

## 成本与延迟（Cost & Latency）

一个 demo 服务一个用户、慢吞吞地、也没人看账单。生产环境服务几千人、卡在一个延迟预算上、而且财务每个月都看账单。这两个世界之间的落差，是很多 AI 部署悄然死亡的地方，而弥合它正是 FDE 的分内事。这一页讲的是决定「一个能跑的原型能否变成可存活产品」的那两个数字：每次请求的美元数，和响应的时间。

### 核心（Core）

对 AI 系统而言，成本与延迟由模型调用主导，而非围绕它的那些服务器。成本大致按「每次请求的 token 数 × 请求数 × 每 token 单价」来扩展；延迟大致是「首 token 时间（time-to-first-token）+ 生成时间」，而生成时间随产出的 token 数增长。你为了让系统便宜、快所做的一切，都是对这几项中的某一项下手。「加更多服务器」——普通 web 应用的那套反射——只会让账单更糟，因为瓶颈在模型调用里，而那些机器从来不是约束。

#### 为什么这是活儿

这个模式是：试点让五十个用户满意，客户说「推广到五万人」，于是同一个设计贵了一百倍，而共享模型在负载下变慢。FDE 是那个提前预见、并把杠杆设计进去的人。一个不能在生产语境里讨论「每次请求成本」和「p99 延迟」的工程师，从没运营过真实部署，而面试官心知肚明。

#### 读前思考

你的原型对每个用户问题做一次大模型调用，效果好极了。现在要求你在同样的预算下撑住 100 倍的流量。在伸手去够「更大的集群」之前，说出两个杠杆。

最能起作用的两个：不该叫大模型的时候别叫（缓存重复请求、把简单问题路由到小模型），以及别发送超过需要的 token（裁剪 prompt 和检索到的上下文）。两者都不是基础设施，两者都是设计。

#### 成本杠杆

**缓存重复请求。** 很多生产负载有很重的「近似相同请求」的头部。对精确或语义上接近的重复做响应缓存，能把「最便宜的那个请求——你根本不用发出的那个」整个省掉。

**选对模型尺寸。** 大多数问题简单，少数问题难。把容易的大多数路由到一个便宜的小模型，把大模型留给难的尾巴。前置一个快速分类器，能回本很多次。

**裁剪 token。** 成本对 token 是线性的，所以过度抓取的检索上下文是对每次请求都在征税。检索更少、更相关的段落（这也降低延迟、并改善扎根性——同一个动作帮了三个问题）。

**缓存共享前缀。** 当每次请求都共享一段很长的系统 prompt 或对话前缀时，缓存它已计算的状态，就能避免在每次调用时重复处理那段相同的内容。

一个算好的估算（示意）：

> （本框内每个数字都是示意的。）假设一个问题大约 2000 token 进、500 token 出，再假设每百万 token 几美元的混合价。那每次问题大约一美分。每天一百万个问题，就是大约一万美元一天——所以裁剪重复的 prompt 文本、或把更便宜的请求路由到更小的模型，不是表面优化，它是「可存活产品」与「被砍掉的产品」之间的差别。确切的价格是波动的；方法——token × 量 × 单价，然后找出主导项——才是面试官想要的。

#### 真实锚点，带日期

方法需要真实数字来「咬住」，所以这里列出两家厂商旗舰与小型模型的挂牌价。价格是波动的——在报给面试官或客户之前，请重查链接页面。

| 模型 | 输入（每百万 token） | 输出（每百万 token） | 来源（截至 2026 年 7 月） |
|------|------|------|------|
| Claude Opus 4.8 | $5 | $25 | Anthropic pricing |
| Claude Haiku 4.5 | $1 | $5 | Anthropic pricing |
| gpt-5.5 | $5.00 | $30.00 | OpenAI pricing |
| gpt-5.4-mini | $0.75 | $4.50 | OpenAI pricing |

这张表除了绝对数字之外，还有两件事可读。每一行里输出 token 的价格都是输入 token 的若干倍，这让冗长的答案本身成了一个成本杠杆。而每家厂商的小模型都只卖其旗舰价的一个零头，这正是把「路由」这个杠杆从「收拾」变成「真金白银」的原因：每一个被路由下去的简单问题，都省掉了那次请求的大部分成本。

#### Prompt 缓存与批量，标价

「缓存共享前缀」这个杠杆有厂商公开的经济账。按 Anthropic 的定价，把一个前缀写进五分钟缓存，成本是基础输入价的 1.25 倍，而后续一次缓存命中是 0.1 倍——同一页说明五分钟档「只需一次缓存读取就能回本」。OpenAI 把缓存输入的定价设为标准输入的十分之一。回本逻辑：

```
Anthropic 五分钟缓存；价格相对基础输入价 = 1.0
  缓存写入 = 1.25        缓存命中 = 0.10
  2 次请求，未缓存： 1.0  + 1.0  = 2.0
  2 次请求，已缓存： 1.25 + 0.10 = 1.35   → 命中一次即领先
  10 次请求，已缓存：1.25 + 9 次命中×0.10 = 2.15
                     vs 10.0 未缓存 —— 大部分前缀成本没了
```

让这个账保持诚实的那个告诫：省下来的只适用于共享前缀，前缀必须在请求间逐字节相同，而且缓存条目会过期，所以经济账取决于同一前缀在缓存生命周期内重现的频率。还有一个已公开的杠杆：两家厂商都卖批量处理——异步、非交互——Anthropic 打 5 折、OpenAI 打 5 折，是任何等得起的东西（eval 也算在内）的最便宜选项。

#### 延迟杠杆

**流式输出 token。** 感知延迟上最大的单一胜利：在生成的同时就吐出 token，让用户立刻看到响应开始。首 token 时间成了要紧的那个数字，而它远小于「全部完成」的时间。

**缓存前缀。** 那个省成本的前缀缓存，也削减了重复处理一段长共享 prompt 所花的时间，直接压缩首 token 时间。

**能省就换更小或更快的模型。** 那个省成本的路由动作通常也省延迟——小模型更快。

**并行化管道。** 检索、护栏检查、以及任何互不依赖的工具调用，应当并发运行，而不是串成一条链。

要大声说出来的那股张力：成本、延迟与质量彼此拉扯。更大的模型更准、更慢、更贵；激进的缓存又便宜又快、却冒着过期的风险。能挣分的是「说出你在优化哪个、为什么」——并把它绑到「什么真的会拖垮这次部署」上。

#### 延迟锚点，带日期

这一页的成本半场把方法锚在了真实挂牌价上；延迟半场也需要锚点。两个数字描述一个模型用起来的感受：首 token 时间（TTFT）和输出速度。Artificial Analysis——大多数人引用的那个基准——把它们定义得很精确：TTFT 是「从向服务或系统发出请求，到收到响应的第一个 token 之间所用的秒数」，输出速度是「收到第一个 token 之后，平均每秒收到的 token 数」。TTFT 是用户盯着的那段沉默；输出速度决定答案一旦开始之后还要多久才能写完。

两个实测锚点，每家厂商的小模型各一个：

| 模型 | 首 token 时间 | 输出速度 | 来源（截至 2026 年 7 月） |
|------|------|------|------|
| Claude Haiku 4.5 | 1.00 秒 | 94.0 token/秒 | Artificial Analysis |
| gpt-5.4-mini | 6.53 秒 | 160.8 token/秒 | Artificial Analysis |

把这两行对照着读：gpt-5.4-mini 一旦开始就流得更快，可用户在看到任何东西之前要等六秒多——那个首 token 数字反映的是一个推理模式的变体，在回答之前花了思考时间，也就是下面那个前沿模型告诫所描述的同一个效应。哪个模型「感觉更快」，取决于你的流程暴露的是哪个数字。这些基准数字在持续变动——新模型修订、新推理硬件——所以引用它们要带上访问日期，就像这张表这样。

前沿推理模型需要单独一个告诫，而且没有任何单一 TTFT 数字对它们公道：推理模式在第一个答案 token 之前要花思考时间，这可能把用户可见的等待推到远超小模型 TTFT 的地方。Artificial Analysis 把它单独追踪为「首答案 token 时间（Time to First Answer Token）」。围绕这个差异来设计面向用户的流程——一个为一秒沉默调优的流程，需要进度指示器、一条临时的状态消息，或者当思考把等待拉长到远不止那么久时换一个小模型。

两家厂商都公开了该拉哪个杠杆。OpenAI 的延迟优化指南量化了一个值得背下来的不对称：把输出 token 砍半，延迟大约减半；而把输入 token 砍半，延迟只改善大约 1% 到 5%。输出长度才是杠杆，这让「简洁作答」、一个最大输出上限、以及简洁的结构化格式，既是为延迟也是为成本而做的活。Anthropic 的指导是定性的，却指向同一个方向：选「够用」里最快的模型（「对速度关键的应用，Claude Haiku 4.5 在保持高智能的同时提供最快的响应时间」）、约束输出长度、并流式输出。

#### 一个 p99 预算，算给你看

一个延迟目标只有在按阶段分解后才成为工程。可观测性 trace 里那条被护栏保护的管道——检索、护栏预检、模型调用、扎根性检查——是一条链，而用户的等待是阻塞路径上所有东西之和。在分布的两个点上做预算：p50 给典型请求，p99 给工单队列会听到的那条尾巴。

```
示意端到端预算 —— 本框内每个数字都是虚构的；
要带走的是方法。答案长度 300 token。

stage                          p50          p99
retrieval                       90 ms       450 ms
guardrail pre-check             15 ms        40 ms
model: time to first token     800 ms     2,500 ms
model: generation              300 tokens ÷ 60 tokens/second = 5,000 ms
groundedness check             400 ms     1,800 ms

first visible token, streaming (retrieval + pre-check + TTFT):
  p50:   90 + 15 + 800                    =   905 ms
  p99:  450 + 40 + 2,500                  = 2,990 ms

full response, groundedness check blocking the stream:
  p50:   90 + 15 + 800 + 5,000 + 400      = 6,305 ms
  p99:  450 + 40 + 2,500 + 5,000 + 1,800  = 9,790 ms
```

这两个总数里折进了两条教训。第一，用户感受到的是「首可见 token 的时间」，所以流式输出几乎隐藏了全部生成时间：同一条管道，感觉像不到一秒，或像六秒多，取决于 token 是否在产出时就上屏。第二，扎根性检查打破了这个把戏。正如护栏页所讲，裁判是串行跑的，在完整草稿之后、在用户看到任何东西之前，所以一个阻塞式检查把流式体验打回了「等完整响应」的等待。这留下三种设计：把检查做得够快以卡进预算（一个短答案配一个小裁判模型）、改成采样或按风险路由的方式跑而非每次请求都跑、或者先流式出草稿、一旦检查失败就撤回——最后一种只在一个短暂可见的错误答案「可承受」的地方才可接受，而在受监管的部署里，通常不是。

有一个告诫让这个算术保持诚实：像框里那样把每个阶段的 p99 相加，得到的是一个保守的规划上界，而不是真实的 p99，因为最慢的 1% 检索和最慢的 1% 模型调用大多发生在不同的请求上。实践上，端到端的尾巴由「自己的尾巴最肥的那个阶段」主导。所以按阶段做预算、按阶段做度量——正是可观测性 trace 所记录的那些逐阶段耗时——并从生产里读真实的端到端分布，让电子表格的估算在那里得到修正。

#### 天花板：速率限制

容量比价格先耗尽：每家供应商都对每个账户设吞吐上限，所以一次推广可能在账单还很舒服时就撞上硬天花板。Anthropic 的限制按用量档位设置，并按每个模型类别用三种方式度量：每分钟请求数、每分钟输入 token 数（ITPM）、每分钟输出 token 数（OTPM）。超过任何一个都会返回「一个 429 错误」并带 retry-after 头，而且执行用的是令牌桶算法，所以容量是持续补充的，而非按时钟边界重置。同一页把本章的缓存杠杆既绑到容量上也绑到成本上，还带了自己的算例：「在 2,000,000 ITPM 的限制和 80% 缓存命中率下，你实际上每分钟可以处理 10,000,000 个输入 token」（Anthropic 速率限制）。你之前标价的那个前缀缓存，也顺带在天花板之下买到了余量。

OpenAI 的限制形状相同：每分钟或每天按请求与 token 计，在组织与项目层级生效，并随累计支出自动毕业到更高档位。

FDE 的教训：上线日的算术要包含天花板。峰值并发用户 × 每次请求的 token 数，对照每分钟 token 限制，能在第一个用户登录之前就告诉你这次推广是否装得进当前档位——而对 429 的带退避重试路径，应当从一开始就设计进去。

#### 自托管：那个交叉问题

一个顺着成本分析追问的面试官，会再推一步：什么时候自托管一个开放权重模型能胜过付 API 的钱？推理比任何数字都重要。一个 API 供应商把它的加速器在众多租户之间摊销，所以它买到的利用率，是单个客户很少能有的；而自托管者要为自己的流量峰谷之间的空闲容量买单，还要再为保持推理服务健康的运营人力买一次单。因此自托管倾向于在三种情形里胜出：持续量大到足以让硬件忙起来、有一个 API 服务不了的自定义微调模型、或者数据驻留与合规约束直接把 API 排除在外（第三种见「安全、合规与数据」）。还要把数字不会替你明说的那句话讲出来：可信的公开交叉点数字并不存在——各种调查的说法横跨两个数量级——所以任何报出盈亏平衡点的人，都欠你他的假设：量、利用率、硬件、人力。说出驱动因素、然后要求这些假设，才是那个强面试答案。

#### 坏 / 好 / 优——「让它能在规模上跑」

**坏** ——「我们会水平扩展，加更多实例。」你把一个 AI 系统当成无状态 web 服务了。成本是按 token 算的，延迟住在模型调用里，所以加实例让这两者原地不动——你在一个它们够不着的瓶颈周围加了一圈服务器。

**好** ——「成本是 token 乘量，延迟是首 token 时间；能缓存就缓存、能换小模型就换小模型。」正确的框架和真实的杠杆——扎实的中级水准。差距：不知道哪一项占主导，也不知道哪个约束最接近崩。

**优** ——「我会先量每次请求成本和 p99，找出主导项，然后对它下手：缓存头部、把容易的大多数路由到小模型、裁剪过度抓取的上下文、并靠流式输出做感知延迟。我从第一天起就对这两者逐请求做仪器化，因为在规模上一个小回归就是一笔大账单或一条工单队列。而且我会优先优化那个最接近拖垮部署的项，而不是那个最容易够到的项。」你把「它能扩展」变成了「在已度量的数字上点名杠杆」，并带一条优先级规则。

#### 面试要带走的

在系统设计轮里，「它能扩展」是一句空话。报出那两个数字——每次请求的美元数、p99 延迟——说出哪一个更接近拖垮部署，并在主导项上给出具体的杠杆。以度量和它确立的优先级开场。

## 安全、合规与数据（Security, Compliance & Data）

最需要前沿部署工程师（forward deployed engineer）的客户，恰恰是约束最硬的那些：银行、医院、国防、制造。对他们而言，AI 系统的聪明在通过安全审查之前一文不值，而那次审查常常是整个部署的门禁。一个把安全与合规当成「别人的阶段」的 FDE，永远上不了线。这一页讲的是那个决定「你的系统是否被允许存在」的约束。

### 核心（Core）

在受监管或企业级部署里，环境就是约束：数据能住在哪、谁能看它、什么必须被记录、以及系统到底能不能碰公网。这些不是以后再加的特性——它们从第一个框开始就塑造架构。资深者的习惯是在 Discover 阶段就把它们摆上台面，因为一个无视它们的设计，无论模型多好，都是胎死腹中。

#### 为什么这是活儿

个人效率型 AI 无视这一切——这正是它不算证据的原因。给真实客户做的生产 AI 住在他们的规则里：数据不能离开他们的区域、监管者必须能审计一个决策、安全团队必须在任何一个用户碰它之前签字。过这道门槛是工程活儿，而这是一个只建过 demo 的 AI 工程师从没做过的活。Morgan Stanley 的案例把这个讲得很明白：一项「零数据保留政策……确保 Morgan Stanley 的专有数据保持私密」，对这笔交易是承重的，是让它得以发生的那几个条款之一。

#### 读前思考

一家银行想要一个基于其内部文档的助手，而它的安全团队问：「我们的数据去哪儿了，你能证明吗？」如果你的回答是「它被送到模型供应商那儿」，你刚刚失去了什么？

你很可能丢掉了这笔交易，或者至少丢掉了接下来的六个月，除非你能确切说出数据流向哪、保留了什么、以及如何隔离。「它去 API 了」是某个从没通过安全审查的人的答案。

#### 从第一个框起就要为之设计的东西

**数据驻留与保留。** 知道数据物理上住在哪、住多久。受监管客户常要求数据留在某个区域、永不被用于训练第三方的模型、且只按政策允许的时长保留。选项从供应商的零保留、区域内 API 档，一直到完全本地化或气隙（air-gapped）部署、完全不外呼。这个选择约束着下游的一切，所以先把它定下来。

**敏感数据处理。** 个人信息（PII）和其他敏感数据，在到达模型或日志之前，需要被最小化、脱敏或 token 化——而「日志」之所以要紧，是因为一条 eval trace 或一次调试 dump，正是敏感数据泄漏的地方。敏感信息泄露是 OWASP Top 10 for LLM Applications 里点名的一个风险；把每一处数据被存储或发送的地方——包括你自己的可观测性——都视为在范围内。

**访问控制与隔离。** AI 系统继承客户的权限模型——用户绝不能通过助手，检索到一份他无法直接打开文档。这意味着检索与生成必须尊重逐用户的访问控制，而客户数据常常是按租户隔离的。一个无视权限的检索系统，就是一个带着友好界面的数据泄漏引擎。

**可审计性。** 在受监管场景里，必须有人能重建「系统为何产出了某个输出」：检索了什么、用了什么 prompt、谁看的、什么时候。那就是可观测性 trace，作为审计记录保存下来。「模型决定的」不是监管者会接受的答案；审计追踪才是让一个 AI 决策可辩护的东西。

### 深入（Deeper）

注意这有多少与护栏、可观测性、甚至采纳重叠。那不是冗余——在受监管部署里，安全就是信任的故事。Morgan Stanley 的顾问之所以采纳这个助手，正是因为该机构严格的标准被看得见地满足了；合规工作和采纳工作是同一件工作。把安全框定为「信任的使能者」而非「对信任的征税」，会改变你先建什么。

#### 各监管制度，以及每个制度所强迫的东西

上面的约束在一个真实客户那里，是带着名字到来的。四种制度覆盖了大多数项目，而每一种都把本课程早已教过的一个设计习惯，转成一条法律或合同义务。表格给出形状；后面的段落给出客户法务或安全团队会期待你知道的具体内容。

| 制度 | 是什么 | 对 AI 部署的强制要求 |
|------|------|------|
| GDPR | 欧盟《通用数据保护条例》，规范个人数据 | 合法依据、数据最小化、索引中的删除路径、自动化决策的人工介入、跨境转移条件 |
| HIPAA | 美国《健康保险可携性与责任法案》，规范健康信息 | 健康数据流转前签署供应商协议、访问控制、审计追踪 |
| SOC 2 | 审计师对服务机构控制措施的鉴证报告 | 文档化、在运行的控制：访问、变更管理、监控 |
| EU AI Act | 欧盟按风险分级的 AI 系统监管 | 高风险系统的全生命周期事件日志与人工监督，有明确截止日期 |

《通用数据保护条例》（GDPR，EU Regulation 2016/679）要求在处理个人数据之前先有合法依据（第 6 条），并要求所处理的数据「充分、相关、且限于必要」（第 5 条）——数据最小化，也就是这一页已经教过的裁剪与脱敏，被重申成了法律。有两条对 AI 系统特别咬人。删除权「不得无故拖延」（第 17 条）伸进了检索索引：一旦个人数据被 embedding 并索引，履行一条删除请求就需要一条重建索引的路径，而这条路径要么从第一天就设计进去，要么在请求到来时根本不存在。而第 22 条授予了对「具有法律或类似重大影响的纯自动化决策」的反对权，包括「获得人工介入」的权利——因此在某些部署里，人在环（human-in-the-loop）是一项法律要求，而不仅仅是信任实践。高风险处理在开始前要先做数据保护影响评估（第 35 条），而跨境转移只在满足条件时才被允许（第 44 条）——正是这一页开头那个数据驻留要求背后的条文。

《健康保险可携性与责任法案》（HIPAA）在美国规范受保护健康信息（PHI）。对 AI 部署最直接后果的那条规则是：PHI 只能在业务伙伴协议（Business Associate Agreement, BAA）之下交给供应商——「通过书面合同记录的充分保证」（45 CFR 164.502(e)）——所以模型供应商必须在任何一条患者记录碰到 API 之前就签署 BAA，而一个不肯签的供应商，无论模型多好，都被排除。HIPAA 的技术保障随后要求：访问控制要把系统限制在已授予的访问权限内，以及审计控制要「记录并审查包含或使用电子受保护健康信息的信息系统中的活动」（45 CFR 164.312）。那条审计控制的要求，就是逐请求的 trace 再一次出现，这一次是监管强制要求的。

SOC 2（System and Organization Controls 2）是一种鉴证（attestation）而非法律：审计师对照 2017 年的 Trust Services Criteria（含 2022 年修订的关注点）来审查一个服务机构的控制，这些标准由美国注册会计师协会（AICPA）发布，覆盖安全性、可用性、处理完整性、保密性与隐私。实践上，审计师要的是文档化、在运行的控制，覆盖访问控制、变更管理、监控等领域。对一个 AI 部署，这直接映射到本部分已经教过的机制上：部署页的版本化、门禁化发布，就是变更管理的证据；而监控证据就是可观测性技术栈——一场 SOC 2 审计，在很大程度上就是要求「这些纪律存在，并留下纸质痕迹」。

《欧盟 AI 法案》（EU AI Act）按风险监管 AI 系统，分四档，从被禁止的实践一直到最小风险。对高风险系统，有两条读起来就像本课程生产页被重申成了法律：系统必须「在技术上允许在其整个生命周期内自动记录事件（日志）」（第 12 条），并且必须被设计得「能够被自然人有效监督」（第 14 条）。时间线是二手材料最容易出错的地方，所以精确陈述它，截至 2026 年 7 月：禁止性条款自 2025 年 2 月起适用，通用模型规则自 2025 年 8 月起适用；透明度义务（第 50 条）自 2026 年 8 月起适用；而高风险制度被 2026 年年中商定的修正案推迟了——对独立系统（附件 III）推迟到 2027 年 12 月，对嵌入受监管产品的 AI（附件 I）推迟到 2028 年 8 月——依据律师事务所对该修正案的跟踪（Gibson Dunn、Travers Smith）。那些是律所摘要；在依赖这些日期之前请核对《官方公报》。如此新鲜的截止日期，正是 FDE 在项目开始时就要重新核实的那类事实，因为对它们的记忆很快过期。

把四行连起来读，模式很清楚：本生产篇已经教过的那些要求——日志与 trace、人工监督、访问控制、版本化发布——在这里以法律要求的形式到来。受哪个制度管辖，是客户的属性，而且在 Discover 阶段就会浮出水面。FDE 的活儿，是知道哪一个适用于本项目，并从第一个框起为它做设计。

#### 坏 / 好 / 优——「你如何处理他们的数据？」

**坏** ——「我们把它送到模型 API；供应商是安全的。」你把答案外包给了一个会拒绝它的安全团队，还暴露了你不知道数据去哪了。

**好** ——「我们用零保留档、脱敏 PII、并限制访问。」对三大件真实、正确的直觉——扎实的中级水准。差距：没有可审计性、没有检索里的逐用户权限、也没有在客户要求时本地化部署的选项。

**优** ——「我会先定驻留与保留——区域内零保留 API，或他们要求时的本地化/气隙——在检索里强制客户的访问模型，让助手无法浮出一个用户打不开的内容，在敏感数据碰到模型或任何日志之前脱敏，并保留每次检索与输出的审计追踪，好让一个决策可以被重建。而且我会在 Discover 阶段就把这一切提出来，因为它塑造架构。」你从第一个框起就为环境做设计，并让系统可审计——这才是真正过得了审查的答案。

#### 面试要带走的

当设计题点名一个受监管领域——金融、医疗、政府——不要等着被问到安全。早点把它摆出来，让它塑造架构：说出数据住在哪、逐用户访问如何强制、以及一个决策如何被审计。从第一个框起就把合规当作一等设计驱动，这是「能演示的系统」与「客户被允许部署的系统」之间的区别。

## 部署与 MLOps（Deployment & MLOps）

前面每一页都在让系统变「好」。这一页讲的是把它送进客户的生产环境，并在那里保持健康。那是 demo 到生产落差中的运营那一半，也是能跑的原型最常死掉的阶段。对 AI 系统而言，部署有一个连很强的基建工程师都会被绊住的转折：你交付的这个东西，可以在没有一行代码改变的情况下变差。

### 核心（Core）

部署一个 AI 系统，意味着把 prompt、模型版本、检索索引和 eval 基线当作版本化、可发布的工件（artifact）来对待，因为它们中任何一个变了，都会改变系统的行为。你分阶段推广（试点 → 受限 → 全量），你让每次发布都过 eval 这道门（概率性系统的 CI 版本），并且你保留一个回滚。那个陷阱是假设「代码没变」就意味着「什么都没变」：一次模型换新、或一次语料重新索引，都能让质量隐形地回归。

#### 现在就该做的

如果你的设计答案止步于「然后我们部署它」，就读这段。现在做这个：练习说出你会钉住的四个塑造行为的工件、你会跑的 eval 门禁、以及回滚目标。当「代码没变」不再听起来像「什么都没变」的证据时，你就完成了。

#### 为什么这是活儿

FDE 交付到客户凌乱的真实数据上，在客户的发布流程之内，在客户的可用性预期之下。一个在干净样本上能跑的 demo，现在要面对真实输入的全分布。两件事让 AI 部署成为一门独立的纪律。第一，定义行为的工件不只是代码：一次 prompt 编辑或一次模型升级，会在你的服务没有任何 diff 的情况下改变输出。第二，「正确」是概率性的，所以你的发布门禁不能是一套绿灯的单元测试；它必须是一个「对照代表性集合的 eval 分数」。一个像无状态 web 服务那样部署 LLM 应用的工程师，会交付一次静默回归，并且直到客户发现才知道。

#### 读前思考

你的服务代码一个月没动过，但用户说答案变差了。没有任何东西被「部署」了。什么变了，什么本该抓住它？

非代码工件里的某个东西变了：模型供应商更新了模型、语料被重新索引了、或上游改了某个 prompt。本该抓住它的，是一个即便代码不变也照样跑的排期化 eval，因为在 AI 系统里，行为的输入超出了你的代码仓库。

#### 一个有据可查的静默漂移案例

这一页的前提——系统可以在没有代码变化的情况下回归——有一张真实的收据，而把它读对，就是这堂课的一半。2023 年，研究者间隔数月测量了相同的 GPT-3.5 和 GPT-4 端点，发现同一个服务的行为已经移动了（《How Is ChatGPT's Behavior Changing over Time?》，Chen、Zaharia & Zou，后发表于 Harvard Data Science Review）。该论文的第一版报告 GPT-4 给质数打标的准确率从 3 月的 97.6% 跌到 6 月的 2.4%，而这个数字在互联网上被传成了「模型变笨了」的证据。

更锋利的读法随之而来。Arvind Narayanan 和 Sayash Kapoor 指出，那个任务里的每一个数其实都是质数，所以一个 6 月的模型如果只是改了习惯——默认答「非质数」、且不再写出它 3 月答案里包含的那段逐步推演（该研究记录到平均答案长度从 638.3 个字符塌到 3.9 个）——就会在没有任何算术能力损失的情况下拿到接近零分。行为漂移了；能力损失从未被证明。作者随后围绕一组均衡的质数与非质数修订了研究，其中 GPT-4 从 84.0% 掉到 51.1%：一次真实的回归，而且比头条数字小得多。

对 FDE 而言有两件事随之而来。一个模型在一个冻结的 prompt 下可以在你脚下漂移，这正是那个「代码不变也照样跑」的排期化 eval，在发布门禁里挣到位置的原因。而当那个 eval 真的闪红时，质数那集就是值得记住的告诫：把集合建成能区分「行为变化」与「能力损失」的样子，因为修其中一个的解，很少也是修另一个的解。

#### 动作

**版本化一切影响输出的东西。** prompt、模型标识、检索索引、以及 eval 集与基线，都是发布工件。钉住它们，记录哪些版本产出了哪些输出，你就能回答「什么变了？」，并回滚到一个已知良好的组合。

**分阶段推广。** 先用少数真实用户在真实数据上试点，然后是一个受限群组，然后全量。每一阶段都会暴露上一组没暴露的失败，因为真实使用比任何测试都广。Morgan Stanley 的案例在全员推广之前用 eval 做门禁，正是这个原因。

**用 eval 给发布设门禁。** 回归套件就是你的 CI：一个改动只有在 eval 守住所承诺的基线时才上线。这就是把「我们改进了 prompt」变成一条基线能够确认的主张的那个机制。

**保留回滚并在之后盯着它。** 部署不是终点线；每次发布都配一个快速回滚、以及能在生产里抓住质量退化的可观测性——而仅靠可用率是看不出来的。

**一个易变技术栈的发布检查清单。** 每次推广之前，重新审计那些会老化的部分：确认钉住的模型仍被支持、索引仍反映语料，然后对照近期基线重跑 eval。新鲜度是发布门禁的一部分。

#### 发布清单（release manifest）

版本的故事是抽象的，直到你把它写成一个文件。下面是一次研究图书馆助手（来自可观测性那起事故）发布所钉住的东西：每次发布一个 manifest，随服务一起入库。（下面这个 manifest 是示意的。版本、日期与分数是虚构的；要研究的是它的「形状」。）

```yaml
# release-manifest.yaml — the versioned artifacts of one release   (illustrative)
release: 2026-06-14-a
service_code: git 4f1a9c2          # the ordinary commit — often unchanged release to release

prompt:
  version: v14                     # the prompt template, versioned on its own
model:
  id: frontier-large-2026-05       # provider model identifier; providers deprecate on a schedule
retrieval_index:
  snapshot: idx-2026-05-31         # the embedded corpus, pinned as a snapshot
  built: 2026-05-31                # the build date that the stale-index incident turned on
eval_baseline:
  suite: research-library-v3       # the fixed question set the release is gated against
  must_clear: 0.90                 # release ships only if the run holds at or above this
rollback_to: 2026-05-20-b          # the previous known-good manifest, ready to restore
```

这个 manifest 是评审者读的那份 diff：五行定义行为的行，与往往没变的服务代码分离开来。它也是回滚目标：恢复一次发布，意味着把 prompt、模型和索引一起恢复。这就戳穿了这一页开头的那句谎言：`service_code` 可以保持不动，而模型标识或索引快照在它底下移动——正是那起索引过期回归的形状。

#### 一次分阶段推广，每一步都设门禁

manifest 说了一次发布「是什么」；推广说的是它如何一步步挣到面向所有人的资格。每一阶段都跑被钉住的 eval 套件，并把分数与 manifest 所承诺的基线对比。通过就扩大受众；回归就停住发布、恢复回滚目标。下面是研究图书馆助手 2026-06-14-a 发布的一次推广，模型升级到 frontier-large-2026-05，从上往下读。（这个 trace 是示意的。群组、分数与耗时是虚构的。）

```
release 2026-06-14-a  ·  baseline research-library-v3 @ 0.90        (illustrative)

[pilot]          8 advisors, real questions, 2 days               (t=0)
                 handpicked users on live data — the first contact with reality

[gate]           eval research-library-v3 after pilot
                 score 0.93  vs baseline 0.90   → PASS
                 widen: pilot cleared, open to the limited cohort

[limited]        120 advisors, one desk, 3 days
                 a broader slice — questions the pilot never asked

[gate]           eval research-library-v3 after limited cohort
                 score 0.86  vs baseline 0.90   → FAIL  (−0.04)
                 the new model regressed on the fixed suite; below the line

[halt]           rollout stops here — full audience never reached
                 restore rollback_to: 2026-05-20-b
                 prompt, model, and index revert together to the last known-good manifest
                 cost of the regression: one desk for part of one day, no wider
```

eval 分数是一个概率性系统所用的门禁，正如确定性系统会读一套绿灯测试套件。它在每一阶段都跑，因为随着受众扩大，失败的成本越来越高：试点的 0.93 本会通过，但受限群组的 0.86 在每一个顾问都继承到回归之前，就把发布停住了。

#### 坏 / 好 / 优——「你如何部署并让它持续运行？」

**坏** ——「我们部署服务并监控可用率。」你把它当成普通 web 应用了。可用率对答案是否还好用只字未提，而你也没有版本化任何真正驱动行为的工件。第一次静默回归对你是隐形的。

**好** ——「分阶段推广，而且上线前测质量。」真实的部署卫生：上线前质量检查 + 分阶段发布，是扎实的。差距：一次性的上线前测试抓不住上线之后模型或语料的漂移，而非代码工件也没有任何版本化的故事。

**优** ——「每个塑造输出的东西都是一个版本化工件——prompt、模型、索引、eval 基线——我按试点到受限再到全量推广，每次发布都用『eval 守住基线』设门禁，保留回滚到一个已知良好的版本集合，并按排期跑 eval，让一次没有代码 diff 的变化照样被抓到。部署是一个持续的门禁，而非一个上线事件。」你让行为版本化、让 eval 成为门禁，并为「静默回归」这个失败做了设计。

#### 面试要带走的

当设计走到「然后我们就上线」时，别止步于推广。说出你会版本化什么（prompt、模型、索引、基线，而不只是代码）、你如何在真实数据上分阶段推广、以及你的发布门禁是「按排期跑的 eval，背后带一个回滚」。把 AI 部署当作一个持续的、以 eval 为门禁的流程——一个在代码首次上线之后还长久运转的流程——正是每个真实项目赖以运转的运营脊梁。
