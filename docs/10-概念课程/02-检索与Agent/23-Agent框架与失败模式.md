# 23 · Agent 框架与失败模式

## 一句话直觉

**框架能加速搭建，也能加速翻车**——先认清失败模式，再挑品牌。

---

## 直觉讲解

市场上有各类 Agent 框架（编排图、工具注册、记忆、追踪）。FDE 选型应看：可观测性、HITL 支持、权限钩子、超时熔断、与客户栈集成，而不是 demo 华丽度。

高频失败模式目录：

| 模式 | 症状 | 缓解 |
|------|------|------|
| 无限循环 | 反复同一工具 | 步数/重复检测熔断 |
| 幻觉工具 | 调用不存在 API | 严格 schema、校验 |
| 沉默失败 | 忽略 tool error | 强制观察错误分支 |
| 权限漂移 | 服务账号过大 | 用户身份下行 |
| 提示膨胀 | 系统提示冲突 | 模块化与测试 |
| 伪异步 | 阻塞外部调用 | 超时与排队 |
| 框架魔法 | 隐藏控制流难审计 | 选可导出轨迹的框架 |
| 过度拆分 | Agent 过多推诿 | 减少角色、硬编排 |

```mermaid
flowchart TB
  Start[任务] --> Loop[框架循环]
  Loop --> Guard{熔断条件?}
  Guard -->|步数/费用/重复| Stop[停止并升级]
  Guard -->|否| Step[Thought/Act]
  Step --> Loop
```

原则：**框架是实现细节，架构原则（有界、HITL、轨迹、权限）不可框架化掉。**

## 工作示例

**案例**：某框架默认「失败自动换工具重试」打爆下游限流，引发联锁 429。  
**修复**：重试策略收归网关；幂等键；对写操作禁止盲目重试。

**案例**：Demo 用内存记忆，生产多副本后「失忆」或「串话」。  
**修复**：外置会话存储，键含 `tenant+user+session`。

**选型表（示意维度）**：本地可调试？支持人工节点？OTLP 追踪？SAC 钩子？许可协议？

## 面试常问取舍

**Q：要不要自研框架？**  
A：默认不。缺的能力用薄封装补；自研编排内核极易变成无文档黑洞。

**Q：如何在面试谈框架？**  
A：先谈失败模式与控制点，再提用过的库，显示判断力。

**Q：开源框架安全吗？**  
A：依赖供应链与默认示例配置常过宽，要审默认值。

| 取舍 | 重框架 | 薄自研胶水+工作流 |
|------|--------|-------------------|
| 速度 | 起步快 | 起步中 |
| 控制 | 看框架 | 强 |
| 锁定 | 高 | 低 |

## 框架采用门禁

- 能否导出完整轨迹？  
- 能否插入 HITL 节点？  
- 默认重试是否威胁写操作？  
- 密钥是否出现在示例里？  
- 许可协议是否兼容交付？  

任一项「否」且短期无法修补，就不要进主干。

## 薄封装建议

业务代码依赖自己的 `ToolGateway` 与 `PolicyEngine` 接口；框架只活在适配层。换框架时不掀桌。

## 深入：Harness 中的失败模式与可靠性（追加）

除上文目录外，开源 Harness 还高频踩这些坑：

1. **外套寄存式崩溃（coat-check crash）**  
   每次工具调用必须恰好一条结果。若在「发起调用」与「写入结果」之间崩溃，对话末尾留下**无人兑现的票据** → 校验拒收整段会话 → 朴素 resume 首请求失败。落盘协议必须保证 call/result 成对。

2. **中间层过厚或过薄**  
   同一个循环可叫 `runLoop` / `run_conversation` / `run_turn` / `query()`；行数差反映「多少策略留在中间层」。厚则能力全但难审计，薄则清晰但缺企业能力。

3. **压缩允许失败，不允许死循环**  
   Hermes 式：floor / two strikes / cooldown / fallback；压缩失败要降级，不能卡死主循环（见图示见 [13-上下文窗口管理](./13-FDE-Agent上下文窗口管理.md)）。

4. **Checkpoint 边界**  
   影子 Git（Hermes）≠ Claude 的提示前快照 ≠ Codex 已移除的 ghost snapshot。明确：**bash 侧效果与子代理编辑**往往不在 undo 范围。
