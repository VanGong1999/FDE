# 28. 十二要素应用（The Twelve-Factor App）

## 一句话直觉

十二要素是**应用与运行它的平台之间的合同**：约定代码、依赖、配置、进程、日志等必须长什么样，这样任意机器、任意平台、任意新同事都能跑起来、扩起来、更新起来——少踩「只在我机器上能跑」的坑。

## 本课问题

- 为何配置进环境变量、进程要无状态、日志打 stdout、绑定端口？这些「一直在用」的规矩从哪来？
- 十二要素解决的「软件侵蚀（software erosion）」是什么？
- 十二项各自在修什么？哪些过时、哪些在 2026 仍硬？
- WebSocket 等「连接即状态」如何与「无状态进程」共存？
- 密钥是否还该放在环境变量里？

---

## 核心概念详解

### 1. 它是什么、管什么、不管什么

**Twelve-Factor App**：约 2011 年，早期云 PaaS **Heroku** 团队（Adam Wiggins 等）总结并发布于 [12factor.net](https://12factor.net)。

两句话概括：

1. 它是**应用（后端服务）与平台**之间的合同；
2. 写明「应用必须怎样」，才能让任意机器/平台/新同事**无意外地**运行、扩展、更新。

今天几乎所有部署平台都**直接或间接假设**你遵守这些规则：Docker、Kubernetes、Render、Railway、Fly、Cloud Run、App Runner、Vercel、Netlify……许多实践已成「默认常识」，人们甚至不再提「十二要素」这个名字——说明它成功了。

**范围**：作为**网络服务**跑的应用（Web、API 等），任意语言/库/DB。桌面端、移动 App **不在**本文件射程。

**不是**：DRY、KISS、K8s 运维手册、微服务教义——只谈应用↔平台接口。

### 2. 历史：为何需要这份合同

2011 前后的部署常态（云尚未像今天普及）：

1. 租机或机房实体机；
2. 手装 OS、语言运行时、DB、依赖；
3. FTP/SSH 拷代码；
4. 在服务器上**手工改配置**。

每台机器都是 **snowflake（雪花）**：独特、手筑、难复现。新人起本机环境要几天，且与生产不一致 → 「**it works on my machine**」；发版要冻结其他工作。

文档称此为 **software erosion（软件侵蚀）**：代码没人改，应用却慢慢坏——OS 打补丁、同机另一应用升级库、维护者离职未记全手工步骤……

十二要素 = 对抗侵蚀的防线。

**文档现状（课程录制时）**：页脚曾长期停在 2017 小改；生态已出现容器、编排、serverless。2024-11 Heroku（Salesforce）宣布开源、中立组织治理，邀请 AWS/GCP 等参与修订；**Next** 分支改写中，仍保留 12 个名字与一句 motto，把原则拆成编号列表并区分「永恒」与「2011 时代」。线上站点当时仍以经典 2011 文本为主。本课：**先讲 2011，再点现代改写**。

### 3. I. Codebase——一份代码库，多次部署

- **修订控制跟踪的一份 codebase**（今天 = Git 等，2011 时仍有人用「final_v2.zip」邮件传）。
- **Many deploys**：deploy = 一次运行中的实例。生产、预发、每 PR 预览……都是 deploy。

差异不在「另起一套代码」，而在 **config**。同一仓不同 commit 可同时跑在不同 deploy；无法把环境描述成「同一 codebase 的某 commit」时，模式已歪。

边界：

- 多仓多应用 = **分布式系统**，每个应用各自遵守十二要素；
- 复制粘贴共享代码 = 违规 → 抽成库，用依赖管理引用（见 II）。

**Monorepo**：不算反模式。Codebase 定义为共享根 commit 的仓（或仓集合）；**一对一**的是「一个应用一份逻辑 codebase」。一仓建五个 app ≈ 五个 codebase 碰巧同仓；禁止的是**同一 app 两处拷贝**。

### 4. II. Dependencies——显式声明并隔离

关键词：**declare** + **isolate**。

- **声明**：仓内有完整准确的清单（`package.json` / `go.mod` / `requirements.txt`·`pyproject.toml` / `Gemfile`…）。无清单 → 新电脑靠扫 import 猜版本，易耗数日。
- **锁文件**（`package-lock.json` / `go.sum`…）钉死直接与传递依赖的精确版本，多年后仍可复现。
- **隔离**：仅有声明不够。例：manifest 要 `requests==2`，系统 Python 已装 v1 且先被 import → 仍跑错。声明无隔离、或隔离无声明，都会失败。

2011 提 `bundle exec`、`virtualenv`、vendoring；shell 出去调本机 ImageMagick 时，macOS Homebrew 的 v7 与 Ubuntu apt 的 v6 行为可完全不同。

**现代**：容器把库 + OS + 系统工具 + 运行时一并冻结——声明与隔离的峰值；常说 Docker「基本解决了」这一条。

### 5. III. Config——配置存环境

**Config** = 很可能在不同 deploy 间不同的一切：DB URL、邮件沙箱 vs 生产、本机 MinIO vs 生产 S3、本机 Redis 容器 vs 托管 Redis……

**开源测试**：能否在**此刻**开源生产代码库而不泄露任何凭证？（问的是「能不能」，不是「会不会」。）不能 → 配置还埋在代码里。

为何用 **环境变量**：

- 换 deploy 易改、不必碰文件；
- 不易误提交进仓（凭证泄露常见路径）；
- OS 级标准，与语言无关。

相对当年各框架私有格式（Java properties、Rails `database.yml`…）常被提交进仓。

课程 Tasker 示例：一大块 Go struct，~38 项全从 env 加载（带前缀）；开发中 config **值**常变，**读配置的代码**几乎不变——符合「变化速率不同的东西不要放一起」。

2011 与改写都反对把配置捆成 `staging.rb` / `production.rb` 这类**命名环境文件**：新环境（PR 预览连另一 DB）会迫使加代码。应**细粒度独立 env**，用设值组合出新 deploy，而非选「模式名」。

#### 密钥争议

环境变量适合 DB **主机名**等；高敏密码呢？Diogo Monica（曾负责 Docker 安全）等指出：env 会泄漏——子进程继承、崩溃页打印 env、Linux `/proc/<pid>/environ` 可读等。

较稳模式：**密钥管理服务**（Vault、AWS Parameter Store 等），启动时读入**内存**，轮换与审计。

立场：

- **配置与代码分离**不可谈判；
- env 仍是**非密钥**配置的正确默认；
- 密钥：小团队用平台注入的 secret env 仍远好于进仓；长大后密钥管理器是常识路径。

### 6. IV. Backing services——后台服务当可附加资源

**Backing service** = 应用经网络消费的一切：Postgres、Redis、队列、SMTP、S3、支付 API……

规则：代码**不区分**「自己运的」和「别人运的」；一律是经 **resource handle（URL + 凭证）** 挂上的附加资源——handle 在 config（III），不在代码。

测试：把本机 Postgres URL 换成 Neon / RDS 等，**零行业务代码改动**，只改 handle → 符合本条。

2011 时「DB 是别人电脑、用 URL 连」显得古怪（当时常同机跑 DB）；2026 反成默认，同机 DB 反成扩展反模式。本条**老化极好**。

### 7. V. Build, release, run——严格分离构建、发布、运行

粗映射今日 CI/CD：

| 阶段 | 产物 |
|------|------|
| **Build** | 取某 commit + 依赖 → 编译/打包 → **build**（Go 单二进制；Node = 应用+node_modules；Docker = image）。**不含** config |
| **Release** | build **+** 该 deploy 的 config → 可运行快照；应有 ID/时间戳，**追加-only、不可变** |
| **Run** | 从某 release 启动进程 |

好处一：**回滚几乎零成本**——坏了就重新跑上一份 immutable release（同 build 新 config 也是新 release）。

好处二：代码只在 build 入口进入流水线 → **无法**在生产机 SSH 热补丁再与仓库漂移（对抗雪花机）。

现代改写把 **immutable** 从隐含写成硬原则。

### 8. VI. Processes——无状态进程

应用以一个或多个**无状态**进程运行：请求间不靠进程内存/磁盘「记住」用户；需持久的进 backing service（IV）。任意请求可由任意进程服务；任意进程可随时消失。

允许：单次事务内的内存/本地盘缓存（如下载→处理→写库后丢弃的临时文件）。若**期望未来请求依赖该文件还在** → 违规。

**Sticky sessions（粘性会话）**：文档明确反对。把登录 session 放进程内存 → 扩到多实例后用户打到另一实例就「随机登出」；粘性只是绕过，杀掉一实例仍集体掉线，新实例也吃不到老用户。Session 是状态 → 放 Redis/Postgres 等。

**与实时课的张力**：WebSocket 连接**就是**进程内状态，严格说违反「无状态」。课程观点：无状态是**默认**；当功能本身就是状态（实时连接）时允许打破，并用 Pub/Sub 等补偿——拇指规则：**若杀任意进程会让用户丢数据，状态就放错地方了**。

### 9. VII. Port binding——通过绑定端口导出服务

2011：PHP 是 Apache 里的模块、Java 丢进 Tomcat——**应用是客人**，Web 服务器版本与配置成了雪花环境的一部分。

规则：应用**自包含**，HTTP 服务器作为依赖库（II）带来；**绑定端口监听**，自行导出服务。

2026 对长驻后端已极平常；本机 `localhost:8080`，生产由反向代理把公网主机名转到进程端口。附带好处：任何绑定端口的应用都能成为别的应用的 backing service——本地与生产只换 handle。

**老化点**：Serverless（如 Lambda）**不**绑定长驻端口，由平台调你导出的函数。改写保留「port binding」标题，同时强调**自包含 + 经声明接口导出服务**，以覆盖长驻端口与 serverless。

### 10. VIII. Concurrency——用进程模型横向扩展

2011 各运行时扩展方式不同（JVM 大进程内线程；PHP/Apache 按需小进程）。十二要素：把**进程**当一等公民，按工作类型拆分并独立扩展：

- **web**：HTTP；
- **worker**：重活（转码、缩图）；
- **clock/scheduler**：定时（夜间群发邮件）……

午餐高峰：web×10、worker×2；夜间：web×5、worker×20——避免「一个大进程复制 10 份」时把闲着的 worker 也扩 10 倍。类型与副本数 = **process formation**（今日 K8s `replicas`、Procfile 等仍是同一思想）。

注：进程内仍可用线程/goroutine/事件循环；**扩展单位是进程**（垂直扩展有天花板；share-nothing 才能跨机）。应用**不要 daemonize、不要写 PID 文件**——生命周期归平台/OS/K8s。本条未被淘汰，而是被编排器消化到「几乎不用想」。

### 11. IX. Disposability——快速启动与优雅停机

进程应可被随时启停且不破坏数据。与第 19 课优雅停机同源：扩缩、滚动发布会频繁杀旧起新——**进程死是生命周期常态，不是事故**。

- 启动慢 → 滚动发布与弹性伸缩全面变慢（60s 启动 × 10 实例 ≈ 10 分钟级）；目标常是**数秒级**启动。
- 停机不优雅 → 发布时 in-flight 请求直接报错。Web：停收新请求 → 做完已有 → 退出。Worker：把当前任务**退回队列**，并具备 **reentrancy / idempotency**（再跑不脏、可安全重复）。
- 还须扛**突然死亡**（OOM 无 SIGTERM 礼遇）。「Crash-only」思想：若崩溃路径已可靠，优雅路径可与崩溃路径合一。

### 12. X. Dev/prod parity——开发/预发/生产尽量同构

三类差距：时间（代码隔周才上、一次合并很多）、人员（写/发/看日志的人不同）、工具（本机 Mac/Windows vs 生产 Linux + 托管服务）。

十二要素倾向：频繁部署、谁写谁发、环境尽量像。今日时间/人员差距已缩小；**工具差距**仍在——尤其 ORM 让人在开发用 SQLite、生产用 Postgres：`LIKE` 大小写语义等可无声改变行为。

建议：backing service 种类在本地/预发/生产尽量一致；容器使「本机起 Postgres」成本远低于 2011。

 nuance：托管 DynamoDB 等无法在本地 100% 复刻（LocalStack 等是模拟）。若托管收益巨大，可接受差距——但要清醒，不是「原则作废」。

### 13. XI. Logs——日志当作事件流

日志**不是**「文件」本身；文件只是一种输出。日志是按时间排序、随应用运行不断流出的**事件流**。

应用**不负责**路由与存储：不写死路径、不自己做轮转。只把事件**无缓冲地打到 stdout**；由执行环境捕获，决定进文件、syslog、Loki、Datadog……

好处：换环境不必改日志代码；流可组合——本机看终端、容器打实例戳、生产多实例合并成按时间的一条流。2011 只提 logs；今日还有 metrics/traces（可观测性）——视为**加法**，不是本条限制你。

### 14. XII. Admin processes——管理任务作一次性进程

一次性任务（迁移、修数脚本）应与常驻进程**同一 codebase/commit、同一 config、同一依赖隔离**，在旁跑完即退——反对 SSH 进生产随手 UPDATE（无评审、无记录、环境漂移）。

典范：**数据库迁移**与应用同仓，启动前跑一次。课程演示：Procfile + 进程管理；一侧 web 绑定端口打 stdout；一侧一次性归档任务同环境跑完退出；Ctrl+C 时连接池关闭、job 收尾——VIII、IX、XII 同框。

### 15. 前六条带来的能力（课程中途小结）

到 VI 为止你已有：一仓代码、声明并隔离依赖、差异在环境、邻居靠 handle 附加、经 build→release→run 上线、以可丢弃的健忘进程运行。后六条在此之上谈端口、并发形态、可处置性、环境同构、日志流、管理任务。

## Checklist

- [ ] 能用「应用↔平台合同」解释十二要素存在的理由
- [ ] 能说明 codebase / many deploys，以及 monorepo 不等于违规
- [ ] 依赖：既有 manifest+lock，又有隔离（理解容器的意义）
- [ ] 配置在 env；能做「开源测试」；密钥知何时升级到密钥管理器
- [ ] 换 backing service 只改 handle 不改代码
- [ ] 能画 build / release / run，并说明不可变 release 如何瞬间回滚
- [ ] 默认无状态；粘性会话是违规；WebSocket 是有意识的例外+补偿
- [ ] 自包含并绑定端口（或 serverless 下的声明接口）
- [ ] 按进程类型独立扩展；不自己守护进程
- [ ] 快启 + 优雅停机 + 扛突然死亡；worker 可重入/幂等
- [ ] 本地与生产 backing service 尽量同类；知托管服务的差距权衡
- [ ] 日志打 stdout，不自管文件路由
- [ ] 迁移等管理任务作同环境 one-off

## 常见坑

| 坑 | 说明 |
|----|------|
| 配置/密钥进仓 | 开源测试失败；泄露日常 |
| 用 staging.rb 式打包环境 | 新环境只能加代码 |
| 进程内存存 session + 粘性会话 | 扩缩与挂实例时集体掉线 |
| 生产 SSH 热修 | 与仓库漂移，侵蚀再现 |
| 开发 SQLite / 生产 Postgres 无感 | 无声语义差异 |
| 应用自己写日志文件并轮转 | 多实例与换平台时处处打架 |
| 把十二要素当成「微服务教义」 | 它只管应用↔平台接口 |
