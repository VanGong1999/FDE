# 24 · 对象存储与大文件

一句话直觉：用户文件**不是**「再写一个 JSON 字段」——别往应用机本地盘塞；用**对象存储**换无限容量与高耐久，用**预签名 URL + 两阶段（pending→ready）**让字节不经过你的服务器，小文件才考虑经后端流式转发。

## 本课要解决什么问题

- 产品说「用户要上传头像/视频」时，直觉「存本地盘 + DB 记路径」为何在生产必炸？
- 块存储 / 文件存储 / 对象存储各适合什么？对象存储放弃了什么、换来了什么？
- 对象到底是什么？「文件夹」为何是幻觉？Key 该怎么设计？
- 元数据面 vs 数据面、纠删码、「11 个 9」、耐久 ≠ 备份——这些词对后端意味着什么？
- 文件如何进桶：**经服务器** vs **预签名直传**？为何推荐预签名 POST + 策略？
- 浏览器直传后，DB 如何知道？如何清理半拉子上传？CORS 要注意什么？

（大文件分片 / Multipart、Range、下载 CDN 等细节在第 25 课展开；本课建立对象存储与上传架构基础。）

## 核心概念详解

### 1. 产品场景与朴素方案

你已有认证、DB、Handler/Service/Repository。新需求：用户上传文件（先想头像）。

**朴素直觉**：

1. 浏览器用 **FormData** 把文件 POST 给你；  
2. 存到服务器**本地文件系统**（ext4 等）；  
3. 路径写入 DB，下次按路径读出返回。

本地开发常「看起来能用」。生产则一路拆穿。

---

### 2. 朴素方案如何全面失败

#### 问题 1：磁盘是短暂的（Ephemeral）

容器/K8s/多数 PaaS：容器重启或重新部署 → 本地盘清空。一次 OOM 重启就能让该实例上所有用户文件蒸发。

挂 **Persistent Volume** 能缓解「短暂」，但挡不住下面几条。

#### 问题 2：水平扩展与无状态

三实例 + LB：上传落到实例 1 的本地盘；两分钟后读请求轮询到实例 3 → **404**。实例越多，命中「有文件那台」的概率越低（约 1/N）。  
这直接破坏水平扩展的核心：**无状态**——实例不该持有别的实例没有的状态。（呼应第 22 课。）

#### 问题 3：盘只能垂直变大

流量可加实例；盘往往只能把**同一块盘做大**，常伴随停机与上限。用户文件却是增长最快的数据之一（删远少于传）→ 垂直盘很快撞墙。

#### 问题 4：耐久性（Durability）

单盘坏了 → 唯一副本没了。  
- **可用性**：现在能不能访问（等一等、修一修或许回来）；  
- **耐久性**：数据是否还在世界上某处。  

耐久性故障不能靠「再等一会」恢复。业界答案是**复制**等多副本工程——不该由你的 Todo 应用自己扛。

#### 问题 5：经服务器下载

50MB 文件、用户 2Mbps 手机网 ≈ 数分钟下载；这期间一个 goroutine / 事件循环 worker 只在**慢速拷字节**。服务器不是 CDN：贵、慢、并发连接有限，且占用本可服务 API 的 I/O 能力。

#### 问题 6：文件与 DB 行没有事务

- 先写盘再写库失败 → **孤儿文件**（占钱、无入口）；  
- 先写库再写盘失败 → **库有路径、盘无文件** → 404/500。  

两边无法原子提交。换对象存储后问题仍在，但可用「先记意图、后校验、后台清理」模式更好解。

**错误假设**：文件是「应用拥有的本地资产」。其实文件有完全不同的访问模式与成本曲线，需要**对象存储**这类系统。

---

### 3. 三类存储

| 类型 | 接口直觉 | 特点 | 典型用途 |
|------|----------|------|----------|
| **块存储** | 按块号读写固定大小块（如 512B/4KB） | 极低延迟（微秒级）；**一次只能挂一台机器** | 给 Postgres/MySQL 等垫底（如 EBS） |
| **文件存储** | 目录、路径、权限、seek、锁、原子 rename 等 POSIX | 功能丰富，但**跨机器协调难**，难无限水平扩 | 传统单机/有限共享场景 |
| **对象存储** | 极简：**Put / Get / Delete / List**（按名） | 放弃原地改、真文件夹、锁等，换**近乎无限水平扩展**与耐久 | 用户上传、静态资源、备份等 |

对象存储的哲学：要能扩到「行星级」，接口必须极简，从而消灭一整类分布式协调问题。

---

### 4. 对象存储的取舍

**你放弃的**：

- 不能原地改/追加；改 1GB 中间一字节 = 整对象下载→改→再上传替换；  
- 无真正目录；  
- 无廉价 rename（= 拷到新 key + 删旧，按体积计费）；  
- 无 OS 式文件锁；  
- 延迟是**毫秒～数十毫秒**（每次都是跨网 HTTP），不是微秒。

**你得到的**：

- 无可变共享状态 → 少大量分布式难题；  
- 无目录树可锁/再平衡；  
- 每次操作自包含 → 全球任意前端节点可服务 → **水平扩展近乎无上限**；  
- 容量近乎无限，无需自建扩盘；  
- 耐久承诺（如 S3 宣传的 **11 个 9**）；  
- 任意会 HTTP 的客户端可直连（浏览器、播放器、App）。

分布式系统里「要无限规模常先放弃可变性」——对象存储是最干净的例子之一。

---

### 5. 对象是什么

一个对象通常包含：

1. **Key**（字符串）——完整身份；  
2. **Value**——字节 blob；  
3. **元数据**——系统侧（大小、Last-Modified、Content-Type、ETag）+ 可选**用户元数据**（如 `uploaded-by=userId`）；  
4. 住在 **Bucket**（桶）里；桶名 + key 在平台上常需全局唯一。

称呼上更准确叫 **object** 而非 file——避免期待文件系统的全部语义。

#### 「文件夹」是幻觉

控制台里的 `uploads/2026/cat.png` 看起来是两层文件夹，实际只是**一个 key 字符串**，`/` 只是字符。List + delimiter 时，服务端对前缀做「按 delimiter 切开」的 **group-by**，在 `CommonPrefixes` 里假装出文件夹。

后果：

- 「移动文件夹」= 成千上万对象逐个拷贝+删除，又慢又贵；  
- 不能有真正的空文件夹（有人用 key 以 `/` 结尾的 0 字节对象骗 UI）。

---

### 6. Key 设计三条规则

1. **永远不要用用户原始文件名当 key**  
   - 碰撞：两人上传 `resume.pdf` → PUT **静默覆盖**（PUT 语义就是整对象替换）；  
   - 路径穿越：`../` 等可能逃出你以为的前缀；  
   - 怪异字符：emoji、RTL、空字节等搞爆下游。  
   → **自己生成 key**（随机）；原文件名存 DB 和/或用户元数据，仅在下载展示时用。

2. **高熵部分放前面**  
   索引常按 key 前缀分区。若全用 `date/hour/...` 开头，同一小时写入砸同一分区 → **热分区**、503 SlowDown。  
   → 前面放 UUID / 哈希前缀等；`user/tenant/uuid` 优于 `2026/04/21/file`。小规模也可能没事，但正确做法几乎零成本。

3. **让 key 携带归属（可选但实用）**  
   `tenantId/userId/objectId` → 鉴权可先做字符串/前缀比较，凭证也可收窄到某前缀，少一次查库。

---

### 7. 幕后：数据面 vs 元数据面

PUT 100MB 时：请求打到无状态前端节点 → 鉴权（验签名）→ 拆成两个问题：

| | **数据面（Data Plane）** | **元数据面（Metadata Plane）** |
|--|--------------------------|--------------------------------|
| 职责 | 把字节存住、活下去 | 记住「桶+key → 分片位置、大小、ETag、类型…」 |
| 特点 | 体量大、操作相对简单 | 体量小、操作极多，要**强一致、极快** |

存艾字节级磁盘是老问题；在全球对海量 key 维护**强一致有序索引**、单次查找毫秒级，才是硬工程。

**强一致 vs 最终一致（直觉）**：强一致 = 写成功后立刻读必看见；最终一致 = 写后读可能短暂 404。S3 历史上 list/读曾最终一致；**2020-12 起**提供强 **read-after-write**——「上传后 sleep/重试」类老建议已过时。

#### 纠删码与「11 个 9」

朴素耐久 = 三副本 ≈ 200% 额外存储。大规模太贵。  
**纠删码（如 Reed-Solomon）**：例如 14 数据分片 + 6 校验 → 20 片散落多故障域；**任意 14 片**可还原。开销约 1.43×，能扛更多同时故障，用 CPU 换磁盘钱。

「11 个 9」≈ 存 1000 万对象，统计上约每 1 万年丢 1 个——来自分片数学，不是魔法。

**耐久 ≠ 备份**：

- 盘坏：系统会救；  
- 你（或 bug、被盗凭证）**删错前缀 / 覆盖写**：系统会**同样耐久地**执行删除/存坏版本。  

需要：开 **Versioning**；重要数据**跨账号复制**到第二桶（凭证被盗时不共享命运）。

#### 元数据面与 List 禁令

元数据可想成巨大分布式有序 KV / B-Tree，按 key 范围分区 → 又与热分区、rename 难有关。  
**List** = 分布式有序索引上的范围扫描，比按 key 点查贵得多。

**铁律：不要在请求路径上 List 桶来回答「这用户有哪些文件」。**  
DB 才是「有哪些文件」的索引；桶只存字节。按 key Get/Head。

对象大小能瞬间知道，是因为大小在元数据里，不必扫盘。

### 8. 条件写（Conditional Writes）

长期：同 key 并发 PUT 谁后到谁赢，失败者**无感知**。  
近年 S3 等支持条件头：

- **If-None-Match: \***：仅当 key **不存在**才创建；已存在 → **412 Precondition Failed**（防静默覆盖/重复 key bug）；  
- **If-Match: &lt;ETag&gt;**：仅当当前内容仍是我读到的版本才替换 → 乐观并发 / compare-and-swap。

这是分布式协调原语，也催生「在 S3 上做 WAL」等玩法。注意：**S3 兼容**≠ 一定支持条件写（如部分厂商不支持）——上线前查文档。

---

### 9. 两种上传架构

#### A. 经你的服务器（小文件可接受）

浏览器 → 你的 API → 你再传到桶。可扫描、算哈希、沿用现有鉴权中间件，少折腾 CORS。适合头像、小 CSV、数 MB 内文档。

**缓冲陷阱**：默认把整个 multipart 读进内存 → 100MB × 20 并发 = 轻松打爆容器内存。本地难复现（小文件、快网、大内存）。

**正确做法**：

- **流式**：边从 request body 读块边写给 S3 SDK，内存≈一块缓冲；  
- **Body 大小上限**：超限直接切断（防 4GB 突袭）。

即便流式，仍受 LB 空闲超时、Nginx `client_max_body_size`（413）、Serverless/API Gateway 载荷硬顶等限制 → **大文件不该走这条路**。

#### B. 预签名 URL（生产默认推荐）

字节**不经过**你的服务器；浏览器直传私有桶。

**预签名 URL**：普通 URL + 查询参数（算法、Access Key Id、时间、过期秒数、覆盖的头、HMAC 签名等）。服务端用密钥签「方法+桶+key+过期…」；桶侧重算比对。改 key/方法或过期 → 403。密钥永不下发浏览器，但浏览器获得**短时、单 key、单操作**能力。

#### 预签名 PUT 的漏洞：体积

签名通常管方法/桶/key，**不管 body 多大** → 「头像 URL」可被用来灌 5GB。

**正解：预签名 POST + Policy**  
签一小段 JSON 策略，返回 URL + 表单字段。策略可强制：

- **content-length-range**（最小～最大，由存储侧强制）；  
- Content-Type 前缀如 `image/`；  
- key 必须以某租户/用户前缀开头。  

违规 → 存储拒绝（如 entity too large），数据不落桶。  
客户端注意：FormData 里 **file 字段最后追加**；不要手写 Content-Type，让浏览器设 multipart boundary。

---

### 10. 两阶段流程：让 DB 知道直传

浏览器直传时服务器看不见字节，如何更新「用户有这个文件」？

1. **Init**：客户端申请上传 → 后端鉴权 → **预先生成 key** → DB 插入 **pending**（记下预期大小/类型等）→ 返回预签名 POST（或 URL）。  
2. 浏览器直传桶。  
3. **Complete**：客户端带 upload id 回调 → 后端对桶做 **Head Object**（轻量元数据）校验存在、大小、类型 → DB **pending → completed/ready**。

**清理**：部分上传会遗弃（关标签、断网、传完却没调 complete）。桶上可对 pending 前缀做生命周期删除；后台任务扫过期 pending 行标记 expired——避免 DB 与桶两套真相漂移。

DB = 「有哪些文件」的真相；桶 = 「字节」的真相。

---

### 11. CORS

浏览器跨域直传桶 → 必须配桶 CORS：允许前端 Origin、PUT/POST，并 **ExposeHeaders 包含 ETag**（分片上传完成时前端要读 ETag；详见第 25 课）。  
curl/Postman 成功、浏览器失败 → 先查 CORS。

## 后端规则与最佳实践（Checklist）

- [ ] 用户文件默认进对象存储，不进应用实例本地盘。  
- [ ] Key 自生成、高熵在前；原名存 DB；勿用用户文件名当 key。  
- [ ] 请求路径用 DB 列文件，禁止 List 桶当业务查询。  
- [ ] 耐久靠厂商 + 自己做 versioning/跨账号复制；勿把「11 个 9」当备份。  
- [ ] 小文件若经服务器：必须流式 + 大小上限。  
- [ ] 大文件/常规生产上传：预签名；优先 **POST+Policy（含 content-length-range）**，慎用裸预签名 PUT。  
- [ ] 两阶段：先 pending 再 Head 校验再 ready；有遗弃清理。  
- [ ] 桶私有；配好 CORS（含暴露 ETag）。  
- [ ] 依赖条件写前确认供应商真正支持。

## 常见坑与反模式

1. 生产容器本地存用户文件 → 重启/换实例全丢或 404。  
2. 多实例本地盘破坏无状态。  
3. 整文件缓冲进内存导致 OOM。  
4. 用用户文件名当 key → 静默覆盖。  
5. 时间戳前缀热分区。  
6. 每次打开「我的文件」就 List 桶。  
7. 以为耐久能救「误删前缀」。  
8. 预签名 PUT 无体积策略 → 被当免费网盘灌爆。  
9. 直传成功却无 complete / 无清理 → DB 与桶不一致、干付费。  
10. 忽略 CORS / 未暴露 ETag → 浏览器完成流程失败。
