# 22 · 扩展与性能续：水平扩展

一句话直觉：水平扩展能「加机器」的前提是**无状态**——任何一台实例都不该独占会话、文件或本地库；状态放到全员都能访问的 Redis / 对象存储 / 托管数据库，再靠负载均衡、读副本、CDN 与异步任务把吞吐和感知延迟一起抬上去。

## 本课要解决什么问题

- 第 21 课讲到水平扩展后，为什么还要专门谈 **无状态（statelessness）**？会话和文件存在本机会怎样翻车？
- **负载均衡（Load Balancer）** 怎么选实例？轮询、加权、最少连接、健康检查各解决什么？
- 应用层水平扩展相对容易，**数据库**为什么难？读副本、复制延迟、分片分别干什么？
- **CDN / 边缘计算**如何对抗地理延迟与 DDoS？什么该放边缘、什么必须回源？
- **异步处理、微服务、Serverless** 各自解决哪一类扩展问题？何时不该上？
- 两课合起来后，工程师应带走哪些**心智模型**（先测量、偏简单、按真实问题扩容）？

## 核心概念详解

### 1. 无状态：水平扩展的钥匙

水平扩展 = 多台**同容量**机器跑**同一份代码**，流量在多实例间分发。这只有在实例**不持有独占数据**时才成立。

- **有状态**：某实例内存/本地盘里存了别的实例看不到的会话、文件、缓存 → 请求落到别的实例就会 401、404 或诡异错误。
- **无状态**：任意实例删掉/重启，剩余实例行为应不变；需要持久化的数据一律放在**所有实例都能访问的外部存储**。

课程反复强调：相对垂直扩展（控制台加 CPU/内存即可），水平扩展必须**从栈的一开始就规划**——会影响代码、基础设施与整条链路。

#### 典型翻车与正解

| 场景 | 错误做法 | 无状态做法 |
|------|----------|------------|
| 登录会话 | 实例 A 把 session 存在进程内存；下次请求到 B → 401 | Session 写入 **Redis** 等共享存储，各实例都能校验 |
| 文件上传 | 实例 A 写本地 SSD；下次读落到 C → 找不到 | 上传到 **S3 / R2 / 自建对象存储** 等共享 blob |
| 数据库 | 用 SQLite，DB 文件在本机磁盘 | 用 **Postgres / RDS** 等中心化数据库 |

拇指规则：水平扩展时，**没有任何信息只活在单实例里**——内存结构、本地文件、本地库都不行。

---

### 2. 负载均衡（Load Balancer, LB）

没有 LB，多实例几乎无法落地：客户端不知道该打哪台机器，也没有统一入口做决策。

**基本形态**：用户 → Internet → **LB** → 多实例；请求经 LB 转发，响应再经同一 HTTP 连接回到客户端。关键在「用什么算法选实例」。

#### 常见算法

1. **轮询（Round Robin）**  
   A → B → C → A…  
   适合：请求成本大致相同、实例规格相同。简单有效。

2. **加权轮询（Weighted Round Robin）**  
   大机（如 8GB/4 核）权重更高，收到更多请求。仍不知道「这个请求贵不贵」。

3. **最少连接（Least Connections）**  
   看当前**活跃连接数**（HTTP 等待响应期间连接视为活跃），把新请求分给最闲的。  
   直觉：贵请求（外呼 API、大表写、多索引更新）会长时间占连接 → 该机少接新活；轻请求很快结束 → 连接归零后继续接。比盲目轮询聪明。

4. **加权最少连接**  
   在 LC 上再叠加容量权重。

5. **最少响应时间 / 基于资源**  
   偏向响应更快、或 CPU/内存更空闲的实例。

HTTP/2、HTTP/3 连接复用细节不同，但「处理中 = 连接忙」的直觉仍有用。

#### 健康检查（Health Checks）

某实例宕机后，若仍轮询到它 → 部分用户 502/503，体验极差。

做法：LB 周期性（如每秒）向各实例发**轻量探测**（常见期望 **200**）。失败则**摘除**（黑名单），用户流量只打健康机；探测继续，恢复后再加回。

健康检查本身应极轻，不构成负载。

### 3. 数据库扩展：有状态组件

应用层一旦把状态外置，加机器吞吐可近似线性；**数据库**仍难扩：数据必须一致，不能像应用那样随意复制多份各自写。

行业常见两招：**读副本** 与 **分片（Sharding）**。

#### 3.1 读副本（Read Replicas）

- **主库（Primary / Master）**：唯一写入口（INSERT/UPDATE/DELETE）。  
- **副本（Replica / Secondary）**：只服务读（SELECT）；数据从主库复制过来。

典型收益：

1. **卸负载**：SaaS 里读常占 70%+；主库从扛 100% 降到主要扛写（约 30%）。  
2. **降延迟**：副本放到用户附近区域（印、中、日等），配合同区域后端，就近读。

**最大代价：一致性与复制延迟（Replication Lag）**

物理距离不可消灭：美东主库写完，印度副本可能要约 200ms 才能追上。SPA 里「保存成功 → 立刻再 GET」若打到滞后副本，会看到旧姓名——支付/发票场景更危险。

常见缓解（都是权衡）：

- 刚写过的实体，短时间读**强制走主库**；  
- 跟踪平均复制延迟，读侧**等到追上再返回**；  
- 前端有意延迟再刷新（如 300ms）。

托管库（RDS、Cloud SQL 等）常一键开区域副本，底层一致性方案由厂商扛；工程师仍要**懂 trade-off**，才能在控制台配对。

#### 3.2 分片 / 分区（Sharding）

当单表到数十亿行，即使有索引，查询与单机资源仍可能顶不住。分片 = 按**分片键**把数据**物理切到多库/多实例**。

例：订单表按**下单日期**切——上半年在实例 1，下半年在实例 2；也可按月一 shard。后端在发 SQL 前先算「数据在哪片」。

同时缓解：

- **查询延迟**（每片行数更少）；  
- **吞吐**（多实例并行接请求）。

难点：选对分片键、跨片查询/事务、再平衡——概念必须懂，自建极易翻车。

#### 3.3 现实建议与分布式库趋势

- **不要轻易自建**复制、分片、备份体系；除非深耕 DBA。  
- 实务：选 Neon / PlanetScale / CockroachDB / Yugabyte / RDS 等，拿连接串接入；在控制台配置备份频率、副本区域、分片策略。  
- 新趋势：托管**分布式数据库**代管分片、复制、分布式事务——仍要懂概念才能配置与排障。

### 4. CDN：对抗光速与地理距离

光纤里光速约 20 万 km/s。东京 ↔ 美东 Virginia 往返约 2 万 km → **纯网络 RTT 下限约 100ms**，再加路由、反序列化、DB、外呼，很容易到 500–800ms。CDN 把内容缓存在用户附近的 **PoP / Edge**，RTT 可从约 100ms 降到数毫秒级。

**收益**：

1. **延迟**：静态资源就近命中。  
2. **卸源站负载**：流量摊到全球节点，源站少扩容。  
3. **安全**：如 Cloudflare 挡在源站前，可吸收/识别 DDoS，避免「水平扩到破产」或整站打挂。

**常放 CDN 的内容**：JS/CSS/HTML 包、图片、视频、字体；也可缓存**不常变的 API**（商品目录等），配合 **purge / tag 失效**。

---

### 5. 边缘计算（Edge Computing）

传统 CDN = 几乎不计算，按文件名吐静态资源。  
**边缘计算** = 在边缘节点上跑一点逻辑再响应。

经典用例：

- **鉴权前置**：无效会话在东京边缘 2–3ms 返回 401，不必跨洋白跑一趟；源站只接合法流量。  
- **按地区/语言定制**：根据边缘区位与浏览器语言返回对应内容。

**不能把一切搬到边缘**：边缘常依托 ISP 协作节点，RAM/CPU 有限（如 1GB/1 核量级）；Worker 类运行时还有限制（文件系统、TCP 等）。例：Cloudflare Workers 用 V8 Isolate。边缘适合鉴权、路由、轻定制；**不能替代**完整源站。

「Edge」一词：早期指网络边缘的 CDN 节点；现在「edge computing」特指在这些节点上做计算——易混淆，注意语境。

---

### 6. 异步处理：降低「感知延迟」

并非所有操作都必须「用户点完立刻看到最终世界」。

例：邀请同事 → 校验 + 写 invites 表约 100ms；同步调邮件 API 再加 200–300ms → 用户干等约 400ms。可改为：写库后立刻 200，邮件任务丢进 **Redis / RabbitMQ / Kafka** 等队列，由 **Worker** 异步发送。用户感知从 400ms → ~100ms。

适合异步的典型任务（用户不指望下一毫秒看到结果）：

- 发信、站内/推送通知；  
- 视频转码、缩略图、字幕；  
- 大账号删除（多表百万行删除可拖到数秒～数十秒）。

Worker 可与 API 同进程，也可独立部署以便单独水平扩展。识别「可卸队列」是早期就能做的性能手段，不必等用户破万。

（与第 14 课后台任务呼应。）

### 7. 微服务 vs 单体

**单体（Monolith）**：一个可部署单元，认证、订单、支付、通知等同仓同进程（水平扩时是多份同一进程）。开发、测试、重构、部署都简单。

**微服务**：拆成多个可独立部署的服务。课程强调：它首先是**扩团队/组织**，不是「性能银弹」。单体也可水平扩。

| 动机 | 说明 |
|------|------|
| 部署解耦 | 大团队下，支付想发版、通知还没就绪 → 单体易绑死 |
| 独立扩容 | 支付吃 CPU，通知很轻 → 拆开后可只扩支付 |
| 技术栈 | Markdown 要 Node 生态，图片处理要 Go/Rust → 可分服务 |

**代价**：进程内调用变 **HTTP/gRPC 网络**（延迟、超时、重试）；调试需跨服务日志与**分布式追踪**；多库带来一致性与复制延迟。

**何时值得**：大团队（课程量级：百级以上开发者）、清晰边界、独立扩容或异构技术需求明确。优势被复杂度压过时，默认**不要**上微服务。

---

### 8. Serverless

传统：**先买好** VM（固定 CPU/内存/盘），自己管 OS、进程、DNS；要么欠配（尖峰崩），要么过配（白付钱）。Autoscaling 可补，但仍有：

- 启动 OS + 拉代码可能要数秒～数分钟，突发窗口来不及；  
- 最大实例数难设；  
- **反应式**（例如内存过 70% 才扩），不是预测；  
- 仍有**最低常开成本**。

**Serverless**：你只管**函数 + 触发事件**；平台在请求来时拉起执行环境，按实际执行时间计费。典型：API Gateway 路由 → 函数。

**主要坑**：

1. **冷启动（Cold Start）**：首次/空闲后再起的延迟；缓解含预热、Firecracker、V8 Isolate（如 Workers 宣称毫秒级），永远难完全追上常开服务器。  
2. **执行时长上限**（如 Lambda 约 15 分钟）。  
3. **无状态**：长连接、连接池、WebSocket 等要重新设计。

**较合适**：偶发重活（转码、缩图）、队列/上传/DB 变更触发的管道。  
**不太合适**：极低延迟敏感（支付）、长连接、强依赖常驻 DB 连接池却未配 Serverless DB。

Serverless 是工具箱中的一件，不是服务器的万能替代。

---

### 9. 两课合集的心智模型

1. **先有问题再有方案**：先用可观测性（日志/指标/追踪，Prometheus+Grafana 或 New Relic 等）量出瓶颈，再缓存、索引、扩容。  
2. **偏简单**：索引优于盲目 Redis；大单体垂直/水平扩优于过早微服务/K8s；复杂度是成本。  
3. **为当前规模留余量扩**：别第一天按百万用户建；用测量驱动成长。  
4. **可观测性是例外**：应从第一天就有生产级观测，别等用户破万。  
5. **性能是持续心态**：优雅处理故障、快速诊断，而非预测一切。

## 后端规则与最佳实践（Checklist）

- [ ] 决定水平扩之前：会话、文件、缓存、DB 是否已全部外置共享？  
- [ ] LB 算法是否匹配流量形态（均匀轻请求 vs 轻重混杂）？是否配置健康检查？  
- [ ] 读多写少：评估读副本；写后立刻读的路径是否规避复制延迟？  
- [ ] 超大表：是否真需要分片，还是索引/归档/托管分布式库已够？  
- [ ] 静态与准静态内容是否走 CDN？源站是否被 DDoS 裸奔？  
- [ ] 边缘只放轻逻辑（鉴权/路由/本地化），不假装成完整后端？  
- [ ] 发信、转码、大删除等是否已卸到队列？  
- [ ] 微服务：是否有大团队/独立扩容/异构栈的硬理由？网络与追踪成本是否算过？  
- [ ] Serverless：是否接受冷启动与时长限制？是否匹配事件型/偶发重活？  
- [ ] 任何优化前：是否已有延迟/错误/瓶颈的测量数字？

## 常见坑与反模式

1. 多实例仍把 Session/文件写在本机内存或磁盘 → 间歇 401/404。  
2. 无 LB、或实例挂了仍轮询到死节点 → 部分用户持续 5xx。  
3. 开了读副本却「写完立刻读副本」→ 幽灵旧数据。  
4. 没量瓶颈就上分片/微服务/K8s → 过早优化 + 运维地狱。  
5. 把边缘当全能后端 → 撞资源与运行时限制。  
6. 把「能异步」的邮件/转码放在请求关键路径里硬等。  
7. 为「看起来现代」拆微服务，小团队却要扛分布式复杂度。  
8. 全站 Serverless 却要求银行级稳定延迟与长连接。  
9. Autoscaling 最大实例无上限 → 攻击或大促一天账单爆炸。  
10. 只学大厂博客方案，不测自己系统的真实瓶颈。
