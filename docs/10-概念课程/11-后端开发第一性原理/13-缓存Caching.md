# 13. 缓存 Caching

## 一句话直觉

缓存 = 把「热数据的一个子集」放到「更快、更省力」的地方，避免反复做重计算或反复打慢存储——用内存换延迟，用过期与淘汰换正确的新鲜度。

## 本课问题

- 缓存到底在优化什么：时间、算力，还是两者？
- 客户端 / 服务端 / 数据库 / CDN / DNS / CPU L1·L2 各算哪一层？
- Cache-Aside、Write-Through、Write-Behind、Read-Through 怎么选？
- LRU / LFU / TTL 解决「内存装不下」和「数据过期」的哪一面？
- 失效（invalidation）为什么是难题？后端日常怎么用 Redis？

---

## 核心概念详解

### 1. 定义：一句人话 + 一句技术话

**人话**：减少完成某项工作所需的**时间**和**努力**。

**技术话**：根据访问频率、近期性、下次再用的概率等，把**主数据的一个子集**放到**访问更快、代价更小**的位置。

缓存是高性能系统的核心杠杆之一——尤其在延迟以毫秒甚至微秒计的场景。

### 2. 三个直觉例子：何时上缓存？

#### Google 搜索

排索引、排序海量网页极贵。像「今天天气」一天被搜百万次——若每次全量重算，延迟与负载爆炸。

做法：分布式**内存缓存**存查询结果；先查缓存：

- **Cache Hit（命中）**：直接返回  
- **Cache Miss（未命中）**：走完整计算 → 写入缓存 → 返回  

#### Netflix + CDN

一部电影多分辨率（1080p/720p…），全球用户要低缓冲。源站在某区域；世界各地 **Edge（边缘）** 节点缓存**子集**内容（按区域热度/ML 决定），就近播放。

要点：**不能把全部片库塞进每个边缘**——缓存贵且容量小；缓存的是「这个区域最可能看的」。

#### Twitter/X 热搜

实时分析全球推文极贵。热搜不会每秒剧变 → 每隔几分钟算一次，结果进 **Redis 类内存库**，读请求吃缓存。

#### 模式总结

两类高频触发缓存：

1. **重计算**（重复做很贵）  
2. **重数据搬运**（反复传大量数据）  

### 3. 后端常看到的三层缓存

课程把日常相关的缓存粗分为：

| 层级 | 例子 | 你在做什么 |
|------|------|------------|
| **网络层** | CDN、DNS 缓存 | 少跨洋、少反复解析 |
| **硬件层** | CPU L1/L2/L3、RAM | 理解「为何内存快」 |
| **软件层** | Redis、Memcached、应用内 Map | 业务直接读写的缓存 |

软件缓存仍靠硬件（RAM）；叫「软件」是因为你通过库/协议交互。

### 4. 网络层：CDN 与 DNS

#### CDN（Content Delivery Network）

- 内容缓存在**地理上靠近用户**的边缘节点（Edge / PoP）  
- **PoP（Point of Presence）**= 某区域一撮边缘机房  
- 流程直觉：浏览器 → CDN DNS 把请求导到最近 PoP → 边缘查本地缓存  
  - Hit：直接吐内容  
  - Miss：回源（Origin）拉取 → 缓存 → 再返回  
- **TTL（Time To Live）**：内容保留多久；过期后下次强制回源刷新  

静态资源（JS/CSS/图/视频）、Vercel 等 Edge 网络都属此类。

#### DNS 缓存

域名 → IP 的解析链路很长（本机 → 递归解析器 → 根 → TLD → 权威服务器）。**多层缓存**避免每次都「递归到底」：

1. 操作系统 DNS 缓存  
2. 浏览器 DNS 缓存  
3. ISP / 公共 DNS（Google、Cloudflare）递归解析器缓存  
4. （部分）权威侧也有缓存  

DNS 是「缓存救性能」的教科书案例。

### 5. 硬件层：L1 / L2 / L3 与「为何 Redis 快」

CPU 旁有多级缓存：

- **L1**：最小最快，每核私有  
- **L2**：稍大稍慢  
- **L3**：更大，常多核共享  
- 再往外：**RAM（主存）** → **磁盘**  

数组顺序遍历快，部分原因是硬件**预取**把邻近块装进 L1/L2。

**RAM（Random Access Memory）**：

- 靠电信号按地址直接访问 → 几乎与方向无关、远快于机械磁盘寻址  
- **容量有限、易失（掉电清空）**  
- 速度用「非持久 + 小容量」换来的  

**Redis / Memcached** 等：

- 工作集放 **RAM** → 读写极快  
- 持久化靠后台刷盘/快照等机制（进程重启可从盘恢复，但热路径仍走内存）  
- 形态：**内存型 KV NoSQL**——键值简单，不像关系库那样强 schema  

云上对应：**AWS ElastiCache** 等托管内存缓存。

### 6. 客户端缓存 vs 服务端缓存 vs DB 缓存

从「谁持有副本」看：

| 位置 | 例子 | 特点 |
|------|------|------|
| **客户端** | 浏览器 Cache-Control、App 本地、Service Worker | 最近用户、零服务端负载；难统一失效、易脏 |
| **服务端 / 中间层** | Redis、应用进程内 LRU、CDN | 多用户共享；你可控 TTL/失效 |
| **数据库侧** | Postgres shared_buffers、查询结果缓存、物化视图 | 对应用透明；调优偏 DBA；不能替代业务级缓存策略 |

后端工程师日常说的「上缓存」，多半是 **服务端 Redis + 明确的读写策略**；客户端与 DB 内部缓存要知道存在，但策略不同。

### 7. 四大读写策略（必会）

课程重点讲了前两种；后两种是同一家族的常见变体，一并掌握。

#### Cache-Aside（Lazy / 旁路缓存）——课程「懒缓存」

```
读：查缓存 → Hit 返回 → Miss 则读 DB → 写入缓存 → 返回
写：通常先写 DB，再删缓存（或更新缓存）——具体团队约定
```

- **懒**：有人真正请求才装填，不预测预热  
- 最常见、实现简单  
- 风险：写后若只更新 DB 忘了删缓存 → **脏读**  

#### Write-Through（写穿）

```
写：同一次请求里「写 DB + 写缓存」一起完成
读：优先读缓存（通常已是新数据）
```

- 缓存几乎总是鲜的  
- 每次写都有双写开销 → 写路径变慢  

#### Write-Behind / Write-Back（写回）——课程未展开，但生产常见

```
写：先写缓存，立刻返回；异步批量刷到 DB
```

- 写极快、可合并写  
- **风险高**：宕机可能丢未刷盘数据；适合可容忍丢失或有完善 WAL/重试的场景  

#### Read-Through（读穿）

```
读：应用只跟缓存说话；Miss 时由缓存层自己去加载 DB 并回填
```

- 与 Cache-Aside 的差别：**加载逻辑在缓存/库封装内**，应用更薄  
- 常和 Write-Through 搭配成「缓存当门面」  

| 策略 | 读 | 写 | 适用直觉 |
|------|----|----|----------|
| Cache-Aside | 应用管 miss | 应用管失效 | 默认首选 |
| Write-Through | 缓存常新 | 同步双写 | 强一致读、写不多 |
| Write-Behind | 快 | 异步落库 | 写吞吐优先、可接受风险 |
| Read-Through | 缓存代加载 | 视搭配 | 想把加载逻辑下沉 |

### 8. 淘汰与过期：LRU / LFU / TTL

内存装不下「全部真相」——缓存永远是**子集**。满了要**淘汰（eviction）**：

| 策略 | 含义 | 直觉 |
|------|------|------|
| **noeviction** | 满了写入报错 | 一般别当默认 |
| **LRU** Least Recently Used | 踢最久没被访问的 | 「最近都没人看」 |
| **LFU** Least Frequently Used | 踢访问次数最少的 | 「一直很少人看」 |
| **TTL** | 键到点自动失效 | 「这段时间后别信它了」 |

TTL 既是过期策略，也可参与淘汰决策（先踢快到期的等，视实现）。

**失效（Invalidation）** 是著名难题：

- 用户改了资料 → 必须删/更新对应缓存键，否则读到旧资料  
- TTL 是「懒安全网」：最坏 N 分钟后自然过期  
- 主动失效更即时，但键设计要清晰（按 userId、按查询哈希等）  

口诀：**读多写少、变化不剧烈** → 适合缓存（商品详情、明星主页、天气、热搜）。

### 9. L1 / L2 在业务里的说法

硬件有 L1/L2；业务上也常说**多级缓存**：

| 层级 | 常见实现 | 特点 |
|------|----------|------|
| **L1** | 进程内（本地 Map、Caffeine、语言级 LRU） | 最快、无网络；多实例各自一份 → 一致性难 |
| **L2** | Redis / Memcached 集群 | 跨实例共享；多一跳网络 |

典型路径：先 L1 → miss 再 L2 → 再 miss 打 DB。CDN 相对源站也可看成「更外层的 L」。

### 10. Redis 在后端的四大刚需场景

#### （1）DB 查询结果缓存

重 JOIN + 聚合、仪表盘高频打——结果 TTL 一小时；写路径手动删键。减轻 DB、降 API 延迟。电商大促时商品详情/价格常缓存。

#### （2）Session 存储

登录后 session token 放 Redis：每请求校验远快于打关系库，也减轻 DB。

#### （3）外部 API 响应缓存

天气等非秒级变化数据：缓存 1 小时，避免打爆第三方额度/账单。

#### （4）限流计数器

中间件读 `X-Forwarded-For`（或等价）→ Redis 里按 IP+时间窗自增 → 超限返回 **429 Too Many Requests**。  
若用 Postgres 做限流：每请求一次 DB + 延迟与负载双杀——故限流几乎总用内存库。

### 11. 与第 12 课的衔接

| 数据库（磁盘） | 缓存（内存） |
|----------------|--------------|
| 容量大、便宜、持久 | 容量小、贵、快、易失 |
| 真相与约束 | 性能与体验 |
| 不能用缓存「替代」库 | 不能把全库塞进缓存 |

## 常见坑

1. **缓存一切** → 成本爆炸，且命中率未必高  
2. **只写 DB 不失效缓存** → 长时间脏数据  
3. **无 TTL 又无淘汰** → 内存打满；或 noeviction 直接写失败  
4. **把缓存当真相** → 重启/驱逐后逻辑崩坏；应用应能回源  
5. **缓存穿透**：故意查不存在的键狂打 DB → 需空值缓存/布隆等（进阶）  
6. **热点 Key**：单键打爆 → 本地 L1 或拆键  
7. **限流计数放关系库** → 延迟与连接池双杀  
8. **TTL 过长**：业务已变用户仍看旧价
