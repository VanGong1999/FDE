# 15. Elasticsearch 全文检索

## 一句话直觉

`LIKE '%laptop%'` 是图书管理员一本本翻书；**倒排索引**是先建「词 → 出现在哪些文档」的目录——Elasticsearch（基于 Lucene）用它做到毫秒级相关搜索，并用 BM25 等把「更相关」排在前面。

## 本课问题

- 为什么商品一多，`ILIKE` 就从 50ms 变成 30 秒？
- 倒排索引如何把「扫文档找词」翻成「扫词找文档」？
- BM25 / 相关度 / 字段加权是什么直觉？
- Fuzzy（容错拼写）解决什么？分片又解决什么？
- 何时用 Postgres 全文检索，何时上 Elasticsearch？

---

## 核心概念详解

### 1. 故事：2005 年电商工程师的噩梦

起初：五千商品，

```sql
SELECT * FROM products
WHERE name ILIKE '%laptop%' OR description ILIKE '%laptop%';
```

约 50ms，岁月静好。

公司膨胀到**百万级**商品后：同样查询 → **几十秒**；老板还要：

1. **更快**  
2. **更聪明**：搜 laptop 应先出 MacBook，而不是电脑包  
3. **容错**：用户打成 `lapotp` 仍要出结果  

这就是全文检索引擎（含 Elasticsearch）出现的产品动机。

### 2. Postgres/`LIKE` 的「图书管理员」隐喻

关系库像一位**知道每本书在哪、但只能一本本翻**的管理员：

- 问「机器学习」→ 从第一本 Harry Potter 扫到最后一本  
- **无相关度**：书名《机器学习导论》与末页偶然出现「机器学习」的小说，顺序随意  
- SQL `ILIKE '%…%'` ≈ 对每一行、每个文本字段做**逐字符模式匹配**——彻底、但慢，且**不排序相关性**

数据爆炸年代（Google 网页、Amazon 目录、LinkedIn 档案），**30 秒不可接受**；今天连 2 秒都嫌长，搜索要在**毫秒**级。

### 3. 关键发明：倒排索引（Inverted Index）

旧思路：文档 → 找词（正排）。  
新思路：**词 → 找文档**（倒排）。

入库时（书上架时）就切词建目录，例如：

| 词 | 出现位置（文档 + 页/偏移） |
|----|---------------------------|
| machine | 《ML 导论》p1,15,23；《机器时代》p5,89；《咖啡机手册》p1 |
| learning | 《ML 导论》…；《学做饭》…；《深度学习基础》… |

查询「machine learning」→ 查目录取交集/合并 → **不必扫全库正文**。

这就是 **inverted index**：把「从内容找词」**倒过来**成「从词找内容」。

### 4. Lucene 与 Elasticsearch 的关系

- **Apache Lucene**：倒排索引为核心的搜索库  
- **Elasticsearch**：在 Lucene 之上的分布式搜索引擎（还有 OpenSearch 等亲戚）  
- 现代 **Postgres 也有全文检索**（`tsvector`/`tsquery` 等）——ES 不是唯一选项  

课程态度：日常后端**不必先啃完评分公式再写业务**；知道场景、会查文档、会调 DSL 往往就够。DB 知识要深，ES 多数场景「会用」即可。

### 5. 相关度：为什么结果顺序突然「懂事」了？

倒排解决「快」；**相关度评分**解决「好」。

直觉加分项（课程举例）：

- 词出现在**标题** → 大幅加分（相对正文末尾一次提及）  
- **词频（TF）**：同一文档里出现次数多 → 更相关（有饱和，不是无限加）  
- 跨库稀有词比烂大街的词更有区分度（见下 IDF）  

于是《机器学习导论》会排在「末页提了一句 ML」的书前面。

### 6. BM25 算法（当作可调工具）

Elasticsearch 默认常用 **BM25** 做相关度。把它当「带旋钮的打分器」即可：

| 因素 | 直觉 |
|------|------|
| **Term Frequency** | 词在**本篇**出现多不多 |
| **Document Frequency / IDF** | 词在**全集**里稀不稀有（太常见则区分度低） |
| **Document Length** | 超长文档「偶然多次出现」要打折，避免长文霸榜 |
| **Field Boosting** | 标题 > 摘要 > 正文（可自定义） |

查询用 **JSON DSL** 声明：哪些字段、什么权重、什么查询类型。不必手写公式，但要会调 boost。

ES 里一条可检索记录常叫 **document**（类 JSON，有点像 Mongo 文档）。

### 7. Fuzzy / 拼写容错

用户搜 `what is treading today`（本意 trending）——好的全文引擎仍能猜到意图。

- **Fuzzy query**：允许编辑距离（插删改若干字符）内的近似匹配  
- Type-ahead（输入建议）也常建在同类能力上  

这是 `LIKE` 几乎给不了、而搜索引擎标配的体验。

### 8. 分片（Sharding）直觉

单机倒排索引再快，也会撞上**数据量与 QPS 上限**。Elasticsearch 把一个索引拆成多个 **shard（分片）**：

| 概念 | 直觉 |
|------|------|
| **主分片（primary）** | 数据的一份分区；写入落到某主分片 |
| **副本分片（replica）** | 主分片的拷贝；分担读、提供冗余 |
| 查询 | 常在多分片上并行搜，再在协调节点合并/排序 |

类比：把大图书馆拆成多个分馆，各管一部分书的「词目录」，问询时分馆一起查再汇总。

后端选型时：数据量小可少分片；预估增长与节点数，避免过度分片（开销大）。课程 demo 用云上单集群即可，生产要单独规划分片与副本。

### 9. 与 Postgres 对比：怎么选？

| | Postgres `ILIKE` / 内置 FTS | Elasticsearch |
|--|------------------------------|---------------|
| 简单子串匹配 | 有，大数据量很慢 | 不靠这个 |
| 倒排 + 相关度 | FTS 有；生态与调优曲线不同 | 强项，DSL 丰富 |
| 拼写容错 / 复杂搜索体验 | 较弱或要扩展 | 强 |
| 运维 | 已有库，零新组件 | 多一个集群（或云服务） |
| 日志分析 | 一般不当主方案 | **ELK**（Elasticsearch + Logstash + Kibana）经典栈 |

**实用决策（课程）：**

- 公司**已有 ES**（例如 ELK 管日志）→ 业务搜索也用 ES 很自然  
- 只有 Postgres、搜索需求中等 → **先试 Postgres 全文检索**  
- 要强相关度、纠错、大规模类型ahead → 倾向 ES  

### 10. 课程 Demo 结论（量级直觉）

同一批约 **5 万** 条评论：

- Neon Postgres：`ILIKE '%term%'` → 常 **数秒级**（示例中出现 ~3s、甚至 ~7.5s）  
- Elastic Cloud 同区域：常 **约 0.5–1s**（仍含网络；相对 DB 子串扫已明显更快）  

公平起见：同区域、同数据、流式返回以免互相拖慢。结论不是「永远抛弃 Postgres」，而是：**子串扫不是搜索架构**。

字段映射直觉：`text` 做分词全文；`keyword` 做精确匹配（如 sentiment 标签）。

### 11. 后端工程师的定位

- **数据库**：必须深入（索引、事务、执行计划……占日常代码绝大部分）  
- **ES**：多数 CRUD 搜索场景，文档 + 示例 + LLM 辅助足够起步；要极致再深挖分片、分析器、相关性调参

## 常见坑

1. **用 `LIKE '%x%'` 硬撑到百万行** → 全表/大范围扫描，索引也帮不上前导通配  
2. **以为「匹配到」就够** → 无排序相关度，转化率差  
3. **为小项目强上 ES 集群** → 运维成本高于收益；先评估 Postgres FTS  
4. **ES 与 DB 双写不一致** → 搜索到已删商品；需同步策略（双写、CDC、定期重建）  
5. **过度分片** → 小数据很多小分片，浪费内存与合并成本  
6. **把 ES 当主数据库** → 缺事务与强约束；真相仍应在业务库
