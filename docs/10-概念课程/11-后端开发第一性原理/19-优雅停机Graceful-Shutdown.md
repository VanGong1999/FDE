# 19. 优雅停机（Graceful Shutdown）

## 一句话直觉

服务器要下线时不能「摔门走人」：先停接待新客，让屋里人吃完饭结账，再关灯锁门——否则支付可能丢单、双扣或数据损坏。

## 本课问题

- 滚动发布 / 扩缩容时，旧进程必须退出的那一刻，进行中的请求怎么办？
- OS 如何用信号（signal）与进程对话？SIGTERM / SIGINT / SIGKILL 区别？
- Connection draining 三步是什么？超时如何定？
- 资源清理按什么顺序？HTTP、DB、WebSocket、后台任务各要注意什么？
- 与 K8s、负载均衡、健康检查如何配合？

---

## 核心概念详解

### 1. 现实场景：发布瞬间的支付请求

零停机部署能保证「新实例 ready 前旧实例不完全消失」，但**最终旧实例必须停**。若此时正在处理关键支付：

- 请求是否丢失？
- 会否竞态导致**双扣**？
- 退款与对账噩梦？

后端必须思考这些问题。业界方案就是 **Graceful Shutdown（优雅停机）**：教服务器「有礼貌地离开」。

比喻：客人还在家里时，不会到点就推出门再摔门；要结束对话、让客人走、收拾好，再关门。

收益：更好的用户体验，减少数据损坏、双扣、事务丢失。

### 2. 进程生命周期（Process Lifecycle）

后端在 OS 里以 **进程（process）** 运行。进程有生命周期：启动（出生）→ 运行（活着）→ 终止（死亡）。

优雅停机紧扣「如何结束」。OS **不会**直接拔电源式杀进程（除非走到 SIGKILL）；而是按协议沟通：

- OS：「该停了」
- 应用：「给我几秒，我收拾完再走」

沟通媒介就是 **信号（signals）**。

### 3. 信号（Signals）——Unix/Linux（及 macOS）的 IPC

服务器上 99% 情况是 Linux。信号是进程间通信（IPC）机制之一。应用**注册 handler**：收到特定信号时执行预定义清理与退出逻辑。

#### 3.1 SIGTERM（terminate）——礼貌请求

- 含义：请你尽快收尾并离开（轻推肩膀，不是立刻击倒）。
- 应用有窗口去：完成手头工作 → 清理资源 → 退出。
- **谁发**：部署系统、进程管理器、编排平台——**Kubernetes**、systemd、**PM2** 等。

收到 SIGTERM 后高层步骤：

1. **Finish existing / in-flight requests**
2. **Clean up resources**
3. **Exit**

#### 3.2 SIGINT（interrupt）——常由 Ctrl+C

- 开发者在终端按 **Ctrl+C** 触发。
- 多为**用户发起**的本地停机。
- **处理方式应与 SIGTERM 相同**：意图都是「要干净地停」，无论人还是程序发起。

#### 3.3 SIGKILL（kill）——无法捕获的「拔电源」

- **不能被 catch，也不能被 ignore**。
- 应用来不及清理，瞬间死掉。
- 比喻：不点关机，直接拔插头。

若你不尊重 SIGTERM/SIGINT，编排器最终会 **SIGKILL**——优雅停机窗口被剥夺，in-flight 请求与资源清理全部落空。所以优雅停机的核心是：**认真响应礼貌信号，在 deadline 内完成 draining**。

### 4. Connection Draining（连接排空）——餐厅打烊隐喻

餐厅要打烊时：

1. **门口不再放进新客人**
2. **告知已在用餐的客人**：还有 15–20 分钟吃完、结账、离开
3. 然后真正关门

后端同理，收到停机信号后：

1. **停止接受新连接 / 新请求**（别再往摊子上加活）
2. **让已在处理的 in-flight（on-the-fly）请求做完**
3. **关闭连接并退出**

不同架构细节不同，原则相同：

| 类型 | 优雅行为 |
|------|----------|
| **HTTP 后端** | 停收新 HTTP；等 in-flight 完成 |
| **数据库进程** | 停新查询/事务；完成已有；再关连接 |
| **WebSocket** | 先通知客户端将关闭，再关 socket（不可突然掐断） |

#### 超时（Timeout）——硬限制

不能无限等。生产常见 **30s**（也有 60s，视业务）。超时后强制结束（最终可能仍落到 SIGKILL）。

超时设计权衡：

- **太短**：打断合法长请求
- **太长**：发布变慢、系统迟钝

依据：**典型请求耗时** + 运维要求。普通 API 30s 往往够；WebSocket / 长任务要单独评估。

#### 与负载均衡 / 服务发现 / 健康检查的协调

Connection draining 还需要与 **LB、服务发现注册/注销、健康检查** 协调：实例准备下线时应尽快从流量池摘掉，避免新请求仍打来。（课程点到：属进阶，与 K8s readiness 等配合。）

**K8s / 滚动发布场景（串联理解）**：

1. 新 Pod Ready，开始接流量
2. 旧 Pod 收到 **SIGTERM**
3. 旧 Pod：失败就绪 / 注销服务发现 → **停收新请求** → 等 in-flight（在 `terminationGracePeriodSeconds` 内）→ 关 DB/Redis 等 → 退出
4. 若超时未退 → **SIGKILL**

因此：应用内 graceful shutdown 超时应 **小于** 平台给的强制杀死宽限，并留余量。

### 5. 资源清理（Resource Cleanup）

「资源」= 运行期占用的系统对象，例如：

- 文件句柄（file handles）
- 网络连接
- 数据库连接 / 连接池
- 临时文件、缓存
- 其它系统资源

不清理 → 句柄与连接泄漏 → 内存与 FD 耗尽、性能劣化。

**数据库**：停机前事务应 **显式 commit 或 rollback**，否则可能不一致、死锁、损坏风险。

**清理顺序：按获取资源的逆序释放**

例：先连了 Redis，再连 DB → 关闭时先关 DB，再关 Redis（或按依赖：先停依赖上层的服务，再关底层连接）。避免「还在用的依赖已被关掉」。

### 6. 代码层直觉（语言无关）

典型框架流程（课程用 Go 演示，概念通用）：

1. 注册监听 **SIGINT / SIGTERM** 的 handler
2. 触发后调用 shutdown：
   - 先 **HTTP Server Shutdown**：框架内部停接收、排空已有连接
   - 再 **关闭 DB**：停新查询、完成进行中、关闭池内 TCP 连接
   - 再关 **后台任务 / Redis**（如 async 队列 workers 优雅退出）
3. 打日志：收到信号 → 各组件关闭 → 「server exited」

本地 Ctrl+C 即使无 in-flight，也可能看到约 1 秒量级的有序关闭日志——说明走了完整流程而非瞬间崩。

多数语言/框架有现成 API（复制官方示例即可），但**必须理解发生了什么、为何重要**。

## Checklist

- [ ] 同时处理 SIGTERM 与 SIGINT，逻辑一致
- [ ] 停收新请求 → 完成 in-flight → 逆序释放资源 → 退出
- [ ] 设置合理 shutdown timeout；与 K8s `terminationGracePeriodSeconds` 对齐
- [ ] DB 事务有明确提交/回滚；连接池被关闭
- [ ] WebSocket / 长连接有「即将关闭」通知
- [ ] 后台 worker 等待当前任务结束再退
- [ ] 滚动发布时配合 readiness：先摘流量再 SIGTERM 排空
- [ ] 关闭过程有结构化日志，便于确认是否「优雅」

## 常见坑

1. **忽略信号**：最终被 SIGKILL，支付/写库半截。
2. **只停 HTTP、忘关 DB/Redis**：连接泄漏或事务悬挂。
3. **清理顺序错误**：先关 DB 还在刷缓存 → 报错风暴。
4. **超时与 K8s 宽限不匹配**：平台已 SIGKILL，应用还以为自己在 draining。
5. **LB 仍打旧实例**：未先失败健康检查 / 未注销服务发现。
6. **WebSocket 直接掐断**：客户端体验差、状态不一致。
