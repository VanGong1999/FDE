# 09 · 校验与转换（Validation）

一句话直觉：客户端发来的一切都不可信——在跑业务、碰数据库之前，先用**校验**确认「形状对不对、说不说得通」，用**转换**把数据收成服务器好用的干净形态。

## 本课要解决什么问题

API 设计不只是路由和业务逻辑，还关乎**数据完整性与安全**。本课回答：

1. 校验发生在架构的哪一层、请求生命周期的哪一刻？
2. 语法 / 语义 / 类型校验分别管什么？
3. 为何「前端校验了」也不能省服务端校验？
4. 转换（transformation）、归一化、消毒如何与校验配合？
5. 关系/条件校验、错误如何聚合、哪些信息不能回给客户端？

## 核心概念详解

### 1. 分层回顾：Repository → Service → Controller

典型后端分层（与第 10 课一致）：

| 层 | 职责直觉 |
|----|----------|
| **Repository** | 数据库连接、查询、增删改；持久化细节 |
| **Service** | 业务逻辑编排：调多个 repo、发邮件、通知、webhook… |
| **Controller / Handler** | HTTP 边界：状态码、响应格式、**入参校验与转换**；再调 Service |

为何拆 Controller 与 Service：把「HTTP 相关」（状态码、序列化形态、校验）与「纯业务」分开，便于测试与复用。

一次调用简化路径：

```
请求 → 路由匹配 → Controller
         →（校验 + 转换）
         → Service →（可选）Repository
         → 数据回到 Controller → HTTP 响应
```

### 2. 校验发生在哪里

**理想位置：** 路由已匹配到对应 Controller 方法之后、**执行任何显著业务逻辑 / 调 Service / 碰库之前**。

校验对象包括客户端带来的一切：

- JSON Body
- Query 参数
- Path 参数
- 相关 Headers（若业务依赖）

做法：可复用的校验中间件/工具 + **针对该 API 的 schema**，逐字段检查。

### 3. 为何必须在入口校验（反例）

假设创建书籍需要 `name: string`（长度 5–100）。若跳过校验：

1. 客户端发 `name: 0`（数字）。
2. 数据一路落到 Repository 的 INSERT。
3. PostgreSQL 列类型是 `text NOT NULL` → 类型不符 → 查询失败。
4. 若错误处理粗糙 → 客户端收到 **500 Internal Server Error**（「服务器出问题了」）。

对用户这是极差体验；对你这是把**客户端错误**伪装成**服务器故障**。

正确做法：入口发现不符 → **400 Bad Request**，明确告知约束未满足，**绝不进入**「意外状态」弄崩系统。

### 4. 三类常见校验

课程强调：分类不是教条，而是设计 API 时的检查清单。

#### 4.1 语法校验（Syntactic）

数据是否符合**约定结构/格式**。

| 例子 | 在查什么 |
|------|----------|
| Email | 是否像 `local@domain.tld` |
| 电话 | 国家码 + 位数等模式 |
| 日期字符串 | 是否匹配 `YYYY-MM-DD` 等约定格式 |

Demo 直觉：空 Body → 「email / phone / date 均为必填」；乱填 email → invalid format；phone 传数字而非字符串 → 类型/格式错误。修好后 → 200。

#### 4.2 语义校验（Semantic）

格式对了，**意思通不通**。

| 例子 | 为何拒绝 |
|------|----------|
| 出生日期在未来 | 人生理上不成立 |
| age = 365 或 430 | 超出合理人类年龄（如 1–120） |

语义规则来自业务与常识，随产品演进可调。

#### 4.3 类型校验（Type）

字段是否为期望的 JSON/本地类型：string、number、boolean、array、object；数组元素也可再约束（如「必须全是 string」）。

### 5. 关系校验与条件校验（Complex）

真实表单不止单字段：

1. **字段相等关系**：`password` 与 `passwordConfirmation` 必须一致；密码还可能有最小长度（如 ≥ 8）。
2. **条件必填**：`married === true` 时必须提供 `partner`（配偶名）；`married === false` 时 `partner` 可选。

这些是**跨字段 / 依赖条件**的约束，校验管道必须支持「看完 A 再决定 B」。

### 6. 转换（Transformation）、归一化与消毒

#### 6.1 校验 vs 转换

- **校验**：确认是否满足约束；失败则 400。
- **转换**：在校验前/后对数据做**改写**，变成下游期望形态。

常放在同一「校验与转换管道」，避免规则散落各处。

#### 6.2 典型场景：Query 参数永远是字符串

`GET /bookmarks?page=2&limit=20` 里，`page`/`limit` 到达服务器时**类型是 string**（HTTP 查询串的本性）。

若 schema 写「必须是 number 且 0 < page < 500」，却不做转换 → 会误报「期望 number 收到 string」。

**正确：** 先 **cast**（`string → number`），再做数值范围校验。这是服务器责任，不是客户端「发错了」。

也可在校验**之后**再转换，把数据收成 Service 最省事的形状。

#### 6.3 归一化例子（课程 Demo）

客户端乱写大小写的 email、电话无 `+`、日期某格式 → 服务器在管道中：

- email → 全小写；
- phone → 补上 `+`；
- date → 统一成内部格式。

再交给 Service。这叫**归一化（normalization）**：同一语义只保留一种权威表示。

#### 6.4 消毒（Sanitization）意识

校验通过仍可能含危险字符（HTML/脚本片段用于富文本等）。按用途：

- 存库前消毒或编码；
- 输出到 HTML 时编码（防 XSS）；
- 永不把未消毒字符串拼进 SQL（用参数化查询）。

消毒是安全卫生；与「格式校验」互补，不是替代。

### 7. 错误聚合与信息脱敏

#### 7.1 错误聚合

一次请求多个字段都不对时，**一次返回所有错误**（数组），而不是修一个再试一个。好处：

- UX 更好；
- 空 Body 时错误列表本身像「迷你文档」，提示 API 期望哪些字段（文档缺失时尤其有用）。

#### 7.2 信息脱敏与边界

| 可以较具体（业务校验） | 必须笼统（见第 8 课认证） |
|------------------------|---------------------------|
| 「email 格式无效」「年龄须 ≤ 120」 | 「Authentication failed」 |
| 「密码至少 8 位」「passwords don't match」 | 不暗示用户是否存在 |

另外：**不要**在 400/500 里返回堆栈、SQL、内部路径、密钥。对客户端给**稳定错误码 + 可读 message**；细节留在服务端日志。

### 8. 前端校验 vs 后端校验（关键铁律）

| | 前端校验 | 后端校验 |
|--|----------|----------|
| 目的 | **UX**：即时反馈，少一次往返 | **安全与数据完整性** |
| 可否省略 | 可弱化（体验变差） | **不可省略** |
| 攻击面 | 可被绕过（改请求、用 Postman） | 最后一道关 |

服务器可能被多种客户端调用：精致 Web 表单、Insomnia/Postman、其他后端、移动 App。若后端「信任前端已经验过」→ 换客户端即崩溃或被灌脏数据。

**设计原则：服务端校验尽可能严格、具体；完全不依赖客户端校验长什么样。**

两者协作 Demo：前端先拦无效 email → 不发请求；通过后再发 → 后端再验一遍 → 200。

### 9. 严格程度如何把握

校验可以很松或很紧，取决于业务。清单思维：

- 必填哪些？
- 类型与格式？
- 长度/范围/枚举？
- 跨字段与条件？
- 默认值与转换？
- 错误如何聚合、文案如何对外？

## 后端规则与最佳实践（Checklist）

- [ ] 所有外部输入（body/query/path/关键 header）进入业务前必经校验。
- [ ] 失败返回 **400**（或约定的 422），不是 500。
- [ ] Query 字符串先转换类型再验数值约束。
- [ ] 列表类参数设合理上下限（防 `limit=1000000`）。
- [ ] 多字段错误一次返回；认证相关错误单独走笼统策略。
- [ ] 转换/默认值/归一化集中在管道，Service 拿到的已是干净数据。
- [ ] 前后端都可验，但**以后端为准**。
- [ ] 对 HTML/脚本场景做消毒；SQL 用参数绑定。
- [ ] Schema 与 OpenAPI 文档同步，减少「靠报错猜字段」。

## 常见坑与反模式

| 反模式 | 后果 | 纠正 |
|--------|------|------|
| 只做前端校验 | 任意客户端灌脏数据 / 500 | 服务端强制 schema |
| 校验散落在 Service/Repo | 遗漏路径、难维护 | 入口统一管道 |
| Query 当 number 却不 cast | 误杀合法请求 | 先转换再校验 |
| 一次只报一个错 | 来回试错成本高 | 错误聚合 |
| 校验错误泄露内部实现 | 助攻攻击者 | 脱敏 + 稳定 code |
| 把「格式对」当成「业务对」 | 未来生日入库 | 补语义校验 |
| 无限信任嵌套深度/数组长 | DoS | 限制大小与深度 |
