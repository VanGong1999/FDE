# 07 · 序列化与反序列化

一句话直觉：客户端和服务器说的是不同「方言」（JS 对象 vs Rust struct），网络上只能传比特——序列化就是双方约定一种**通用中间格式**，发出前「打包」、收到后「拆包」。

## 本课要解决什么问题

前端（常为 JavaScript）与后端（可能是 Go / Rust / Python / Node）**数据类型完全不同**：一边动态、一边严格编译。两边却要通过 HTTP / gRPC / WebSocket 交换业务数据。

核心问题：

1. 机器 A 上的内存结构，如何变成可在网络上传输的字节流？
2. 机器 B 如何把字节流还原成自己语言能理解的数据结构，再跑业务逻辑、再回传？
3. 为什么需要「共同标准」，而不是各自随意发二进制？

本课答案：**序列化（Serialization）** = 把本语言数据 → 共同格式；**反序列化（Deserialization）** = 共同格式 → 本语言数据。整条往返合在一起，就是客户端与服务器「看得懂彼此」的基础。

> 课程提醒：后端领域技术极多（协议、数据库、序列化格式各有一堆）。学习策略是先精通**业界最常用的一条路径**（HTTP + REST + JSON + 如 PostgreSQL），再按需扩展。

## 核心概念详解

### 1. 客户端—服务器与传输通道

典型模型：

- **Client（前端）**：浏览器里的 React / Vue / Angular 等 JS 应用。
- **Server（后端）**：本机或云上（AWS / GCP / Azure）的进程。
- **通信方式**：HTTP（传统 REST）、gRPC、WebSocket 等。本系列主线是 **HTTP / REST**。

HTTP 请求大致结构：方法 + URL、Headers、（可选）Body。响应同理。本课聚焦：**Body 里的数据双方如何「看懂」**。

### 2. 为什么需要共同标准（语言无关）

假设 JS 发 `{ name: "..." }`，Rust 服务器要收到后变成 `struct`。若没有约定：

- JS 的 number / string / object 与 Rust 的 `i64` / `String` / `struct` 无法直接对应；
- 网络只懂比特，不懂「对象」。

解决方案（思想实验 → 工业实践）：

1. 双方**事先约定**一种格式规则（标准）。
2. 发送方：本语言数据 → **序列化**为该格式 → 上网络。
3. 接收方：从网络拿到该格式 → **反序列化**为本语言类型 → 跑业务。
4. 回响应时再反向做一遍。

因此：**序列化/反序列化 = 在传输（或存储）时，在「领域/语言专用表示」与「共同标准」之间来回转换**，目标是**跨语言、跨环境可理解**。

### 3. OSI 心智模型（后端工程师要关心哪一层）

OSI 有多层（应用层 ↔ … ↔ 物理层）。数据会变成帧、IP 包、最终 0/1 与电信号/光信号。

**后端工程师的心智模型：**

- 你负责的是**应用层**上的「共同格式」（如 JSON）。
- 中间层怎么拆包、怎么变成比特，**不是日常职责**。
- 服务器侧最终又会把比特还原成同一应用层格式；你只读/写 JSON（或选定的其他格式）。

### 4. 序列化标准家族：文本 vs 二进制

| 类别 | 常见格式 | 特点 |
|------|----------|------|
| **文本型** | JSON、XML、YAML | 人类可读；调试友好；体积相对大 |
| **二进制型** | Protobuf、Avro、MessagePack 等 | 更紧凑、解析更快；需 schema / 代码生成；对人不可直接读 |

本系列 HTTP REST 主路径选 **JSON**（课程估计日常约八成场景）。其他格式在配置、日志、服务间 RPC 等场景同样常见。

### 5. JSON 详解（本课主格式）

**JSON = JavaScript Object Notation**，外观像 JS 对象，但**不限于 JS**：配置文件、REST Body、结构化日志等都大量使用。

**基本规则（必须记住）：**

- 整体用 `{ }` 包住对象；数组用 `[ ]`。
- **键必须是双引号字符串**；不能用数字/布尔当键。
- 值可以是：字符串、数字、布尔、`null`、数组、**嵌套对象**。
- 嵌套对象同样遵守「键双引号 + 上述值类型」。

示例直觉：

```json
{
  "id": 1,
  "title": "Book",
  "author": "Alice",
  "address": {
    "country": "India",
    "phone": 3456
  }
}
```

**优点：** 人类可读、生态巨大、与前端天然亲近。  
**代价：** 体积与解析成本高于二进制格式；类型表达能力有限（见下文坑）。

### 6. JSON / XML vs Protobuf（选型直觉）

| 维度 | JSON | XML | Protobuf |
|------|------|-----|----------|
| 可读性 | 高 | 中（冗长） | 低（二进制） |
| 体积/速度 | 一般 | 通常更大 | 通常更优 |
| Schema | 可选（JSON Schema） | XSD 等 | **强制 `.proto`** |
| 典型场景 | 公网 REST、前后端 | 遗留企业集成、部分 SOAP | 内部微服务、gRPC |
| 互操作 | 几乎所有语言都有库 | 广泛但偏「企业」 | 需生成代码；跨语言仍强 |

**互操作性（Interoperability）要点：**

- 「能互操作」≠「随便发」。双方必须对**同一 schema / 同一字段语义**达成一致。
- JSON 靠约定字段名与类型；Protobuf 靠 `.proto` 与字段编号；XML 靠标签与命名空间。
- 换格式通常要同时改：客户端库、服务端编解码、文档、版本策略。

**粗略选型：**

- 对外公开 REST、浏览器客户端 → **JSON** 默认首选。
- 高 QPS 内部 RPC、强契约演进 → 认真评估 **Protobuf + gRPC**。
- 对接只认 XML 的老系统 → 保留 XML 适配层，内部仍可 JSON/Proto。

### 7. 嵌套结构

JSON（及多数格式）允许任意深度嵌套：订单里有用户、用户里有地址、地址里有坐标……

规则：

- 嵌套层仍是同一套类型规则。
- 反序列化时，目标语言类型要能**一一映射**嵌套（如 Go struct 嵌套、TS interface 嵌套）。
- 过深嵌套会加重解析成本与认知负担；API 设计上常「拍平」或拆资源（见第 11 课资源导向）。

### 8. `null`、日期与时区（极易踩坑）

序列化格式往往**没有**「日期类型」——JSON 只有 string / number / bool / null / object / array。

| 问题 | 说明 | 实践建议 |
|------|------|----------|
| **`null` vs 缺字段** | `{"a": null}` 与 `{}` 语义不同；有的语言映射成 `Optional`，有的直接报错 | 文档写清；校验层明确「必填 / 可空 / 可省略」 |
| **日期** | 常存 ISO-8601 字符串，如 `"2025-11-05T01:11:00Z"` | **统一一种字符串约定**；禁止各端各写一套 |
| **时区** | `"2025-11-05"` 无时区；本地时间与 UTC 混用会导致「差一天」 | 存储与传输优先 **UTC**；展示层再转用户时区 |
| **数字精度** | JS `Number` 是 IEEE 双精度；大整数可能丢精度 | 大 ID / 金额用**字符串**或专用 decimal 约定 |
| **布尔** | 有人发 `"true"` 字符串 | 校验层拒绝；或明确转换规则（见第 9 课） |

Protobuf 等有更明确的标量类型与 `google.protobuf.Timestamp`，仍要在业务层约定时区语义。

### 9. Schema 校验

「能 parse 成 JSON」≠「是业务要的数据」。

推荐分层：

1. **语法层**：是不是合法 JSON / 合法 XML / 合法 Protobuf 二进制。
2. **Schema 层**：字段是否存在、类型是否匹配、枚举是否合法、嵌套是否符合约定（JSON Schema、OpenAPI、`.proto`、XSD）。
3. **业务语义层**：生日不能在未来、年龄不能 365（见第 9 课）。

**原则：反序列化成功之后、业务逻辑之前，做 schema / 校验。** 校验失败返回 **400 Bad Request**，不要拖到数据库层才炸出 **500**。

### 10. 安全：反序列化前（与紧随其后）的校验

反序列化是攻击面：

- **过大 payload**：故意发超大 JSON → CPU/内存打满 → 限大小、超时。
- **过深嵌套 / 巨型数组**：解析器递归或分配爆炸 → 限制深度与元素个数。
- **类型混淆**：该要对象却给数组；或给意外字段（若框架「自动绑定到对象」可能覆盖敏感属性——取决于语言/框架，需配置白名单或显式 DTO）。
- **不可信数据**：永远假设 Body/Query/Header **来自不可信客户端**；先校验再入库、再拼 SQL、再当命令执行。
- **不要把反序列化结果直接当可信身份**：用户 ID、角色等应从认证上下文取，而不是盲信客户端 JSON（见第 8、10 课）。

口诀：**先校验，再信任；先限流限大小，再 parse；parse 后仍要 schema + 语义校验。**

### 11. 真实请求流（课程演示直觉）

以 `POST /api/books` 为例：

1. 客户端发 JSON：`{ "id", "title", "author" }`。
2. 经网络各层，服务器应用层再次得到 JSON。
3. 服务器反序列化 → 写入业务结构 → 可能追加到列表。
4. 响应再序列化为 JSON（例如 `{ "books": [ {...}, ... ] }`）。
5. 客户端反序列化并渲染 UI。

整段往返，就是序列化与反序列化在真实系统中的样子——概念不多，但**无处不在**。

## 后端规则与最佳实践（Checklist）

- [ ] 团队明确：**对外默认 JSON**；内部 RPC 是否上 Protobuf 单独决策并写进规范。
- [ ] 文档（或 OpenAPI）写清每个字段的类型、是否可空、日期格式与时区。
- [ ] Content-Type 与实际 Body 一致（如 `application/json`）。
- [ ] 反序列化失败 → **400**，并返回可行动的错误信息（勿堆栈泄露）。
- [ ] 限制 Body 大小、JSON 深度、数组长度。
- [ ] 嵌套 DTO 与领域模型分离；不要把 ORM 实体直接暴露给客户端。
- [ ] 大整数 / 金额 / 高精度：避免裸 JS number 来回传。
- [ ] 日志里的结构化数据也可用 JSON，但**脱敏**（密码、token、PII）。
- [ ] 变更字段时做**向后兼容**（加可选字段易；删改字段难）——二进制 schema 更要版本策略。

## 常见坑与反模式

| 反模式 | 为何糟 | 更好做法 |
|--------|--------|----------|
| 假定「前端校验过了就安全」 | Postman / 脚本可绕过前端 | 服务端必须校验（第 9 课） |
| 日期用本地字符串且无约定 | 跨时区错乱 | UTC + ISO-8601 |
| `null`、缺省、空字符串混用 | 下游 NPE / 脏数据 | Schema 明确三态 |
| 无限信任自动绑定 | 质量劫持、意外字段写入 | 显式 DTO + 白名单 |
| 列表一次返回整库 | 序列化拖垮 CPU/带宽 | 分页（第 11 课） |
| 对外 API 直接换 Protobuf | 浏览器与生态摩擦大 | 对外 JSON；对内可 Proto |

## 与前后课的关系

- **前：HTTP / 路由** — 知道请求如何到达服务器；本课解释 Body「长什么样、如何被理解」。
- **后：校验与转换（第 9 课）** — 反序列化之后立刻做语法/类型/语义校验与归一化。
- **后：Handler 分层（第 10 课）** — Handler 负责绑定（bind）JSON → 本地类型；可下沉到中间件。
- **后：REST 设计（第 11 课）** — 资源表示（representation）本身就是序列化后的样子；字段命名要一致（如 camelCase）。
