# 12. 数据库基础

## 一句话直觉

数据库就是「程序关掉之后，数据还在」的持久化系统：用磁盘换容量与价格，用 schema、约束、索引和事务换正确性与可查询性——后端几乎所有业务状态，最终都落在这里。

## 本课问题

- 为什么不能只用内存或文本文件存业务数据？
- 「持久化」到底保证什么？
- 关系型 vs 非关系型怎么选？为什么课程推荐 Postgres？
- schema、外键、约束、索引、迁移各自解决什么痛点？
- JOIN、参数化查询、事务并发在真实 API 里怎么落地？
- ORM、连接池、ACID/CAP 在第一性原理里各占什么位置？

## 核心概念详解

### 1. 为何需要数据库：从「关掉就丢」说起

想象一个待办 App：你勾掉任务后关掉应用，下次打开发现列表还在——这就是**持久化（persistence）**：数据要在进程结束、机器重启、甚至跨地点之后，仍以「你期望的状态」存在。

没有持久化，每次打开都是空白世界：进度、订单、账号全部消失。日常几乎所有「下次还能看到」的体验，背后都是某种持久化。

### 2. 「数据库」一词很宽：从通讯录到磁盘库

广义上，**任何结构化存储**都可以叫数据库：

| 例子 | 说明 |
|------|------|
| 手机通讯录 | 按人组织的结构化数据 |
| 浏览器 Local Storage / Session Storage / Cookie | 键值式持久化 |
| 记事本里的笔记文件 | 极简「库」 |

共性：提供 **CRUD**（Create / Read / Update / Delete）的持久层。

但在**后端语境**里说「数据库」，通常特指：**基于磁盘（HDD/SSD）的、由 DBMS 管理的大规模持久化系统**（Postgres、MySQL、MongoDB 等）。

### 3. 为什么用磁盘，而不是全放 RAM？

| | 主存（RAM） | 辅存（磁盘） |
|--|-------------|--------------|
| 速度 | 极快 | 相对慢 |
| 容量 | 贵、少（常见 8–64GB） | 便宜、大（512GB–数 TB） |
| 掉电 | **易失**（关机清空） | **非易失**（写到盘上） |

- **缓存**（Redis 等）偏 RAM：用速度换容量与易失性。
- **传统数据库**偏磁盘：用容量与持久性换一点延迟。

后端工程师要记住分层：热数据可进缓存；真相与历史大多在磁盘库。

### 4. DBMS 不只是「把文件写到盘上」

**DBMS（Database Management System）** 负责：

1. **数据组织**：让增删改查在 GB～TB 级仍可接受  
2. **访问接口**：高效 CRUD  
3. **完整性（Integrity）**：类型、约束、关系正确，不接受「金额字段塞字符串」这类脏数据  
4. **安全**：用户、角色、权限，防未授权访问  
5. （进阶）扩展、负载均衡等运维能力  

**为何不直接用文本文件？** 历史与现实都会撞上：

| 痛点 | 说明 |
|------|------|
| 解析慢且易错 | 每次找客户都要自己拆行、比对；JS/Python 等更吃亏 |
| 无结构 | 无法强制「金额必须是数字」 |
| 并发灾难 | 两人同时读到金额 40，一人 +20、一人 −20，最后可能只剩 60 或 20——**丢更新** |

DBMS 正是为了在规模化后仍保持正确与高效。

### 5. 关系型 vs 非关系型

#### 关系型（Relational）

- 数据进 **表（table）**：行 + 列  
- **预定义 schema**：列名与类型事先定好，不能随意塞异形文档  
- 表间用 **外键（foreign key）** 等表达关系  
- 查询语言：**SQL**  
- 例子：MySQL、**PostgreSQL**、SQL Server  

**红利**：强完整性——任意时刻你能信任「列类型、关系、约束」的一致性。

#### 非关系型（Non-relational / NoSQL）

- 以 MongoDB 为例：表≈**集合（collection）**，行≈**文档（document）**  
- **灵活 schema**：同集合里文档结构可以不同  
- 适合：原型快跑、CMS 内容形态多变（图文、代码块、嵌入视频等事先难定死）  

**代价**：完整性更多靠**应用层**自己保证 → 代码易漏、易引入不一致。

#### 选型直觉（课程举例）

| 场景 | 更合适 |
|------|--------|
| CRM：客户、商机、联系人要准、要可关联分析 | 关系型（如 Postgres） |
| CMS / 博客内容形态多变 | 非关系型（如 Mongo）或关系型 + JSON 字段 |

### 6. 为何课程默认走 PostgreSQL？

1. **开源免费**，可自托管  
2. **贴近 SQL 标准**，日后迁到 MySQL 等成本较低  
3. **可扩展**：文档极厚，扩展机制丰富，覆盖多数 SaaS 场景  
4. **可靠、可扩展**（运维面）  
5. **一流的 JSON / JSONB**：动态内容不必为此单独上 Mongo——CRM 要严格、CMS 要灵活，往往一张 Postgres 就能兼顾  

讲师观点：没到「百万用户级、盯着某一个瓶颈死磕」之前，**先选 Postgres**，别在 MySQL vs Postgres 上过早纠结。

> SQL 是查询语言；Postgres 是执行 SQL 的 DBMS。本课跳过 SELECT/GROUP BY 等入门，假设你另学过 SQL/Postgres 基础。

### 7. 常用数据类型（后端够用的那一层）

| 类型族 | 要点 |
|--------|------|
| **SERIAL / BIGSERIAL** | 自增整数；生产主键常用 **BIGSERIAL**（容量更大） |
| 整数 | smallint / integer / bigint——按范围选 |
| **decimal / numeric** | 精确小数；**价格、金额务必用**，别用 float |
| real / double / float | 快但不精确；面积等「差一点无接受」可用 |
| **char(n)** | 定长，不足补空格——现代几乎别用，除非固定长度代码（如星期缩写） |
| **varchar(n)** | 变长有上限；Postgres 里写 `255` 多半是 MySQL 习惯的遗留，无特殊含义 |
| **text** | 任意长度文本；**官方与讲师都推荐默认用 text**，长度在应用层校验，少做无意义的迁移 |
| boolean / date / time / timestamp / timestamptz / interval | 时间相关；带时区用 `timestamptz` |
| **UUID** | 很适合主键（全局唯一、难猜） |
| **JSON / JSONB** | JSONB 二进制存储，查询/索引更强——**优先 JSONB** |
| 数组、网络地址、几何、XML 等 | 偶用；查文档即可 |

**金额铁律**：准确优先 → `decimal`/`numeric`；浮点只适合「误差不伤业务」的科学计算类字段。

### 8. 迁移（Migrations）：生产库的版本控制

生产上不能「打开 TablePlus 随手改 schema」——改了谁也说不清、无法回滚、无法复现。

**迁移** = 有序的 SQL 文件（常带时间戳或序号）+ CLI 工具（如 **dbmate**、golang-migrate）：

```
db/
  migrations/
    20240101_create_users.up.sql   （或同文件内分 -- migrate:up / down）
    20240102_add_indexes.sql
```

| 概念 | 含义 |
|------|------|
| **Up** | 应用变更：建表、建索引、建类型… |
| **Down** | 撤销 Up：删表、删索引…（便于回滚；有的团队少用 Down，但经典做法仍有） |
| **schema_migrations 表** | 工具记录「当前版本」，避免重复执行 |

**为什么需要？**

1. **追踪变更历史**（与代码一起进 Git）  
2. **可回滚**到已知良好 schema  

关系库有严格 schema → 一切结构变更都应走迁移。

**Seeding（种子数据）**：另写迁移或脚本，往开发库塞测试数据（生产用户流不会这么干）。可用 CTE 可读地链式插入用户→档案→项目等。

### 9. Schema 建模直觉：项目管理平台例子

课程用 **项目管理** 库演示（对应前课 API 建模）：

#### Enum：完整性 + 文档

如 `project_status = {active, completed, archived}`，列类型绑 enum：

- DB 层拒绝非法字符串  
- 新人扫一眼迁移文件就知道允许值——**不必翻遍应用代码**（文档价值往往不亚于约束）

#### 表与关系

| 关系 | 怎么建 |
|------|--------|
| **1:1**（users ↔ user_profiles） | 档案表主键 = `user_id`，同时是指向 users 的外键 |
| **1:N**（project → tasks） | tasks 上 `project_id` 外键；一个项目多任务 |
| **N:M**（users ↔ projects） | **链接表** `project_members`：`(project_id, user_id)` **复合主键** + 角色等属性 |

外键 **参照完整性** 行为（课程强调）：

| 策略 | 含义 |
|------|------|
| `ON DELETE RESTRICT` | 用户仍有项目时禁止删用户 |
| `ON DELETE CASCADE` | 删项目 → 级联删其 tasks / members |
| `ON DELETE SET NULL` | 删用户 → 任务 `assigned_to` 置空 |

另有 **CHECK**（如 priority 只能 1–5）、**UNIQUE**、**NOT NULL**、默认值（status 默认 pending）等。

**为何用户基本信息与 profile 拆表？** 档案字段会膨胀、变更频繁——拆开便于演进（1:1 常见动机）。

命名习惯（课程）：表名复数、`snake_case`。

### 10. 查询与连接（JOIN）

列表用户且要带上档案，避免前端二次请求：

- 从 `FROM` 写起（先搞清数据从哪来），再 `SELECT`  
- **LEFT JOIN** user_profiles：没有档案也要返回用户行  
- 可用 `json_build_object` 等把档案嵌成 JSON 字段，方便一次 API 返回  

**参数化查询**：动态值用占位符（`$1` / `:user_id`），**禁止拼接字符串**——防 SQL 注入，也是驱动/ORM 的正确用法。

列表 API 常见能力：

- 过滤（如姓名首字母 `ILIKE 'J%'`）  
- 排序（白名单字段 + ASC/DESC，默认如 `created_at DESC`）  
- 分页（`LIMIT` / `OFFSET`；注意 UI 页码从 1、DB offset 从 0）  

动态 SQL 往往在应用层/ORM 里拼装：有参数才拼进 `WHERE`，没有就不加。

CRUD 对应：`INSERT ... RETURNING *`、`UPDATE ... SET 部分字段`、按 id `SELECT` 等。

### 11. 索引（Index）

类比**书末索引**：查「第 4 章」不必从第 1 页翻到第 54 页。

无索引时，按条件找行 ≈ **顺序扫描（sequential scan）** 整表（磁盘上各行位置散落）——百万行时极慢。

有索引时：维护「字段值 → 行位置」的查找结构（底层常见 **B-Tree**，本课不深挖），按值快速定位。

**何时考虑建索引？**（拇指法则）

字段频繁出现在：

1. `WHERE`  
2. `JOIN` 条件  
3. `ORDER BY`  

且该查询**调用频繁、延迟敏感**。

注意：

- **主键自动有索引**，不必重复建  
- **外键默认不自动索引**——`tasks.project_id`、`tasks.assigned_to` 常需手建，否则「某项目下全部任务」JOIN 很慢  
- 按默认排序方向建索引（如 `created_at DESC`）可避免再排序  
- **索引有写放大**：每次 INSERT/UPDATE 都要维护 → 别无脑全表建索引；先建、监控，冷查询可删  

### 12. 触发器（Trigger）

`updated_at` 每次行更新应刷新为「当前时间」：

- 笨办法：每个 UPDATE 语句手写  
- 好办法：库级 **BEFORE/AFTER UPDATE 触发器** 调函数，自动改 `NEW.updated_at`  

一次写好，所有路径（含漏写的 SQL）都一致。

### 13. 事务与并发（课程语境 + 第一性原理补全）

文本文件的「两人改金额」问题，本质是缺**并发控制**。关系库用**事务（transaction）**把多步写成原子单元：要么全成，要么全不成。

#### ACID（必会）

| 字母 | 含义 | 直觉 |
|------|------|------|
| **A** Atomicity 原子性 | 事务内全部成功或全部回滚 | 转账：扣款与入账不能只成一半 |
| **C** Consistency 一致性 | 事务前后都满足约束/业务不变量 | 余额不为负、外键仍成立 |
| **I** Isolation 隔离性 | 并发事务互不「脏」干扰（有隔离级别） | 避免脏读、不可重复读、幻读 |
| **D** Durability 持久性 | 提交后即使崩溃，数据仍在（写日志/刷盘） | 「提交成功」就要扛得住宕机 |

课程里的 CHECK、UNIQUE、外键、enum，都是「一致性」的落地抓手；事务则是并发下保住 ACID 的外壳。

#### CAP（分布式视角，选型时用）

在**分区（网络分裂）**时，系统难以同时完美满足：

| | |
|--|--|
| **C** Consistency | 所有节点看到同一最新数据 |
| **A** Availability | 每个请求都能得到（非错误）响应 |
| **P** Partition tolerance | 网络分区时系统仍能运转 |

现实是：**P 几乎必须扛**，于是在 C 与 A 之间取舍。单机/主从强一致的 Postgres 偏 **CP**；部分大规模分布式 NoSQL 偏 **AP**（最终一致）。不要背口号——问：「分区时我更怕读到旧数据，还是更怕服务不可用？」

### 14. 连接池（Connection Pool）

每次请求新建 TCP 到数据库，握手成本高。**连接池**在应用侧预开若干连接，请求来了借、用完还。

好处：降延迟、控并发连接数。  
风险：池耗尽 → 新请求卡住或 500（第 16 课也会提到）。要配好池大小、超时、泄漏检测。

### 15. ORM 取舍

课程在动态过滤/排序时提到：真后端会用 **ORM** 或手写 SQL 拼装。

| | ORM | 手写 SQL / Query Builder |
|--|-----|---------------------------|
| 优点 | CRUD 快、对象映射省事、迁移常集成 | 复杂 JOIN/报表可控、易看执行计划 |
| 缺点 | 易 N+1、生成烂 SQL、抽象泄漏 | 样板多、易拼错、注入风险（若未参数化） |

第一性原理：**理解 SQL 与索引优先**；ORM 是加速器不是替代品。热路径、报表、多表 JOIN 往往要回 SQL 或仔细查 ORM 生成的语句。

### 16. 后端日常 80% 在做什么？

1. 看 API 入参 → 动态构造**参数化**查询  
2. 执行 → 序列化成 JSON 返回  
3. 用迁移演进 schema；用索引/触发器优化正确性与性能  

高级特性很多，但这套闭环覆盖日常大半工作。

## 常见坑

1. **用 float 存钱** → 跨系统对不上账  
2. **varchar(255) 当信仰** → Postgres 无意义，还逼出多余迁移  
3. **生产手改 schema** → 无法复现、无法回滚  
4. **外键字段不建索引** → JOIN 列表 API 拖垮库  
5. **索引建太多** → 写入变慢、维护成本高  
6. **字符串拼接 SQL** → 注入 + 难维护  
7. **列表 API 不分页** → 一次拖全表  
8. **把 Mongo「灵活」当无约束** → 脏数据进库，应用层到处补洞  
9. **忽略连接池** → 流量上来先被自己打挂  
10. **只信 ORM** → 线上出现 N+1 才第一次看 SQL
