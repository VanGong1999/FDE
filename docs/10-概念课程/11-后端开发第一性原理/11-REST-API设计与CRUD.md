# 11 · REST API 设计与 CRUD

一句话直觉：先把 API **设计成稳定、一致、可猜测的资源接口**，再写代码——REST 的核心是用统一的 HTTP 语义对**资源**做转移，而不是为每个动作发明一套私有协议。

## 本课要解决什么问题

后端大量时间花在 API 设计上。即便有 REST「标准」，新手仍常纠结：

- 路径用单数还是复数？`PUT` 还是 `PATCH`？
- 非 CRUD 的「自定义动作」用什么方法？
- 列表如何分页、过滤、排序？如何版本化？
- 成功/失败响应如何保持一致？要不要 OpenAPI？

本课从历史约束到可执行规则，建立**一套可复用的设计清单**，让你和调用方少猜、少开会。

## 核心概念详解

### 1. 历史与 REST 从哪来

- **1990 前后**：Tim Berners-Lee 推动 WWW，带来 URI、HTTP、HTML、早期浏览器与服务器。
- **规模危机**：用户暴增，原架构吃力。
- **Roy Fielding（约 1993 起）** 提出约束以提升可扩展性；后与伯纳斯-李等推动 **HTTP/1.1**；2000 年博士论文正式命名 **REST（Representational State Transfer）**。

#### REST 六大约束（高阶）

| 约束 | 含义 |
|------|------|
| **Client–Server** | UI 与数据/业务分离，独立演化 |
| **Uniform Interface** | 统一交互方式（资源标识、通过表示操作、自描述消息、HATEOAS 等） |
| **Layered System** | 分层；可插负载均衡/代理而不破坏核心 |
| **Cache** | 响应须标明可缓存与否 |
| **Stateless** | 每请求自带处理所需信息（与第 8 课 Session 补偿「应用状态」不矛盾：协议层仍无状态） |
| **Code-On-Demand（可选）** | 如下发 JS 临时扩展客户端 |

### 2. 「REST」名字拆解

- **Representational**：资源用某种**表示**呈现——JSON（当今 API 主流）、XML、HTML…同一「用户」资源可对 API 客户端给 JSON、对浏览器给 HTML。
- **State**：资源当前属性/条件（如购物车里的商品、数量、总价）。
- **Transfer**：通过 HTTP 方法在客户端与服务器之间**转移**这些表示。

合起来：在约束下，用统一接口转移资源表示的架构风格 → 今日所说的 REST API。

### 3. URL 结构与路径设计规则

通用 URL 零件：`scheme`（http/https）→ `authority/domain` → `path`（层级用 `/`）→ `query` → `fragment`（前端锚点，API 较少用）。

**工业常见 API 形态：**

```text
https://api.example.com/v1/books
https://api.example.com/v1/books/{id}
```

规则清单：

1. **资源名用名词复数**：`/books` 而非 `/book`；取单个仍是 `/books/{id}`（集合下的一员），不要改成单数。
2. **`/` 表示层级关系**：集合 → 成员 → 子资源/动作。
3. **小写**；空格变 **连字符 `-`**；避免空格、下划线、随意大小写（跨环境易踩坑）。
4. **Slug**（可读标识）：如书名 `Harry Potter` → `harry-potter`。
5. 生产常用子域 `api.` + 路径版本 `v1`（见下）。

### 4. 幂等性（Idempotency）与 HTTP 方法

**幂等**：同一操作执行 1 次与 N 次，对服务器产生的**副作用结果相同**（关注「你的请求造成的副作用」，不是「期间别人是否改了数据」）。

| 方法 | 典型用途 | 是否幂等 |
|------|----------|----------|
| **GET** | 读取 | 是（无副作用） |
| **PUT** | 用完整表示**替换**资源 | 是 |
| **PATCH** | **部分**更新字段 | 是（同一 payload 重复打，最终状态一致） |
| **DELETE** | 删除 | 是（删一次后，再删通常 404，但资源已不存在的状态不变） |
| **POST** | 创建；或开放式**自定义动作** | **否**（每次可能新建一条） |

补充：

- **HEAD**：只要头；**OPTIONS**：CORS 预检等。
- **PUT vs PATCH**：公开 API 尽量遵守语义——整替换用 PUT，部分字段用 PATCH。现代 SPA/JSON API **更常用 PATCH**。对内混用伤害较小，对外会造成集成方错误假设。
- **非 CRUD 动作**（发邮件、归档、克隆）：规范上把 **POST** 当作开放式方法，例如 `POST /organizations/{id}/archive`。

### 5. 资源导向设计流程（先设计接口，再写代码）

1. 从 **线框 / 用户故事 / 需求** 出发，找出名词 → **资源**（经验法则：需求里的名词多半是资源）。  
   例：项目管理 SaaS → organizations、projects、tasks、tags、users…
2. （通常）先做 **DB schema**，再回到 API（DB 细节下集；本课可假设已有表）。
3. 为每个资源列出动作：CRUD + 业务自定义动作。
4. 用 Insomnia/Postman/**OpenAPI** **只设计接口**（路径、方法、body、响应），不先陷进某一门语言实现。
5. 再进入 Handler/Service/Repo 编码（第 10 课）。

端到端消费链直觉：用户 ↔ 前端 ↔ **你的 API** ↔ DB。看清用户如何碰数据，API 才好用。

### 6. CRUD 映射样板（以 organizations 为例）

假设资源字段：`id, name, status, description, createdAt, updatedAt`（后三者常由服务器生成，**不要**让客户端随便写权威 id/时间）。

| 操作 | 方法 | 路径 | 成功状态码 | 成功体直觉 |
|------|------|------|------------|------------|
| 列表 | GET | `/organizations` | **200** | 分页信封（见下） |
| 创建 | POST | `/organizations` | **201** | 新建出的完整资源 |
| 获取单个 | GET | `/organizations/{id}` | **200** | 单个资源 |
| 部分更新 | PATCH | `/organizations/{id}` | **200** | 更新后的资源 |
| 删除 | DELETE | `/organizations/{id}` | **204** | **空 body** |
| 自定义动作 | POST | `/organizations/{id}/archive` | **200**（或视结果定） | 动作后的资源等 |

要点：

- **同一路径**可用不同方法区分：`GET /organizations` 列表 vs `POST /organizations` 创建。
- 单个资源的 GET / PATCH / DELETE **路径外形相同**，靠方法区分。
- **POST 不总是 201**：自定义动作若未「创建新资源」可为 200；**克隆**若新建了实体则可为 201。
- JSON 字段名建议统一 **camelCase**（`organizationId`、`createdAt`）。
- 跨资源保持**命名与结构一致**（都用 `description`，不要有的 `desc`）——一致性是好后端的标志。

### 7. 列表 API：分页、过滤、排序

列表若一次倒出全表 → 序列化贵、网络慢、UI 卡。用 **pagination**。

#### 7.1 分页响应信封（课程示例形态）

```json
{
  "data": [ /* 当前页资源数组 */ ],
  "total": 50,
  "page": 1,
  "totalPages": 5
}
```

- `data`：本页数据  
- `total`：符合条件的总条数（与本页大小无关，便于 UI「第 10/50 条」）  
- `page`：当前页  
- `totalPages`：总页数（无限滚动可用「page === totalPages」停止）

#### 7.2 查询参数

| 参数 | 含义 | 默认值建议（Sane defaults） |
|------|------|------------------------------|
| `limit` | 每页条数 | 如 10 或 20；并设上限防滥用 |
| `page` | 页码 | **1** |
| `sortBy` | 排序字段 | 如 `createdAt` |
| `sortOrder` | `asc` / `desc` | **desc**（最新在前） |
| 过滤字段 | 如 `status=active`、`name=...` | 不传 = 不过滤 |

**未传参数时不要 400**，由服务器填默认值——体验远好于强迫客户端每次传齐。

过滤示例：`?status=archived` 只返回归档组织；多个过滤可组合。

**404 规则（重要）：**

- `GET /organizations/{id}` 找不到 → **404**。  
- `GET /organizations?status=nope` 结果为空 → **200 + `data: []`**，不是 404。  
  因为列表问的是「集合查询」，不是「某一个必须存在的实体」。

### 8. 自定义动作 vs 硬用 PATCH

例：归档组织时不仅改 `status`，还要级联处理项目/任务、发通知……表面像改字段，实质是**领域动作**。

推荐：

```text
POST /organizations/{id}/archive
POST /projects/{id}/clone
```

层级清晰：集合 → 成员 → 动作名。克隆可能返回 **201**（新项目）；归档返回 **200** + 更新后实体。

### 9. 版本化（Versioning）

常见做法：路径前缀 `/v1/...`、`/v2/...`（也有 Header 版本等）。

目的：破坏性变更时，老客户端仍可打 v1，新客户端迁 v2。从第一天就预留版本位，比上线后硬切路径成本低。

### 10. OpenAPI / Swagger 意识

从设计阶段就维护 **OpenAPI（Swagger）**：

- 交互式文档与试调（playground）；
- 前后端契约；
- 减少「读源码或瞎试」；
- 与校验/代码生成可打通。

**好后端的辨识度：** 是否持续、一致地维护 OpenAPI，而不是事后补文档。

### 11. 一致性响应与错误

成功：

- 结构稳定（列表永远同一种信封；单个资源字段命名稳定）。
- 状态码符合上表语义。

失败（与第 9、10 课呼应）：

- 校验失败 → 4xx + 聚合错误信息（脱敏）。  
- 未认证 → 401；无权限 → 403；限流 → 429；真故障 → 500（无堆栈）。  
- 错误体建议稳定字段：如 `code`、`message`（便于前端映射文案）。

### 12. 设计阶段的「理智默认值」与可读性

- 创建组织时，若未传 `status`，服务器可默认 `active`（业务上合理）。  
- POST 只要求**真正必需**的字段，其余给安全默认。  
- **避免缩写**（`description` 不要 `desc`）——你写 API 时的上下文，集成方没有。  
- 路由、query、body、响应四者全部**全局一致**。

## 后端规则与最佳实践（Checklist）

- [ ] 先设计接口（OpenAPI/Insomnia），再编码。  
- [ ] 资源复数名词；`/resources/{id}`；自定义动作用 `POST .../{id}/action`。  
- [ ] CRUD 与 HTTP 方法/状态码语义对齐（201/204/404 规则记牢）。  
- [ ] 列表：分页 + 默认排序 + 可选过滤；空列表 200。  
- [ ] Query 全可选 + sane defaults；`limit` 有上限。  
- [ ] JSON camelCase；跨资源字段命名一致。  
- [ ] 路径版本 `/v1`；破坏性变更走新版本。  
- [ ] 维护 OpenAPI；示例与真实行为一致。  
- [ ] 成功/错误响应形状团队统一。  
- [ ] id/createdAt/updatedAt 由服务器掌管。

## 常见坑与反模式

| 反模式 | 为何糟 | 纠正 |
|--------|--------|------|
| `/book/1` 单数路径 | 破坏集合语义与一致性 | 始终复数 |
| 用 GET 做删除/修改 | 缓存/爬虫误触发 | 写操作只用写方法 |
| 列表空结果返回 404 | 前端难区分「无数据」与「地址错」 | 200 + `[]` |
| 无分页一次返回十万行 | 性能与 UX 双崩 | limit/page |
| 强迫客户端每次传 page/limit | 摩擦大 | 服务端默认 |
| 到处缩写、字段改名 | 集成方不断猜 | 一致、可读 |
| 先写代码再想路径 | 返工多、风格漂移 | 设计会话先行 |
| 所有 POST 都当 201 | 自定义动作语义错 | 按是否创建资源选择 |
