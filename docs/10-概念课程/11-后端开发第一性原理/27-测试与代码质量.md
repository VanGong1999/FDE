# 27. 测试与代码质量（Testing & Code Quality）

## 一句话直觉

测试是**第二个程序**：跑你的程序并对「发生了什么」下断言；坏测试、假绿、易碎测试比「暂时零测试」更危险——因为它们给你**虚假信心**，并扭曲团队对失败的反应。

## 本课问题

- 前二十多课故意零测试，为什么？坏测试比没测试更糟在哪？
- 测试 / runner / assertion / 回归 各是什么？
- 单元 / 集成 / E2E 与「小/中/大（碰不碰进程、机器、外网）」哪种心智模型更可执行？
- Dummy / Stub / Spy / Mock / Fake；状态验证 vs 交互验证；为何「只 mock 你拥有的」？
- 为何测数据库要用真库（Testcontainers）而不是内存假库？时间与网络怎么测？
- TDD 红绿重构何时好用？Flaky、覆盖率、变异测试、圈复杂度与静态工具如何用？

---

## 核心概念详解

### 1. 为何整门课先故意零测试

前面大量概念课（认证、库、分层、缓存、队列、实时……）**刻意没写测试**。

原因：匆匆写的、不完整的、**坏的测试**，比没有测试更有害——它们给人「代码/应用很稳」的**虚假信心**。概念本身比「每个视频塞一小段测试」更重要；本课再系统讲清测试，并尽量讲透「为什么」。

范围：后端工程师自己写、自己跑的那约 **80%** 测试。不展开公司级手工 QA、测试管理工具、移动端/前端浏览器自动化等。

### 2. 测试到底是什么

**测试 = 第二个程序**：运行你的程序，并对「发生了什么」提出主张（claims）。

动机很多：TDD（先写测试当目标）、文档、指引……但**最有用、最重要**的动机是抓 **回归（regression）**：

- 几个月前写的逻辑，后来加功能时仍应表现如初（当时手测通过的样子）。
- 本课所有类型、指标、工具，都是这一定义的变体。

测试领域很大（有人专职测试）；我们收窄到「后端工程师日常」。

### 3. 没有框架也算测试；框架解决什么

最根本形态（任意语言）：

1. 另一段代码调用你的后端逻辑；
2. 给定事先定好的输入；
3. 看输出；不对就报错 / panic / 抛异常。

手写 if、手写 runner、手写 mock，在复杂后端里**不可扩展**——于是有库与语言内置测试设施。

语言 / 框架通常提供 **test runner**：

- 找出测试文件 → 跑起来 → 漂亮报告：多少过、多少挂。
- 以 Go 为例：`go test` 会生成 `_testmain.go`、链出 `board.test` 二进制再执行——**runner 替你写 main、收集结果**。

**Assertion（断言）**：条件不成立就失败/停止该测试。Go 标准库没有独立 `assert`，常用 `if` + `t.Errorf`；其他语言有断言库。失败信息要**有意义**，方便别人调试。

### 4. 回归 + CI：测试套件真正的价值

**回归** = 过去已修过的 bug 又回来了（同事改函数、改接口、改行为——团队里很正常）。

典型：GitHub Actions 等 CI 在合并 PR 前跑全套测试。失败 → **立刻**知道新代码在挖旧坑，而不是等用户投诉。收益：能**快速加功能**，同时用确定性套件钉住「旧 bug 必须保持已修」。

### 5. 单元 / 集成 / E2E——以及更可执行的「尺寸」模型

#### 5.1 传统三分

| 类型 | 含义（课程表述） |
|------|------------------|
| **Unit** | 隔离测「一个单元」；单元无普适定义（函数？struct？包？服务？靠经验认） |
| **Integration** | 测两段以上一起工作；常含**你没写的外部件**（如数据库） |
| **End-to-end** | 像真实用户走完整系统：常从**登录/鉴权**开始，带着 session 走创建任务等旅程 |

集成可不尊重「用户必经的每一条路径」（可绕过鉴权中间件直接测内部逻辑）；E2E 通常要覆盖用户真实路径。

同一行为可用多种方式测（课程看板示例）：

1. Mock bus（只记录 publish）  
2. 真 bus + hub  
3. 真起 HTTP 端口发 POST  
4. 真 Postgres  

耗时启示：**贵的不是「覆盖了多少逻辑」**，而是**是否离开本进程进入外部世界**（起容器的 Postgres 可占掉大半秒数）。

#### 5.2 测试金字塔 vs 「允许碰到什么」

金字塔：底宽 = 大量便宜快速的单测；中 = 较少集成；顶 = 很少 E2E。越高越慢、越贵（钱/CPU/内存/时间）。

课程更推荐的可执行心智模型——不问「覆盖系统多少」，而问 **「这个测试被允许碰到什么」**：

| 尺寸 | 允许 |
|------|------|
| **Small** | 单进程；不碰网络、DB、文件系统；不人为 sleep |
| **Medium** | 同机：本机容器里的 DB/Redis 等；**不上外网** |
| **Large** | 几乎什么都能碰 |

优点：无人能仲裁「算不算单测」；机器却能客观检查「有没有开 socket」。规则可强制，意见不可。

Unit / Integration / E2E 回答的是 **scope（范围）**；回归测试、功能测试、性能测试、安全测试等是**同一套范围上的变体**（回归可以是单测；安全检查可以是 E2E）。课程后半主要用「碰了什么」来想问题。

### 6. Test Doubles：Dummy / Stub / Spy / Mock / Fake

现实 handler：改板 → 发布 bus → 写 Postgres → 可能查支付额度 → 可能发邮件……测试时不能真扣卡、真发信。

**Test double（测试替身）**：长得像外部依赖、可替换上去。名字来自影视「替身演员」。口语里五类常被统称 **mock**，但细分有用：

| 类型 | 行为 |
|------|------|
| **Dummy** | 签名要、实际不用（如测试时塞一个空 logger） |
| **Stub** | 无论怎么问，总返回预先写好的同一答案（如总返回 user 7） |
| **Spy** | 像 stub，但**还记录**被怎么调用、改了什么 |
| **Mock** | 事先设期望（如 `save` 必须恰好以某参调用一次）；不满足就失败 |
| **Fake** | 能用但不适合生产的实现（内存 map 当用户库），输入输出行为对齐真实现 |

#### 状态验证 vs 交互（行为）验证

- **State verification**：问系统**现在状态**——任务是否在 done？序号是否 +1？
- **Interaction / behavior verification**：问 double **看见了什么**——`publish` 是否以 `task.moved` 调了一次？

若重构把「两次 publish」合成「一次组合事件」，对外看板不变：

- 状态验证往往仍绿；
- 交互验证因调用次数变了而红 → **change detector test（变更检测器）**：测的是实现步骤，不是最终结果。

**拇指规则**：默认只断言系统**现在是什么**，不要断言「怎么走到的」。交互验证仅在必要时用（例如邮件必须恰好发一次）。Google 有相关论述可延伸阅读。

#### 「不要 mock 你不拥有的」

支付客户端若完全按你编的成功对象 mock：测试全绿，生产却因真实字段名、重复扣款错误格式等炸裂——**测试里一切都是你自己写的**。

规则：**Don’t mock what you don’t own.**

做法：

1. 用薄包装 / 自己的 interface 包住第三方，生产与测试都依赖**你拥有的形状**；
2. 对包装与真实沙箱 API 做少量、快速的契约对齐测试（不反复真扣款）。

### 7. 依赖注入与「函数式核心 / 命令式外壳」

难测的根因：handler **自己凭空创建** DB/Redis 客户端 → 外部无法替换。

**Dependency Injection**：依赖从参数传入，不自造。框架可选；本质相同。程序变大时框架可改善体验。

结构建议：

- **Functional core**：业务计算尽量纯——吃值、出值，易测、无可 mock。
- **Imperative shell**：薄层负责对外网、DB、第三方说话——难测，但因薄，该测的也少。

这样更**愿意**写测试。

### 8. 数据库：假内存库的陷阱与真库廉价化

本能：DB 慢 → 用内存 map / H2 / 假 repository 换速度。

换来：速度、可维护感；放弃：**保真度（fidelity）**。

真实数据层 bug 往往活在 Postgres 侧：错列名、缺索引、唯一约束、事务语义、Postgres 有而假实现没有的 JSON 算子……**你刚好把会出问题的那一层换掉了**。

正解：**用真数据库测**，并让它便宜、好用。两种手法：

1. **每测一事务**：开头开事务，结尾 **rollback**（库干净；要求代码能接收 transaction handle——回到 DI）。
2. **模板库**：Postgres 可从模板快速克隆库；每测自有库、可并行。

**Testcontainers**：从测试代码起真容器，返回可连地址；多语言 SDK。课程演示：Postgres 18 容器约 7 秒就绪（**整包一次**），随后各测用模板克隆，单测毫秒级；整包约 10.5 秒量级。

### 9. 网络与时间

**网络**：仍先包装第三方；若要测自己的 HTTP 客户端/头处理，可起真本地 HTTP 服务器（Go `httptest` 等），请求走真 TCP。Node 有 MSW 等在网络层拦截。

**时间**：`sleep(100ms)` 等异步 → 本机过、CI 因负载变成 110ms 失败。加长 sleep 治标不治本，且拖慢套件。

两解：

1. **等条件/信号**（channel、callback），不等抽象时长；
2. **注入时钟**，测试完全控制「现在几点」。

**Hermetic testing（密封测试）**：测试自带环境——不依赖人手起的库、不依赖「某服务必须已在跑」；起则起、完则停。Testcontainers = 对 DB 密封；注入时钟 = 对时间密封。才能在本机 / SSH / GitHub Actions 任意跑。

### 10. TDD：红 → 绿 → 重构

TDD 是**工作流**，不是新测试种类（仍是 unit/integration/e2e，只是**先写**）。

| 阶段 | 含义 |
|------|------|
| **Red** | 为尚不存在的行为写测试并跑红 |
| **Green** | 写**最少**代码让测试过（允许暂时丑代码） |
| **Refactor** | 绿了再整理；再跑仍须绿——**多数人跳过这步** |

红阶段是设计：迫使你在实现前从**调用方**想象 API；测试难写/别扭 → 接口本身有问题，几分钟内发现。

绿之前先红：避免「自己写的代码配自己写的测试，第一次就绿却不知道断言有没有在查该查的东西」。

演示：任务禁止从 todo **直达** done（须经 doing）→ 先写「应报错」的红测 → 加最小 if → 绿 → 把规则抽到 `canMove` 再跑仍绿。

生态争论（可作延伸阅读）：

- Kent Beck 论 TDD 循环；
- Ian Cooper《TDD, Where Did It All Go Wrong》：unit ≠ 每个 class；应对**模块公开行为**测，否则一重构碎百测；
- DHH《TDD is dead》：反对 test-first 文化与「为可 mock 而设计」；曾与 Beck、Fowler 激辩。

课程立场：TDD 是好工具，当**你知道答案长什么样但还不知道怎么造**（解析器、计价规则、状态机）时极好；当你仍在探索空间、比选架构时，往往**不是**合适工具——后端大量功能属于后者。

### 11. Flaky tests（不稳定测试）

同一代码，有时过有时挂。比没测试更糟：缺测你知道有洞；flaky 会训练团队「再跑一遍就过」——真失败来时也先重跑而不是修。

2014 Luo 等研究：开源项目里 flaky 修复主因前三：

1. **Async wait 不对**（对应 sleep 问题 → 改等信号）；
2. **并发竞态**；
3. **测试顺序依赖**（B 只有在 A 之后才过——共享全局/行/文件）。

顺序依赖在加测或开并行时爆发。处理：删掉（删测往往划算）/ **隔离检疫（quarantine）**并写上负责人+日期+原因 / 重试（最不推荐）。课程偏向 quarantine 并留下上下文。

### 12. 覆盖率：能说什么、不能说什么

**Coverage** = 跑测试时执行到了代码的百分之几。工具常插桩计数；为 0 的块 = 从未跑过。

陷阱：

- 只记录「跑过没」，不记录「有没有真正断言」→ 调遍所有函数却零断言也能 100%。
- 不止一个数：**行覆盖** vs **分支覆盖**（一个 if 无 else：行可 100%，分支可能 50%）。

实证研究（Inozemtseva & Holmes, ICSE 2014）：控制套件大小后，覆盖率与抓到的真实缺陷只有**低到中等**相关；固定「必须 80%/100%」当质量目标**不够**。

可取三点：

1. 文中量级参考：约 60% 可接受、75% 可赞、90% 杰出——**无普适理想数**；
2. **未覆盖（红线）比百分比更有信息**；
3. 强制 100% → 工程师写低价值测凑数，然后停止改进。

### 13. 变异测试（Mutation testing）

用工具**故意弄坏**代码（`>`→`>=`、`+`→`-`、返回改 0……）→ 每个损坏版叫 **mutant** → 跑你的测试：

- 测试失败 = mutant **killed**（好）；
- 仍通过 = **survived**（断言没在查该查的）。

分数 = killed 占比。课程用 Stryker 示例：行覆盖 100% 的分页函数，变异分约 **52%**——表面覆盖满，实际断言弱。

### 14. 代码复杂度与静态工具

#### 圈复杂度（Cyclomatic complexity）

独立路径数。McCabe 1976：图上 **E − N + 2**；捷径：**1 + 决策点数**（每个 if/循环/case/`&&`/`||`）。无分支函数 = 1。

常见经验：多数函数 **≤ 10**；作者称合理非魔法。大 switch 多 case 会把数抬很高但代码仍好读 → 单看此指标会误伤。

#### 认知复杂度（Cognitive complexity）

Sonar 提出：测「多难看懂」而非「多少路径」。扁平 switch 几乎不加分；**嵌套**加重。故长扁平 switch：圈复杂高、认知低；深嵌套：圈复杂中、认知高。

用法：别盲信数字；当**旗标**指向该读的代码，团队再决策。

#### Linter / Formatter / Type checker / 静态分析

| 工具 | 做什么 |
|------|--------|
| **Linter** | 模式问题（条件恒真、未检查 error……）；不代替编译器语法，也不证明业务正确 |
| **Formatter** | 统一排版，不改语义 |
| **Type checker** | 类型用错（如对 string 做算术） |
| **Static analysis** | 更强：不运行代码，沿值追踪可疑条件 |

代码质量主观：ESLint / go lint 等有帮助，但没有单一确定性「高质量」仪表。

## Checklist

- [ ] 能解释为何「坏测试 / flaky」比零测试更危险
- [ ] 能口述：测试是第二个程序；runner 与 assertion 各干什么
- [ ] 能用「碰进程 / 同机 / 外网」给测试定尺寸，而不仅背金字塔名词
- [ ] 能区分五种 double，并默认做状态验证
- [ ] 遵守「不 mock 你不拥有的」；第三方走包装 + 沙箱契约测
- [ ] 数据层测真库（事务回滚 / 模板库 / Testcontainers），懂假库丢保真度
- [ ] 不用 sleep 赌异步；等信号或注入时钟；追求 hermetic
- [ ] 知道 TDD 红绿重构何时适用、何时不适合探索型后端功能
- [ ] 对 flaky：修根因或 quarantine，不养成「再跑一遍」
- [ ] 覆盖率看红线；变异测试测「测试有没有在断言」
- [ ] 圈复杂与认知复杂对照看；linter/format/type 作底线

## 常见坑

| 坑 | 说明 |
|----|------|
| 为概念课硬塞半吊子测试 | 虚假信心 > 暂时没有 |
| 交互验证绑死实现细节 | 一重构全红（change detector） |
| Mock 支付/邮件真客户端形状 | 生产格式一变测试仍绿 |
| 用内存假库「测数据层」 | 真正的 SQL/约束 bug 测不到 |
| CI 里靠 sleep | 负载一高就 flaky |
| 测试间共享全局状态 | 开并行即爆 |
| 强制 100% 覆盖 | 凑数测，质量停摆 |
| 跳过 TDD 的 refactor | 永久留下绿着的烂代码 |
| 对 flaky 加 retry 了事 | 训练团队忽略真失败 |
