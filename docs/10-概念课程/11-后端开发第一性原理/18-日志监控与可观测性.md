# 18. 日志、监控与可观测性（Logging, Monitoring & Observability）

## 一句话直觉

日志告诉你「发生了什么」，指标告诉你「趋势与健康度」，链路追踪告诉你「一次请求走过了哪些组件、卡在哪」——三者合在一起，系统才真正「可观察」。

## 本课问题

- Logging / Monitoring / Observability 分别是什么？为何说它们是「光谱」而非满分清单？
- 可观测性「三支柱」logs / metrics / traces 如何协作排障？
- 为何生产要用结构化（JSON）日志，本地却更爱可读文本？
- Prometheus / Grafana / Jaeger 与 New Relic / Datadog 怎么选？
- 告警如何设才不「告警疲劳」？

---

## 核心概念详解

### 1. 先建立心态：实践是光谱，没有「100% 可观测」

Logging、Monitoring、Observability 各自都够写一整门课；且业界没有「我们公司已做到全部最佳实践」这种满分状态——都是按资源在光谱上推进。先知道这一点，后面看到一堆产品名时不会被吓倒。

本课偏实践，会结合代码直觉（系列多数课刻意少看代码，本课例外）。

### 2. 为什么需要？分布式现实

现代后端跑在多服务器、多区域，用户全球分布。需要工具与方法论跟踪：**服务里发生了什么、基础设施状态如何**。

可粗分为：

| 概念 | 直觉 | 产出 |
|------|------|------|
| **Logging** | 记录重要/可疑/安全相关事件 + 元数据 | 「发生了什么」 |
| **Monitoring** | 持续看健康与性能，聚合历史与近实时状态 | 「趋势与是否异常」 |
| **Observability** | 从外部输出推断内部状态 | 需三支柱齐备才称「可观测」 |

「近实时」通常有约 **10–15 秒**延迟：若每毫秒狂推数据，观测系统本身会被打爆。

### 3. 可观测性三支柱（Pillars）

1. **Logs（日志）**：请求生命周期、启动/关闭、业务事件等记录。
2. **Metrics（指标）**：可量化数字——QPS、错误率、延迟、业务量（如创建了多少 Todo）等；与监控强相关。
3. **Traces（链路追踪）**：把一次请求当成「事务」：从入口（前端 / LB / 后端）经过 Handler → Validation → Service → Repository → DB，看触达了哪些组件、在哪失败。

#### 监控 vs 可观测性（一句话对比）

- **传统监控**：告诉你「有问题」（告警），但常常到此为止。
- **可观测性**：在你正确埋点后，不仅说「有问题」，还能指向「哪里出了问题」。

#### 协作排障工作流（课程核心故事）

1. 设阈值：如错误率 > 80% → Slack Webhook 告警。
2. 打开 **Metrics**：看吞吐、错误、延迟等。
3. 从指标跳到相关 **Logs**（失败请求日志）。
4. 从某条日志跳到 **Trace**：请求进了哪个函数、传到哪、在哪挂掉。
5. 据此快速定位并修复。

开源常见栈：**Grafana（看板）+ Prometheus（指标）+ Loki/Promtail（日志）+ Jaeger（追踪）**；也可用 **New Relic / Datadog** 等一体化商业方案（本课演示用 New Relic）。

### 4. Logging 深挖

#### 4.1 日志级别（Levels）

| 级别 | 用途 |
|------|------|
| **debug** | 本地排障，细节多；生产通常关闭，否则刷屏 |
| **info** | 正常业务事件（如 Todo 创建成功）、成功操作 |
| **warn** | 介于成功与错误之间，如用户输错密码——多半不是系统故障 |
| **error** | 校验失败、DB 查询失败等真正错误 |
| **fatal** | 极严重；进程往往退出并由编排重启 |

#### 4.2 结构化 vs 非结构化

- **开发**：倾向**人类可读**的 console 文本（可着色），方便扫一眼发现问题。
- **生产**：**结构化日志**，最常见 **JSON**（status、message、userId、requestId…），方便 ELK、Loki、Grafana 等解析与检索。纯文本行难稳定抽出 userId / requestId。

原则：**本地可读，生产可解析**。

#### 4.3 实践要点（与代码演示对应的概念）

- 启动时按环境选级别：local → debug/info；production → info。
- 请求入口 Middleware：创建 **transaction / span**，写入 service、env、IP、UA、requestId、userId、email、tenant 等，放进 **request context**，下游 Service 取出继续挂属性。
- 每个重要步骤：`info`/`debug`/`error` 打点；失败把 error 挂到 trace；成功挂业务事件日志（Todo 创建 + id/title/category/priority）。
- **Instrumentation（埋点）**：测量函数/请求属性的实践。
- **OpenTelemetry**：跨语言的开放标准与 SDK/生态，即便用 New Relic 也可接 OTel Collector 以增强控制。

### 5. Monitoring 与 Metrics

监控 = 持续看健康与性能，跟踪随时间模式。

**Metrics** = 具体数字（历史窗口或近几十分钟）：

- 处理了多少请求、多少失败（常把状态码 ≥ 某种非成功约定算失败）
- 业务指标：创建 Todo 数、失败数
- 运行时：GC、内存、吞吐、平均响应时间等

在看板里：从错误率 → 相关日志 → 单条日志的字段（app、env、error code、host、IP、level、method、path、spanId、timestamp）→ 关联 Trace → 某路由的 transaction 详情。

### 6. 工具选型直觉

| 路线 | 组件 | 适合 |
|------|------|------|
| 开源 Grafana 栈 | Prometheus + Grafana + Loki/Promtail + Jaeger | 有人维护、要掌控与成本可控 |
| 商业一体化 | New Relic、Datadog 等 | 团队小、想少运维、快速接入 |

配置整套可观测并不简单；没经验/没人力时，商业方案常更务实。无论哪条路，都需要：

- **开发**：代码侧打日志、埋 metrics、传 trace context
- **DevOps / 基建**：采集、存储、看板、告警管道

### 7. 告警与「告警疲劳」（Alert Fatigue）

路线图与本课共识：

- 定义有意义的阈值
- 告警应**可行动（actionable）**
- 只对真正必要的情况告警，避免刷屏导致人忽略真故障

（例：错误率飙升发 Slack，而不是每个 debug 都喊人。）

### 8. 安全与合规提醒（路线图点到）

日志中避免写入密码、API Key 等敏感数据；日志留存与访问也要符合合规——与第 17 课配置、第 20 课安全呼应。

## Checklist

- [ ] 理解 logs / metrics / traces 各自回答什么问题
- [ ] 生产结构化 JSON；本地可读文本；级别按环境切换
- [ ] 关键请求带 requestId / trace；业务关键事件有上下文（userId 等）
- [ ] 有看板能看吞吐、错误率、延迟；告警可行动且不过量
- [ ] 排障路径：告警 → metrics → logs → traces 打通
- [ ] 开发埋点 + 基建采集两边都到位
- [ ] 日志不落敏感明文

## 常见坑

1. **只监控不追踪**：知道「挂了」却不知道「哪挂了」。
2. **生产打 debug 全文**：成本与噪音爆炸，还可能泄露细节。
3. **纯文本生产日志**：工具解析脆弱，查 userId 极痛。
4. **告警过多**：告警疲劳 → 真问题被淹没。
5. **以为买了 Datadog 就自动可观测**：代码不埋点，看板是空的。
6. **日志里打密码 / Token**：观测系统变成泄密通道。
