# 23 · 并发与并行

一句话直觉：后端大部分时间在**等 I/O**（数据库、外呼、磁盘），CPU 却闲着；**并发**让程序在等待时去做别的事，**并行**才是多核同一时刻真的同时算——多数 Web API 更缺并发，CPU 重活才更缺并行。

## 本课要解决什么问题

- 若 Web 服务器一次只能处理一个请求，为什么在生产里根本不可用？
- 等待 DB 那几十～上百毫秒里，CPU 在干什么？不用并发会浪费多少？
- **I/O-bound** 与 **CPU-bound** 怎么区分？后端通常偏向哪边？
- **并发（Concurrency）** 与 **并行（Parallelism）** 差在哪？单核能不能「同时处理」多请求？
- 操作系统级 **线程**、**事件循环（Event Loop）**、Go 的 **goroutine** 各自如何工作？代价是什么？
- `async/await` 底层在干什么？单线程异步是否就没有竞态？
- 共享状态如何导致竞态？锁 / 互斥 / Channel 等直觉是什么？

本课偏**心智模型**，不是「抄一段就上线」的技巧清单；理解后更利于调试、结构设计和架构选型。

---

## 核心概念详解

### 1. 为什么必须能「一次做多件事」

若服务器同步、一次只处理一个浏览器请求：其余上千用户只能排队或收到「忙」。生产不可接受。

每种语言/runtime（Node、Python、Rust、Go…）都提供表达「同时处理多件事」的方式（`async/await`、线程、goroutine、虚拟线程等）。很多人会用这些关键字，却不懂背后机制——本课从根上补这块。

---

### 2. 不用并发的代价：等 I/O 时 CPU 空转

典型 API：收请求 → 查库 → 等结果 → 返回。

等待网络（本地约 1–2ms；跨 AZ 约 20–30ms；跨区域约 90–100ms）期间，若程序**完全同步且一次一请求**：

- CPU **空闲**，只是干等数据包；
- 现代 CPU 粗算约 **30 亿指令/秒 ≈ 300 万指令/毫秒**；干等 100ms ≈ 浪费约 **3 亿条**本可执行的指令。

更现实的中等复杂度 API：3–5 次 DB + 邮件/Redis 等，合计约 5 次网络；若每次平均等 50ms → 约 **250ms 纯等 I/O**，真正 CPU 工作可能只有约 **10ms** → 硬件约 **95% 时间闲置**。

课程概括：典型后端 **>70% 时间花在 I/O**（网络、文件、stdin/stdout）。并发要解决的正是：等 I/O 时用 CPU/内存去做**别的请求或任务**。

---

### 3. I/O-bound vs CPU-bound

| 类型 | 含义 | 例子 |
|------|------|------|
| **I/O-bound** | 瓶颈在等外部（网络/磁盘等），CPU 帮不上忙 | DB、HTTP 外呼、读文件、写日志 |
| **CPU-bound** | 瓶颈在算 | JSON 解析/校验（通常很短）、图像矩阵运算、加密验 JWT、视频编码 |

后端多数路径是 **I/O-bound** → **并发几乎是刚需**：否则无法同时挂起大量等待。  
重 CPU 活（图像、视频、重加密）更受益于 **并行（多核）**。多数 SaaS API 两者都要，但整体更偏并发；除非业务本身是转码/加密密集。

---

### 4. 并发 vs 并行（务必分清）

**并行（Parallelism）**  
同一时刻执行多条指令 → 需要硬件：至少两核才能两指令真并行。一核一时刻只能执行一条指令。

**并发（Concurrency）**  
关于**如何组织程序**：可启动、暂停、恢复多段工作，使人感觉在「同时推进」；**单核也能做**。某一时刻仍只跑一条指令，但在时间片上交错。

口诀（课程表述）：

- 并行 = **同时做**多件事；  
- 并发 = **同时应对**多件事（即便某一刻只做一件）。

#### 时间线直觉（单核并发）

请求 A、B 同时到达，仅一核：

1. A 先用 CPU 做校验/反序列化约 5ms；  
2. A 发起 DB 查询，进入等待 → 调度器把 CPU 给 B；  
3. B 算一阵后也等 DB；  
4. A 的 DB 先返回 → 再拿到 CPU 收尾并响应；B 同理。

客户端视角：A、B「都在处理中」；放大某一时刻：CPU 只服务其中一个。这就是并发。若两核：**同一时间窗**上 A 与 B 可真并行。

服务器还在打日志、发遥测、跑后台任务——CPU 在大量「等 I/O」的任务间跳跃，避免空转。

---

### 5. 两大底层机制：线程与事件循环

语言里的 goroutine、`async/await`、Java 虚拟线程等，大多建在二者之上（或二者的变体）。

---

### 6. 线程模型

线程 = OS 提供的独立执行流。创建线程时 OS 会准备：

- **栈**：函数调用链、局部变量；  
- **指令指针**：执行到哪一行，便于切回。

**调度**：由 **OS 调度器**决定谁跑、谁停。通常给每个线程一个时间片（毫秒级），到点**抢占（preemptive）**——不管愿不愿意都暂停并切走。

遇 **阻塞 I/O**（读 socket、等 DB）：线程告知 OS「我卡住了」→ 标为 blocked → 切到别的可运行线程；I/O 完成后变 runnable，再等调度器挑中（不一定立刻拿到 CPU）。

**进程 vs 线程**：不同进程内存隔离；**同进程内线程共享堆/全局**——可经指针读写同一对象，通信快（无拷贝、无序列化），但极易竞态（后文）。

多核时，多线程可真并行，加速 CPU-bound。

#### 线程的三大开销

1. **内存**：Linux 上栈常可达约 8MB 虚拟（物理按需），仍有真实占用。若「每请求一原生线程」，1 万并发尖峰 × 0.5–1MB ≈ 数 GB 仅栈，易 OOM。  
2. **创建**：需 syscall，内核建栈、数据结构、挂到调度器——微秒到毫秒，高并发下是延迟源。  
3. **上下文切换**：存寄存器、记账、选下一线程、恢复——约 1–10µs；线程远多于核时，大量时间耗在切换而非干活。高并发下「每请求一线程」常吃力。

推荐延伸阅读（课程提及）：*Operating Systems: Three Easy Pieces*。

---

### 7. 事件循环模型

典型：**单线程** + 回调/队列，不靠「很多 OS 线程」堆并发。

要点：**绝不阻塞事件循环**。

某请求要查库：不傻等，而是用语言原语（常是 `async`）登记「等结果回来再继续」，把 CPU 控制权交回事件循环；任务进队列。循环迭代检查 I/O 是否完成（Linux **epoll**、macOS **kqueue** 等 OS 能力可同时监视大量连接），完成则跑对应回调。

对 **I/O-bound**：事件循环通常比「海量线程」更高效——无巨量栈、无疯狂上下文切换。  
对 **CPU-bound**：线程 + 并行往往更快；若在事件循环线程上跑 100ms 重算，**整个循环卡住**，所有请求一起遭殃。

因此 JS 等语言大力推广回调 / Promise / `async/await`，引导你在 I/O 点交出控制权。

#### async/await 是什么

相对「回调地狱」（嵌套多层 `db.query(..., cb)`），`async/await` 是**语法糖**：`await` 之后到函数结束的代码，逻辑上等价于「I/O 完成后的回调」。对**该函数**交出控制，事件循环去干别的；结果回来再从 `await` 下一行继续。

底层可想成**状态机**：每个 `await` 是状态边界；`async` 函数被编译成可暂停/恢复的状态机。这也解释：

- 为何只能在 `async` 函数里 `await`（整函数要变成状态机）；  
- 为何阻塞事件循环致命（状态机无法推进到下一状态）。

---

### 8. Goroutine / 虚拟线程（以 Go 为例）

「线程」若指 OS 原生线程 → 重。Go 提供 **goroutine**（概念上像虚拟线程，文档不这么叫）：由 **Go runtime 调度器**管理，而非直接每活一个 OS 线程。

- HTTP 标准库常为**每个请求**起一个 goroutine；因极轻，可负担。  
- `GOMAXPROCS`：默认约等于 CPU 核数的 OS 线程（M）；goroutine（G）进各线程队列。  
- G 遇 I/O 阻塞 → runtime 暂停该 G，同 M 上跑别的 G；切换常接近**改指针**，远轻于 OS 上下文切换。  
- 可同时存在成千上万 goroutine；映射到少量 OS 线程。

直觉：像线程模型，但多一层用户态调度，I/O 与 CPU 都较高效。Java 新版虚拟线程同属「轻量用户态任务」家族。

---

### 9. 三种模型处理「两请求 + DB」的对比直觉

| | 线程模型 | 事件循环 | Go goroutine |
|--|----------|----------|--------------|
| 暂停方式 | OS 阻塞/切换线程 | 注册回调，单线程循环 | Runtime 暂停 G，换到其他 G |
| 恢复方式 | OS 调度器 | 回调 / await 续体 | Runtime 调度器 |
| 典型成本 | 栈 + 切换重 | 单线程轻，怕 CPU 堵死 | 极轻，每请求一 G 可接受 |

对外行为（都能同时服务多请求）相似；效率与编程约束不同。

---

### 10. 竞态与共享状态（并发的「税」）

并发问题大多来自**共享可变状态**。

#### 丢失更新（Lost Update）

两线程对同一 `counter` 做 `+1`，理想结果 2。实际是：读 → 加 → 写 三步可交错——两线程都读到 0，都写成 1 → **丢一次更新**。这就是**竞态（Race Condition）**。

#### 单线程 async 也不免疫

例：全局 `balance=100`，两处并发 `withdraw(100)`：

1. 第一个检查 `balance >= 100` 通过，`await` 处理取款 → 交出控制；  
2. 第二个同样检查通过（仍见 100）；  
3. 第一个回来把 balance 减成 0；  
4. 第二个再减 → **-100**。

`await` 边界就是交错窗口。**单线程异步 ≠ 无竞态**。

#### 常见对策（直觉级）

- **锁 / Mutex**：进入临界区前抢锁，同时只允许一个执行者改共享状态；  
- **Channel（Go）**：用消息传递，由**单一** goroutine 拥有并更新状态，避免多者直写同一变量。

细节可极深；本课目标是建立 I/O vs CPU、并发 vs 并行的框架，再带着问题去学同步原语。

---

### 11. 本课收束

- **I/O-bound + 高并发**（Web、网关、大量外呼）：`async/await`、事件循环、goroutine/虚拟线程通常更合适。  
- **CPU-bound**（图像/视频/重计算）：线程 + **并行**往往更合适。  
- 并发：等 I/O 时别浪费 CPU。  
- 并行：多核同一时刻多算。  
- 多数后端工作**更偏并发**；懂区别才能选对工具。

## 后端规则与最佳实践（Checklist）

- [ ] 设计 API 时分清：这段是在等 I/O，还是在吃 CPU？  
- [ ] I/O 密集服务：避免「同步阻塞 + 极低并发」浪费机器。  
- [ ] 事件循环语言：回调/`await` 之间不做长时间 CPU 重活；重活卸载到 Worker/线程池。  
- [ ] 不要默认「每请求一 OS 线程」撑高并发（除非有虚拟线程/goroutine 这类轻量模型）。  
- [ ] 共享可变状态（内存计数器、余额、缓存 map）：默认假设有竞态，用锁、单一写者或把真相放进 DB 事务。  
- [ ] 不要因为用了 `async/await` 就认为没有竞态。  
- [ ] 选型时：并发解决「同时等很多 I/O」；并行解决「算得更快」——问对问题再选模型。

---

## 常见坑与反模式

1. 同步阻塞整条请求链，机器 CPU 空、用户却在排队。  
2. 在 Node/单线程事件循环里做大图像处理 → 全站卡死。  
3. 把并发与并行当同义词，单核却期望「真同时算」。  
4. 线程爆炸：无上限创建原生线程 → 内存与上下文切换拖垮延迟。  
5. 多线程无同步改共享 map/计数器 → 偶现错账、难复现 bug。  
6. 异步取款/库存：检查与扣减之间插入 `await`，双花或超卖。  
7. 只学关键字用法，出了调度/阻塞问题无法排查。
