# 14. 后台任务与队列

## 一句话直觉

后台任务 = 任何**不必卡在「请求→响应」同步路径上**的工作：先让 API 快速回用户，把发信、转码、清数据等交给队列里的工人慢慢做，并可失败重试。

## 本课问题

- 为什么发验证邮件不能写在注册 API 的同步路径里？
- Producer / Broker / Worker 各自干什么？
- 邮件、图片、支付回调后处理、清数据、报表各适合怎样的任务形态？
- 重试、幂等、可见性超时、优先级、调度怎么配合？

---

## 核心概念详解

### 1. 定义：跑在请求-响应之外

客户端 ↔ 服务器的一次 HTTP 交互是 **request-response lifecycle**。

**后台任务（background job / task）**：任何在这条同步链路**之外**执行的逻辑——不要求「调用当下毫秒级完成」，可以卸到别的进程，按你配置的方式完成。

关键词：**非关键路径阻塞**、**可异步**、**可延迟**。

### 2. 动机：用「注册发邮件」把问题钉死

同步写法：

1. 校验邮箱密码 → 写库 → 生成验证码  
2. **当场**调 Resend / Mailgun / Brevo 等发信 API  
3. 等第三方返回成功/失败，再给前端响应  

灾难剧本：

| 情况 | 用户体验 |
|------|----------|
| 发信失败且你没处理好 | 整个注册 API 500，用户以为注册失败 |
| 发信失败但你吞了错误 | 前端写「邮件已发送」，实际没有 → 用户傻等、点重发、再失败… |
| 第三方慢或抖动 | 注册接口超时、网关掐断 |

你不控制第三方的流量尖峰与宕机——**同步耦合 = 把别人的稳定性写进你的 P99**。

异步写法：

1. 同步路径：校验、写库、生成验证码、**把「发信所需数据」序列化（如 JSON）推进队列**  
2. 立刻返回 200/201：「我们已发送验证邮件…」  
3. 另一进程的 **Worker** 取出任务 → 反序列化 → 调发信 API  

验证码通常 15–20 分钟有效；邮件在毫秒～数秒内送达完全够用。队列堆积时也可能到 5–10 秒级——仍远优于拖垮注册。

### 3. 失败时的第二大红利：重试

Worker 调发信失败 → 任务失败 → 框架（Celery / BullMQ / asyncq 等）把任务**重新入队**：

- 常见 **指数退避（exponential backoff）**：1 分钟 → 2 → 4 → 8…  
- 配置最大次数（如 5 次）  
- 大厂邮件服务很少连续宕机数分钟 → 往往第 2～3 次就成功  

同步路径里很难优雅地做这套「隔几分钟再试」而不拖死用户。

### 4. 核心架构：Producer / Broker / Worker

把队列想成后端的 **待办清单**：

```
[Producer 生产者]  --enqueue-->  [Broker 代理/队列]  --dequeue-->  [Worker/Consumer 工人]
     你的 API 进程                    RabbitMQ / Redis PubSub / SQS…         独立进程
```

| 角色 | 职责 |
|------|------|
| **Producer** | 应用代码：组装任务所需全部信息 → 序列化 → **入队（enqueue）** |
| **Broker** | 暂存任务，直到有工人来取；常由 RabbitMQ、Redis、**AWS SQS** 等承担 |
| **Worker / Consumer** | 独立进程（可同仓不同进程，或另一套服务）：监控队列 → **出队（dequeue）** → 反序列化 → 执行已注册的 handler |

Worker 侧通常配置：

- 监听哪个队列（邮件队列 vs 推送队列…）  
- 期望的数据结构（反序列化契约）  
- 真正干活的函数（以前同步写在 API 里的那段）  

多节点时：可有多组 Producer、多组 Consumer——水平扩展工人即可吞吐翻倍。

### 5. 确认、可见性超时：任务不能「蒸发」

工人处理完应向队列发 **ACK（acknowledgement）**：「成功，可以删掉这条。」

若工人崩溃、外部挂起、超时未 ACK：

- **Visibility timeout（可见性超时）**：任务在超时前对其他工人「不可见」（视为处理中）；超时仍无 ACK → 重新对其他工人可见，避免任务丢失  

设计目标：**至少一次（at-least-once）** 投递很常见 → 同一任务可能被执行多次 → 必须 **幂等**（见下）。

### 6. 典型场景清单（SaaS 后端几乎都会碰到）

| 场景 | 为何出同步路径 |
|------|----------------|
| **发邮件** | 依赖外部 SMTP/API；可重试 |
| **图片/视频处理** | 缩放、多分辨率编码，CPU/耗时长 |
| **生成报表** | PDF/HTML 周报月报；常配合定时 |
| **推送通知** | 调 Apple/Google 推送服务；存 device token 后异步发 |
| **支付后续** | 支付成功后记账、开权限、发收据——常异步，且要幂等 |
| **清数据 / 删账号** | 跨表、跨分片、删对象存储；可能数十秒～分钟 |
| **清理孤儿 Session** | 定期扫库删过期会话，释放空间 |

### 7. 任务形态：一次性 / 周期 / 链式 / 批量

#### 一次性（One-off）

由请求触发一次：注册验证信、欢迎信、重置密码、有人给你发消息时的通知。最常见。

#### 周期 / 调度（Recurring / Scheduled）

按 cron 或库内调度：每天 0 点发日报、每周日汇总、每月底清理。

Celery / BullMQ 等自带 **scheduled / cron-like** 能力；也可用系统 cron 触发「入队」。

#### 链式（Chain / 父子依赖）——以 LMS 上传视频为例

1. 上传完成（可预签名直传 S3）→ API 快速 ACK  
2. **父任务**：视频转码多分辨率  
3. 成功后并行：  
   - 生成缩略图 → 再处理多尺寸缩略图  
   - 语音转写字幕  
4. 缩略图任务依赖转码；转写与缩略图生成可并行，但都依赖「转码完成」  

要点：**有依赖就链式/编排；无依赖就并行**，别揉成一个巨型任务。

#### 批量（Batch）

- **删账号**：API 立刻 200 + 登出（可给 3～7 天冷静期）；Worker 扫项目成员、资产、头像、最后删用户并发「已删除」邮件——一个任务再扇出多个子任务  
- **半夜给全体用户发周报**：一次调度扇出成千上万同构任务  

### 8. 重试与幂等（Idempotency）——设计红线

队列常是 **至少一次**：失败重试、可见性超时重投 → **同一业务可能跑两遍**。

**幂等**：执行一次与执行多次，副作用相同（或第二次安全地变成 no-op）。

删账号例子：

- 应用里多步删库 + 外呼，中途失败 → 重试从 0 再来  
- 应用**事务**包住关键写操作，失败则回滚，避免「删了一半」的脏状态  
- 外呼（删 S3、发邮件）用幂等键 / 先查后做，避免重复收费或重复骚扰  

支付、扣库存、发券：**没有幂等就不要上重试**。

### 9. 优先级（Priority）

真实系统里任务并不平等：

| 优先级直觉 | 例子 |
|------------|------|
| 高 | 支付确认后的履约、安全相关告警、密码重置邮件 |
| 中 | 普通验证邮件、互动通知 |
| 低 | 批量报表、冷数据清理、非关键统计 |

做法：

- **多队列**：`critical` / `default` / `bulk`，工人数按队列倾斜  
- 或 Broker 原生优先级（RabbitMQ priority queue 等）  

避免：低优大批量饿死高优（饥饿）。限流与独立工人池常一起上。

### 10. 调度（Scheduling）

- **延迟任务**：注册后 24 小时发「未验证提醒」  
- **Cron 表达式**：`0 0 * * *` 每天零点入队清理任务  
- **准时窗口**：报表类可接受分钟级漂移；支付对账要更严  

调度器只负责「到点把任务丢进队列」，真正执行仍在 Worker——保持 **调度与执行分离**。

### 11. 设计考量与最佳实践（课程清单）

| 项 | 要点 |
|----|------|
| 幂等 | 可安全重试 |
| 错误处理与日志 | 发生在另一进程，漏处理 = 静默丢业务 |
| 监控 | 队列深度、成功/失败数、失败原因；Prometheus + Grafana 等 |
| 水平扩展 | 加人（更多 Consumer 节点） |
| 有序性 | 若业务要顺序，确认框架支持 ordered delivery |
| 对外部限流 | Worker 调第三方也要退避，免 429/账单爆炸 |
| **任务要小而专一** | 单任务单职责；失败别拖垮整条大流水线 |
| **避免超长任务** | 长就拆块或链式 |
| 告警 | 队列过长、Worker 挂掉要能叫醒人 |

框架举例：Python **Celery**、Node **BullMQ**、Go **asyncq**；Broker：**RabbitMQ**、**Redis**、**SQS**。

### 12. 收益总结

- API **更快、更稳**，少超时  
- 外部依赖失败可 **重试**，不绑架用户请求  
- 重 CPU / 批处理 / 定时维护有安放之处  
- 用户体验：先看到成功页，邮件稍后到达——符合心智

## 常见坑

1. **把发信放同步路径** → 注册成功率绑死在邮件商  
2. **非幂等任务开着重试** → 重复扣款、重复邮件轰炸  
3. **巨型任务** → 一点失败全盘重做，浪费 CPU  
4. **无监控** → 队列静默堆积，用户一周收不到信才发现  
5. **Worker 与 Web 抢同进程** → 互相拖垮；应隔离进程/容器  
6. **忽略 429** → 重试风暴打爆第三方  
7. **删账号同步扫全库** → 网关超时、前端以为失败
