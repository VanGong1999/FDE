# 17. 配置管理（Config Management）

## 一句话直觉

配置是应用的「DNA」：同一份代码在不同环境里长成不同行为；把环境差异、密钥与开关从代码里抽出来，才能在不改业务代码的前提下改变系统行为。

## 本课问题

- 为什么「配置」远远不止数据库密码和 JWT Secret？
- 分布式系统里配置一乱，会出现怎样的「配置混沌」？
- 配置该存在哪：env、YAML、密钥管理服务、还是混合？
- 多环境（dev / test / staging / prod）的优先级为何不同？
- 安全与校验：密钥怎么管、谁能看、如何避免「缺一个变量就整站诡异」？

---

## 核心概念详解

### 1. 配置管理是什么（比「存密码」大得多）

按定义：配置管理是**系统化地组织、存储、访问与维护**后端应用全部「设置」的方法。

多数人一听配置，脑子里只有：

- 数据库连接串、密码
- JWT / Session Secret
- 第三方 API Key（邮件、支付、鉴权服务等）

这就像「说车只有发动机」——引擎重要，但漏掉约 90% 的其它能力。配置还决定：

| 维度 | 例子 |
|------|------|
| 启动与连接 | 监听端口、超时、连接池大小 |
| 运行行为 | 日志级别、指标发往何处 |
| 环境差异 | 本地 vs 生产用不同 DB / 池大小 |
| 功能开关 | Feature Flags：新旧结账流、按用户/地区灰度 |
| 安全策略 | Session 超时时长 |
| 业务规则 | 单笔订单最大金额等可集中调整的规则 |
| 性能调优 | 如 Go 的最大 CPU 数等环境变量 |

电商后端的配置可能同时包含：DB 超时/主机/端口/用户/密码、Stripe 密钥、Feature Flags、连接池、Session 超时、业务上限……它们**特性不同**：有的极敏感、有的只影响行为、有的常变、有的跨环境相同、有的按环境不同。

### 2. 分布式系统与「配置混沌」

现代后端几乎不跑在孤岛上：多服务、DB、缓存（如 Redis）、消息队列、第三方集成（鉴权、邮件等）。每个集成点都需要「怎么连、失败怎么处理、怎么做性能与安全」的配置。

若没有系统化的配置策略，容易陷入 **configuration chaos（配置混沌）**：

- 硬编码值散落在代码各处
- 各环境行为不一致、难以复现
- 密钥泄露带来安全洞
- 出事时不知道「是哪条配置」导致生产故障

前端配错可能只是错弹窗或错路由；**后端配错**可能：泄露客户数据、错处理支付、拖垮整站。后端又跑在多样环境（云、机房、容器、Serverless、Edge），各自要求不同配置——所以配置管理是后端工程师的核心功课。

### 3. 配置类型（选型存储/安全/访问模式的基础）

并非所有配置平等，类型决定存储机制、安全措施、谁可访问、哪些环境可见。

#### 3.1 应用设置（Application Settings）

最常见一类，例如：

- **日志级别**：开发常用 `debug` 便于排查；生产常用 `info`，避免淹没关键日志
- **端口**：本地常 `8080`；生产视 VPS / K8s 而定
- **连接池大小**：控制 DB 连接上限
- **超时**：例如 HTTP 超时 60s，而 AI 出图平均 80s → 会得到 **504**，请求被丢弃

#### 3.2 数据库配置

连接所需：host、port、username、password、database name → 常拼成 connection URL；还可含查询超时等。

#### 3.3 外部服务

邮件（Mailchimp、Resend…）、支付（Stripe）、鉴权（Clerk）等，几乎都要 API Key / 客户端初始化参数。

#### 3.4 Feature Flags（功能开关）

用于**动态启用/禁用**功能，无需改代码发版。例：新结账流只对美国用户开、印度用户仍走旧流，做 A/B 或灰度。

#### 3.5 其它常见类

- **Infra / DevOps 相关配置**
- **安全配置**：JWT Secret、Session Secret 等
- **性能调优参数**（语言/运行时相关）
- **业务规则配置**：希望集中管控、可调的业务逻辑参数

### 4. 配置来源 / 存储方式

存储选择取决于：安全、速度、环境。

#### 4.1 环境变量（Environment Variables）——最常见

- 本地：`.env` + 库（如 dotenv 一类）把文件加载进 OS 环境（本质是 OS 能力，库只是帮你 `export`）
- 容器 / K8s：部署时注入 env
- 云上常见流水线：部署触发 → 从 **Vault / AWS Parameter Store / Azure Key Vault / Google Secret Manager** 等拉取 → 注入进程环境 → 应用启动时读取

语言无关：Node、Python、Go 等都普遍用。

#### 4.2 配置文件

- **JSON**：无法写注释是大痛点
- **YAML**：业界更流行，可写注释、便于团队共享知识（开源项目如认证相关 Go 服务、Apache 系仓库常见 `config.yaml`：server、log level、storage、session 等）
- **TOML**：较新的常用选项

#### 4.3 键值存储与云原生配置工具

轻量 KV（行为上类似 env）以及 Consul、etcd 等；大流量、多云、K8s 自动扩缩时常用 **HashiCorp Vault**、云厂商密钥服务做**集中密钥与配置**。

#### 4.4 混合策略（Hybrid）与优先级

现实中常：启动时拼出 runtime settings，按**预定优先级**从多源加载，例如：

1. AWS Parameter Store（最高）
2. `config.yaml`
3. 环境变量

再按环境条件加载。关键：**事先约定优先级**，避免「到底听谁的」混乱。

### 5. 为什么要按环境区分配置？

同一份**应用代码**不变，靠配置改变行为——这正是解耦的意义。若硬编码，换环境就要改代码。

各环境首要目标不同：

| 环境 | 首要优先级（典型） |
|------|-------------------|
| **Dev / 本地** | 开发者效率、调试能力 |
| **Test（如 CI）** | 自动化校验、质量保证 |
| **Staging** | 尽量镜像生产行为，便于提前发现问题 |
| **Production** | 可靠性、安全、性能 |

**连接池大小**示例（课程中的取舍）：

- Dev 本地：池子 10，机器够用、开发无顺
- Prod：池子 50，应对流量与尖峰
- Staging：可能只设 2——功能上尽量像生产，但**刻意压低云成本**（Staging 主要是开发/测试用，可接受略慢）

原则：按该环境的目标写配置，而不是「全环境一套抄生产」。

### 6. 安全与访问控制（配置管理的底线）

1. **永不硬编码密钥**（生产 DB URL、Clerk/邮件/支付 API Key 等）——显而易见但必须反复强调。
2. **尽量用云密钥管理**：Vault、Parameter Store、Key Vault、Secret Manager。它们通常提供：
   - **静态存储加密**
   - **传输加密**（拉取时密文 + 在 infra / CI / K8s 侧用私钥解密）
   - 对安全「宁可过工程化一点」往往值得
3. **最小权限（Least Privilege）访问控制**：大团队要规划谁能看什么。
   - 前端：后端 API URL、前端集成所需 Key
   - 后端：DB、Redis、Elasticsearch 等
   - 云主机 / EC2 等：主要给 DevOps
4. **定期轮换**：API Key、JWT Secret 等，降低长期泄露风险。
5. **启动时校验配置（本课最强调的一点）**  
   很多人：`process.env.XXX` 直接用，缺了变量生产才「怪行为」或崩。  
   正确做法：部署后、业务服务起来前，用校验库（TS 用 Zod、Go 用 validator 等）校验：
   - 哪些必填、哪些可选、默认值在哪设
   - 来源是 env、YAML 还是 Parameter Store 都一样要验  
   **若本课只记住一件事：永远校验配置。**

## Checklist

- [ ] 配置已从业务代码解耦；换环境不靠改代码
- [ ] 分清：应用设置 / DB / 外部服务 / Feature Flags / 安全 / 性能 / 业务规则
- [ ] 密钥不进仓库；生产用密钥管理服务
- [ ] 明确多源加载时的**优先级**
- [ ] Dev / Test / Staging / Prod 目标不同，池大小、日志级别等差异有意为之
- [ ] Feature Flags 用于灰度 / A/B，而不是靠改代码开关功能
- [ ] 启动时 schema 校验所有配置；缺必填则**快速失败**
- [ ] 访问控制遵循最小权限；密钥定期轮换

## 常见坑

1. **以为配置 = 密钥**：忽略超时、池大小、日志级别、Feature Flags → 行为与成本失控。
2. **硬编码散落**：换环境改代码、排障无法复现「当时配置是什么」。
3. **Staging 强行 1:1 复制 Prod 容量**：云账单爆炸；或反过来完全不像 Prod，测不出问题。
4. **不校验 env**：缺变量时生产「诡异」比启动即报错更难查。
5. **密钥进 Git**：即使删文件，历史里仍在 → 必须轮换。
6. **全员可读全部 Secret**：违反最小权限。
