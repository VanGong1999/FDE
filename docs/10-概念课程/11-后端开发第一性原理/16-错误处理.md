# 16. 错误处理

## 一句话直觉

错误不是例外事件，而是后端日常天气：问题不在「会不会出错」，而在「出错时能否快速发现、隔离损害、对用户说人话、对内部留足线索」——用 fail-fast 防带病上线，用 fail-safe / 降级保核心体验。

## 本课问题

- 逻辑错误和运行时/基础设施错误有何不同？何者更阴险？
- Fail-fast 与 fail-safe / 优雅降级分别在何时用？
- 全局错误 handler 为何是「最终安全网」？
- 怎样写「面向用户」又「不泄密」的错误信息？
- Sentry、健康检查、告警在容错体系里各站哪一环？

## 核心概念详解

### 1. 心态：错误是常态

现实清单（课程开场）：

- 数据库查询会失败  
- 外部 API 会超时  
- 用户会扔脏数据  
- 业务会撞上没想到的边角  

问题从来不是「是否会发生」，而是**发生时你准备好了没有**。本课偏**心智与原则**，不是某一框架的 try/catch 语法课。

目标心态：**故障容忍（fault-tolerant）**——预估最坏情况，并知道如何探测与收敛。

### 2. 错误类型地图

#### （1）逻辑错误（Logic errors）——最阴险

代码**跑得通**，结果**是错的**。

例：电商折扣算了两遍 → 运费变负数 → App 不崩，但**每单都在亏钱**；可潜伏数周数月。

常见成因：

- 需求理解偏了（sprint 沟通含糊）  
- 算法/计价算错  
- 没覆盖某用户行为边角  

涉及支付、安全时：可持续**腐蚀数据与报表**，比直接 500 更危险。防护：测试、监控业务指标（成功率骤降）、代码评审、对账。

#### （2）数据库错误

后端几乎绑死在 DB 上，库挂 ≈ 产品挂。

| 子类 | 例子 |
|------|------|
| **连接错误** | 网络、库过载、**连接池耗尽** → 大片 500、前端白屏 |
| **约束冲突** | 邮箱 UNIQUE 重复；订单引用不存在的 customer_id（外键） |
| **查询错误** | SQL 拼错表名；过复杂查询超时 |
| **死锁** | 事务互相等待，成环 |

连接池：预开 TCP，避免每次握手——优化手段也会成为故障点（池满）。

约束类：很多应在校验层提前挡住；**唯一性**最终只有库知道 → 必须翻译成友好信息（「邮箱已被注册」），别冒成裸 500。

#### （3）外部服务错误

支付、邮件、S3、Redis、Clerk/Auth0… 每一个都是**你控制不了的故障点**。又不能全自研。

失败原因包括：

- 网络：超时、DNS 失败、分区  
- 鉴权：坏凭证、过期 token、权限不足  
- **限流 429**：被第三方判定请求过多  
- **服务宕机/维护**：AWS/GCP 事件级连锁  

对策直觉：指数退避、降级、备用节点、核心路径（支付/下单）与非核心（推荐/邮件）隔离。

#### （4）输入校验错误

用户/客户端送来的数据不合规——**最易预期、最易处理**的一类。

入口处强制：格式（邮箱/电话/日期）、范围（金额上下限、字符串长短、数组长度）、必填字段 → 通常 **400 Bad Request**。

与第 9 课校验呼应：校验是防脏数据与恶意输入的第一道防线。

#### （5）配置错误

缺环境变量、staging/prod 配置不一致。

| 策略 | 结果 |
|------|------|
| **启动时校验必填配置，缺失则拒绝启动** | 最佳：蓝绿部署下旧版本仍服务，新版本起不来也不切流量 |
| **启动不管，运行到某 API 才爆** | 最差：用户当面 500 |

→ 这就是 **fail-fast** 的经典应用（见下节）。

#### （6）运行时错误（Runtime）广义理解

进程已在服务流量时炸开的一切：未捕获异常、空指针、超时、依赖不可用、资源耗尽……与「编译/启动期就能抓到的问题」相对。

策略分野：

- 能启动前发现的 → **尽早失败**  
- 运行中不可避免的 → **隔离、降级、重试、告警**  

### 3. Fail-fast vs Fail-safe

#### Fail-fast（快速失败）

**一发现不变量被破坏，立刻停下来**，不要带着错误状态继续跑。

课程例：缺 `OPENAI_API_KEY` → **进程启动失败**，而不是上线后第一个用户生成图时才 500。

还适用于：迁移未完成就接流量、关键依赖 ping 不通就不要标 healthy、校验失败立刻 400。

#### Fail-safe / 优雅降级（Graceful degradation）

对**不可恢复或暂时不可用**的依赖：**缩小爆炸半径**，保住核心功能。

手段举例：

- Redis 挂了 → 回源 DB 或关掉个性化，**下单仍可用**  
- 推荐服务挂了 → 展示默认列表  
- 邮件挂了 → 注册成功，邮件进队列稍后重试（第 14 课）  

课程对应说法：**containment（遏制）+ graceful degradation**——切缓存数据、关非必要功能、提供替代路径。

| | Fail-fast | Fail-safe / 降级 |
|--|-----------|------------------|
| 时机 | 启动、配置、明确非法输入 | 运行中依赖故障、局部过载 |
| 目标 | 不要带病服务 | 不要全站陪葬 |
| 用户感受 | 部署失败/明确 4xx | 「部分功能不可用」但仍能完成主流程 |

二者不是对立：同一系统里，**配置用 fail-fast，外部依赖用 fail-safe**。

### 4. 可恢复 vs 不可恢复：即时响应策略

| 类型 | 例子 | 策略 |
|------|------|------|
| **可恢复** | 邮件 API 抖一下、短暂连接池紧张、网络毛刺 | **重试 + 指数退避**；注意别把已过载系统再打死 |
| **不可恢复（短期）** | 依赖长时间宕机、功能整体不可用 | **遏制 + 降级**；切备份、关非核心 |

自动恢复：进程重启、清坏缓存、切备援——要演练，乱自动有时会**加剧故障**。  
需人工判断的：写清 runbook，压力下也能快速执行。  
**数据完整性优先**：备份、按时间点恢复、重放日志——数据是唯一真正「搬不走」的资产。

### 5. 主动探测：错误发生前就开始处理

课程金句：**最好的错误处理，在错误发生之前。**

#### 健康检查

- `GET /health` 或 `/status` → **200 表示活着**（负载均衡/编排靠这个摘掉病实例）  
- 不够：还要验证**真的在干活**  
  - DB：连通性 + 代表性查询耗时是否恶化  
  - 支付：定期测试交易  
  - 邮件：对内部地址发探测信  
  - 鉴权：测发 token / 验 token  
  - 配置已加载、关键缓存已预热、内部结构一致  

合起来 = **主动错误检测（proactive detection）**。

#### 监控与可观测性（本课点到为止，系列后续深挖）

- 别只看错误率；**性能劣化**往往是崩溃前兆  
- 覆盖：HTTP、DB、外部依赖、业务逻辑错误  
- 性能：延迟、资源、吞吐  
- **业务指标**：成功支付数骤降——即使技术错误率「看起来还行」  
- 日志：结构化 JSON，便于 Grafana/Loki 等聚合  

### 6. 传播控制与错误边界

不是所有错都该在当场「吞掉」：

- 底层异常 **包装上下文** 后向上抛，到有业务语义的一层再决断  
- 语言工具：JS/Python 的 try/catch；Go 的 `error` 层层返回  
- **服务边界**：超时、独立进程、**消息队列解耦**——一服务的 bug 不拖死另一服务  

→ 与第 14 课队列同一哲学：异步边界 = 故障边界。

### 7. 全局错误处理（Global handler）——最终安全网

典型分层：

```
Routing → Handler（校验/绑定）→ Service（编排）→ Repository（单次 SQL）
```

任意层都可能炸：校验失败、唯一约束、无行、外键失败……

**全局错误中间件**（请求进出的闸口）：

1. 各层把错误**冒泡**到中间件（throw 或 return error）  
2. 中间件按**错误类型**映射 HTTP 响应  

课程图书管理例子：

| 错误 | 对用户 |
|------|--------|
| 书名超 500 字（校验） | **400** + 字段说明 |
| 书名 UNIQUE 冲突 | **400**「书已存在」（用户数据问题，不是 500） |
| `SELECT` 无行（no rows） | **404**「id=123 的书不存在」 |
| 外键：作者 id 不存在 | **404**「作者不存在」 |
| 未识别异常 | **500** + **泛化文案**「出了点问题」——**绝不回传原始堆栈/表名** |

两大好处：

1. **稳健**：不会因某 Repository 忘了处理约束 → 用户只看到含糊 500  
2. **去重**：映射逻辑集中一处，避免每个 SQL 调用复制粘贴  

一次建设、长期微改——课程称为最划算的错误处理投资之一。

### 8. 面向用户的错误信息 × 安全

#### 原则

- **对用户**：可行动（改哪个字段、下一步做什么）  
- **对攻击者**：不提供内部结构（表名、约束名、SQL、堆栈）  
- **对运维**：完整细节进日志（含 correlation id），不进响应体  

默认 500 分支：固定文案（Internal Server Error / Something went wrong），原始 error 只打日志。

#### 登录接口的经典反例

不要区分：

- 「该邮箱不存在」  
- 「密码错误」  

应统一：**「邮箱或密码不正确」**  

否则攻击者可枚举哪些邮箱已注册，再对命中邮箱狂撞密码（OWASP 等 cheat sheet 有系统建议）。

#### 日志安全

即使日志「只在内网」，大公司日志常进多家 SaaS；泄露事件里**日志是重灾区**。

禁止落盘：密码、完整卡号、API Key、无必要的 PII 邮箱等。  
鉴权失败：优先记 **user id + correlation id**，不要记密码明文。

### 9. Sentry 与告警：把「未知 500」变成可行动信号

课程强调监控/告警心智；工程上常见落地：

| 工具角色 | 做什么 |
|----------|--------|
| **Sentry**（或同类） | 捕获未处理异常与显式 `captureException`：堆栈、发布版本、用户上下文、面包屑；按指纹归并，避免告警洪水 |
| **指标告警** | 错误率、P99、队列深度、健康检查失败 → PagerDuty/短信/飞书 |
| **日志系统** | 全文检索与审计（可与 ELK 联动，见第 15 课） |

实践建议：

- 全局 handler 在返回 500 时**上报 Sentry**  
- 对可预期的 4xx **不要**当异常刷屏（或单独低优先级）  
- 告警要有**可操作 runbook**，避免「半夜响铃但无人知道该重启谁」  

### 10. 限流与退避（外部依赖）

收到 **429** → 等待 → 加倍等待再试（指数退避）。与第 13 课自建限流、第 14 课任务重试同一家族算法。

## Checklist

- [ ] 能区分逻辑错误 vs 基础设施/运行时错误，并知道前者为何危险  
- [ ] 能列举 DB / 外部依赖 / 校验 / 配置 四类故障  
- [ ] 能用「启动校验配置」解释 fail-fast  
- [ ] 能用「Redis 挂了仍能下单」解释 fail-safe / 优雅降级  
- [ ] 能区分可恢复（重试）与不可恢复（降级）  
- [ ] 知道健康检查不止 ping，还要查 DB/关键依赖  
- [ ] 能画出全局 error middleware 与 400/404/500 映射  
- [ ] 登录错误文案不泄露「用户是否存在」  
- [ ] 500 不回传内部细节；敏感信息不进日志  
- [ ] 知道 Sentry/告警在「发现与归并」中的位置  

## 常见坑

1. **逻辑错无监控** → 静静亏钱  
2. **约束冲突冒成 500** → 用户无法自助改邮箱  
3. **配置缺失运行时才爆** → 部分流量吃满错误  
4. **重试无退避 / 无上限** → 雪崩  
5. **降级没设计** → Redis 一挂全站挂  
6. **每层各自格式化错误** → 行为不一致、易漏  
7. **把 DB 报错原文发给前端** → 助攻注入与侦察  
8. **登录区分「无用户/错密码」** → 账号枚举  
9. **日志打印密码和密钥** → 日志管道即泄密面  
10. **只有 /health 返回 200** → 实例「活着」但已经查不了库
