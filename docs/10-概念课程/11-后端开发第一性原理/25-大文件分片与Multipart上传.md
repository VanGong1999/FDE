# 25 · 大文件分片与 Multipart 上传

一句话直觉：几百 MB 以上别再赌「一次 PUT」——对象存储有 **5GB 单次上限**，断线即重头、单 TCP 跑不满带宽；用 **Multipart（创建 → 并行传分片 → 完成）+ 预签名**，并配上 **遗弃分片生命周期** 与 **正确的下载/Range/CDN** 策略。

## 本课要解决什么问题

- 为何「单次 PUT」在大文件场景会从四面漏风？（硬上限、不可续传、吞吐、体验）
- Multipart 的三次（加 abort）API 各自干什么？分片能否乱序、并行、单独重试？
- 为何有 **最多 1 万片** 上限？分片大小怎么动态算？为何推荐约 16–64MB？
- Multipart 对象的 **ETag 为何不能当 MD5**？完整性怎么验？
- 半截 Multipart 为何会**隐形扣钱**？生命周期规则怎么配？
- 浏览器 + 预签名的完整大文件架构长什么样？如何断点续传？
- 下载为何绝不能经应用服务器转发？预签名 GET 与 CDN 缓存如何打架？Range / HLS 解决什么？

---

## 核心概念详解

### 1. 单次 PUT 为何不够：四个独立理由

第 24 课的小文件/中等文件流程，到「大视频、CAD、数据库 dump、航拍婚礼素材」会不够。单次 PUT 至少有四类问题：

#### 理由 1：硬上限 5GB

单次上传请求不能超过约 **5GB**——这是**对象存储 API** 的限制，不是你后端随便定的。产品若接受更大文件，架构上就必须上 Multipart（或等价方案）。

#### 理由 2：全有或全无（All-or-nothing）

传到 4.8GB / 5GB 时 Wi‑Fi 闪断 → 上传取消，**不能续传**，下次从 0 开始。消费级/移动网络传 20–30 分钟很常见，中途抖一下就会让用户崩溃。

#### 理由 3：单连接吞吐上不去

单条 TCP（HTTP 底下那条）往往吃不满链路：窗口/RTT 限制，且对丢包极敏感（拥塞窗口塌缩再爬升）。你可能有 200–500Mbps，单流上传却卡在约 30Mbps。

修复思路在网络层：**多连接并行**，各有拥塞窗口，一条卡不影响其它——下载器（IDM 等）开多连接加速同理，并非改了物理带宽。

#### 理由 4：体验差

进度粗糙，难暂停，关标签/断网几乎等于死刑。

→ 答案：**Multipart Upload**。

---

### 2. Multipart：三次调用（外加 Abort）

协议核心只有三步：

#### Step 1：Create Multipart Upload

告诉存储：桶、key、Content-Type 等 → 返回 **Upload ID**。  
直觉：像 Git 的 **staging**——分片会堆在暂存区，**key 上尚无正式对象**；此时 Get 该 key → **404**。直到最后 Complete 才「提交」。

#### Step 2：Upload Part（每个分片一次）

带上 Upload ID、**Part Number**、字节。  
关键性质：

- 每次是**独立 HTTP 请求** → 可**并行**、可**乱序**（part 7 可先于 part 2 到）；  
- 失败可**单独重试**该片，不影响其它片；  
- 成功返回 **ETag**——必须保存，Complete 时要用。

#### Step 3：Complete Multipart Upload

提交 Upload ID + **按顺序的 (partNumber, ETag) 列表**。  
存储把各片组成一个对象。惊喜：即便最终 50GB，Complete 也很快——它主要是**元数据操作**：记录「该对象由这些分片按此顺序构成」，并非把 50GB 物理拼成新文件再写一遍（呼应第 24 课元数据面 vs 数据面）。

#### 第四个调用：Abort Multipart Upload

明确取消未完成的 multipart，丢掉暂存分片（见下文「遗弃上传」）。

---

### 3. 分片大小与 10,000 片上限

硬上限：**最多 10,000 个 part**。

若固定每片 5MB → 最大约 **5MB × 10000 = 50GB**。用 5MB 去传 60GB，会在第 10001 片失败——前面 50GB 已传完，**极贵的失败**。

**正确做法**：按文件大小**动态**算分片大小，保证 part 数 ≤ 10000（大致 `ceil(fileSize / 10000)` 量级），但不要对小文件也拆成近万片。

实用公式直觉：

- 设默认地板（floor）如 **16MB 或 32MB**；  
- 再算「为不超过 10000 片所需的最小片大小」；  
- 取**较大者**。  

课程个人习惯：16–32MB 做地板 → 可覆盖约 160–320GB 而少纠结公式。

**为何不片越大越好？**  
片大小 = **重试粒度**。一片 500MB 失败就要重传 500MB；16–32MB 失败便宜。甜区大约 **16–64MB**。

---

### 4. ETag 陷阱

普通单次 PUT：ETag 常是内容的 **MD5**。很多人本地哈希后与 ETag 比对做完整性——对单次 PUT 合理。

**Multipart 对象的 ETag 不是整文件 MD5**，而是类似「各分片 MD5 的组合 + `-` + 分片数」（常见看到以 `-42` 这类结尾）。用「整文件 MD5 == ETag」会误判失败。

端到端完整性应：

- 用存储的 **Checksum** 能力（现代 AWS SDK 可算 CRC32C / SHA256 等，并可要整对象校验）；或  
- 客户端算 **SHA-256**，写入用户元数据，上传后由**后台任务**核对——还可顺带做去重。

---

### 5. 遗弃的 Multipart：看不见却一直在付费

场景：已传约 300 片 × 32MB ≈ 10GB 暂存，用户关标签，**既没 Complete 也没 Abort**。

结果：

- 这 10GB **仍占存储并按月计费**；  
- **List 桶 / 控制台对象列表看不到**——因为正式对象还不存在；  
- 要用「列出未完成 multipart」类 API/CLI 才看得见（课程演示：控制台只显示一个对象，CLI 却列出多笔未完成上传、数百 MB 分片）。

**生产铁律**：每个桶从第一天就配生命周期规则——例如 **7 天后 Abort 未完成的 Multipart**。7 天是常见默认平衡；几乎零成本，永久堵住费用漏洞。

---

### 6. 预签名 + Multipart：生产完整架构

大文件从浏览器上传的典型链路：

1. 浏览器 → `POST /uploads/init`（文件名、大小、类型）。  
2. 后端：鉴权 → 算分片大小 → **Create Multipart Upload** → DB 插入 **pending** → 为各分片生成预签名 URL → 返回 `uploadId`、`partSize`、各 part URL。  
3. 浏览器对桶发 **N 路并行 PUT**（甜区约 **4–6**；过多会在本地争带宽）。  
4. 浏览器 → `POST /uploads/complete`，带 uploadId + `[{partNumber, ETag}, …]`。  
5. 后端调 **Complete Multipart** → **Head Object** 校验大小/类型等 → DB pending → completed/ready → 可选往队列发 `file.uploaded`（审计、转码、WebSocket 通知 UI）。

#### 实现四点

1. **不要一次预签 10000 个 URL**（init 响应会变成数 MB JSON）→ 按需批次签，如每次 100。  
2. 并行度 **4–6** 为宜。  
3. 浏览器 `File.slice` 得到懒加载 Blob → 内存约 **partSize × 并发度**，不是整个文件。  
4. 桶 CORS 必须 **暴露 ETag**，否则 JS 读不到响应头，无法 Complete。

#### 可恢复上传（几乎白送）

刷新后客户端问：「这个文件是否有进行中的上传？」→ 后端查 pending → `ListParts(uploadId)` 看桶上已有哪些片 → 只给**缺失片**发新预签名 → 从 part 341 等处继续，而非从 0。

#### Demo 量级直觉

2GB 文件 → 约 16MB × 125 片，并发 5：网格上灰=等待、蓝=传输中、绿=完成；进度由「已完成片数」稳定估算；网络面板可见约 125 个直达桶域名的 PUT，最后一次 Complete 打你的 API。

---

### 7. 下载：永远不要经你的服务器代理

下载次数通常远大于上传。若 Handler `GetObject` 再把字节拷到 Response：

- 整个下载期间占着 goroutine/事件循环；  
- 云厂商按**带宽/出站（egress）**收费，流量穿你的机器 = 多付钱；  
- 比 CDN 慢（CDN 全球节点 vs 你少数区域）。

原则：用户取文件应**直接从桶或 CDN**，不要经应用当中继。

#### 模式 1：公开内容 / 私有桶 + CDN

站点静态资源、公开商品图等：桶可公开，或更好——**桶私有，仅 CDN 可读**；长 Cache-Control + **内容寻址 key**（key=内容哈希）→ 内容变则 URL 变，缓存最简单。通常最便宜最快。

#### 模式 2：预签名 GET——与缓存的冲突

流程类似预签名 PUT：后端鉴权后发短时（如 5–15 分钟）预签名 GET。

问题：URL 含时间戳与签名 → **同一文件每次 URL 不同** → CDN 视为不同资源 → **命中率≈0**，白挂 CDN 仍付满额 egress。

缓解：

- **便宜做法**：签成「有效至整点/下一小时」等对齐过期，同一小时内用户拿到相同 URL，CDN 能缓存（牺牲一点过期精度）；  
- **正经做法**：用 CDN 自己的签名 URL / **签名 Cookie**，鉴权在边缘完成，CDN 全权缓存。视频会话要拉成百上千分片时，尤其不该每片都回源站签名。

#### Range 请求：206 / Content-Range / 416

客户端说：只要字节 1_000_000–3_000_000。  
服务器：**206 Partial Content** + `Content-Range`（这些字节、总长度）。非法范围 → **416 Range Not Satisfiable**。

这是 **HTTP 语义**，对象存储原生支持。解锁：

- **视频拖拽**：算偏移 Range，不必下完前 30 分钟；  
- **断点续下**：从断点字节继续；  
- **并行下载**：多连接各拉不同 Range（下载器加速）。

可用 Range 只读文件头（如 PNG 魔数）做类型探测，省带宽。

#### 分段流媒体：HLS / DASH

Range 渐进下载有上限：仍是**一个版本**的文件。Netflix/YouTube 等按网速切码率 → **自适应码率**：转码多清晰度 → 切成数秒分片 → **清单（manifest）**；播放器先拉清单，再按下载速度选更高/更低清晰度分片。

对对象存储：**每个分片与清单都是普通对象**；难在**转码流水线与队列 Worker**，不在「怎么存」。若视频只是产品配角 → 用 Mux、Bunny 等托管；若流媒体是核心 → 自建管道才划算。

---

### 8. 钱：存储、请求次数、Egress

大致三类账单：

1. **存储**：GB·月；  
2. **请求次数**：写/删通常比读贵一个数量级；  
3. **Egress**：数据离开云厂商——下载大户杀手。  

这也是 Cloudflare R2 等「**egress 免费**」宣传杀伤力大的原因。价格常变，架构决策前看官网价目。

---

### 9. 与第 24 课合并的速记清单（大文件向）

对象存储放弃原地可变，换容量与耐久；Key 自生成、高熵在前；元数据写入时定好；DB 索引「有哪些文件」，桶存字节；小文件可经服务器流式+限大小；大文件浏览器预签名（优先 POST+策略）；两阶段 pending + Head 校验；大文件 Multipart + 动态分片；别信 Multipart ETag 当 MD5；每桶 Abort 未完成 multipart 生命周期；下载走预签名 GET/CDN，不经应用；Range 做拖拽/续传/并行；视频用 HLS/DASH 分片。

## 后端规则与最佳实践（Checklist）

- [ ] 产品接受 >5GB 或弱网大文件 → 默认 Multipart，不赌单次 PUT。  
- [ ] 分片大小按文件动态算，遵守 10000 片上限；地板约 16–32MB，甜区约 16–64MB。  
- [ ] 保存每片 ETag；Complete 时按序提交。  
- [ ] 完整性：Checksum 功能或自管 SHA-256 + 后台校验；**不要**用 Multipart ETag 当整文件 MD5。  
- [ ] 每桶生命周期：**自动 Abort 未完成 Multipart**（如 7 天）。  
- [ ] 浏览器：init → 并行分片（4–6）→ complete；分批预签名；CORS 暴露 ETag。  
- [ ] 支持续传：ListParts + 只签缺失片。  
- [ ] 下载禁止经应用代理；公开资源 CDN+内容寻址；私有资源注意预签名与 CDN 缓存策略。  
- [ ] 需要拖拽/续传/加速下载 → 用 Range（206）。  
- [ ] 流媒体产品想清楚：托管转码 vs 自建 HLS/DASH 管道。  
- [ ] 架构评审看清存储 / 请求 / egress 哪项会爆。

## 常见坑与反模式

1. 固定 5MB 分片传超大文件 → 撞 10000 片上限，浪费已传流量。  
2. 单次 PUT 传 GB 级 → 弱网重头再来。  
3. 用 Multipart ETag 做 MD5 校验 → 误报损坏。  
4. 无 Abort 生命周期 → 暂存分片隐形月费。  
5. 一次预签上万 URL → init 响应过大。  
6. 浏览器并发开太高 → 本地带宽互抢、更不稳定。  
7. CORS 未暴露 ETag → 无法 Complete。  
8. 下载走自己的服务器 → 占满 worker + 双倍带宽账单。  
9. 预签名 GET 每次唯一 URL → CDN 永不命中。  
10. 把「对象存储会存」当成「替你做视频自适应」——转码管道仍要自己或托管服务。
