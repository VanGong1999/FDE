# 21. 扩展与性能（Scaling & Performance）

## 一句话直觉

用户说的「慢」几乎总是延迟；用平均值会骗自己——看 P50/P90/P99，先测量找到瓶颈，再谈缓存、索引和扩容；系统不能跑在 100% 利用率上还指望稳定。

## 本课问题

- 「快」如何用数字定义？为何平均值在性能场景几乎没用？
- P50 / P90 / P99 怎么读？为何工程师死磕尾部延迟？
- 吞吐与延迟如何联动？利用率曲线为何会指数恶化？
- 为何「先加缓存/加机器」经常白忙一周？
- N+1、索引代价、连接池、缓存失效、垂直 vs 水平扩展要点是什么？

---

## 核心概念详解

### 1. 延迟（Latency）：用户真正感受到的「慢」

用户从点击按钮 → 浏览器发请求 → 服务处理（常查库、调外部 API）→ JSON 回传 → 渲染，整段耗时就是**延迟**。人们说「你们 App 好慢」，说的就是延迟——无论他们知不知道这个词。

#### 1.1 延迟不是单一数字

同接口：一次 50ms（缓存命中 / 机闲），另一次 200ms（查库 / 机上已有 50 个并发）。真实流量不可在白板上精确预言。

若只报平均：`(50+200)/2 = 125ms`——**几乎不传达分布**。性能语境下，平均值常**误导甚至无用**；变差（variance）才关键。

#### 1.2 为何平均值危险（极端例）

1000 次请求平均 100ms，但可能是：99% &lt; 50ms，而 1% 要 **5 秒**。那 1% 是真实难受的用户。放大到日均 100 万请求 → **1 万次**要等 5 秒；平均值仍可能「看起来挺好」，你却看不见尾部地狱。

#### 1.3 百分位：P50 / P90 / P99

| 指标 | 读法（课程强调的直觉） |
|------|------------------------|
| **P50** | 一半用户体验到的延迟量级（中位数感） |
| **P90** | 约 **10%** 用户达到该延迟（100−90） |
| **P99** | 约 **1%** 用户达到该延迟；也可说 99% 用户更快 |

后端常盯 **P95/P99**：尾部往往对应最复杂业务路径（支付、重查询、外部服务、Webhook 等待）。这些用户常是**高价值客户**（下单者 vs 随便逛逛的人）。讨论性能/扩容时，P50/P90/P99 会反复出现——先学会行话。

---

### 2. 吞吐（Throughput）

- **延迟**：单次请求从发到响应多久  
- **吞吐**：单位时间能处理多少请求（RPS / RPM）

二者相关但反直觉：低负载时延迟很美（如 10 RPS → 150ms）；冲到 1000 RPS 可能延迟飙到 2s。要回答「能不能撑住黑五 / 邮件爆发 / 上了播客」必须**同时**看吞吐与延迟。

负载升高时：延迟先缓慢变差，过某点后**急剧变差**——与下一节利用率有关。

---

### 3. 利用率（Utilization）与延迟曲线

**利用率** = 系统容量中正在被使用的比例。0% 空闲；100% 打满、濒临崩溃。

#### 冰淇淋店 / 高速公路类比

- **低利用率**：店里没人 → 点完立刻拿到（低延迟）
- **高利用率**：店员做每个冰淇淋仍要 2 分钟，但你在长队里等（服务速率没变，**排队**让感知延迟暴涨）
- **公路 50%**：畅行；**80%** 变道困难；**90%** 时好时堵；**100%** 完全锁死

后端同理：CPU/内存利用率升高 → 请求排队 → 等待变长。直觉以为延迟随利用率**线性**升，实际接近满载时往往**指数恶化**。

#### 生产启示

- **不能**在 100% 利用率下还期望稳定表现  
- 需要 **headroom（余量）**：生产常见跑在 **约 60–80%**，留 ~20% 吃流量尖峰  
- 真实流量是 **burst（突发）**，不是节拍器：均值 40% 时，一阵突发就能瞬间打满——没缓冲就崩

---

### 4. 瓶颈（Bottleneck）：先测量，别猜

「系统慢」= 某处特定组件在拖后腿。实务中常跳过定位，直接套「标准答案」：加缓存、升级 Postgres、水平加机器——有时运气好，更多时候**花一周治错病**，真凶仍在。

#### 课程故事

`GET /products/:id` 变慢 → 本能怪数据库 → 花一周上 Redis → 仍慢 → 加细粒度计时后发现：

- DB ~10ms，缓存 ~5ms  
- 真正杀手：同步写远程日志（Elasticsearch 等）**阻塞**整请求 ~**500ms**

其它常见「以为是 DB」其实是：JSON/XML 序列化、**响应体过大导致网络传输**等。

**法则：Never guess, always measure.（先测量，再优化。）**

---

### 5. Profiling 与分布式追踪

#### Profiling（分析）

运行时采样：哪些函数吃时间。输出可用 **Flame Graph（火焰图）**：宽 = 更耗时，栈向上堆叠。首次看图常惊讶：**瓶颈不在你以为的业务逻辑**，而在 JSON 序列化或循环里调外部 API。

局限：CPU profiler 对 **I/O bound**（DB、文件、外部 HTTP、队列等待）不敏感；典型 SaaS 性能问题多为 I/O，CPU 重活（图像/ML）才更吃 profiler。

#### Distributed Tracing（分布式追踪）

沿请求跨组件打时间戳：进 handler、查库、调外部 API 各花多久。例：业务代码 2ms，DB 800ms → 去优查询。属可观测性（见第 18 课），是定位延迟的利器。

---

### 6. 数据库常见性能问题

DB 常成瓶颈有道理：落盘持久化、并发一致性、复杂查询——但要先摘「低垂果实」。

#### 6.1 N+1 查询问题

模式：先查 N 条，再在循环里每条再查 1 次相关数据 → **1+N** 次查询。

前端类比：列表 20 篇博客再循环 20 次拉作者 = 21 次 HTTP；1000 条 → 1001 次。每次查询有网络、解析、规划、执行开销；哪怕单次 5ms，1000 次 = 5s 转圈。

**后端才是重灾区**（对 DB 而言，App 像「前端」）。ORM 写法很像普通 `for`，却在背后打爆 SQL：

```text
posts = db.select.posts...
for post in posts:
    author = db.select.author where id = post.author_id  # N 次
```

修复：批量 / Join / ORM 的 `select_related` / `prefetch_related` / `includes` / `join` 等 → 例如 **2 次查询**（帖子 + 作者们），与列表长度脱钩。开发期打开 ORM SQL 日志，确认没有隐藏 N+1。

#### 6.2 索引（Indexes）

无索引 ≈ 图书馆无目录：按作者找书只能**全表扫描（sequential / full table scan）**。索引（常用 **B-Tree**）维护列值有序副本 + 指向行，按 `author_id` 可直接定位。

百万行：全表或许数秒；有索引可到几十～百毫秒级（量级示意）。

**索引不是免费的：**

1. **占空间**（随表增长）  
2. **每次 INSERT/UPDATE/DELETE 都要维护索引** → 索引过多会显著拖慢写

策略：

- 主键通常已有索引（如 Postgres）  
- 明显高频条件（如 `author_id`）可建表时加上  
- 不确定的列：用监控/追踪确认热点查询后再加  
- **忌**：给每一列都建索引  

进阶：

- **复合索引 (user_id, created_at)**：顺序重要；可支撑「两列」或「只有左前缀 user_id」；通常**不能**只用右列 `created_at`  
- **覆盖索引（Covering）**：查询所需列都在索引里，免回表；索引更大，需权衡  
- 用 **`EXPLAIN ANALYZE`**：看是否 Seq Scan、用了哪个索引；加索引后再跑对比是否变 Index Scan

#### 6.3 连接池（Connection Pooling）

每次新建 DB 连接要：TCP 三次握手、认证、加密协商、会话状态、DB 侧分配内存……昂贵。若每请求建连即关 → 延迟税 + 易耗尽 Postgres 连接上限（常几百级）→ 尖峰时 DB 崩溃。

**池化**：维持一组空闲连接，借用 → 查询 → 归还，复用连接。

| 类型 | 含义 | 风险 |
|------|------|------|
| **应用内池（Internal）** | 驱动内置池 | 水平扩展到多实例时，实例数 × 每池大小可能 **超过 DB max_connections**（如 3×150 &gt; 300） |
| **外部池（External）** | 如 **PgBouncer** 统一池化 | 多实例共享一个池上限，尖峰更可控 |

生产有自动扩缩时，更常需要外部池。

### 7. 缓存与性能

查询与索引、池都优化后 DB 仍慢 → 缓存：把贵操作结果放入 Redis 等，命中则几十 ms 级返回。

#### 失效（Invalidation）——两大难之一

名言：编程两难——命名与缓存失效。数据一变，CDN/浏览器/反向代理/应用缓存多层都要对齐。

两种主策略：

1. **基于时间（TTL）**：如 5–10 分钟过期；难在选「最优 TTL」（过短命中率低，过长易脏）  
2. **基于事件**：更新用户资料时主动删/失效缓存；准，但每个写路径都要记得——漏一处就脏读  

#### 本地 vs 分布式 vs 分层

- **本地缓存**（进程内 Map）：极快（数 ms），多实例 → **不一致**  
- **分布式**（Redis/Memcached/Valkey）：多实例共享，但多一次网络（可能几十 ms）  
- **分层（Tiered）**：最热数据本地 + 上游 Redis  

#### 模式

| 模式 | 行为 | 取舍 |
|------|------|------|
| **Cache-Aside（懒加载）** | 读：先缓存再 DB，回填；写：更新 DB 并删缓存 | 最常用、直观 |
| **Write-Through** | 写时同时更新 DB 与缓存 | 少 miss；写更慢 |
| **Write-Behind** | 先写缓存立即返回，异步落 DB | 写快；DB 失败会不一致 |

#### Cache Hit Rate

90% 命中 = 90% 请求不用打 DB。过低（如 20%）说明策略/容量/访问模式不对。影响命中率：TTL、缓存容量、是否理解用户访问模式。

---

### 8. 垂直扩展 vs 水平扩展

流量涨 → 单机资源不够 → 两种基本路线：

#### 垂直扩展（Scale Up）

换更大机器：更多 CPU 核、RAM、磁盘/SSD、更快网卡。

- **优点**：架构几乎不变；代码不用为分布式改；运维简单；有时「一台大机器」比「两台一半」更省且省去多机协同成本  
- **缺点**：**硬件天花板**；**单点故障**（一台挂全站挂）；难做**多地域**就近接入  

#### 水平扩展（Scale Out）

加更多中等实例一起服务。

- **优点（理论）**：吞吐近似线性加；可无限加机器；一台挂了其它顶上；可多地域 + LB 就近路由降延迟  
- **缺点：复杂度**——需要负载均衡与算法、会话/状态同步、网络分区时冲突决策、实例挂了如何摘除与回流……分布式系统往往是**换一类问题**，不是消灭问题  

选择取决于你更愿应对哪一类问题。

---

### 9. 其它性能实践（路线图要点）

- **批处理**大数据，减轻 DB 压力  
- **避免泄漏**：关文件句柄、DB 连接；长任务后清理  
- **减小网络开销**：缩 payload、压缩  
- **性能测试与 profiling**  
- **先写清晰可维护代码，避免过早优化**；模块化便于局部优化  
- 过载时**优雅降级**而非整站崩  
- 非关键路径（发信、打日志）**卸到队列/后台**，把资源留给关键路径（呼应第 18 课同步日志陷阱）

## Checklist

- [ ] 看 P50/P90/P99，不只看平均延迟  
- [ ] 同时理解吞吐与延迟在负载下的关系  
- [ ] 生产留利用率余量（约 60–80%），应对 burst  
- [ ] 变慢时先埋点/追踪/火焰图，再改架构  
- [ ] 消灭 N+1；用 EXPLAIN ANALYZE 指导索引  
- [ ] 索引克制；懂复合索引顺序与写放大  
- [ ] 连接池：多实例场景评估 PgBouncer 等外部池  
- [ ] 缓存：明确 TTL/事件失效与 hit rate；慎选模式  
- [ ] 扩展：先吃透垂直上限与单点，再上水平与 LB  
- [ ] 非关键 I/O 异步化；过载可降级  

## 常见坑

1. 平均延迟「很好」，P99 用户在离职边缘。  
2. 利用率打满还加功能。  
3. 猜是 DB → 盲目加缓存；真凶是同步日志/大 payload。  
4. ORM 循环查库造成 N+1。  
5. 给所有列建索引 → 写入变慢。  
6. 每实例内部池 × 自动扩缩 = 撑爆 DB max_connections。  
7. 缓存只加不失效 → 脏数据。  
8. 过早微优化，代码变不可维护。
