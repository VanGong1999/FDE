# 08 · 认证与鉴权

一句话直觉：**认证（Authentication）回答「你是谁」；鉴权/授权（Authorization）回答「你能做什么」**——先验明正身，再按权限开门。

## 本课要解决什么问题

每天登录、注册、第三方「用 Google 登录」、调 OpenAI 的 API Key……背后都是身份与权限体系。后端工程师必须搞清：

1. 有状态（Session）与无状态（JWT）各自解决什么、牺牲什么？
2. Cookie、Session、JWT、API Key、OAuth2/OIDC 分别用在哪？
3. 密码如何安全存放？角色权限如何建模？
4. 有哪些经典攻击与防御（错误信息泄露、时序攻击、CSRF/XSS/MITM、暴力破解）？

## 核心概念详解

### 1. 两句话定义

| 概念 | 问题 | 一句话 |
|------|------|--------|
| **Authentication（认证）** | Who are you? | 给主体（用户/服务）赋予并验证**身份** |
| **Authorization（授权）** | What can you do? | 在该上下文中判定**能力与权限** |

上下文可以是网站、OS、手机 App、某个租户/组织。

### 2. 历史脉络（帮助理解「为何长成现在这样」）

1. **前工业社会**：熟人信任、村长担保、握手——**隐式认证**，无法跨村扩展。
2. **印章时代**：蜡封 = 早期「认证令牌」（你**拥有**什么）；可被伪造 → 出现 bypass。
3. **口令时代（电报等）**：共享口令短语 = 你**知道**什么；静态共享秘密。
4. **主机与密码（1960s）**：MIT CTSS 多用户密码；曾明文存储，打印密码文件事故推动「**不可逆哈希**」思想。
5. **现代密码学**：哈希、Diffie–Hellman 等非对称密码、PKI；Kerberos 票据 → 令牌思想先驱。
6. **MFA**：知（密码）+ 有（OTP/卡）+ 是（生物特征）。
7. **21 世纪**：云、移动、API → OAuth2、JWT、Zero Trust、无密码（WebAuthn）；未来方向含去中心化身份、行为生物特征、**后量子密码**。

原则演变：**Something you have → something you know → 多层组合 → 委托令牌而非共享密码**。

### 3. 三大基础构件：Session、JWT、Cookie

#### 3.1 为何需要 Session：HTTP 天生无状态

HTTP **按设计无状态**：每个请求自包含，服务器默认不「记得」上一次。早期静态网页够用；电商购物车、保持登录等**动态交互**需要「跨请求记忆」→ **Session**。

**Session 工作流：**

1. **创建**：登录成功 → 服务器生成唯一 `sessionId`，把用户数据（角色、购物车等）存入持久层（文件 → DB → Redis/Memcached）。
2. **下发**：把 `sessionId` 通过 **Cookie** 发给浏览器。
3. **后续请求**：浏览器自动带上 Cookie → 服务器用 ID 查存储 → 恢复用户上下文。
4. **过期**：短生命周期（如 15 分钟）；过期后需重新建立。

存储演进：文件 → 数据库 → 分布式内存（Redis）以换速度与可扩展性。

#### 3.2 JWT（JSON Web Token）：把状态「塞进令牌」

分布式、多区域、微服务下，同步 Session 成本高（内存、复制延迟、一致性）。JWT（约 2015 形式化）提供**无状态传声明（claims）**。

**结构（三段，`.` 分隔，Base64URL）：**

1. **Header**：元数据（如签名算法）。
2. **Payload**：声明——常见 `sub`（用户 ID）、`iat`（签发时间）、可选 `name`/`role` 等。
3. **Signature**：用密钥对前两段签名；防篡改。改了任意内容，验签失败。

**优点：**

- **无状态**：不必为每个会话做服务端存储（省成本）。
- **可扩展**：多实例共享验签密钥即可验身份。
- **可移植**：可放 Authorization Header、Cookie 等（注意存储安全）。

**缺点：**

- 令牌被盗即可冒充，直到过期。
- **难以单独吊销**某一用户：改全局密钥会踢掉所有人。
- 纯 JWT 无法「实时查」谁还在线。

**混合方案：** 验签后仍查黑名单/版本号（Redis）——用少量状态换可吊销；但会引发「既然查库了为何不全用 Session」的权衡。业界常见建议：生产中复杂系统优先 **成熟 Auth Provider**（Auth0、Clerk 等）；学习阶段应自己实现一遍以理解权衡。

#### 3.3 Cookie

Cookie = 服务器通过 HTTP 机制在**浏览器里存一小段数据**，且：

- 通常**仅对该站点后续请求自动附带**；
- 一站点看不到另一站点的 Cookie（浏览器隔离）；
- 可设 `HttpOnly`（JS 读不到，减 XSS 偷 Session）、`Secure`（仅 HTTPS）、`SameSite`（减 CSRF）等。

认证里 Cookie 常承载 `sessionId` 或 JWT，自动化「服务器发令牌 ↔ 客户端回传」循环。

### 4. 有状态 vs 无状态认证

#### 4.1 有状态（Stateful）典型流

```
Client → 用户名/密码 → Server
Server 校验 → 生成 sessionId → 写入 Redis/DB
Server → Set-Cookie(sessionId, HttpOnly) → Client
后续请求自动带 Cookie → Server 查存储 → 识别用户
```

**Pros：** 中心化控制；易吊销/登出；实时掌握活跃会话；多数 Web App 更安全、好管。  
**Cons：** 扩展与跨区域同步成本；运维复杂度。

#### 4.2 无状态（Stateless / JWT）典型流

```
Client → 凭证 → Server
Server 校验 → 用密钥签发 JWT（含 userId、role…）→ 返回客户端
后续请求：Authorization: Bearer <JWT>
Server 验签 → 从 payload 取身份（不查会话库）
```

**Pros：** 易水平扩展；适合分布式与部分移动/API 场景。  
**Cons：** 吊销难；密钥轮换影响面大。

#### 4.3 如何选（经验法则）

| 场景 | 倾向 |
|------|------|
| 浏览器 Web / SaaS 主站 | **有状态 Session**（或 BFF + 短 JWT） |
| 大规模分布式 API、多服务验身份 | **JWT / 无状态**（或网关统一验） |
| 移动 + Web 混合 | 混合：Web 有状态，移动/第三方 API 无状态 |
| 不确定、中大型生产 | **外部 IdP / Auth Provider** |

### 5. API Key 认证

**用途：** 不是给人点登录表单的，而是给**程序化访问**——机器对机器（M2M）、第三方集成、配额与权限可控的服务器访问。

流程直觉：在平台 UI「生成 API Key」→ 得到密码学安全随机串 → 请求时放 Header（或约定位置）→ 服务端识别身份、套餐、配额。

例：ChatGPT 网页是人对 UI；同一模型能力用 API Key 给**你的后端**调用——无人工输密码的登录环。

**Pros：** 生成简单；适合 M2M。  
**Cons：** 长期密钥泄露风险高；需轮换、最小权限、环境隔离；粒度通常粗于 OAuth scope。

### 6. OAuth 2.0 与 OpenID Connect（OIDC）

#### 6.1 问题：委托（Delegation）

站点越来越多 → 密码复用、管理疲劳。更致命：旅行 App 要读 Gmail 行程、社交 App 要导通讯录——早期错误做法是**把密码分享给第三方** → 全权限、难吊销、一次泄露全盘崩。

**OAuth 思想：** 用**有限权限的令牌**代替密码共享。

#### 6.2 OAuth 角色

| 角色 | 例子（「Facebook 读我的 Google 通讯录」） |
|------|------------------------------------------|
| Resource Owner | 你（用户） |
| Client | Facebook（请求访问的应用） |
| Resource Server | Google 上存通讯录的服务 |
| Authorization Server | 负责登录并签发令牌的一方 |

OAuth 1.0 已解决「不共享密码的委托」；OAuth 2.0（约 2010）简化实现（Bearer Token）、按应用类型提供多种 **Flow**，但代价是实现细节仍易踩坑。

**常见 Flow：**

- **Authorization Code**：服务端应用（现应 + PKCE）。
- **Implicit**：浏览器应用（**已不推荐**）。
- **Client Credentials**：纯 M2M，无用户。
- **Device Code**：智能电视等输入受限设备。

重要：**OAuth 本身擅长授权（能访问什么），不完整解决「登录身份是谁」。**

#### 6.3 OIDC（约 2014）

在 OAuth2 上增加 **ID Token**（通常是 JWT），携带 `sub`、签发时间、签发方、姓名邮箱等 → 「Sign in with Google/Facebook/Discord」的技术底座。

直觉：OAuth2 + OIDC = 数字时代的门卫与钥匙匠——**只给要过的门、只给申请过的权限**。

### 7. 密码：哈希与加盐（Hash + Salt）

**绝不存明文密码。** 注册时：

1. 对密码做**慢哈希**（如 bcrypt / scrypt / Argon2，非简单 MD5/SHA 一次）。
2. **Salt（盐）**：每用户随机盐，防彩虹表；同一密码不同用户哈希不同。
3. 库中只存哈希（及盐/参数）；即使用户 DB 泄露，也难还原明文。
4. 登录时：用相同算法哈希输入，与存储值做**常量时间比较**。

服务器自己也无法「查出原密码」，只能验证「这次输入是否匹配」。

### 8. 授权模型：RBAC 与 ABAC

#### 8.1 为何需要授权

认证通过 ≠ 全能。例：笔记 App 普通用户可 CRUD 自己的笔记；回收站/「死亡区」数据仅管理员可见。若用「上帝字符串」塞进每个请求 → 易被截获、难多人授权、难管理。

**Authorization = 不同用户拥有不同能力集合。**

#### 8.2 RBAC（Role-Based Access Control）

- 定义角色：`user` / `admin` / `moderator`…
- 角色绑定权限：读、写、删、访问某资源…
- 用户注册时赋角色；请求早期解析角色（可从 JWT/Session 或查库），交给后续中间件/Handler。
- 无权限 → **403 Forbidden**（注意与 401 区分：401 未认证或认证失败；403 已认证但不够权限）。

多租户组织里，管理员可给成员分配读/写等——仍是 RBAC 思想的延伸。

#### 8.3 ABAC（Attribute-Based Access Control）概要

按**属性**决策：用户部门、资源敏感级、时间、IP、租户……规则更细，也更复杂。适合强合规、细粒度策略；实现上常见策略引擎（如 OPA）。初学先扎实 RBAC，再按需上 ABAC。

### 9. Web 安全相关威胁（认证语境必知）

| 威胁 | 含义 | 与认证的关系 / 缓解 |
|------|------|---------------------|
| **CSRF** | 诱导已登录用户浏览器向受害站发请求 | Cookie 自动附带 → 用 SameSite、CSRF Token、关键操作二次确认 |
| **XSS** | 注入脚本读页面/存储 | 可偷 localStorage 里的 JWT；优先 **HttpOnly Cookie**、严格输出编码、CSP |
| **MITM** | 中间人窃听/篡改 | **全站 HTTPS**；HSTS；不在明文信道传 Cookie/Token |
| **暴力/字典攻击** | 试密码 | 速率限制、账户锁定/冷却、MFA、强密码策略 |
| **Timing attack** | 用响应时间差推断「用户是否存在」或比对进度 | 见下节 |
| **信息泄露型错误消息** | 「用户不存在」vs「密码错误」 | 统一笼统文案 |

### 10. 认证错误消息与时序攻击

#### 10.1 错误消息要笼统

友好文案对攻击者同样友好：

- 「用户不存在」→ 攻击者换邮箱继续扫。
- 「密码错误」→ 确认用户名有效，专心暴破密码。
- 「尝试过多已锁定」→ 暴露策略细节。

**认证失败一律：** 如 `Authentication failed`（或同等笼统语）。其他业务校验可以更友好；**唯独认证流程要对攻击者「模糊」。**

#### 10.2 Timing attack

典型登录步骤：① 查用户是否存在 → ② 是否锁定 → ③ 哈希比对密码。

若 ① 失败立刻返回，比 ③ 失败（含慢哈希）**更快**，攻击者可测延迟推断用户名是否存在。

**防御：**

1. 使用**常量时间**比较函数比对哈希。
2. 即使用户不存在，也走完「假哈希 / 固定延迟」，抹平时间差。
3. 配合速率限制与笼统错误消息。

### 11. 速率限制（Rate Limiting）

限制单 IP / 单用户在窗口内的请求数，防暴破登录、防刷接口。超限返回 **429 Too Many Requests**。常做成中间件（见第 10 课），与认证紧密配合。

## 后端规则与最佳实践（Checklist）

- [ ] 分清认证 vs 授权；401 vs 403 语义正确。
- [ ] 密码：Argon2/bcrypt + 每用户盐；禁止明文、禁止可逆加密当「存储」。
- [ ] Session Cookie：`HttpOnly` + `Secure` + 合适的 `SameSite`。
- [ ] JWT：短 TTL；敏感操作可再鉴权；慎放 localStorage；吊销策略预先设计。
- [ ] 生产优先成熟 IdP；自研仅在充分理解威胁模型后。
- [ ] OAuth：能用 Authorization Code + PKCE 就不用 Implicit；scope 最小化。
- [ ] API Key：可轮换、可过期、可限权限；存哈希而非明文（若可能）。
- [ ] RBAC 在请求早期解析并写入 request context。
- [ ] 认证错误消息笼统；防 timing；登录接口强制速率限制。
- [ ] 全站 HTTPS；关键操作防 CSRF。

## 常见坑与反模式

| 反模式 | 更好做法 |
|--------|----------|
| 明文或可逆加密存密码 | 慢哈希 + 盐 |
| JWT 永不过期且无黑名单 | 短 TTL + 刷新策略 / 可吊销设计 |
| 把 JWT 当「绝对安全」塞进 localStorage | 评估 XSS；考虑 HttpOnly Cookie / BFF |
| 「上帝 API Key」万能权限 | 最小权限、分环境 |
| 分享用户密码给第三方集成 | OAuth 委托令牌 |
| 登录返回「用户不存在」 | 统一 Authentication failed |
| 只靠前端隐藏管理员按钮 | 服务端强制鉴权 |
