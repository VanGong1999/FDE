# 20. 后端安全（Backend Security）

## 一句话直觉

攻击者不关心你用什么框架，只关心「开发者在哪里做了假设」——几乎所有漏洞都来自：把用户输入当可信数据、或把数据当成可执行的代码。

## 本课问题

- 安全域很广（浏览器/网络/OS/应用），后端工程师至少要守住哪些？
- 注入类攻击的共同根因是什么？SQL / NoSQL / 命令注入如何防？
- 密码为何不能明文、不能只用快哈希？盐、慢哈希、成本因子是什么？
- Session / Cookie / JWT 各有哪些坑？限流怎么分层？
- BOLA / BFLA 等授权漏洞为何「过了登录」仍会炸？
- XSS、CSRF、误配置与「纵深防御」如何落地？

---

## 核心概念详解

### 1. 目标：建立偏执心态，而非背一份漏洞清单

安全是巨大领域：浏览器安全、网络安全（TLS）、**服务器 OS 安全**、以及**应用代码安全**。本课聚焦后端工程实践，目标不是「明天上线所有炫技」，而是：

> **写每一行代码时，安全都在后脑勺。**  
> 没有「绝对安全」的应用；技术在变，漏洞会一直出现——但必须尽力。

不要背抽象列表；要学会**像攻击者一样想**：开发者在哪里做了假设？

常见危险假设：

- 用户输入是干净的
- 用户就是他们声称的人
- 请求一定来自「我们的前端」
- 没人会开 Network 面板改参数

截止日期压力下「只想 happy path」很正常；攻击者专戳边界、改输入、挑战每一个假设。心智模型应跨语言通用：Go / Python / Node / Rust 都一样，每次写代码问：**安全上什么可能出错？**

---

### 2. 注入攻击总论：语言边界 +「代码 vs 数据」混淆

后端同时说多种「语言」：

- 对 DB → **SQL**
- 对浏览器静态资源 → HTML/CSS/JS
- 对 OS → **Shell** / 系统调用

每种语言有自己的语法与特殊字符（引号、分号、注释符、`$` 操作符…）。**用户输入从一种语言语境跨进另一种**时，特殊字符可能变成「命令」——这就是注入的根因。

一句话：**把本该是数据的东西，当成了可执行代码（或反过来）。**

防御总原则：

- 用户输入必须**始终是数据**，绝不当可执行物
- 用能 **分离结构（代码）与数据** 的 API：参数化查询、参数数组传给进程等
- **禁止**用字符串拼接 / 模板把用户输入混进控制语法
- 每当你在拼一个「会被另一系统解释」的字符串且其中含用户输入 → **停下来找参数化替代方案**（几乎总有）

---

### 3. SQL 注入（深挖）

#### 3.1 Happy path vs 攻击

登录：邮箱+密码 → 服务端查库。若用**字符串拼接**把用户输入塞进：

```sql
SELECT * FROM users WHERE email = '<用户输入>'
```

攻击者邮箱填入类似：

```text
' OR '1'='1' --
```

拼接后逻辑变成：`email = '' OR '1'='1'`（恒真），`--` 注释掉后面多余引号 → **返回全部用户**。生产表还有哈希密码、地址、电话等敏感字段。

更狠：闭合后加 `'; DROP TABLE users; --` → 试图删表。现代驱动常默认禁止「多语句」，旧驱动/配置不当仍可能中招。攻击者还可 `UNION` 拖库、读文件、甚至在某些配置下执行 OS 命令——攻击面极大，故 SQL 注入几十年仍极危险。

SQL 中特殊含义举例：单引号定字符串、分号分隔语句、`--` 行注释、`OR`/`DROP` 等关键字。

#### 3.2 缓解 1：参数化查询 / Prepared Statements（首选）

不要拼接。把**查询模板**与**运行时数据**分开发给数据库，例如占位 `$1` / `?`，执行时传入用户输入。

数据库把槽位内容**纯当数据（字符串）**，恶意引号不会再「闭合」语句——整段攻击载荷只是一串垃圾邮箱，匹配不到行，也无法改写命令。

ORM 默认参数化；手写 SQL 时驱动也鼓励参数化。**唯一常见翻车**：故意拼 raw string。

校验层本应拦住非邮箱格式；即使校验弱，参数化仍是最后防线。

#### 3.3 缓解 2：DB 账号最小权限

应用连接 DB 的账号应主要只有 **DML**（SELECT/INSERT/UPDATE/DELETE），不要给随意 **DDL**（DROP/ALTER TABLE）权限——即便注入成功，也难直接删表。

#### 3.4 NoSQL 并非免疫

MongoDB 等用类 JSON 查询对象；若把用户 JSON **直接**当查询，攻击者可注入 `$ne` / `$gt` / `$exists` 等操作符。同样是「结构被用户控制」。（课程吐槽：若已选错数据模型，安全往往不是唯一担忧——但仍须警惕。）

---

### 4. 命令注入（Command Injection）

目标从 DB 换成 **操作系统**。

例：用户上传图片，后端调 `ffmpeg` 等 CLI，并把**用户提供的输出文件名**拼进 shell 命令：

```text
ffmpeg ... -o <用户输入>
```

若输入为：`; rm -rf /` 或管道、`&` 后台任务等 → 分号后变成新命令，后果可为删根目录、挂马等。各 shell（bash/zsh/fish）特殊字符不同，熟练攻击者会研究逃逸。

**修复（同构于 SQL 参数化）**：用语言提供的 API，**命令与参数分开传递**，参数直接交给进程，**不经过 shell 解释器**。这样用户字符串只是 argv 数据，不当代码。

### 5. 认证安全与密码存储

#### 5.1 能买就买 Auth 服务（务实建议）

生产级认证远不止「JWT 校验 + Cookie」：有状态会话、多设备撤销、OAuth 社交登录、邮箱密码与 Google 登录账号合并、权限模型……自己做要数周且易在安全或 UX 上砍角。Clerk 等厂商有专职安全团队。预算允许时优先托管；用户量极大、账单过高后再考虑自建。即便用托管，仍需理解原理与安全集成。

#### 5.2 密码存储演进

| 做法 | 问题 |
|------|------|
| **明文** | 库一破全泄漏；员工/DBA 可见；用户常多站复用密码 → 撞库接管 |
| **仅快速哈希（MD5/SHA256）** | 不可逆，但 **彩虹表** 可匹配常见密码；GPU 每秒可算海量哈希 → **离线暴力**仍可行 |
| **哈希 + 每用户随机盐（Salt）** | 盐须密码学安全随机；同密码不同哈希 → 彩虹表失效 |
| **慢哈希 + 成本因子（bcrypt / scrypt / Argon2id）** | 故意算得慢；合法登录多几十～几百 ms 可接受；攻击者从「十亿次/秒」降到「几次/秒」→ 破解从天级变世纪级 |

行业：长期默认 **bcrypt**；较新标准倾向 **Argon2id**。不要用 MD5/SHA256 存密码（它们适合文件完整性等场景）。

登录时：取盐与哈希 → 对输入做同样慢哈希 → 比较。

推荐阅读方向：Lucia Auth 文档类「安全认证实践指南」（课程提及；库本身已转为指导向）。

#### 5.3 会话（Session）

登录成功后服务端通常：

1. 生成 **128–256 bit** 级密码学安全随机 **Session ID**（不可猜测，否则会话劫持）
2. 存会话（Redis 或主库）+ 元数据：userId、创建时间、过期、IP、User-Agent 等
3. 把 Session ID 放进 **Cookie**，后续请求自动带回 → 服务端查表识别用户

#### 5.4 Cookie 关键 Flags

| Flag | 作用 |
|------|------|
| **HttpOnly** | JS 读不到 Cookie → 减轻 XSS 偷 Session/JWT |
| **Secure** | 仅 HTTPS 发送 → 防公共 Wi‑Fi / 中间人明文偷 Cookie |
| **SameSite** | `Strict` / `Lax` / `None`（`None` 需 Secure）。限制跨站带 Cookie → 大幅缓解 CSRF |

敏感凭证：**不要放 localStorage**（任意 XSS 可读）。

#### 5.5 JWT / 无状态认证

结构：Header.Payload.Signature。Payload 含 claims（`sub`、`iat`、自定义如 name/admin）；用服务端 Secret 签名。篡改 Payload 会导致验签失败。

注意：Payload 只是 **Base64**，**不是加密** → 勿放敏感信息。

| 优点 | 缺点 |
|------|------|
| 服务端可不存会话；易水平扩展 | **即时撤销困难**（库被盗号难一键踢全设备） |
| | 社区缓解：黑名单；**短 access + refresh token**；refresh 服务端可吊销 |

存储：localStorage 易被 XSS；HttpOnly Cookie 更稳妥——又回到 Cookie 方案。课程建议：**无强扩展诉求时优先有状态 Session**；多实例可用 **Redis 存 Session**。若用 JWT：短过期、refresh、HttpOnly Cookie。

#### 5.6 登录限流（多层）

无限流 → 每秒海量试密（撞库）或把服务打挂。

认证接口应**更严**，业务接口可相对松。建议分层：

1. **每 IP**：如 10 次/分钟（挡简单脚本；共享出口 IP / 代理池会误伤或被绕过）
2. **每账号**：如 15 分钟内 5 次失败锁定（挡对单账号轮换 IP；挡不住「一密打遍多账号」）
3. **全局**：系统级失败登录上限 → 触发告警、封 IP、上验证码等

目标：防撞库成功 + 防流量打爆。

### 6. 授权漏洞：过了登录 ≠ 能碰所有数据

**认证** = 你是谁（对应 users 哪一行）。  
**授权** = 你被允许做什么。

常见假安全感：路由层 `requireAuth` + 粗粒度角色/权限过了 → 服务层按 `id=5` 直接查库，**不校验该对象是否属于当前用户** → 改个 ID 读别人账单/发票。

#### 6.1 BOLA（Broken Object Level Authorization）

对象级授权缺失。修复：在**真正访问点**（Repository/查询）带上归属条件，例如：

```sql
WHERE id = $1 AND user_id = $contextUserId
```

对 SELECT/UPDATE/DELETE/INSERT 凡触及对象都要做。

**403 vs 404**：先查出对象再判归属并回 **403**，会向攻击者确认「该 ID 存在」→ 便于枚举后社工。更好：一条查询「id + 归属」无行 → 统一 **404**，让「不存在」与「存在但无权」不可区分。

#### 6.2 BFLA（Broken Function Level Authorization）

功能级：如 `/admin/invoices` 仅靠「URL 保密」——**Security through obscurity**。任何登录用户猜到 URL 即可拉全站发票。修复：服务端强制校验**管理员/角色/权限**，不能靠藏链接。

其它实践：自动化测鉴权场景（防回归）；敏感管理接口与鉴权失败写**审计日志**并告警探测行为。

---

### 7. XSS（跨站脚本）

攻击者设法在**受害者浏览器、在你的站点上下文**执行其 JS → 可读页面敏感数据、冒充用户调 API、偷非 HttpOnly 凭证、跳转钓鱼、篡改页面。

**Stored XSS 例**：评论 Markdown→HTML 后未经消毒存库并 `innerHTML`/注入 DOM；恶意 `<script>` 被每个浏览者执行。React 的 `dangerouslySetInnerHTML` 名称即警告。

类型还包括 Reflected XSS、DOM-based XSS。根因仍是：**用户内容在 HTML/JS 语境被当代码**。

防御：

1. **消毒/转义（首要）**：存库与输出前处理用户 HTML
2. **CSP（Content-Security-Policy）**：限制脚本来源、禁 inline script 等——属**纵深最后一道**，不能代替消毒
3. Session 用 HttpOnly，降低 XSS 偷票价值

---

### 8. CSRF（跨站请求伪造）——简述

利用浏览器**自动附带 Cookie** 的特性：用户登录 bank.com 后访问 evil.com，恶意页自动向 bank.com 发请求并带上 Cookie。

课程观点：现代栈 + **SameSite=Lax/Strict**（浏览器默认多已是 Lax）+ 合理 CORS 下，CSRF 风险大减；遗留系统仍须重视。另可用 CSRF Token 等经典手段。

---

### 9. 安全误配置与其它

- **密钥进 Git**：即使删文件，历史仍在 → **立即轮换**；密钥走 env / Vault / Parameter Store
- **生产开 debug 日志**：堆栈、SQL、敏感字段进生产日志，日志一破等于图纸泄露；生产用 info 等合适级别
- **安全响应头**：CSP、`X-Frame-Options`（防 iframe 点击劫持）等；现代框架常有一键 security middleware

---

### 10. 纵深防御与安全设计原则（收束）

所有漏洞都关于 **边界**：数据跨系统、跨权限、跨语言、跨标记语言。每次跨边界问三句：

1. 数据在哪里跨边界？
2. 我对数据做了什么假设？
3. 假设错了会怎样？

**没有单层防御完美** → 分层：

1. **输入校验**（入口尽早、尽量严）
2. **参数化操作**（DB / OS / 文件）
3. **在访问点做授权**（对象级）
4. **安全头与策略**（CSP、CORS、Cookie Flags）——缩小突破后破坏面
5. **监控与审计日志**——可疑访问告警

原则对应路线图：**最小权限、纵深防御、失败时偏安全（fail secure）、职责分离、Security by Design**。

延伸学习（课程推荐）：

- **PortSwigger Web Security Academy**（免费实验）
- **OWASP Top 10** 与 **OWASP Cheat Sheets**（认证、会话等专题）

## Checklist

- [ ] 一切用户输入：校验 + 消毒；跨边界不当代码
- [ ] SQL/NoSQL 参数化；禁止拼接查询；DB 账号最小权限
- [ ] 调 OS/CLI：命令与参数分离，不经 shell 拼接
- [ ] 密码：盐 + Argon2id/bcrypt；禁明文与快哈希
- [ ] Cookie：HttpOnly + Secure + SameSite；慎放 localStorage
- [ ] 登录多层限流；管理接口强鉴权（反 BFLA）
- [ ] 对象访问带归属条件（反 BOLA）；鉴权失败勿随意泄 403 枚举
- [ ] XSS：消毒为主，CSP 为辅
- [ ] 密钥不进仓库；生产日志级别正确；安全头中间件开启
- [ ] 敏感操作与鉴权失败有审计

## 常见坑

1. 「我们用了 ORM所以没有注入」——仍可能 raw SQL / 错误 API。
2. 「NoSQL 没有 SQL 注入」——有操作符注入。
3. SHA256 存密码 + 无盐/快哈希 → GPU 打穿。
4. JWT 放 localStorage；或超长过期无法撤销。
5. 只在网关鉴权，数据层不按 user_id 过滤。
6. 靠隐藏 `/admin` URL「保密」。
7. 密钥进过 Git 只删文件不轮换。
8. 生产 debug：SQL 与堆栈变情报。
