# 26. 实时后端系统（Realtime Backend Systems）

## 一句话直觉

请求-响应只能「浏览器问、服务器答」；多人看板要「别人一拖任务，你立刻看见」，就必须让服务器也能主动开口——并且只为**真正发生的事件**付费，而不是为「每秒在问有没有变化」付费。

## 本课问题

- 任务管理多人协作：A 拖任务，B 为何必须刷新才能看见？HTTP 的根本限制是什么？
- 轮询 / 长轮询 / SSE / WebSocket 各自解决什么、还缺什么？
- 一台机器能扛多少长连接？文件描述符、端口四元组、内存分别卡在哪？
- 多实例时连接「粘」在一台机器内存里，如何用 Pub/Sub 让事件跨实例送达？
- at-most-once、断线追赶、扇出（fan-out）、重连风暴分别怎么处理？

---

## 核心概念详解

### 1. 产品场景：看板「实时」到底要什么

前面课程里，后端几乎都是同一形状：**浏览器提问 → 服务器回答**（认证、DB、Handler/Service/Repository、缓存、后台任务、对象存储……）。

任务管理产品里一个很普通的需求：两人盯着同一块看板；A 把任务从「待办」拖到「进行中」；B 在世界上另一处，应**立刻**看到卡片移动——不是刷新页面、不是再导航一次，而是**直播式**更新。

一旦你开始想怎么实现，会撞上 HTTP 模型的硬限制（第 5 课已强调）：

- **对话总是客户端发起**；服务器不能「先开口」。
- 服务器只能**回复**已经问过的问题，或把一次请求**拖很久**再答；但**发起通信**这件事，服务器做不到。
- 因此：服务器上若已有「浏览器没主动问过」的新消息，**没有合法通道**把信息推到浏览器。

本课目标：在「服务器应能先说话」的前提下，弄清网络层长什么样、资源成本多少、多实例怎么接。

### 2. 第一直觉：轮询（Polling）

既然服务器不能主动通知，客户端唯一办法是：**自己在循环里不断问**。

典型实现：每 3 秒问一次——「看板 `412` 在过去 3 秒有没有变化？」

- 多数时候答案是 **no**。
- 偶尔（有人挪了任务）答案是 **yes**：返回具体变更，或让你「整板重拉再渲染」。

**能用，也有合理场景**：内部工具、用户很少、几秒延迟可接受 → 每隔几秒轮询完全说得通。

但面向用户的产品、要「做对且可扩展」时，要继续推边界：看**哪一层会先崩**。

### 3. 轮询的代价（What polling costs）

#### 3.1 延迟：平均是间隔的一半

间隔 3 秒 → 一次变更在其他人屏幕上出现的**平均等待 ≈ 1.5 秒**（纯算术：平均延迟 ≈ 间隔 / 2）。

想更「跟手」？把间隔改成 1 秒 → 体验更好，但……

#### 3.2 成本跟「在看的人」成正比，跟「发生的事」无关

假设 1 万个浏览器同时开着看板：

| 间隔 | 粗算 QPS |
|------|----------|
| 每 3 秒一问 | ≈ 10 000 / 3 ≈ **3333 次/秒** |
| 每 1 秒一问 | ≈ **10 000 次/秒** |

每一次都是完整 HTTP：负载均衡 → 鉴权中间件验 token → 日志中间件写一行 → Service 查库 → 序列化 JSON。多数时候答案仍是「没变」——却照样消耗鉴权、日志、DB。

把间隔从 3s 缩到 1s：体验大约好 3 倍，**账单也大约坏 3 倍**。

更刺眼的对比：一块板**整天无人操作**，与一块板**每秒都有变更**，在纯轮询下对服务器的资源消耗可以**几乎一样**——因为你付的是「请求本身」，不是「有价值的事件」。

#### 3.3 移动端：无线电与电量

手机上每次轮询都会唤醒 **radio（无线电）**——手机最贵的能耗行为之一。无变更也在耗电、耗流量。

#### 3.4 本课要达到的目标（设计原则）

1. **服务器应能先说话** → 消灭「空转请求」。
2. **资源应对齐真实事件/变更**，而不是对齐「开着页面的浏览器数量」。

### 4. 长轮询（Long Polling）

思路：既然 HTTP 只能「问了再答」，就让服务器**慢一点答**。

流程：

1. 浏览器发请求；服务器**不立刻回**，把请求挂住（可挂近一分钟），干等。
2. 一旦有变更 → 写入响应并返回 → 连接关闭。
3. 浏览器立刻再开一轮长轮询。

曾写进 **RFC 6202**（也写了它的问题）。核心缺陷是**间隙（gap）**：

- 服务器答完 → 客户端处理 → 再发新请求，这段时间**没有连接**。
- 平均延迟约「一次网络往返」；最坏可达三次以上——间隙里可能丢变更。

结论：能用、用了很多年，但不是终点。

### 5. Server-Sent Events（SSE）

再进一步：长轮询在「答完就关」；若**响应永远不结束**呢？

#### 5.1 机制（仍是 HTTP）

1. 浏览器发普通 **HTTP GET**。
2. 服务器回 **200**，`Content-Type: text/event-stream`。
3. **不关连接**；有事就往同一条连接里再写一点文本。
4. 标签页/网络还在，连接就一直开着；关掉标签页才会断。客户端可按重试策略重连。

**不是新协议**：仍走 HTTP 头与响应体。浏览器原生支持重连；重连时自动带 **`Last-Event-ID`**（上次收到的事件 ID），服务端可「从断点续推」。

#### 5.2 事件格式（约四个字段）

常见字段：

| 字段 | 作用 |
|------|------|
| `id` | 事件序号；断线后用于追赶 |
| `event` | 事件名，如 `task.moved` / `task.deleted` |
| `data` | 载荷，前端可直接用来插卡/改状态 |
| `retry` | 建议浏览器隔多久再重连 |

#### 5.3 SSE 并不「低人一等」

有人觉得「真·实时 = WebSocket，SSE 是玩具」——不对。生产案例：

- **Uber** 司机行程推送平台：SSE。
- **LinkedIn** 即时消息（含输入指示、已读回执）：SSE。
- 几乎所有大模型 API 的 **token 流式输出**（CLI / 浏览器）：SSE 的 `data` 字段。

价值：兼容性好（就是 HTTP）、浏览器自带重连与 `Last-Event-ID`。关键是**选型**：看场景是否只需「服务器 → 客户端」单向推送。

#### 5.4 SSE 的硬限制：单向

名字里的 **Server-Sent**：服务器可以整天说，客户端**不能**用同一条实时连接回说。

看板拖拽要通知服务器 → 仍是**另一次 POST**，不能与 SSE 共享那条推送连接。很多产品完全够用；若需要**同一连接双向**，就要 WebSocket。

### 6. WebSocket：同一连接双向

#### 6.1 Handshake（握手）——先当 HTTP，再升级

WebSocket **不是**一上来就是 WS：先发普通 **HTTP GET**，带着：

- `Upgrade: websocket`
- `Sec-WebSocket-Key`：16 随机字节的 Base64

服务器：

1. 把该 key 拼上规范里的**固定字符串**；
2. 做 SHA-1，再 Base64；
3. 放进 `Sec-WebSocket-Accept`；
4. 回 **101 Switching Protocols**。

这串固定字符串**不是加密**（谁都能算）——作用是证明「对面真懂 WebSocket」，而不是某个不懂协议的缓存在回放旧的 200。

握手完成后：连接仍开着，但**不再是 HTTP**——没有方法、状态码、常规头；变成**双向帧流**，两边随时可写。

仍从 HTTP 起步的好处：沿途设备几乎都会说 HTTP，穿透性好。

#### 6.2 帧（Frames）与 mask 位

RFC 用位图描述帧，要点：

- **FIN**：是否消息最后一片；
- **opcode**：1 文本、2 二进制、8 close、9 ping、10 pong、0 延续；
- **mask** 位 + 载荷长度（小消息头可仅 **2 字节**——对比长轮询每次成百字节的 HTTP 头，带宽差很多）。

**Masking（掩码）**：浏览器 → 服务器的每一帧必须掩码。载荷每个字节与 4 字节密钥 XOR（密钥明文放在帧里，**不是加密**）。

为何存在？协议制定时发现：恶意页可对「不懂 WS 的中间缓存代理」做**缓存投毒**——在升级后的字节流里塞出「像是对某热门资源的 GET」的样子，让代理缓存攻击者内容。浏览器用**页面 JS 猜不到的随机密钥**掩码后，攻击者无法精确控制线上字节形态，假 HTTP 请求构不成。规范要求**每帧密钥随机**。掩码保护的是「你与用户之间的通信通道安排」，不是数据机密性。

#### 6.3 Ping / Pong：区分「空闲」与「已死」

任一侧可发 ping（opcode 9），对侧必须 pong（10）——**心跳**。

原因在 TCP：用户进电梯、手机 Wi‑Fi↔蜂窝切换等，连接可能静默死亡——**没有 close、没有错误**。服务器仍握着 socket，以为人还在。空闲连接与死连接对外观相同。唯一办法：发点东西看有没有回。生产常见：ping 后约 **30 秒**无 pong → 判死、关连接、释放资源。

### 7. 一台机器能扛多少连接？

实验语境：16 核、约 61 GB 空闲内存的 Linux；极简 Go 服务**只 accept 并握着连接**（无业务逻辑），测「能握多少」。

#### 7.1 文件描述符（File Descriptors）

Unix 上「一切皆文件」；网络 socket 也是文件 → 每条连接占一个 FD。能开多少连接 ≈ 能开多少文件。

- 默认 `ulimit -n` 常是 **1024**。
- 打 2000 连接时，会停在约 **1017**（还要扣 stdin/out/err、监听 socket、epoll 等开销）。客户端侧往往只是**握手超时**，不是立刻 Connection refused；服务器日志则是 **too many open files**，健康检查仍可能正常——只是拒新连接。

语言差异：同机同 shell 里，Python 可能仍见 1024；**Go runtime 启动时会把软限制抬高**（因 Go 不用 `select` 那套有硬上限的 FD 集合）。「会撞上千 FD」问题**存在，但依赖语言**：Node/Python/Java 更易撞；Go 空间大得多。

#### 7.2 端口与四元组（Four-tuple）

FD 限制抬走后，实验可停在约 **28 190**，错误变成 **cannot assign requested address**。

查内核允许的临时端口范围（例：32768–60999）→ 约 **28 232** 个端口；减去机器上已占用的，与实测吻合。

常见误解：「服务器只有 65535 个端口，所以最多约 6.5 万连接」——**错**。TCP 连接由四元组标识：

**源 IP + 源端口 + 目的 IP + 目的端口**

服务器侧（目的 IP、目的端口）固定；若压测客户端也只有一个源 IP，则**只有源端口能变**——耗尽的是**客户端出站端口池**，不是「服务器只能开 6.5 万」。

修复压测：让客户端从**多个源地址**拨号（例：每地址 2.5 万 × 3 = 7.5 万）→ 零失败。这也是生产压测常要**多台机器**的原因。

#### 7.3 内存：真正的天花板

约 7.5 万空闲连接时，进程堆相对空闲态的增量粗算：**每连接约 9.5–9.9 KB 堆**（约 9750 字节量级）。百万连接 ≈ 堆 **不到 10 GB**（尚不含内核 socket 结构）。61 GB 机器上「百万空闲连接」在内存上可行。

注意：这 ~9 KB 多半不是「socket 本身」，而是**每连接一个 goroutine + buffer**。超大规模时，常见做法是**不用一连接一 goroutine**，而是用 **epoll** 等在一处监视大量 socket。

### 8. 第二台机器：无状态后端 vs 有状态连接

生产不会只有一台：自动扩缩、容器挂了再起……都会让连接掉线再接。

场景：两实例在负载均衡后。

- 浏览器 A → 实例 1；浏览器 B → 实例 2；两边都有活的 WebSocket。
- A 拖任务 → **B 什么都看不见**。

原因：连接状态在**某一进程的内存**里（socket、goroutine、「谁在看看板 412」的登记）。实例 2 从未听说过 A——两个进程，可能在两个机房。

整门课一直在把后端做成 **stateless**（任意实例可处理任意请求）；本课却说：**持久连接本身就是状态**，住在特定进程内存，**不能搬、不能共享**。一旦 accept 了 WebSocket，**全世界只有这一实例能直接跟该用户说话**——与前面架构原则冲突。

#### Sticky session 解决不了「两人同时看」

粘性会话：LB 尽量把同一客户端送回同一实例（含重连）。A 仍连实例 1，但 **B 仍在实例 2**——B 仍不知道 A 的事件。粘性会话解决的是「会话粘在一台上」，不是「跨实例广播变更」。

#### 正解：Publish / Subscribe（发布订阅）

看板 412 上发生变更的实例：**不要只本地推送**，而是 **publish 到某个 topic**；中间件（Redis / NATS / Kafka 等）把事件交给**所有订阅了该 topic 的实例**；各实例查自己握着的连接，找到盯着 412 的 socket，写帧。

于是：**收到变更的实例** 与 **真正推到用户的实例** 可以不是同一台。

### 9. At-most-once、断线追赶、扇出、重连风暴

#### 9.1 Redis Pub/Sub：Fire-and-forget

Redis 经典 Pub/Sub 是 **at-most-once**：发布瞬间某实例未连上 → **消息永久消失**（不排队、不延迟重试）。

部署窗口：实例下线 → 新实例起来之间的几秒，该实例上用户相关的 publish **全丢**；其他人要等到刷新才看到。选型时要清楚：需要 **at-least-once**（落盘 + ack）时，应考虑 **Redis Streams / Kafka / 队列** 等，而不是裸 Pub/Sub。

#### 9.2 Catch-up（追赶）策略

用户常会断：网络切换、合盖、LB 空闲超时……生产级实时系统除了「送达」，还要有**追赶**。

形状与 SSE 相同：**给每条消息编号**；客户端重连时声明「我上次收到的是 ID/序号 N」；服务器从 N+1 起补发。Uber 一类平台：客户端报 sequence 0 起收递增序号；断线后报「我到 2 了」，服务从 3 继续。对应 SSE 的 `Last-Event-ID`。

#### 9.3 Fan-out（扇出）

3 万人盯同一块板 → 一人挪一次任务 ≈ **3 万次写**。工作量 ≈ **事件数 × 订阅者数**。

Discord 写过：大型社区同时在线约 3 万人时，单条事件扇出实测约 **900 ms～2.1 s**。思路：不要在单点做完全部扇出，把工作摊到**真正拥有收件人连接的机器**上。

#### 9.4 Reconnect storm（重连风暴）

一实例握 5 万连接突然挂掉 → 客户端**同时**重连，且都要初始状态（哪些板、哪些任务、谁在线）→ **一秒 5 万次昂贵请求**。Slack 一类实践：让「连上」变便宜——在**边缘缓存**放好客户端启动所需信息，风暴时别打穿到 origin/core。

### 10. 本课未展开但依赖同一地基的方向

- **Presence（在线状态）**：谁此刻在平台上。
- **协同编辑**：两人同时改同一内容（Notion / Google Docs 的实时光标）→ CRDT 等一整类算法。

这些都能再讲很多小时；本课内容是**之上可继续加能力的基础**。

### 11. 演进路线小结

| 阶段 | 做法 | 主要问题 |
|------|------|----------|
| 起点 | 只能答客户端已问的问题 | 服务器无法主动推送 |
| 轮询 | 客户端定时问 | 成本 ∝ 观众数，≠ 事件数；延迟；耗电 |
| 长轮询 | 挂住请求等变更 | 重开间隙丢变更 |
| SSE | 永不关的 HTTP 流 | 仅服务器→客户端 |
| WebSocket | HTTP 升级后双向帧流 | 连接即状态；多实例需 Pub/Sub 等 |
| 规模 | FD → 客户端端口 → 内存 | 压测要多源；超大规模勿一连接一 goroutine |
| 多实例 | Pub/Sub + 序号追赶 | at-most-once、扇出、重连风暴 |

## 常见坑

| 坑 | 说明 |
|----|------|
| 用更快轮询「假装实时」 | 延迟降了，账单与 DB 一起炸 |
| 以为 SSE 不如 WebSocket | 单向推送场景 SSE 往往更合适、兼容更好 |
| 把 mask 当成加密 | 明文密钥；防的是代理缓存投毒 |
| 无心跳的长连接 | 死连接占满 FD/内存，服务「半死不活」 |
| 以为服务器最多 65535 连接 | 混淆了端口与四元组；压测客户端端口先耗尽 |
| 多实例只靠粘性会话 | 解决不了「另一用户在另一实例」 |
| 用 Redis Pub/Sub 却当至少一次投递 | 发布窗口丢消息，只能靠刷新发现 |
| 实例挂了无边缘缓存 | 重连风暴打穿 origin |
